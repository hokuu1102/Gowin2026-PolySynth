## 🎯 赛题硬性指标

| 指标 | 要求（拓展） |
|---|---|
| 独立可控演奏维度 | **≥2**（≥3） |
| 基础复音数 | **≥4**（≥32） |
| 控制→出声延迟 | **≤10 ms**（≤5 ms 且确定性） |
| 合成链 | 全部 **RTL 实现** |
| 音频输出 | **I2S → DAC** |
| 音色数 | **≥2** |
| 拓展要求 4 | **脱机演奏 LED 曲目指引** |

> ⚠️ **评分陷阱**：**吞吐量 = 同时活跃可闻独立振荡器总数 × 实际音频输出采样率**，
> 且原文明确「**过采样不叠加加分**」→ **单纯拉高采样率是无效努力**。

## 🧩 当前方案一句话

```text
左手区：2 行 × 8 列磁轴网格（16 轴位）→ 选音 + 力度 + 滑音

```

## ⭐ 三条设计铁律

| # | 铁律 |
|---|---|
| **1** | **同一只手要移动来切换的操作，必须同一个平面、同一高度**（⛔ 任何键帽高度差都不允许） |
| **2** | **能用物理正交解决的，不要用算法解决** |
| **3** | ⭐ **「间距」是霍尔类器件唯一的量程 / 阈值调节旋钮**（场强不够就移近，太强就移远） |

**三条方法论纪律**（都是踩坑换来的）：

1. **设计用「最小值 / 最大值」，绝不用「典型值」**
2. **"别人能用" ≠ "我们能用"**
3. **推荐方案前先确认"它能不能被当前阶段的验证手段验证"**

## 🚫 不做 / 🟡 暂缓

> ⚠️ **两者不同**：**⛔ 结构性排除** 是不因时间而改变的；**🟡 暂缓** 是**排在后面、有时间就做**。

### ⛔ 结构性排除（不因时间而改变）

| ⛔ | 原因 |
|---|---|
| 播放预录 PCM 音频 | **赛题红线** |
| 使用板载 CPU 参与音频通路 | **不合规** |
| ⭐⭐ **音频 / 视觉效果的"生成"用软核或 MCU** | ⭐ **官方明确红线**（2026-09-19 答复）：用了**可能不计入该部分工作量**。⚠️ 但**专用状态机不算软核**（`K-40`/`K-81`） |
| 串口屏进入**演奏通路** | **延迟不可控**（⚠️ 屏本身照做，只是**不做演奏输入**） |
| FSR / 全电容传感方案 | **已否决** |
| 片内 ADC + 外部多路复用器 | **已否决** |
| **每轴位两个霍尔测横向位移** | **被机械结构否掉**：磁轴**直上直下**，磁铁固定在轴体上**不产生横向位移** → 两个霍尔测到几乎同一个 Z 信号，差分≈0（见 `files/历史/采集链参数复核-过时-旧共享总线口径.md` §五-①） |

### 🟡 暂缓（**有时间再做**，先留接口）

| 🟡 | 定位 | 前置条件 | 留的接口 |
|---|---|---|---|
| **蓝牙 + 手机 App 联动** | ⭐ **不是不做，是排在最后** —— 原文是"**可**搭载"，属**加分项而非必需项** | ⛔ **必须等五条红线全部达标 + 核心功能完成之后**才动 | UART 已存在（`J2`/`J8`）· **`J10` 备用通用 IO** 已预留 → 将来加**不用改板** |

> ### 📌 为什么蓝牙排在最后（而不是"不做"）
>
> 赛题原文（拓展要求 4）：「实现脱机演奏 **LED 曲目指引**功能，辅助规范演奏节奏；
> **可**搭载蓝牙模块与手机 App 联动，支持在线曲谱下载、演奏键位自定义、演奏录音回传等拓展功能」
>
> | 项 | 判断 |
> |---|---|
> | **优先级** | 同一句里的**前半段（LED 曲目指引）是核心**，我们**先做那个**；蓝牙是"**可**"→ 排后面 |
> | **工作量** | 蓝牙 + App 是**一整个子系统**（BLE 协议栈 + App 开发）—— **34 天里给它排不进主线**，但**排得进"如果提前做完"的余量** |
> | ⚠️ **代价** | 它会**挤占五条红线**的打磨时间 → 所以**明确排在红线之后**，而不是"顺手做" |
> | ✅ **对策** | **先留接口**（不用改板）→ **成本为零**，将来想做随时能加 |
