## 三、⚠️ PLL 的两个大坑（直接关系到我们的音频时钟）

### 坑 1：不要用 PLL 输出做"全设计系统时钟"

经验库 `23` / `L31`：**Gowin 上这么干 → 综合通过、板子完全死**（连串口都没输出）。

### 坑 2：IP 向导里"输入频率"填错 → 所有输出**静默减半**，不报任何错

经验库 `24` / `C09` / `U34` 的实例：向导里填了 **100 MHz**，而板载晶振实际 **50 MHz**
→ 两路输出静默减半（期望 50M 实际 25M）→
按 50M 算出的"最优采样相位"实际是"最差"，为此绕了一整天。

更严重的连带后果：**PLL 的 VCO 跑到了规格外**
（声明 100M / 实物 50M → VCO≈350 MHz，而手册要求 ≥700 MHz）→ **越规格运行**。

> ### ⭐ 我们的方案天然避开了这两个坑
>
> 我们的音频时钟是**直接用 50 MHz 原始时钟做整数分频**：
> ```
> MCLK  = 50 MHz ÷ 4   = 12.500 MHz
> BCLK  = MCLK ÷ 4     =  3.125 MHz
> LRCLK = MCLK ÷ 256   = 48.828 kHz  ← fs
> ```
> **全程只用两个计数器，不需要 PLL** → 不碰坑 1，也没有"输入频率填错"的机会。
>
> ⚠️ **所以：不要"顺手改成 PLL 更规范"** —— 那正好是踩进这两个坑的路。
> 若将来确实需要 PLL，先查 `U22`（GW5AT 的 PLL IP 是 `PLL_ADV`，不是 `rPLL`）
> 与 `U34`（用数据手册的 AC 指标反查前提）。

## 六、⚠️ 两条使用经验库的纪律

### 6.1 ⚠️ 经验库是**公开**仓库 —— 往里加东西要脱敏

```
远端：git@github.com:hokuu1102/experience.git
可见性：**public**（已核实：未认证 API 可见、在公开仓库列表里）
```

| ⛔ 不要写进经验库 | 理由 |
|---|---|
| 本项目的**赛题选型结论**（如"定为就地数字化"/"选 HAL49E"） | 赛前公开自家方案不合适 |
| 队友**真人姓名** | 与本项目同一条规矩（写角色不写人名） |
| 具体**赛题/队名/学校**信息 | 同上 |

**该写进去的是**：可跨项目复用的**器件知识**与**排查方法**（这正是经验库的定位）。

> 📌 我正在往 `器件积累.md` 加的 D06~D09 属于"通用器件知识"，
> 但里面带了"**已选定**"这类项目口径 —— **提交前需要过一遍，把项目口径改成通用表述**。
> （该仓库当前有未提交改动：`器件积累.md`、
> `C:\Users\hokuu\Desktop\经验\fpga\FPGA问题排查手册.md`）

### 6.2 状态标签与"证据强度"纪律（经验库的核心约定）

经验库要求所有结论带状态标签：
`[假设]` / `[验证中]` / `[已基本确认]` / `[已确认]` / `[已排除]`，
且**只有验证过的才能写进"最终方案"**。

⭐ 这套纪律和我们项目自己的两条铁律是同一件事：
- 我们的「**设计用最小值/最大值，绝不用典型值**」
- 我们的「**别人能用 ≠ 我们能用**」

➡️ **建议本项目也采用同一套标签** —— 尤其在"仿真验过 / 上板验过"必须分开标注时
（经验库 `C13` 的教训：**把弱证据当强证据**是失去真实系统后最大的风险）。
