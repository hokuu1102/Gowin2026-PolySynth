# 🔒 W3 接口冻结表（FPGA 音频引擎）

> **这份是什么**：W3（FPGA 音频引擎）**三个子模块之间的接口契约**。

## 〇、⭐ 五条硬约定（先看这个，比信号表更重要）

| # | 约定 | 违反的后果 |
|---|---|---|
| **1** | ⭐ **单时钟域**：全设计只用 `clk_sys = 50 MHz`，**禁止派生时钟**；用**节拍脉冲**（`tick_*`）代替 | 跨时钟域亚稳；且经验库明确记载 **Gowin 上用 PLL 输出做全设计系统时钟 → 综合通过但板子全死** |
| **2** | **统一复位**：`rst_n` 同步复位、**低有效**，全设计极性一致 | 混用极性是最常见的集成 bug |
| **3** | ⭐ **固定流水线深度** —— 每个模块的延迟拍数**写进接口表且不许随意改** | 延迟预算的"确定性"靠它保证；深度一变，`files/模块/延迟预算逐段分解.md` 的预算就失效 |
| **4** | ⭐ **单周期脉冲必须"边沿时刻断言"**，⛔ 不许"事后查询" | 经验库 `L12`：脉冲信号事后查询必然漏采 |
| **5** | **一人一文件**（或一目录）—— 三人不改同一个 `.v` | 否则 git 冲突 + 语义冲突 |

> ⚠️ 第 1 条是**刻意设计**：我们**不需要 PLL**（50 MHz 整数分频即得 `fs`）。
> **⛔ 不要"顺手改成用 PLL 更规范"** —— 那正好是已知会炸的那条路。

## 三、⭐ 接口定义（三条通路）

### 接口 ① · 事件通路（W3a → W3b）

**为什么单独一条**：⭐ **事件驱动 Note ON/OFF，要求低延迟且固定**。

```verilog
// 音符事件 —— 单周期脉冲
typedef struct packed {
    logic              valid;      // 单周期脉冲，边沿时刻断言（约定 4）
    logic [3:0]        axis_id;    // 轴位 0..15
    logic [6:0]        note_num;   // 0..127（双模式映射后的结果）
    logic [7:0]        velocity;   // 0..255 ⚠️ 见下方"默认力度"
    logic [1:0]        kind;       // 0=note_on 1=note_off 2=pluck
} note_evt_t;

// ⭐ 力度修正事件 —— 后到，用于更新"已在响"的 voice
typedef struct packed {
    logic              valid;
    logic [3:0]        axis_id;    // 按轴位寻址（W3a 不知道 voice_id）
    logic [7:0]        velocity;
} vel_update_t;
```

> ### ⭐⭐ `vel_update_t` 的存在原因（**这是从延迟预算里挖出来的陷阱**）
>
> 力度用**双阈值测速法**（越过浅阈 t1、深阈 t2，Δt 小 = 力度大）。
> **若等 t2 到了才发声** → 延迟由"演奏者拨多快"决定 → **不可控 → 违反「确定性无抖动」**，
> 且慢按可能几百 ms 才响。
>
> ✅ **正确做法：越过 t1 就发声**（用 `velocity = DEFAULT_VEL` 起音），
> t2 到了再用 `vel_update_t` **修正**那个 voice 的音量。
> 修正发生在 ADSR 起音阶段内（几十 ms），**听感上就是"这个音的力度"**。
>
> ⚠️ **对 W3b 的要求**：`NoteManager` **必须支持"更新在响 voice 的参数"**。
> （详见 `files/模块/延迟预算逐段分解.md` §三）

### 接口 ② · 参数通路（W3a → W3b）

```verilog
// 表情参数 —— 持续调制，可周期性更新
typedef struct packed {
    logic              valid;
    logic [3:0]        axis_id;
    logic signed [11:0] pitch_bend;  // 滑音偏移（半音/音分编码待定）
    logic [7:0]        vibrato;      // 颤音深度（来自右手推子）
    logic [3:0]        timbre;       // 音色选择（≥2 种）
} expr_param_t;
```

> ⚠️ **铁律**：**参数永不产生音符**（见 `files/模块/整体模块框图.md` §三）。
> 这是"误触发"问题的**结构性解法** —— 调制动作（横向滑音、抖行程）**在架构上就不可能**被当成新音符。

### 接口 ③ · 音频通路（W3b → W3c）

```verilog
typedef struct packed {
    logic              valid;        // ⭐ 每个样本一个脉冲（fs 节拍）
    logic signed [23:0] sample;      // 单声道（立体声则在 W3c 复制）
} audio_t;
```

> 📌 **单声道 vs 立体声**：当前按**单声道**走（DAC 双声道输出同一路即可）。
> 若要做立体声效果（合唱/混响的声像），在 **W3c** 内部展开 —— **不改这条接口**。

## 四、⏱ 各模块延迟拍数（**约定 3 的落地**）

| 段 | 模块 | 延迟拍数 | 说明 |
|---|---|---|---|
| ① | `chan_scan` → `w3a_top` | 设计时填 | 采集节拍固定 |
| ② | `event_extract` | ≤ 5 拍 | 阈值 + 不应期状态机 |
| ③ | `note_manager` | ≤ 4 拍 | 分配 + 参数更新 |
| ④ | `voice` / `osc` 流水线 | 设计时填（**固定值**） | 相位累加 → 查表 → ×包络 |
| ⑤ | `mixer` 求和树 | `log2(POLY_TARGET)` + 2 拍 | 饱和处理 |
| ⑥ | `fx_*` | ⭐ **0 拍**（不阻塞） | 干湿混合**不得**引入通路延迟 |
| ⑦ | `i2s_tx` | ≤ 1 个采样周期 | 移位输出 |

> ⚠️ **每个模块做完后要把实际拍数回填这张表** —— 它与 `延迟预算逐段分解.md` 必须对得上。
> ⭐ **两端合计若超过 5 ms / 1024 拍 就说明设计有问题**（预算显示只用了 ~0.6 ms）。

## 五、⛔ 六条禁令（违反即集成失败）

| # | 禁止 | 原因 |
|---|---|---|
| **1** | 用**派生时钟**（除 `clk_sys` 外） | 约定 1；Gowin 上有实测炸机案例 |
| **2** | **不用缓冲/大 FIFO** 放在确定性通路上 | 缓冲深度**直接变成延迟**；块缓冲 128 样本 = +2.6 ms |
| **3** | 让**参数**产生音符事件 | 破坏"误触发"的结构性解法 |
| **4** | 共用**相位累加器**或**包络**来省资源 | ⛔ 评分规则要求"独立"——共用就**不算独立振荡器**，吞吐量数会缩水 |
| **5** | 在**事件通路上加去抖等待** | 去抖引入固定延迟；用**不应期**（先触发再封锁）代替 |
| **6** | 三人同改 `top.v` / `clk_gen.v` / `top.cst` 而不通知 | 集成层是汇合点 |

## 六、🔄 变更流程（接口一旦冻结）

```text
① 想改接口 → 先在群里说明「原接口 / 想改成什么 / 为什么」
② 得到另外两人确认（涉及全局参数还要全员）
③ 改这份文档 + 打版本号（v0.1 → v0.2）
④ 再改代码 —— ⛔ 不许"先改代码后补文档"
⑤ 提交信息写清「改了哪条接口、影响谁的模块」
```
