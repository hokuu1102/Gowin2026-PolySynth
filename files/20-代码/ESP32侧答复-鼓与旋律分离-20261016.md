## 二、§八 三个待确认项：逐条答复

### 1. "你们的谱里有 crash / ride / 更多嗵鼓吗？" ⇒ **有，而且必须扩到 3 位**

实测数据（出处：`ESP32侧追问-下行inc位宽装不下鼓机-20261014.md:94`，用户那份真谱面）：

```
鼓轨用到的 12 个 GM 音高：36, 38, 42, 45, 46, 47, 48, 50, 51, 53, 55, 57
```

对照 §4.3 的表：

| GM | 名称 | §4.3 归类 | 备注 |
|---|---|---|---|
| 36 | Bass Drum 1 | Kick ✓ | |
| 38 | Acoustic Snare | Snare ✓ | |
| 42 | Closed Hi-Hat | HiHat ✓ | |
| 45 / 47 / 48 / 50 | Tom 系 | Tom ✓ | |
| **46** | **Open Hi-Hat** | **表外 ⇒ Tom** ✗ | 镲族 |
| **51** | **Ride Cymbal 1** | **表外 ⇒ Tom** ✗ | 镲族 |
| **53** | **Ride Bell** | **表外 ⇒ Tom** ✗ | 镲族 |
| **55** | **Splash Cymbal** | **表外 ⇒ Tom** ✗ | 镲族 |
| **57** | **Crash Cymbal 2** | **表外 ⇒ Tom** ✗ | 镲族 |

⇒ **12 个里有 5 个是镲族，本轮口径下全部会变成嗵鼓**（听感：镲像嗵鼓）。
另有 37 Side Stick / 39 Hand Clap 在旧口径里算 Snare，新表里也没有 ⇒ 同样归 Tom。

**建议**：`drum_type` 扩到 **3 位（8 件）**，例如
`0=Kick 1=Snare 2=HiHat 3=Tom 4=OpenHat 5=Crash 6=Ride 7=Clap`（具体分法你们定）。

⚠️ **扩位有个连带约束，请一并评估**（我方实现时发现的）：
`note_off` 是按 `(axis, src)` 配对的，而新口径下**四件鼓的 src 都是 `SRC_KDRUM`**
⇒ 隔离完全靠 **axis**（这就是方案 B 的 12/13/14/15）。
若扩到 8 件，就需要 **8 条鼓轴**，而现在自由轴只有 12..15 四条（旋律占 0..11）。
两条出路，请你们选：
- **甲**：旋律轴池缩到 0..7（8 条），把 8..15 让给鼓 —— 代价是旋律并发上限从 12 降到 8；
- **乙**：`note_off` 的配对键从 `(axis, src)` 改成 `(axis, drum_type, src)` —— **零帧位域代价**，但要改 RTL。

### 2. "BASE_NOTE 取哪个？" ⇒ **采纳 45，但有一个必修的坑**

- 采纳 `BASE_NOTE = 45`（与指板表最低音 A2 对齐），我方已按 45 实现。
- 量程核对：`45 + 31 = 76 = E5` ⇒ §2.1 写的"覆盖 MIDI 45..76（A2..E5）"**正确**；
  §八-2 写"覆盖 A2..G4"是**笔误**（G4 = 67，不是 76）。
- ⚠️ **坑**：低于 45 的音会被钳到 0 ⇒ **如果引导轨是贝斯，灯会指到最低那一盏**。
  实测本测试曲贝斯音区 **40~47**，其中 40~44 全部会被钳。
  - 若要照顾低音区：`BASE_NOTE = 40`（40..71 = E2..B4，5 位仍装得下），代价是高音区上限降到 B4；
  - 二者不可兼得 ⇒ **取决于哪条轨当引导轨**。我方先按 45 实现，并在网页日志里报"被钳了几个音"。
- 📌 另：`note_off5` 的越界**在字层查不出来**（5 位字段装不下 32，`pack_word` 会静默掩码截成 0）。
  所以"越界必须被拒"只能在**入参层**做 —— 我方已在 `score_word.validate_fields()` 里实现，
  并要求 `mid2evt.py` 转换时调用它（⛔ 只靠 `load_events_hex` 等于这条判据没有）。

### 3. "上行帧的 axis 回传 drum_type 可以吗？" ⇒ **可以，但请补一个"这是鼓"的标志**

- 你们的方案（鼓事件 `axis` 回传 drum_type、旋律回传 0）**零额外逻辑**，我方接受。
- ⚠️ 但**旋律也完全可能是 axis = 0** ⇒ 光看 axis 分不清"鼓的 Kick(0)"与"旋律的轴 0"，
  我方映射回 GM 时必然有一半是错的。
- **建议**：上行帧里也带一位"这是鼓"（放哪由你们定 —— 例如复用 `timbre` 的高位，
  或在上行帧 v1.x 里加一位）。你们给了格式，我方按格式改 `esp32/tools/evt2midi/` 与网页回传页。

## 二·五、实现过程中新发现的两条约束（也是你们决策要用的）

### 甲、判据③（旋律不许占 12..15）逼出一条隐含上限：**旋律轨最多 12 条**

新口径下鼓固定占 12..15 ⇒ 旋律只能用 0..11（12 条轴）。
我方顺序编号已改成 `模 12`，**超过 12 条旋律轨时会开始共用轴号** ⇒
同轴同源的两个 voice 会互相清（听感：随机少音/挂音）。

- 现在真实谱面只有 4~6 条旋律轨 ⇒ 够用；
- 但**根治要么扩轴号位宽、要么让 FPGA 侧允许"同轴多 voice 共存"** —— 请你们评估。
- 我方已在工具里对"旋律轨 > 12"打 WARNING（⛔ 不静默）。

### 乙、`mid2evt.py --drum-track` 的**轨序号包含第一条空 Tempo 轨**

手册 §4.1 第三条要求"允许显式指定哪条轨是鼓"，我方按 **0-based 全轨序号**实现：
一条 Guitar Pro 导出的谱通常是 `0=Tempo空轨 · 1=Bass · 2=Guitar · …`，
所以**真鼓轨常常是 5 而不是 4**。已加"指定项没匹配上就 WARNING 点名"。
📌 如果你们的联调脚本要显式指定，建议**用轨名子串**（如 `--drum-track Drums`）而不是序号。

### 丙、额外证据：新旧产物**逐位对照**

`mid2evt.py` 改完对真曲做过逐位比对：**314 条旋律事件的 bit63..5 与改前完全相同（0 条差异）**，
只有新增的 `bits[4:0]`（note_off5）在 244 条上变了；tempo 事件**一字未变**。
⇒ 本改动对既有字段**零回归**（可放心合入）。

### 丁、🔴 交叉验证查出一条**老差异**：两条生产通路的 `vel` 字段不一致（请裁定要不要本轮一并修）

我用同一份真曲分别走**网页上位机**和 **`mid2evt.py`**，产出各 576 条字，逐条按
`(tick, kind, is_drum, drum_type/note_off5)` 配对比较（**事件本身 0 条对不上**，即内容一致），
差异只在两个字段：

| 字段 | 网页上位机 | `mid2evt.py` | 影响 |
|---|---|---|---|
| `vel` | 旋律 = MIDI 真实力度（实测 58/84/88/92/96/98）· 鼓 = **175/220/230/235** · OFF = 0 | **一律常量 130**（含 OFF 与鼓） | 同一条谱从两条通路灌下去**响度不同**；鼓尤其（130 vs 230） |
| `axis`（旋律） | 动态分配 6 条（0..5） | 顺序 4 条（0..3） | 都满足"旋律 ≤11"的约束，**只是 voice 占用不同**，可接受 |

📌 `mid2evt.py:581` 原话是 `vel = 130  # MIDI files carry velocity; keep it simple` ——
**这行在本次改动之前就存在**（不是本次引入的回归），手册也没提 `vel`，所以我方**不擅自改**。

**请你们裁定**：
- 若 `vel` 对 FPGA 侧只是幅度（会被 `play_seq`/`seq_arb` 用），那两条通路应当**口径一致** ——
  建议 `mid2evt.py` 也改成"旋律用 MIDI 力度、鼓用 175/220/230/235、OFF 写 0"（与网页一致，
  也与 2026-10-14 那份 `drum_map` 生效值一致）；
- 若 `vel` 在你们那边**根本不参与发声**，那就维持现状，我方在文档里注明即可。
