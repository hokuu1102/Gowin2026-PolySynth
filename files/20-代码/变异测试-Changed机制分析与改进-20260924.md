# 🔬 `-Changed` 机制的可靠性分析与改进方案

> **日期**：2026-09-24 凌晨
> **起因**：⭐ 用户提出 —— *"改一点就全部跑完？总不能以后也改 10 分钟跑 6 小时吧。
> 以后小改动就跑对应部分，涉及大层面的再全部跑，而且最好在每天收工的时候跑。"*
> **结论**：⭐⭐ **用户的策略完全可行，但 `-Changed` 现在有一个【会给假结论】的真缺陷，必须先修。**

---

## 〇、⭐⭐ 一句话结论

| 项 | 结论 |
|---|---|
| ⭐ 用户的策略（小改跑局部 / 大改+收工跑全量） | ✅ **完全可行，且是正确做法** |
| ⭐ `-Changed` 现有实现 | ⚠️ **基本可用，但有一个真缺陷** ⇒ 🔴 **改动共享文件时会给出"通过"的假结论** |
| 🔴 **必须先修** | ⭐ **`top.v` / `tb_all.ps1` / `tb/models/*` / `tb/checkers/*` 被改 ⇒ 强制 FULL**<br>⚠️ **脚本头部【已经承诺】了这条，但代码里【没实现】** |

## 一、⭐ 现有实现（⭐ 已逐行读过，⛔ 不是猜的）

```powershell
if ($Changed) {
  $changedFiles = @()
  $g1 = & git -C $root diff --name-only HEAD      # ⭐ 工作区 vs HEAD
  if ($g1) { $changedFiles += @($g1) }
  $g2 = & git -C $root diff --name-only --cached  # ⭐ 暂存区 vs HEAD
  if ($g2) { $changedFiles += @($g2) }
  $changedFiles = @(... Sort-Object -Unique)
  if (changed == 0) { $mutations = @() }          # ⭐ 0 个 ⇒ 走下面的 FAIL
  else {
    $norm = $changedFiles | ForEach-Object { $_.Replace('/', '\') }   # ⭐ 归一成反斜杠
    $mutations = $mutations | Where-Object {
      $mf = $_.file
      @($norm | Where-Object { $mf -like "*$_*" -or $_ -like "*$mf*" }).Count -gt 0
    }
  }
}
```
📌 位置：`bringup/mutation_test.ps1` **第 418~436 行**

### 1.1 ⭐ 它做对的地方（⭐ 值得肯定，⛔ 别重写）

| # | 做法 | ⭐ 为什么对 |
|---|---|---|
| **1** | ⭐ **同时看工作区 + 暂存区** | ⚠️ 只看工作区会漏掉"已 `git add` 但没 commit"的改动 |
| **2** | ⭐ **正反双向 `like`** | ⭐ `$mf -like "*$c*"` 或 `$c -like "*$mf*"` ⇒ ⚠️ 容忍"一边是相对路径、一边是绝对路径" |
| **3** | ⭐⭐ **0 匹配 = `exit 5`（FAIL）** | 🔴 **这是最关键的一条**（⭐ 脚本第 446~452 行有明确注释）：<br>*"selecting 0 mutants is NOT a pass ... reporting PASS there would be exactly the 'no verdict counted as success' mistake（`C29` / `K-97`）"* |
| **4** | ⭐ 打印 `[selected: ..., of N]` | ⭐ **可观测** —— ⚠️ 看日志就知道"这次只跑了几个" |

> ⭐ **第 3 条尤其重要** —— 它说明写这个脚本的人**已经知道**"空选择 ≠ 通过"，
> ⇒ ⚠️ **但下面这个缺陷说明：同类错误换了个面目又出现了。**

## 二、🔴 真缺陷：**共享文件被改时不会触发 FULL**

### 2.1 脚本头部【承诺】了什么

```
bringup/mutation_test.ps1 第 39~41 行：
#     * before commit / push .......... FULL run (no arguments)
#     * touched a SHARED file ......... FULL run, always
#       (sim/tb_all.ps1, tb/models/*, tb/checkers/*, sim/evidence/*)
#     * touched rtl/top.v ............. FULL run (it is the integration point)
```

### 2.2 代码里【实现】了什么

🔴 **什么都没实现** —— 全文 grep `FULL` 只有 **2 处**，都是**显示字符串**：
```
行 439: if ($selNote -ne "") { ... [selected: ...] } else { ... [FULL] }
行 443: Write-Host ("    estimated: ...")
```

⇒ ⭐ **没有任何"若 changed 含 top.v ⇒ 强制全量"的代码。**

### 2.3 🔴 后果（⭐ 这才是危险的地方）

⭐ 实测匹配逻辑（⭐ 用脚本【真】逻辑跑过）：

| 改动文件 | `-Changed` 选中的变异体 | ⚠️ 应该选中 |
|---|---|---|
| `rtl/w3a/calib_span.v` | ⭐ 只选 `calib_span` 的 | ✅ **正确** |
| **`rtl/top.v`** | 🔴 **只选 `top.v` 自己的（第 I 组那几个）** | 🔴 **应该是【全部】** |
| **`sim/tb_all.ps1`** | 🔴 **1 个都选不中** ⇒ ⚠️ 走 0 匹配 ⇒ `exit 5` | 🔴 **应该是【全部】** |
| **`tb/models/mcp3208_model.sv`** | 🔴 **只有用到它的那几个** | 🔴 **应该是【全部】** |

🔴 **最危险的是第 2 行**：

```
⭐ 场景：⭐ 我改了 top.v 的某个集成细节（⭐ 比如本轮给 u_calib0 接了 .span/.cal_ch）
⇒ ⭐ `-Changed` 只跑 "top.v 自己的那几个变异体"（⚠️ 可能只有 2~3 个）
⇒ ⭐ 它们**全 caught** ⇒ 🔴 **脚本报"全部通过"**
🔴 而真实情况：⭐ **这次改动可能破坏了 calib_span / uart_tx / i2s_tx 的某个变异体**
   ⇒ ⚠️ **那个 LEAK 完全没被发现**
```

⚠️ **这正是 `K-97` / `C29` 那一族**：
> **"没有验证"被当成了"验证通过"。**
⭐ 只不过这次它换了件衣服 —— ⚠️ 不是"0 个"（那个已经被挡住了），
而是 **"选少了但非 0"**（🔴 **没有任何守卫**）。

### 2.4 ⭐ 为什么 `top.v` 是特例（⭐ 值得写清楚）

⭐ `top.v` 是**集成点** —— ⭐ 它**例化所有模块**，而且：
* ⭐ 改一个端口的接法（⭐ 如本轮 `.cal_ch` 从 `at_ch` 改成 `cal_ch_mux`）
  ⇒ ⚠️ **会影响那个模块的全部行为**
* ⭐ 改一个参数（⭐ 如 `TRIG_TH`）
  ⇒ ⚠️ **会让一批变异体从"被抓住"变成"抓不住"**（⭐ 阈值变了，判据的敏感度就变了）
* ⭐ 改 `SOURce_A_SEL` / `DEMO_CHORD_ON`
  ⇒ ⚠️ **会改变哪条链被例化**（⭐ 甚至整块被优化掉）

⇒ ⭐ **`top.v` 的改动在语义上等价于"全量改动"** —— ⚠️ 这就是为什么注释里写了它要 FULL。

## 三、✅ 修法（⭐ 三处，都很小）

### 3.1 ⭐ 核心修法：加一个"强制 FULL"判定

```powershell
# ⭐ 插在 `if ($Changed) { ... }` 的【最前面】
#   ⭐ 语义：⭐ 这几类文件一改，【所有】变异体都可能失效 ⇒ ⭐ 不许只跑局部
$forceFullPatterns = @(
  'rtl\top\.v$',            # ⭐ 集成点：例化/参数/连接的改动影响全局
  'sim\tb_all\.ps1$',       # ⭐ 回归器本身：改它 = 改所有判据
  'tb\models\\',            # ⭐ 从机模型：所有用到它的 tb 都受影响
  'tb\checkers\\',          # ⭐ 断言检查器：同上
  'sim\evidence\\'          # ⭐ 证据目录：不参与判定，改了无意义 ⇒ ⚠️ 提示即可
)

if ($Changed) {
  ... 收集 changedFiles ...
  $forced = @($norm | Where-Object {
    $p = $_
    @($forceFullPatterns | Where-Object { $p -match $_ }).Count -gt 0
  })
  if ($forced.Count -gt 0) {
    Write-Host "NOTE: -Changed saw a SHARED/integration file -> forcing a FULL run:" -ForegroundColor Yellow
    $forced | ForEach-Object { Write-Host ("        " + $_) -ForegroundColor Yellow }
    $mutations = $allMutations      # ⭐ 不走筛选
    $selNote   = "-Changed=>FULL (shared file touched)"
  } else {
    ... 原来的筛选 ...
  }
}
```

⭐ **关键点**：
* ⭐ **必须用 `$allMutations`**（⭐ 即筛选**之前**的完整列表）⇒ ⚠️ **别用已被 `-Filter`/`-File` 筛过的**
* ⭐ **打印出"是哪几个文件触发的"** ⇒ ⭐ **可观测**（⭐ `K-106` 纪律：⛔ 不许静默改变行为）

### 3.2 ⭐ 次要修法：把"选少了"也变可观测

⚠️ 现在只打印 `[selected: N, of M]` ⇒ ⭐ 建议**额外提示相对比例**：
```
⭐ 若 selected 数 < M 的 30% ⇒ 打一行：
   "NOTE: only N of M mutants selected. If your change touches shared
    infrastructure, re-run with no arguments (FULL)."
```
⚠️ **理由**：⭐ 让"我这次只验了一小部分"这件事**显式可见**，
⛔ 而不是靠人去算 `N/M`。

### 3.3 ⭐ 顺手修：`-Changed` 与 `-Filter`/`-File` 的**组合语义**

⚠️ 现在三个开关**可以同时给**，而代码是**顺序筛**：
```
-Filter M01 -Changed   ⇒ ⭐ 先按 Filter 筛，再按 Changed 筛
```
⇒ ⚠️ **两者取交集** ⇒ ⭐ 这**通常是期望的**，⚠️ 但**没有文档说明**。
⭐ 建议：在头部注释里**明确写一句**"多个开关是**取交集**"。

## 四、⭐ 修完之后的正确用法（⭐ 回答用户的策略问题）

⭐ **用户的策略完全可行**，⭐ 具体落地成这样：

| 场景 | ⭐ 命令 | ⭐ 耗时 |
|---|---|---|
| ⭐ **改一个模块**（如只动 `calib_span.v`） | `mutation_test.ps1 -File w3a` 或 `-Changed` | ⭐ **几分钟** |
| ⭐ **改 `top.v` / 回归器 / 模型** | `mutation_test.ps1`（⭐ **全量**） | 🔴 ~5 h |
| ⭐ **准备 commit / push** | `mutation_test.ps1`（⭐ **全量**） | 🔴 ~5 h |
| ⭐ **每天收工** | `mutation_test.ps1`（⭐ **全量，挂后台睡觉**） | 🔴 ~5 h |

> ⭐⭐ **收工跑全量 + 睡觉** = ⭐ **最优解**：
> * ⭐ **不占用白天产能**（⭐ 白天改代码、跑回归 + PnR）
> * ⭐ 且脚本的**收尾步骤**会"从干净 RTL 再跑一次回归"
>   （⭐ 脚本头部第 35~36 行：*"regression from CLEAN RTL, so you start the next day
>   with clean evidence"*）⇒ ⭐ **第二天早上拿到的是干净证据** ✅

⚠️ **一条硬前提**（⭐ 脚本自己写了）：
🔴 **跑全量之前【必须先 commit】** ——
⚠️ 因为脚本会**就地改可跟踪文件**，⭐ 若它中途被杀（断电 / `job_kill`），
⚠️ **没有 commit 可以退回** ⇒ 🔴 **分不清"残留变异"和"我自己的改动"**。

📌 **本文件就是这条前提的活证据**：
⭐ 2026-09-24 凌晨我因 ESP32 merge 冲突**主动 `job_kill` 了变异测试**
⇒ 🔴 **`rtl/clk_gen.v` 残留了 M01 变异**（`- 1` 被改成 `- 2`）
⇒ ⭐ **靠 `.bak` + 字节级比对才手工还原**（⭐ 幸好脚本留了 `.bak`）。

## 五、⚠️ 另一条并行禁令（⭐ 本轮新增，⭐ 比 `K-119` 更宽）

🔴 **`K-119` 原文**：*"变异测试跑的时候：⛔ 不碰 `rtl/`、⛔ 不 `git add`"*

⚠️ **本轮发现它【不够宽】** —— 🔴 **还有一条：⛔ 不能与【另一个 worktree 的 git 操作】并行**：

```
⭐ 本项目的仓库拓扑（⭐ 实测）：
   C:/Users/hokuu/Desktop/FPGA/FPGA2026        [main]         ← FPGA 线
   C:/Users/hokuu/Desktop/FPGA/FPGA2026-esp32  [feat/s3-ble]  ← ESP32 线
   ⚠️ 两者【共享同一个 .git】⇒ ⭐ .git/worktrees/ 下各有一份 HEAD
   📌 `git worktree list` 实测确认
```

🔴 **风险**：
* ⭐ 变异测试**改 `rtl/` 并靠 `.bak` 还原**（⛔ 不经过 git）
* ⚠️ 而**另一个 worktree 的 `merge` / `checkout` / `reset`** 可能
  ⇒ 🔴 **覆盖被变异的那个文件** ⇒ ⚠️ 变异测试的结论**作废**
  ⇒ 🔴 或者反过来：**merge 拿到被变异的源码** ⇒ ⚠️ **把变异提交进去**

📌 **实测现场（2026-09-24 凌晨）**：
⭐ ESP32 那边正在 merge（`MERGE_HEAD` 存在、100 文件已暂存、含 `bringup/mutation_test.ps1`）
⇒ ⭐ **立即停掉变异测试** 是对的。

⭐ **建议补进 `K-119`**：
> 🔴 **变异测试运行期间**：⛔ 不碰 `rtl/`、⛔ 不 `git add`、
> **⛔ 且不与【另一个 worktree 的任何 git 写操作】并行**（`merge`/`rebase`/`checkout`/`reset`）。
