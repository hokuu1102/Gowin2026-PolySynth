### 1.2 ⭐⭐ 事件格式（64 bit/事件）—— **这是冻结契约**

```python
# tools/mid2evt.py （pack_event）
bit 63..44   tick        (20 bit)   音乐时间，PPQN=960   ⭐ 2026-09-22 由 16 位改
bit 43..23   inc         (21 bit)   相位增量 phase_inc（kind==2 时改存 tick_inc）
bit 22..19   axis        (4 bit)    轴号 0..15
bit 18..11   vel         (8 bit)    力度
bit 10..9    kind        (2 bit)    0=note_on, 1=note_off, 2=换速
bit  8..7    timbre      (2 bit)    音色号 0..3 —— 2026-09-22 夜新增
bit  6..0                (7 bit)    保留，写 0
```

> 🔴 **2026-09-22 夜：`tick` 由 16 位改为 20 位**（⭐ 旧版 `& 0xFFFF` 会让真实曲子的时间轴
> 静默回绕 **12 次**）⇒ ⭐ **详见 `play_seq接口冻结契约.md` §1.1**。
> ⭐ **记录仍是 64 bit** ⇒ ⛔ **本节下面的"9 字节帧"结论不受影响**。

> ⚠️ **注意 `tick` 只有 16 bit** ⇒ **最大 65535 tick = 68.3 拍**（PPQN 960）
> ⇒ 🔴 **整曲无法用单条 16 bit tick 表达** —— ⭐ **这是 U-19 缓冲区大小、和 play_seq 设计的硬约束**（见 §四）

## 二、🔴 缺什么（按依赖顺序）

### 2.1 ⭐ 缺口 A：速度表不进 `.hex`（`mid2evt.py` 改）

**现状**（`mid2evt.py:379`）：速度表**只写进 `report.txt`**，⛔ **不写进 `events.hex`**
⇒ ⭐ **FPGA 拿不到变速信息** ⇒ ⚠️ **变速曲目会按单一 BPM 播放（错拍）**。

**要做的改动**（⭐ 与总账 §5.1 方案一致）：

| # | 改动 | 细节 |
|---|---|---|
| 1 | 新增 `kind = 2` | 表示「**换速**」，⛔ 不新开字段 |
| 2 | **复用 `inc` 字段** | 换速事件里 `inc` **改存 `tick_inc`**（相位增量，⛔ 不是 phase_inc） |
| 3 | 事件插入 | 在每个 set_tempo 的 tick 处插一条 `kind=2` |
| 4 | tick 表校验 | 换速事件的 tick 同样受 **16 bit 限制**（见 §四） |

**⭐ `tick_inc` 怎么算**（⚠️ 必须与 `beat_gen.v` 口径一致）：

```
一拍 = PPQN = 960 tick
tick 频率 f_tick = BPM/60 × 960  [Hz]
每 tick 的相位增量 tick_inc = round(2^32 × f_tick / 50e6)
```

⇒ ⭐ **验收判据**：`tick_inc` 输出端**校验非 0**（`tick_inc=0` ⇒ 时钟静止，总账 §5.1 已标风险 3）

### 2.2 🔴 缺口 B：事件流怎么进 FPGA（**全新，无任何代码**）

⭐ 这是**最大的洞** —— 事件在 PC 上、要进 FPGA，中间**什么都没有**。

**要新建传输工具 `evt2uart.py`**（⭐ 放在 `tools` 目录下，⚠️ **尚未创建**）：

| # | 功能 | 细节 |
|---|---|---|
| 1 | 读 `events.hex` | 纯文本，一行一个 64 bit 十六进制 |
| 2 | 打包成帧 | ⭐ 见 §三 协议 |
| 3 | 发串口 | `pyserial`，**115200 8N1**（⚠️ 必须与 `BAUD_DIV=434` 匹配） |
| 4 | 流控 | ⚠️ **不能灌太快** —— FPGA 侧要有握手（见 §三） |
| 5 | 计时基准 | ⚠️ **关键**：事件带的是 **tick**，⛔ 不是绝对时间 |

**⚠️ ⭐⭐ 最大的设计问题：谁来"踏" tick？**

有两种根本不同的做法，⛔ **必须二选一，不能含糊**：

| 方案 | 谁掌握节拍 | 优点 | 缺点 |
|---|---|---|---|
| **A · FPGA 自主**（⭐ 推荐） | `beat_gen` 跑，PC **只预灌**事件 | ⭐ 抖动 = 0（硬件时钟）；⭐ 断连不影响演奏；⭐ 符合"纯硬件实时" | ⚠️ 需缓冲区（U-19，2 KB） |
| **B · PC 主控** | PC 按真实时间发，FPGA 来一条放一条 | 简单、无需缓冲 | 🔴 **PC 抖动直接变成音频抖动**；🔴 违反"确定性上界"（你拍板决定 8） |

⇒ ⭐ **建议 A**：**PC 只负责"把谱子搬进去"，节拍由 `beat_gen` 硬件产生**。
⭐ 这正好复用已有的 `beat_gen`，且满足你拍板的「延迟要确定性上界」。

#### ⭐⭐ 2.3.1 ESP32 的职责边界（⚠️ 2026-09-22 夜探讨）

⚠️ **问题**：解析 MIDI 文件**交给 ESP32 还是上位机**？会不会碰红线？

**结论**：⭐ **两种都合规**，⭐ **但推荐"ESP32 只当中转"**。

| 方案 | 谁解析 MIDI | 合规性 | 评价 |
|---|---|---|---|
| **甲 · ESP32 解析** | ESP32 收到 `.mid` → 自己转事件流 | ✅ **合规** —— ⭐ 文件解析**不是音频合成**（见 §6.6） | ⚠️ 固件复杂（要移植 `mid2evt` 逻辑） |
| ⭐ **乙 · ESP32 只中转** | ⭐ **上位机解析 → ESP32 纯透传字节流** | ✅ **更安全** | ⭐⭐ **推荐** —— ⭐ 固件极简 |

> ⭐⭐ **为什么推荐"只中转"**：
> ① ⭐ **ESP32 固件越简单越不容易出问题**（⚠️ 透传 = 几行代码）；
> ② ⭐ **解析逻辑只维护【一份】**（在 `mid2evt.py`）—— ⛔ 不用在 ESP32 上重写一遍 C 版本；
> ③ ⭐ **合规上更无可指摘** —— ⭐ **ESP32 连数据内容都不看，纯粹搬运**。

> ⚠️ **但要注意**：⚠️ **两种方案下，FPGA 侧【完全一样】** ——
> ⭐ **FPGA 收到的都是一串事件帧**，⛔ **不关心它从哪来**（⭐ USB 线 / 蓝牙 / 串口都一样）。
> ⇒ ⭐ **这个选择【不影响 FPGA 设计】**，⭐ 可以先做有线、以后再定蓝牙侧怎么分工。

#### ⭐⭐ 2.3.2 FPGA 只做音频链路吗？—— ✅ **是的，但要注意一条边界**

⭐ **用户的判断正确**：**FPGA 只负责"从事件流到出声"**。

| 环节 | 谁做 | 为什么 |
|---|---|---|
| ⭐ **解析 MIDI 文件** | **上位机 / ESP32** | ⛔ **不是实时任务**（⭐ 可以慢、可以抖） |
| ⭐ **传输事件流** | **ESP32 透传** | ⛔ 不涉及音频生成 |
| ⭐⭐ **合成音频** | ⭐ **FPGA** | 🔴 **必须 FPGA** —— ⭐ 这是评分核心（逐样本实时） |
| ⭐ **可视化生成** | ⭐ **FPGA** | 🔴 **必须 FPGA**（⭐ 主办方答复③："视觉效果不要用 MCU"） |

> 🔴 **唯一的边界**：⭐ **FPGA 侧不能变成"播放器"** ——
> ⭐ **它必须【逐音、逐样本实时合成】**，⛔ **不能是"解码一段音频"**。
> ✅ **事件流 = 演奏指令** ⇒ ⭐ **FPGA 收到后仍是自己算波形** ⇒ ✅ **完全合规**（详见 §六 红线分析）。

### 2.4.2 ⭐ 逐段说明

**① PC 侧打包（`evt2uart.py`，🔴 要新建）**

⚠️ **`events.hex` 是纯文本**，⛔ **不是二进制**：
```
0000a50000000000        ← 一行 = 一个事件（16 个十六进制字符）
```
⚠️ 文件里的 `a5` 是**十六进制字符**，⛔ 不是字节 `0xA5`
⇒ ⭐ **必须先 `int(line, 16)` 解析成整数，再拆成 8 个字节**。

**② 帧格式**（⭐ 建议，见 §三）：
```
每帧 9 字节：  byte0 = 0xA5（帧头）   byte1..8 = 64 bit 事件（大端）
```

**③ FPGA 侧 `uart_rx.v`（✅ 已有）** —— 端口极简：
```verilog
input  wire       rx_i;         // 串行输入
output reg  [7:0] rx_data_o;    // ⭐ 收到的字节
output reg        rx_done_o;    // ⭐ 单周期脉冲
```
⇒ ⭐ **"每收一个字节，`rx_done_o` 响一下"** —— ⚠️ **它只管收字节，⛔ 不懂"帧"**。

**④ 帧解析（🔴 要新建）** —— 组装状态机：
```
等 0xA5 → 收 8 个字节 → 拼成 64 bit → 写缓冲，给 valid 脉冲
```
⚠️ **陷阱**：`0xA5` 也可能是**事件数据里的合法字节**（如 `tick = 0xA5xx`）
⇒ ⭐ **对策：⛔ 不做"任意位置扫描"**，⭐ **严格按 9 字节节奏走**；
⭐ **失步则让 PC 重发复位序列**（一串 `0xA5`）⇒ ⭐ **误同步不可能发生**。

**⑤ 缓冲 + `play_seq.v`（🔴 最关键的缺口）**

⭐⭐ **核心问题：谁来"踏" tick？** ⚠️ 事件带的是 **`tick`（音乐时间）**，⛔ 不是绝对时间。

| 方案 | 谁掌握节拍 | 评价 |
|---|---|---|
| ⭐ **A · FPGA 自主** | `beat_gen` 跑，PC **只预灌**事件 | ⭐ **抖动 = 0**（硬件时钟）；⭐ 断连不影响演奏；⭐ 符合"纯硬件实时" |
| **B · PC 主控** | PC 按真实时间发，来一条放一条 | 🔴 **PC 抖动直接变音频抖动** ⇒ 🔴 **违反"确定性上界"**（决定 8） |

⇒ ⭐⭐ **必须选 A**：**PC 只搬谱子，节拍由 `beat_gen` 硬件产生。**

```
PC 灌 1024 个事件 → FPGA 存进缓冲（⭐ 8 KB，见 `整曲缓冲大小定案.md`）
beat_gen 跑 → 每出一个 tick，play_seq 查缓冲里有没有这个 tick 的事件
           → 有就吐给 evt_merge
缓冲将空 → 通知 PC 再灌一批
```

### 2.4.3 ⭐⭐ 换速（U-7）怎么进来

⭐ 这就是 **B 方案**（`timbre` 进事件）的姊妹项 —— ⭐ **同样用事件字段承载**：

```
events.hex 里插一条 kind=2 的事件：
  kind = 2         → 换速
  inc  = tick_inc  （⛔ 不是 phase_inc！）
  tick = 该换速生效的 tick
```

`play_seq.v` 读到 `kind=2` ⇒ ⭐ **把 `tick_inc` 写到 `beat_gen.tick_inc_i`**
⇒ ⭐ **硬件时钟立刻变速，相位连续、不跳拍**（⭐ `beat_gen` ⛔ 不用改，已核实）。

### 2.4.4 ⭐ 换板后引脚（✅ 已定）

| 信号 | 引脚 | 方向 |
|---|---|---|
| **UART2_TX**（FPGA → ESP32） | `PMOD0_IO2` = **`G21`** | FPGA 输出 |
| **UART2_RX**（FPGA ← ESP32） | `PMOD0_IO3` = **`G22`** | ⭐ FPGA 输入（接对方 TX） |

### 2.4.5 ⭐⭐ 蓝牙进来之后，整条链长这样

```
手机 App ──蓝牙 SPP──> ESP32 ──串口透传──> FPGA ──> 实时合成 ──> PCM5102A ──> 贝斯音箱
   │                      │                    │
   │              ⭐ 只搬运字节        ⭐ 只做音频链路
   └── 或：上位机解析好 → 蓝牙 → ESP32 → FPGA（⭐ 推荐，见 §2.3.1）
```

⭐⭐ **关键点**：⚠️ **换不换蓝牙，FPGA 侧【一模一样】** ——
⭐ **它收到的永远是一串事件帧**，⛔ **不关心从哪来**（USB 线 / 蓝牙 / 别的）。
⇒ ⭐ **所以可以先做有线跑通，再加蓝牙**（⛔ 不引入新变量）。

## 三、⭐ 建议的串口帧协议（**待你拍板**）

⚠️ **这是新增设计，必须你确认**。当前 `uart_rx.v` 是**通用字节接收器**，⛔ 没有帧概念。

**⭐ 建议：极简定长帧**（⭐ 因为 FPGA 侧没有 CPU、⛔ 不能做复杂解析）

```
每帧 9 字节：
  byte 0      : 0xA5          帧头（固定魔数）
  byte 1..8   : 64 bit 事件  大端（与 events.hex 顺序一致）
```

**为什么用固定帧头而不是长度字段**：

| 理由 | 说明 |
|---|---|
| ⭐ **纯硬件可解析** | 8 个移位寄存器 + 比较器即可，⛔ 不需要状态机解析长度 |
| ⭐ **可重同步** | 丢字节后扫到 `0xA5` 即恢复（⭐ 但要防"数据里正好有 0xA5"⇒ 见下） |
| ⚠️ **代价** | 吞吐 9/8 = 12.5% 开销（⭐ 可接受，事件很少） |

**⚠️ 必须处理的风险：数据里出现 `0xA5`**

⭐ `0xA5` 是**合法的事件载荷字节**（例如 `tick=0xA5xx`）。
⇒ ⚠️ **简单扫 `0xA5` 会误同步**。

**⭐ 对策（三选一，建议 3）**：

| # | 做法 | 评价 |
|---|---|---|
| 1 | 转义（`0xA5` → `0xA5 0x00`） | ⚠️ 复杂，需 FPGA 侧反转义 |
| 2 | 变长帧 + 长度校验 | ⚠️ 更复杂 |
| 3 | ⭐ **软复位序列 + 固定间隔** | ⭐ **推荐**：PC 先发一串 `0xA5`（≥ 2 帧时间）让 FPGA 状态机归位，之后**严格按 9 字节节奏发**；⭐ FPGA 侧**只在"第 0 字节位置"看帧头**，⛔ 不做任意位置扫描 ⇒ ⭐ **误同步不可能发生** |

⭐ **方案 3 的关键**：**不做自由扫描** ⇒ **失步后由 PC 重发复位序列**，而不是 FPGA 自己猜。

**⚠️ 反压/流控（⛔ 不能省）**

⚠️ FPGA 侧缓冲区满时必须能喊停，否则**丢事件**（🔴 正是 `evt_merge` 要解决的同类缺陷）。
⭐ 建议：**开一条反向 UART**（FPGA → PC），FPGA 发 `0x11`=可发 / `0x13`=暂停。
⚠️ 代价：多占 1 个 IO + 需要 FPGA 侧一个 `uart_tx`（⚠️ **当前没有 `uart_tx.v`** ⇒ ⭐ **要新建**）。

> ⚠️ **替代方案（⭐ 更省）**：**PC 侧限速**，按谱子真实时间放慢发送（例如提前 8 拍灌满就不再发）
> ⇒ ⭐ **不需要反向通道**，但 ⚠️ **依赖 PC 守时** ⇒ 违背"确定性上界"。
> ⭐ **建议**：**先做限速版（快），若是上板发现丢事件再加反向通道**。

## 四、⚠️ 与 U-19（整曲缓冲）的强耦合

🔴 **`tick` 字段只有 16 bit** ⇒ 最大 **65535 tick ≈ 68 拍** ⇒ ⚠️ **整曲装不下**。

**⇒ 必须选择**：

| 方案 | 说明 | 评价 |
|---|---|---|
| **1 · 滚动预灌**（⭐ 推荐） | 缓冲 2 KB（≈ 256 事件），PC **提前 8 拍**灌下一段 | ⭐ 内存极小；⚠️ 依赖 PC 不断连 |
| **2 · 扩 tick 到 32 bit** | 改事件格式 ⇒ 🔴 **要改 `mid2evt.py` + FPGA 侧** | ⚠️ 破坏已冻结契约 |
| **3 · 全曲预载 BSRAM** | 整曲 ≈ 24K 事件 × 8 B = **192 KB** | 🔴 **BSRAM 不够**（现用 5%，但 192 KB 远超） |

⭐ **建议方案 1**，且**与 `evt_merge`/`looper` 争 BSRAM 的账要一起算**（总账 U-19 已标）。
