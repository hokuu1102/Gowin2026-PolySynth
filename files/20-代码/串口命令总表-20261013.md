## 二、⭐ 加新命令的**检查清单**（⛔ 漏一步就是上板白干）

🔴 **`calib_cmd.v` 加一条命令要改【6 处】**，漏任何一处都会静默失效：

| # | 改哪 | 说明 |
|---|---|---|
| **1** | `parameter [7:0] CMD_XXX = 8'hXX` | 常量 |
| **2** | `output reg xxx_req_o` | 输出端口 |
| **3** | `wire byte_is_xxx = (rx_data_i == CMD_XXX);` | 译码 |
| **4** | 复位块 + 默认清零块：`xxx_req_o <= 1'b0;` | **两处**（缺一个 ⇒ 脉冲不清） |
| **5** | `if (byte_is_xxx) xxx_req_o <= 1'b1;` | 出脉冲 |
| **6** | 🔴🔴 **把 `byte_is_xxx` 加进 `byte_is_cmd` 总闸** | ⭐ **`'A'` 就是漏了这一步 ⇒ 上板完全无效** ✅ |

⚠️ **第 6 步是头号陷阱** —— 代码里 `:380-382`（四个新字母）和 `:385-387`（`'Y'`）
**两条注释都写着"必须在这里"**，⭐ **而我加 `'A'` 时还是漏了**。
⇒ 现在有判据守着：`tb/w3a/tb_calib_cmd.sv` 的 `'A'` 段（含"帧内不得触发"）。

📌 **另需同步**：
- `cmd_tab[N] = CMD_XXX` + `N_CMD` 加一（**查重表**）
- `top.v` 的回包映射：`rep_req` 里加 `| cmd_xxx_req`，`rep_byte` 里加 `: cmd_xxx_req ? 8'hXX`（**否则落到兜底 `'x'`，上板无法确认受理**）
- `top.v` 里把 `xxx_req` 接到真正的消费者

## 三、⚠️ 与串口屏的关系（**同一条线！**）

🔴 **串口屏和命令共用 D14** ⇒ 必须知道这条边界：

| 谁 | 协议 | 谁解析 |
|---|---|---|
| **命令字母** | 单字母 | `calib_cmd` |
| **串口屏帧** | `<返回码>` + 载荷 + `FF FF FF` | `uart_ui` |
| **`0xA5` 事件帧** | `0xA5` + 8 字节 | `evt_uart_rx`（⭐ **已改走 ESP32 独立口 G22**） |

**屏的返回码**（`uart_ui.v:136-140`）：
| 码 | 含义 |
|---|---|
| `0x65` | 控件点击事件 |
| `0x70` | 字符串变量返回 |
| `0x71` | 数值变量返回 |
| `0x88` | 系统启动成功（握手） |
| `0xFF`×3 | 帧结束符 |

**屏的控件号**（`uart_ui` 认领的）：`0` = 模式切换 · `1` = 起始音 · `2` = Test Mode 档位

⚠️ **仍然存在的风险**（⭐ 如实标注）：`calib_cmd` **只跟踪 `0xA5` 帧**，**不认识屏帧**
⇒ 屏帧载荷里若出现命令字母（如 `0x41` = `'A'`），**`calib_cmd` 会误当命令执行**。
📌 **当前实际安全**：屏的控件号是 0/1/2（⛔ 不是 0x41）⇒ 碰撞概率低
📌 **但 `RET_STR`（字符串返回）帧会携带任意文本** ⇒ ⚠️ **理论上可能撞**
⇒ ⭐ **根治**：给 `calib_cmd` 加一个 `in_frame_i`（接 `ui_in_frame`）门控 —— 那正是 `P0-02` 当年的做法
（⭐ 它 2026-10-11 被删，是因为当时**曲谱也共用这条线**；**现在曲谱有独立线了**，
所以**给 `calib_cmd` 单独加回这个门控是安全的** —— ⚠️ 待评估）
