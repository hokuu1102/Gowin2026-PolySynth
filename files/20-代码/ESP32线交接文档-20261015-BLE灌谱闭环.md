## 三、两条最贵的教训（下个会话必看）

### 教训一：`ble=rxN` 是**自开机累计**，不是"本次已收"

**症状（实测）**：
```
已发 75 KB · ESP32 实收 240 KB · 在途 -166 KB · 收速 805.5 KB/s
```
**实收比已发还多，在途算成负数。**

**后果**：`在途 > 窗口` 永远不成立 ⇒ **流控彻底失效** ⇒ 全速冲 ⇒ 丢帧。
这解释了那个怪现象：**一次会话里"前面慢而能放、后面快而放不了"**。

**修法**：本次上传记基线，只用增量：
```js
fcAckedBase = lastBleRx;                          // 上传开始时
fcAcked = Math.max(0, st.bleRx - fcAckedBase);    // 之后一律用增量
```
（累计值变小时要跟着挪基线——清池会把它清零。）

**一般化**：拿到任何"累计计数器"，先问一句"它是自开机累计还是本次累计"。

### 教训二：流控的**窗口大小本身就是丢帧的成因**

关键不在"丢了多少"，而在**什么时候丢**：
```
已发 75 KB  → 实收 11 KB    （这一步丢了 85%）
已发 93 KB  → 实收 46 KB
已发 150 KB → 实收 96 KB    （累计 36%）
```
开头在途=0 ⇒ 流控不拦 ⇒ **一口气把整个窗口灌进链路** ⇒ 控制器 RX 缓冲爆。

**结论**：窗口**不是**"能收多快"的上限，而是**突发量**。
窗口与 notify 周期**互相依赖**，必须一起调：
- 小窗口 + 慢通知 = 很慢
- 大窗口 + 快通知 = 照样丢

**两个必须知道的陷阱**：
1. **打开 COM29 会复位 ESP32**（`rst:0x15 USB_UART_CHIP_RESET`）
   ⇒ 必须在用户操作**之前**开好，之后**不要再动串口**。
2. **抓取会占住 COM29** ⇒ 期间**烧录必然失败**（`Could not open port`）。
   ⇒ 烧录前先杀掉抓取任务。

### 烧录

### 网页侧的两个坑

1. **必须 `Ctrl + Shift + R` 强制刷新**。本轮踩过：普通刷新后浏览器跑的是旧版页面，
   导致"关掉 notify 开关"看起来没生效，**整次 A/B 测试作废**。
2. **诊断开关必须只关被测对象**。本轮踩过：`USE_STAT_NOTIFY = false` 同时关掉了
   流控和完整性核对 ⇒ **把自己的仪表一起关了**，那次测得 29.4 KB/s 却什么也验证不了。

### 判据写法（本项目硬性）

- **必须验证非空洞性**：把修法改回 bug 形态，判据**必须变红**，再改回来必须全绿。
  本轮每条判据都做了这一步。
- **宁可误报，不可失效**。本轮踩过：为消一个 `rx(` 误报给检查器加"剥正则字面量"，
  结果剥得太激进把真代码也吃掉 ⇒ 判据失去非空洞性（等于废掉）。已回退，改用极小白名单。
- **正则捕获组永远是字符串**。本轮踩过：`frameEv` 忘了转数字 ⇒ 下游 `n(v)`
  因 `typeof !== "number"` 返回 null ⇒ **整块静默跳过**，日志里没有那行，
  我一度误以为是"没丢帧"。
- **解析不到必须喊出来**，⛔ 不许静默跳过。
