# ESP32 侧需求：`0xABF1` 必须支持 **Write With Response**（2026-10-14）

> **收件人**：FPGA 线
> **提出人**：ESP32 线（用户实测 + 串口日志定位）
> **紧急度**：🔴 **阻塞** —— 灌谱**丢 39% 数据**，曲子"只有一截"
> **关联**：`ESP32侧需求-STAT周期性notify-20261014.md`（另一条，🟡 不阻塞）

---

## 一、需求一句话

**请给 `0xABF1`（灌谱通道）加上 `ESP_GATT_CHAR_PROP_BIT_WRITE` 位**
（现在是 `READ | WRITE_NR`，**只有无确认写**）。

---

## 二、🔴 实测证据（不是推测）

### 2.1 串口日志（我方直接抓 ESP32 的 UART0）

```
ble=rx104640 tx0 fail=0 drop=0 mtu=517 conn=1 sub=1
frame=total=1 tf=18935 ev=11621 rst=4 unk=0
pool=11621/233016 sent=121 ovf=0 late=1 exp=18935 mm=1
```

| 项 | 值 |
|---|---|
| 网页实际交给 `writeValueWithoutResponse` 的字节 | **170460**（18935 事件） |
| **ESP32 实际收到** | **104640 字节** |
| ⇒ 差额 | 🔴 **65820 字节 = 39%** |
| 池里帧数 | 11621（11621 × 9 = 104589 ≈ 实收 ✓ 自洽） |
| `ble.drop` | **0** |
| 上行环 | **0/163840（空）** |
| `ovf` | **0** |

### 2.2 这三条一起说明**丢在空中**

- `ble.drop = 0` ⇒ ⛔ 不是 `ble_buf_push()` 截断
- 环是空的 ⇒ ⛔ 不是环满
- `ovf = 0` ⇒ ⛔ 不是池满（⭐ 我方已把池从 160 KB 提到 2 MB，溢出一项已解决）
- ⇒ 🔴 **那 65820 字节【根本没到 ESP32】** —— 在 BLE **链路层**就丢了

### 2.3 而 `WRITE_NR` **让丢包无法被发现**

`WRITE_NR` = 无确认写：
- 浏览器把数据放进队列就**立刻 resolve**（⛔ 不等对端）
- ⇒ 链路层丢包时，**浏览器不知道**、**ESP32 更不知道**（它没收到，自然不计 drop）
- ⇒ 🔴 **静默丢数据**，只能靠 `tf=18935` vs `ev=11621` 事后才发现

⚠️ 我方已经加了节流（`PACING_MS=20`，实测 **19.5 KB/s** —— 对 BLE 来说**很慢**），
   ⛔ **仍然丢 39%** ⇒ ⭐ **说明这不是"发太快"，而是"无确认写本身不可靠"**。

## 三、请你们做的

### 方案 A（推荐，一行）：给 `0xABF1` 加 `WRITE` 位

```c
/* gatt_svc.c:68-69 现在是： */
static const uint8_t s_prop_recv = ESP_GATT_CHAR_PROP_BIT_READ |
                                   ESP_GATT_CHAR_PROP_BIT_WRITE_NR;

/* ⭐ 改成（两个位都留，客户端自己选）： */
static const uint8_t s_prop_recv = ESP_GATT_CHAR_PROP_BIT_READ |
                                   ESP_GATT_CHAR_PROP_BIT_WRITE |
                                   ESP_GATT_CHAR_PROP_BIT_WRITE_NR;
```

⭐ **保留 `WRITE_NR` 位**：这样老客户端不受影响，新客户端可以选带确认写。
   📌 也请确认 `0xABF3`（命令）要不要一起加 —— 命令只有 1 字节、丢了后果也大
   （用户实测出现过"发了起播但没反应"）。

**为什么这就够了**：带确认写时，浏览器会**等 ESP32 的 ATT 响应**才 resolve
   ⇒ ⭐ **天然的流控** ⇒ 缓冲区满了对端不响应 ⇒ 浏览器自动等待
   ⇒ 🔴 **不可能再丢**。

**代价**：吞吐会降一些（每次写要等一个 ATT 往返）。
   ⭐ 但**可靠 > 快** —— 而且我方会按"能确认的速率"发，总体反而更稳。

### 方案 B（若不想加 WRITE 位）：加一个**分块确认**协议

⭐ 例如：PC 每发 N 帧，就写一次命令"请报已收帧数"，ESP32 在 STAT 里回 `ev=`；
   PC 发现 `ev` 没涨就**重发**那一块。
   ⚠️ 这需要双方都改，⛔ 比方案 A 复杂得多。
