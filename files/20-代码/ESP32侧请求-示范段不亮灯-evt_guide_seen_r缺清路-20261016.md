# ESP32 侧请求：示范段（bit6=0）点不亮 LED —— `evt_guide_seen_r` 缺"清路"

> 收件人：FPGA 线
> 触发：用户实测「示范—重复模式，**示范段不亮、重复段反而亮了**；复位后示范段仍不亮」
> 结论：**ESP32 侧的数据已逐位证实正确**（§一，含上线字节反解）；现象与"LED 闸门只认
> `bit6`"完全一致 ⇒ 问题在 `evt_guide_seen_r` 这个闩锁**没有与"起播/重灌"绑定的清路**
> （它唯一的清路是 `rst_n_sync`），或板上位流不含该项。

---

## 〇、⭐ 2026-10-16 深夜追加：用户实测把问题收窄了（本节的证据比 §三 的自测更强）

用户的观察是**决定性**的：

| 段 | 载荷里的 `bit6` | 用户实测 LED |
|---|---|---|
| 示范 | **0** | ⛔ **不亮** |
| 重复 | **1** | ✅ 亮 |

⇒ 这正是"**闸门只等于 `evt_guide_only`**"的行为 —— 即 `~evt_guide_seen_r` 那一项
**在板上没有生效**（要么位流里没有，要么该闩锁在示范段播放**之前就已经是 1**）。

### 0.1 ESP32 侧的证据（逐位，可复现）

1. **打包字**：两段**除 `tick` 与 `bit6` 外零位差**（力度 / 轴 / 音色 / `note5` 全同）：
   ```
   示范段旋律 16 个 / 重复段旋律 16 个
   除 tick/bit6 外【零位差】
   示范段 bit6 集合 = [0]     重复段 bit6 集合 = [1]
   示范段 note5 = 全 26        重复段 note5 = 全 26
   ```
2. **上线字节**（`buildPayload` 输出，9 字节/帧，反解 8 字节字）：
   ```
   payload = 918 字节
   示范段(tick<7680) : bit6=0 -> 17（16 音符 + 1 tempo）  bit6=1 -> 0
   重复段(tick≥7680) : bit6=0 -> 0                        bit6=1 -> 16
   tick ≥ 停止线      : 0 帧
   ```
⇒ ⭐ **"重复段亮、示范段不亮"这件事，只能由 `bit6` 解释**；
`note_off5` / 音高 / 力度 / 轴在两段完全相同，⛔ 排除"字段填错"。

### 0.2 🔴 一条我们踩到的关键点：**重灌谱不会清 `evt_guide_seen_r`**

上位机每次换谱/重灌前会发一段 **reset 序列**（连续 `0xA5` 事件帧）——
它的作用是**冲掉 FPGA 的事件缓冲**（换谱面消音）。
但它**不触碰 `evt_guide_seen_r`** —— 按你们 RTL，那个寄存器的清路**只有 `rst_n_sync`**
（`rtl/top.v:1757-1760`）：

```verilog
if (!rst_n_sync)                          evt_guide_seen_r <= 1'b0;
else if (ps_note_valid && evt_guide_only) evt_guide_seen_r <= 1'b1;
```

⇒ 🔴 **后果**：只要播过一次 `bit6=1` 的重复段，**之后每一次重灌 + 重播**，
`~evt_guide_seen_r` 都恒 0 ⇒ **示范段永远不亮**，直到真正断电/复位。
⚠️ 用户说"复位之后也不亮" —— 若那次"复位"只是**重灌谱**（不是真断电 / 不是 `rst_n`），
现象就完全对得上；若确实真断电后仍不亮 ⇒ 见 §三 的第二种可能（位流旧）。

## 一、ESP32 侧载荷（完整口径）

示范—重复的载荷（用户裁定的三段式：示范 N 小节 → 重复 N 小节 → 之后停止）：

| 段 | `bit6` | 期望行为 | 实测 |
|---|---|---|---|
| 示范 | **0** | 出声 **＋ 亮灯** | 16 字，全部 `guide=0` ✓ |
| 重复 | **1** | 只亮灯 | 16 字，全部 `guide=1` ✓ |
| 之后 | — | 无任何事件 | 最大 tick = 15359（= 停止线-1）✓ |

⇒ ⭐ **`bit6` 的用法没变**（与你们既有的 `tb_top_guide_bit6` 口径一致）：`0` = 出声、`1` = 只亮灯。
⇒ 但"**出声 + 亮灯**"这个组合，在你们当前的 LED 闸门下**结构上拿不到**（见 §二）。

## 二、根因：`evt_guide_seen_r` 没有清路

`rtl/top.v:7293`：

```verilog
.note_valid_i   (ps_note_valid & (guide_only_r | evt_guide_only
                                  | ~evt_guide_seen_r | ps_is_note_off)),
```

`rtl/top.v:1757-1760`：

```verilog
reg evt_guide_seen_r;
always @(posedge clk) begin
  if (!rst_n_sync)                          evt_guide_seen_r <= 1'b0;
  else if (ps_note_valid && evt_guide_only) evt_guide_seen_r <= 1'b1;   // ⛔ 只有 set，没有 clr
end
```

⇒ 它是一次性的"这份流里见过逐事件指引吗"闩锁。**但"起播"不是复位**：
同一份位流里，只要 `bit6=1` 的事件播过一次，`evt_guide_seen_r` 就**永久为 1**，
此后 `~evt_guide_seen_r = 0` ⇒ **`bit6=0` 的示范段拿不到灯**（`guide_only_r=0` 时）。

📌 这与你们注释里写的"`bit6` 恒 0 的旧工具链 ⇒ `~evt_guide_seen_r` 恒 1"**不冲突** ——
那个前提是"整份流都没有 bit6"；而示范—重复**故意在同一份流里混用两种**（前段 0、后段 1），
所以闩锁的副作用就暴露了。

## 三、两种可能（用户已做过自测，只剩这两条）

用户实测：**真复位后示范段仍不亮**（且重复段亮）。剩下只有两种可能：

| # | 可能 | 判据 / 怎么区分 |
|---|---|---|
| **A** | **位流是旧的** —— 不含 `~evt_guide_seen_r` 那一项（`top.v:7293-7294` 是 2026-10-15 收尾才加的） | 查板上位流的构建时间 / 重新 PnR 下载后再测；若下载**新位流**后示范段亮了 ⇒ 就是这条 |
| **B** | **位流是新的，但 `evt_guide_seen_r` 在示范段之前就已是 1** | 用 SignalTap/仿真看起播头几拍该寄存器；⭐ 注意 §0.2 —— 上位机换谱只发 reset 序列（冲事件缓冲），**⛔ 不清这个寄存器**，所以"重灌一次"不算复位 |

⚠️ 两者都指向同一处代码，⛔ 不必等区分清楚才动手 —— §四 的修法对 A/B **都成立**
（A 要重出位流，B 要加清路；而 §四-① 本来就要重出位流）。

## 四、请求的修法（二选一，我们倾向 ①）

### ① 起播时清零 `evt_guide_seen_r`（最小改动，推荐）

在**起播**（`T_TRANSPORT_START` / `play_seq` 起播 / `seq_arb` 复位那一刻）把
`evt_guide_seen_r <= 1'b0`。语义变成"**本次演奏**里见过逐事件指引吗"——
与 `~evt_guide_seen_r` 的设计意图（"整份流都没标 ⇒ 退回裸 `ps_note_valid`"）一致，
只是把作用域从"上电以来"收窄到"本次起播以来"。

⭐ **建议同时挂两个清点**（因为"重灌谱"不经过起播，见 §0.2）：

| 清点 | 为什么 |
|---|---|
| **起播**（`T_TRANSPORT_START`） | 同一份流重播时，示范段也要能亮 |
| **换谱/冲缓冲**（上位机发的那串连续 `0xA5` reset 序列） | 换一份谱时状态必须是干净的，⛔ 不能继承上一份的"见过 bit6" |

⚠️ 注意：`evt_guide_seen_r` 的 set 条件在 `ps_note_valid` 上（**演奏拍**），
所以清零挂在**起播**上是对的；挂"上传完成"上不够（上传完成后还没播，
同一份流重播仍会踩同一个坑）。

### ② 让 LED 不再依赖"有没有见过 bit6"（更彻底，且直接解决本需求）

即把 `~evt_guide_seen_r` 改成**恒真**（你们 `top.v:1750` 的注释里已把这个选项写出来了）：

```verilog
.note_valid_i (ps_note_valid & (guide_only_r | evt_guide_only | 1'b1 | ps_is_note_off))
```

⇒ LED 变成"**只要是音符事件就指**"，`bit6` / `'U'` 只决定**要不要出声**。
语义更简单，而且**天然支持"出声 + 亮灯"**（正是示范段要的）——
⛔ 而且**不再依赖任何闩锁**，A/B 两种可能一次性都消掉。
⚠️ 代价：**普通演奏（bit6 全 0、`'U'` 关）LED 也会亮** ——
⚠️ 这与你们既有 tb 里"没有指引标记 ⇒ 不点灯"的判据**冲突**，要一起改。
⭐ 但按赛题 B4「脱机演奏 LED 曲目指引」，**灌谱就指键**其实更贴题。

## 五、我们这边不动

⛔ ESP32 侧**不改 `bit6` 语义**（`0` 出声 / `1` 只亮灯），因为：
- 改成"示范段也置 1" ⇒ 示范**不响了** ✗（那这个模式就没意义了）；
- 现状下"出声 + 亮灯"在你们闸门里**无解**（`bit6=0` 与 `guide_only_r=1` 都会导致"响则不亮"）。

⇒ 修好 §四 任一条后，我方**零改动**即可看到"示范段出声 + 亮灯"。
