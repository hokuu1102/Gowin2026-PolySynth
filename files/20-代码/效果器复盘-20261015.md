## 一、最重要的一条：一个根因，11 处症状

### 🔴 我犯的错

我在 `fx_dist.v` / `fx_trem.v` 里**把乘积打了拍**，但下游**用的是组合版本**：

```verilog
// ❌ 我原来写的
wire signed [SUM1_W-1:0] prod1 = s0 * gain_r;   // 组合
wire signed [SUM1_W-1:0] shr1  = prod1 >>> GAIN_FRAC;   // 🔴 用的是组合的 prod1
...
always @(posedge clk) p1 <= prod1;              // ⭐ 这个寄存器【白打了】
```

⇒ 🔴 **数据路径比 valid 路径【短一拍】** ✗
⇒ 🔴 **输出样点与它自己的 valid 错拍** ✗
⇒ ⭐ **这就是"错拍"（pipeline misalignment）** ✓

### ⭐ 队友的修法

```verilog
// ✅ 修后
wire signed [SUM1_W-1:0] shr1 = p1 >>> GAIN_FRAC;   // ⭐ 用【寄存器】p1
```

⇒ ⭐ **一处改动，但影响整个模块的行为** ✓

### 🔴 为什么我的判据没抓到

队友的原话（`review` 第 Standards-2 条）：

> `tb/w3c/tb_fx_dist.sv:80-94` 在撤掉 valid 后**保持 sample**；
> 流测试主要**数 valid**，而非**逐样本队列比对**。
> **数据提前数拍仍可能绿。**

⇒ ⭐ **教训**：⭐ **"数 valid 条数"不是契约** ——
契约是"**每一个 valid 对应的那个样点，值必须对**" ✓
⇒ ⭐ 我后来在 `tb_uart_ui` 里写的"双向验证"思路是对的，
   但**当时没用在 fx 的流判据上** ✗

## 二、逐条清单

### 2.1 `rtl/w3c/fx_dist.v` —— 6 处

| # | 我原来的写法 | 问题 | 队友的修法 |
|---|---|---|---|
| 1 | `shr1 = prod1 >>> GAIN_FRAC` | 🔴 **数据比 valid 早一拍** | `shr1 = p1 >>> GAIN_FRAC` |
| 2 | `prod2 = c2 * trim_r`（实时 `trim_r`） | 🔴 **在途样本被后改的参数污染** | 加 `trim_s1/s2`，⭐ 让补偿参数**跟着样本走** |
| 3 | `en_sr <= {en_sr[..], en_r}` | 🔴 `en_r` 晚一拍 ⇒ valid 对齐偏 | `en_sr <= {en_sr[..], en_i}`（⭐ 与 gain/trim 同拍） |
| 4 | `peak_o <= peak1` | 🔴 峰值**没延时**，与五拍输出**不同源** | 加 `peak_s2/s3/s4`，⭐ 与样点同拍 |
| 5 | `peak_o` **无条件**更新 | 🔴 **空闲拍也在写** ⇒ 统计到无效数据 | `if (v_sr[PIPE-1]) peak_o <= peak_s4` |
| 6 | 削波计数**不看 valid** | 🔴 **闲置总线过载也计数**（实测：0 个有效样本 ⇒ `clip_count = 94`）| `if (v_sr[PIPE-1] && en_sr[PIPE-1] && clip_s4)` |

### 2.2 `rtl/w3c/fx_trem.v` —— 5 处

| # | 我原来的写法 | 问题 | 队友的修法 |
|---|---|---|---|
| 1 | `shr = prod >>> DEPTH_W` | 🔴 同一类**错拍** | `shr = p1 >>> DEPTH_W` |
| 2 | 用**实时** `depth_i` 算增益 | 🔴 在途样本被污染 | 新增 `sample_att` / `sample_gain`，⭐ **接受那一拍的深度** |
| 3 | `phase <= phase + rate_r` | 🔴 用了**打拍后**的速率 | `phase <= phase + rate_i`（⭐ 同拍） |
| 4 | `en_sr <= {.., en_r}` | 🔴 晚一拍 | `en_sr <= {.., en_i}` |
| 5 | `sample_o <= en_sr[PIPE-1] ? sat : s2` | 🔴 `sat` 与 valid 错拍 | 加 `y2` 寄存，⭐ `? y2 : s2` |

### 2.3 `rtl/w3c/fx_chain.v` —— 5 处（⭐ 全是我【写错的注释/常量】）

| # | 我写的 | 实际 | 影响 |
|---|---|---|---|
| 1 | `PIPE_TOTAL = 16` 拍 = 320 ns | ⭐ **17 拍 = 340 ns** | ⚠️ 延迟预算报错 |
| 2 | 合唱 = 4 拍 | **3 拍** | ⚠️ 逐级预算错 |
| 3 | 延迟 = 4 拍 | **3 拍** | ⚠️ 同上 |
| 4 | `valid_i` 间距 ≥ 4 | ⭐ **≥ 5**（保守） | 🔴 **按 4 发会错** |
| 5 | `assign pipe_o = PIPE_TOTAL` | 🔴 **`pipe_o` 报的是常量 16**，不是真实值 | 🔴 **上层核对延迟会被误导** |

⭐ 队友的修法：`localparam PIPE_CYCLES = 17; assign pipe_o = PIPE_CYCLES;` ✓

## 三、🔴 最严重的一条：单位增益恒等契约失效

队友的 Spec-1 条（**P1 级**）：

> 规格 §4.3 承诺旁路数值恒等，模块还定义 active unity/depth0 恒等。
> 独立公开端口诊断下：**dist 启用且 gain=1、trim=1 时 valid 输出 0**；
> **trem 启用且 depth=0 也输出 0**。相同输入下硬旁路正确。

⇒ 🔴 **这不是"效果不够明显"，而是"输出直接是 0"** ✗
⇒ ⭐ 根因就是上面那 11 处错拍 —— **样点提前跑掉了，valid 到的时候读到的是错的** ✓

### ⭐ 这条怎么发现的（方法值得学）

他写了两个**新诊断夹具**：

| 夹具 | 做法 | 结果 |
|---|---|---|
| `tb_fx_public_contract` | 只从**公开端口**观察，⭐ **不 force 内部寄存器**，⭐ 不改算法 | exit 1，明确 FAIL（4 条路径各 4 个错样）|
| `tb_fx_clip_valid` | 送 **0 个有效样本**，保持过载无效数据 100 拍 | `accepted_samples=0` 而 `clip_count=94` ⇒ 🔴 FAIL |

⇒ ⭐ **方法要点**：
1. ⭐ **只用公开端口**（⛔ 不 force 内部）⇒ 结论**站得住** ✓
2. ⭐ **合法 64 拍间隔**（⭐ 满足模块声明的 ≥PIPE 拍要求）⇒ ⛔ 不是"用非法激励刷出来的红" ✓
3. ⭐ **明确区分"实测发现的问题"和"预期负向 PASS"** ✓
