## 二、⭐ "够不够"不能凭感觉 —— 要按预算表对一遍

> **结论先说**：**逻辑规模上大概率够，但"够不够"取决于两个具体数字：BSRAM 与乘法器。**
> 这两个不查清楚，任何"够用/不够用"的说法都是猜。

### 2.1 必须先查的 6 个数字

| # | 资源 | 为什么关键 |
|---|---|---|
| 1 | **逻辑单元 / LUT 数** | 决定能塞多少并行逻辑 |
| 2 | **寄存器数** | 通常与 LUT 成比例 |
| 3 | ⭐ **BSRAM 总量（Kbit）** | **本项目最大的风险点**（效果器延迟线） |
| 4 | ⭐ **乘法器 / DSP 数量** | 若用 FM、滤波、部分加性合成会吃 |
| 5 | **PLL 数量** | 音频时钟 + 其他 |
| 6 | 全局时钟网络数 | 多时钟域设计需要 |

> 📄 请从 `GW5AT-60` 的 **datasheet / 用户手册**查到这 6 个数字，填进下面的预算表。

## 三、资源预算表（按模块，粗估）

> 下列数字是**估算量级**，用于判断"哪个模块是消耗大头"，**不是精确值**。

### 3.1 逻辑（LUT / 寄存器）

| 模块 | 粗估量级 | 说明 |
|---|---|---|
| 传感器接口 + 采集时序 | 小 | 计数器 + 状态机 + 少量算术 |
| 标定 / 滤波（每通道） | 中 | 若用乘法滤波会吃 DSP；用移位近似可省 |
| Note / Event Manager | 小 | 事件队列与仲裁 |
| **Voice 管理** | 中 | N 个 voice 的分配、抢占、释放 |
| **DDS / 波形发生器 × N** | **中～大** | 相位累加器 + 波形查表 + 插值；**时分复用可大幅压缩** |
| ADSR 包络 × N | 中 | 分段计数 + 斜率 |
| 声部混音 | 中 | 多路加法 + 饱和 |
| 效果器（Reverb/Delay/Chorus） | **大** | 延迟线寻址 + 全通/梳状滤波 |
| 可视化（波形/频谱/李萨如） | 中～大 | FFT 是逻辑大头 |
| **LED 驱动** | 小～中 | 可寻址灯珠要发送状态机；I2C 驱动 IC 最省 |
| I2S 发送 + 时钟分频 | 极小 | 几个计数器 |
| UI 串口协议 | 小 | 收发 + 寄存器堆 |
| **合计** | —— | **取决于是否做时分复用** |

> ⚠️ **最关键的一条设计判断**：
> 48 kHz 采样率下，**每个样本有约 1041 个 50 MHz 时钟**。
> 32 voice 若**时分复用**，每 voice 只有约 32 个时钟 → **勉强够但要精打细算**。
> **如果全并行**，则是 32 套独立硬件 → **逻辑规模直接乘 32 倍**。
> ➡️ **"32 voice"能不能做，主要取决于"并行还是时分"，而不是器件大小。**

### 3.2 ⭐ BSRAM 预算（最大风险点）

| 用途 | 粗算 | 量级 |
|---|---|---|
| **Delay 效果器 · 延迟线** | 200 ms @ 48 kHz × 24 bit = 9 600 样本 × 24 bit | **≈ 230 Kbit** |
| Delay · 1 秒长延迟 | 48 000 样本 × 24 bit | **≈ 1.15 Mbit** |
| **Reverb**（多条梳状 + 全通延迟） | 通常等效几十～200 ms 的多条延迟线 | **≈ 0.5～2 Mbit** |
| 波表 / 波形存储器 | 1024 点 × 16 bit ×（波形数 × 八度） | 100～500 Kbit |
| 可视化缓冲 | 波形/频谱缓冲 + 可能的屏帧缓冲 | 10～500 Kbit |
| **LED 双缓冲** | 12 灯 × 24 bit | **≈ 0.3 Kbit（可忽略）** |
| **合计（含效果器）** | —— | **≈ 1～3 Mbit 量级** |

> 🔴 **结论：效果器是 BSRAM 消耗的绝对大头。**
> **"做一个 1 秒的 Delay 就要 1.15 Mbit"** —— 所以第一步必须查清器件有多少 BSRAM。
>
> **如果 BSRAM 不够**，可选路径：
> ① 缩短延迟时间（用 100~200 ms 的短延迟 + 反馈模拟长延迟）
> ② 降低位宽（24 → 16 bit）
> ③ 只做一个效果器而不是三个
> ④ 用外挂 SRAM/PSRAM（占 IO，但换 BRAM）

### 3.3 乘法器 / DSP 预算

| 用途 | 是否吃乘法器 |
|---|---|
| 纯 DDS + 波表查表 | ✅ **不吃**（查表即得幅度） |
| 幅度缩放（ADSR × 样本） | 吃，但**可时分复用 1~4 个乘法器** |
| **FM 调频合成** | 吃（每算子一个）→ 4 算子 × 32 voice = **128** 量级 |
| 滤波器（每 voice 一个） | 吃（每阶一个） |
| FFT（可视化） | 吃（蝶形运算） |

> ➡️ **如果做纯 DDS/波表 + 时分复用幅度，乘法器压力很小。
> 一旦上 FM 或逐 voice 滤波器，乘法器需求会跳一个量级。**

## 三之二、⭐ 按 A2 决策的**定量**预算（2026-09-13 新增）

> **依据**：`files/20-代码/合成引擎架构决策.md`（每 voice 1~2 个独立振荡器）

> **口径**：⚠️ 下表的每 voice 估算**是量级估算，不是综合结果** ——
> **唯一能定论的手段是跑一次综合**（`gw_sh` + `run all` 看报告，见 `files/40-参考资料/经验库与可复用资产.md` §二）
> **责任人**：FPGA 侧（乙）

### 3.4 ⭐ 器件资源基线（**已查到，不必再查**）

| 资源 | **60K**（`GW5AT-LV60PG484AC2`） | **138K** | 倍率 |
|---|---|---|---|
| LUT | **59,904** | 138,240 | 2.3× |
| FF（寄存器） | **59,904** | 138,240 | 2.3× |
| ⭐ **BSRAM** | **2,124 kb**（118 块） | **6,120 kb**（340 块） | 2.9× |
| SSRAM | 468 kb | 1,080 kb | 2.3× |
| ⭐ **DSP（乘法器）** | **118** | **298** | 2.5× |
| PLL | 8 | 12 | 1.5× |

### 3.5 每 voice / 每振荡器的私有资源（估算）

| 项 | 私有 / 共享 | 估算 |
|---|---|---|
| **相位累加器**（32 bit） | 🔒 每**振荡器** | 32 FF + ~32 LUT |
| **相位增量寄存器**（32 bit） | 🔒 每**振荡器** | 32 FF |
| 波表地址生成 + 查找 | 每振荡器 | ~20 LUT |
| **ADSR**（计数 + 电平 + 状态机） | 🔒 每 **voice** | ~80 FF + ~50 LUT |
| 失谐系数 | 每 voice | ~16 FF |
| **包络乘法** | ♻️ **可 TDM 共享** | 1 DSP（共享 1~4 个） |
| 求和树 | ♻️ 共享 | `log2(N)` 级 |

**单 voice（`OSC_PER_VOICE=1`）** ≈ **145 FF / 105 LUT**
**单 voice（`OSC_PER_VOICE=2`）** ≈ **210 FF / 160 LUT**

### 3.6 ⭐ 场景表：复音数 × 振荡器数

| 场景 | 振荡器数 | FF | LUT | 占 60K 的 FF | 占 60K 的 LUT |
|---|---|---|---|---|---|
| 32 voice × 1 | 32 | 4,640 | 3,360 | **7.7 %** | 5.6 % |
| **32 voice × 2** | **64** | 6,720 | 5,120 | **11.2 %** | 8.5 % |
| 48 voice × 2 | 96 | 10,080 | 7,680 | 16.8 % | 12.8 % |
| **64 voice × 2** | **128** | 13,440 | 10,240 | **22.4 %** | 17.1 % |

**加上其它模块（粗估 LUT）**：采集链 ~1,500 ｜ 可视化（**FFT 是大头**）~3,000~8,000 ｜
效果器逻辑 ~2,000 ｜ LED + 串口屏 ~500 ｜ I2S + 时钟 ~200 → **合计 ~8,000~12,000**

> ### ✅ 结论 1：**LUT / FF 完全不是瓶颈**
> 最激进的配置（**64 voice × 2 振荡器 = 128 个振荡器**）也只占
> **约 22 % FF / 17 % LUT**；连上其它模块也才 **~37 % LUT**。
>
> ➡️ ⭐ **复音数可以放心上探** —— 支持 `A2-0` 里"按 2 个振荡器设计 + 参数化"的做法。

### 3.7 DSP（乘法器）预算

| 用法 | 需求 | 够不够 |
|---|---|---|
| 纯波表查表（DDS） | ✅ **不吃** | —— |
| 包络乘法（每振荡器） | ⚠️ 128 个振荡器 → 若各占 1 个 = **128 > 118** | ⚠️ **超了** |
| ⭐ **但可 TDM 共享** | 1 个乘法器在 **1041 拍/样本**内做 128 次乘法：`128 × 4 拍 = 512 拍 < 1041` ✅ | ⭐ **够** |
| FFT（可视化） | 吃（蝶形运算），~4~8 个 | 够 |
| 效果器滤波 | 少量 | 够 |

> ### ✅ 结论 2：**DSP 够 —— 但必须做时分复用（TDM）**
> ⛔ 不能给每个振荡器配一个独立乘法器（128 > 118）。
> ⭐ 好在 48.828 kHz 下**每样本有 1024 个 50 MHz 时钟**，TDM 的余量很充裕。

### 3.8 ⭐⭐ BSRAM 预算 —— **唯一真短板**

| 用途 | 估算 | 说明 |
|---|---|---|
| **波表**：4 种音色 × 2048 点 × 16 bit | **131 kb** | ⚠️ 点数别贪：64K 点会到 4 Mb |
| **混响**（4 梳状 + 2 全通，等效 ~200 ms） | **~600 kb** | 条数与延迟长度都要克制 |
| **合唱**（3 条 × 1024 × 16 bit） | 49 kb | |
| **延迟 echo**（200 ms @ 48.8 kHz × 16 bit） | 154 kb | ⚠️ **1 秒长延迟 = 1,150 kb（直接吃掉一半）** |
| 可视化：FFT 缓冲 2048 × 16 × 2 | 64 kb | |
| 可视化：波形缓冲 1024 × 16 | 16 kb | |
| **合计（克制版）** | **≈ 1,014 kb** | 占 60K 的 **48 %** ✅ |
| **合计（豪华版：1 秒长延迟）** | **≈ 2,010 kb** | 占 60K 的 **95 %** ⚠️ |

> ### ⚠️ 结论 3：**BSRAM 是唯一需要盯的资源**，而它**几乎全由"效果器延迟线"决定**
>
> | 效果器策略 | 60K 够不够 |
> |---|---|
> | **短延迟（100~200 ms）+ 反馈模拟长延迟** | ✅ **够**（~48 %） |
> | 做 **1 秒真延迟线** 或豪华混响 | ⚠️ **吃紧甚至不够**（~95 %） |
>
> ➡️ **建议：效果器按"短延迟 + 反馈"设计**，⛔ 不做 1 秒真延迟线。
> 这同时也满足赛题（只要求"实现混响、延迟、合唱**等**效果器"，**没要求延迟时长**）。

### 3.9 🎯 C2 的结论

| 资源 | 判断 | 依据 |
|---|---|---|
| **LUT / FF** | ✅ **绰绰有余** | 最激进配置 + 全部模块 ≈ 37 % |
| **DSP** | ✅ **够**（需 TDM） | 时隙余量充裕 |
| ⭐ **BSRAM** | ⚠️ **是唯一真短板**，但**可控** | 取决于效果器延迟线长度 |

> ### 🔴 所以：**60K 大概率够用**，前提是**效果器不做长延迟线**。
>
> **但这不是结论，只是"预算通过"** —— ⚠️ **真正的确认只有一条路**：
> 写一版 32 复音骨架 → **`gw_sh` + `run all`** → 看报告里的 BSRAM/LUT/DSP 实际占用。
> ⭐ 这件事**不需要板子、不需要 IDE**（见 `files/40-参考资料/经验库与可复用资产.md` §二）。
> 现列为 `files/00-总览/规划待办清单.md` 的 **C5（保留项）**。

**若综合下来 BSRAM 不够，按这个顺序退**：

```text
① 缩短延迟线时长（1 s → 200 ms），用反馈补长尾
② 位宽 24 → 16 bit（延迟线内部）
③ 减少效果器数量（3 个 → 2 个）
④ 波表点数 2048 → 1024，音色数 4 → 2
⑤ 最后才考虑 138K
```

> ⚠️ **注意**：**复音数不在退让清单里** —— 因为它不吃 BSRAM（波表共享），
> 只吃 LUT/FF，而 LUT/FF 有大把余量。**别用"减复音"来解决 BSRAM 问题**（无效）。

## 四、⚠️ 两个风险点（按优先级）

| 优先级 | 风险 | 判断方法 | 不够时的退路 |
|---|---|---|---|
| **1** | **BSRAM 不够**（效果器延迟线） | 查器件 BSRAM 总量，与 §3.2 的 1~3 Mbit 对比 | 缩短延迟 / 降位宽 / 减效果器数量 / 外挂存储器 |
| **2** | **乘法器不够**（若用 FM / 滤波） | 查 DSP 数量，与 §3.3 对比 | 改用波表 + 加性合成 / 减少每 voice 的滤波器 |

> **纯逻辑部分大概率够**；**真正的瓶颈通常在存储（BSRAM）而不是逻辑。**

## 五、⭐ 龙芯（LS2K1000）该怎么处理

### 5.1 先看赛题原文怎么要求

> 基础要求 2：「完整音频生成通路**全部基于 FPGA HDL 硬件逻辑实现**，支持逐样本实时音频运算……
> 严格控制演奏延迟，实现控制信号到音频输出总延迟 ≤10 ms，**杜绝软件串行运算滞后问题**。」
>
> 基础要求 3：「所有输出音频均由 FPGA 根据实时演奏指令逐音、逐样本实时生成……
> **严禁直接播放预录 PCM 音频**、预置推流及整段录音触发，**保障实时合成核心属性**。」

### 5.2 结论：**不用龙芯是对的，而且用它做音频反而不合规**

> ⚠️ **2026-09-19 已问主办方，拿到明确口径**（见 `K-40`）—— 下表**按官方答复修订过**：
>
> ① 用 **MCU/软核**的部分**可能不计入工作量**（成品或自制一样）；
> ② 只要**不是绝大部分功能**都用软核/MCU，**不会导致弃赛**；
> ③ ⭐⭐ **选题二的「音频」与「视觉效果」绝对不要用软核/MCU**；
> ④ ⭐ **"软核"专指通用 CPU/MCU 软核**（跑 C 语言那种）；⭐ **专用状态机 / 串行架构的算法加速器【不是】软核**；
> ⑤ "不计入工作量"⛔ **不是扣分**，而是**影响该部分功能的设计与实现得分**；且**1% 用了不会让整个模块清零**。

| 用途 | 是否合规 | 依据 |
|---|---|---|
| **CPU 参与音频生成 / 播放音频** | ❌ **不合规**（且**不计工作量**） | 答复③；也正是赛题要防的"软件串行运算滞后" |
| ⚠️ **CPU 做可视化 / 视觉效果（李萨如、频谱、波形）** | ⚠️ **已划进禁区**（原写"✅ 合规"，**2026-09-19 更正**） | 答复③明确点名"**视觉效果**"；详见 `K-81` |
| CPU 做 UI 菜单、曲目存储与下发、网络/蓝牙、文件管理 | 🟡 **边缘** —— 不在"音频/视觉效果"里，但**仍可能不计工作量** | 答复①；⛔ 别让它承担演奏通路 |
| ⭐ **我们自己写的专用状态机驱动**（`tlc5916` / `mcp3208` / `i2s_tx`） | ✅ **合规，且全额计入工作量** | 答复④：**专用状态机不是软核** —— "这体现了 FPGA 的不可替代性" |
| **CPU 完全不初始化** | ✅ **最省事、零风险** | 无任何合规争议 |

> ➡️ **推荐：完全不用龙芯。**
> 它不参与音频与视觉效果，也就没有任何合规风险，而且**少一个功耗与噪声源**。
>
> ⚠️ **可视化要守的一条**：⭐ **"生成"必须在 FPGA 内**（`vis_tap` 输出**算好的波形/频谱点**），
> 屏/HDMI 只做**搬运与显示** ⇒ 这样才站得住"**基于 FPGA 逻辑实时生成可视化**"（`K-81`）。

### 5.3 ⚠️ 但有两个真实的坑

#### 坑 1：**"不用 CPU" ≠ "被 CPU 占的引脚就能用"**

**已有实证**（`ADA107硬件确认记录.md` §6/§9）：

```
J14.12 → 原走线到 ball R19
      → R19 被 Gowin P&R 判为 CPU 专用脚：
        PR2017 cannot be placed ... dedicated pin (CPU)
      → 不能作普通 IO，只能飞线到旁边的 P17 测试点
```

> ➡️ **说明板上有"CPU 专用脚"**，它们被预留给 CPU 接口使用。
> **即便不使用 CPU，这些 ball 依然可能受限。**
> **行动**：排引脚时留足余量，并且**一定要实际跑一次 P&R 验证**（不能只看原理图）。

#### 坑 2：未使用的 CPU 会不会反过来影响 FPGA？

需要确认：

| # | 要确认的事 |
|---|---|
| 1 | CPU 与 FPGA 之间是否有**共享总线/时钟**？CPU 侧会不会驱动信号？ |
| 2 | CPU 未上电/复位时，FPGA 侧能否**独立正常工作**？ |
| 3 | 两者是否**共用电源域**？是否有相互干扰 |
| 4 | 板载 50 MHz 时钟（F13）是否**独立于 CPU**（来自板载晶振） |

> ➡️ **最好的做法**：做一个**最小验证** —— 烧一个纯 LED 闪灯或串口输出的程序，
> **确认 CPU 完全不参与时 FPGA 侧一切正常**。

### 5.4 ✅ 答辩时怎么讲（这条很有说服力）

> **"整条音频通路 100% 在 FPGA HDL 内部实现；CPU 未参与，断开/不初始化 CPU 也能正常演奏。"**

**证据方式**：现场演示时**先不给 CPU 上电**（或不让它启动），直接演奏 ——
声音照常出来，就**当场证明了"不是软件在算"**。

这正好对应赛题"必须证明是 RTL 实时合成，而非播放预录 PCM"的核查点。
