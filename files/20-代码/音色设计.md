# 🎹 音色设计

> **要解决什么**：赛题红线「**音色数 ≥2**」—— ⛔ 不是"能换表"，而是**≥2 种听得出不同的乐器音色**。
> 而且音色是 **W3b 开工前唯一还缺的东西**（不知道做什么音色，就不知道波表和 ADSR 要什么参数）。
> **日期**：2026-09-13 ｜ **责任人**：乙（实现）+ 全员（听感定稿）
> **依据**：`files/20-代码/合成引擎架构决策.md` §七（最方便改的版本）｜`files/30-方案决策/评分规则对齐.md` §二-2
> **状态**：🔴 待团队定"具体是哪几个音色"，但**配方与存储方案已定**

## 〇、⭐ 三条设计原则

| # | 原则 | 理由 |
|---|---|---|
| **1** | ⭐ **音色要匹配我们的输入方式** | 我们的输入是**拨弦触发 + 力度 + 滑音 + 颤音** → 音色该是**弹拨类/持续音类**，而不是"电子音效" |
| **2** | ⭐⭐ **力度要调制"亮度"，不只是"音量"** | 真实乐器的力度是**音色变化**（弹重更亮），不是单纯变响。这是「力度感应」最能拿分的实现方式 |
| **3** | **音色靠"波表 + 实时参数"，不靠预录** | ✅ 波表存的是**单周期波形**（几百~几千点）；音高/包络/叠加**全是实时算的** → 这是**合规的证明**（见 `files/历史/验收计划-过时-已并入仿真与验证方案.md` §一-⑤） |

## 一、⭐ 音色清单

> **必做 2 个（红线）+ 可选 1 个（展示 FM）**

| # | 音色 | 性质 | 为什么选它 | 优先级 |
|---|---|---|---|---|
| **T1** | **弹拨类**（筝 / 竖琴 / 电钢质感） | ⚡ 快起音 + 衰减 | ⭐ **与"拨弦"输入天然匹配**；力度→亮度最明显；滑音/颤音在弦上很自然 | 🔴 **必做** |
| **T2** | **持续音类**（风琴 / 弦乐 pad） | 🌊 慢起音 + 长延音 | ⭐ **与 T1 形成对比**；⭐ **失谐双振荡器的价值在这里最明显**（合唱感）；颤音在持续音上最容易被听出来 | 🔴 **必做** |
| **T3** | **FM 音色**（钟声 / 电钢） | 🔔 金属感 | 🟡 **展示"FM 按调制运算器统计"对应的评分项**（⛔ 不冲吞吐量） | 🟡 可选 |

## 二、每个音色的配方

### T1 · 弹拨类

| 要素 | 设定 | 说明 |
|---|---|---|
| **波表** | **锯齿波 / 脉冲波**（谐波丰富） | ⚠️ 用**两张表**：`soft` / `hard` —— 见下方力度映射 |
| **ADSR** | Attack **≈2 ms**（几乎瞬时）<br>Decay **≈0.3~1 s**<br>Sustain **低（0.2~0.3）**<br>Release **≈0.2~0.5 s** | ⭐ 快起音 + 衰减 = 弹拨特征 |
| **力度映射** | ⭐ **力度 → 波表插值**（soft表 ↔ hard表）<br>叠加：力度 → 音量（弱调制） | ⭐ **这是"力度→亮度"的核心实现** |
| **失谐** | 轻微（**1~3 音分**） | 增加厚度但保持音准清晰 |
| **效果器** | 混响（短） | |

### T2 · 持续音类

| 要素 | 设定 | 说明 |
|---|---|---|
| **波表** | **多谐波叠加**（如 1/2/3/4/5 次谐波递减；可留奇次谐波做"风琴"感） | 同样用 soft/hard 两表 |
| **ADSR** | Attack **≈20~50 ms**<br>Decay 短<br>Sustain **高（0.8~1.0）**<br>Release **≈0.5~1.5 s** | ⭐ 慢起音 + 高延音 = 持续音特征 |
| **力度映射** | 同 T1（亮度插值） | |
| **失谐** | ⭐ **较大（5~15 音分）** | ⭐ **双振荡器的合唱感在这里最明显** —— 也最能在验收时证明"两个振荡器真的都在响"（拍频可闻） |
| **效果器** | **合唱** + 混响 | 直接对应"合唱"这个赛题点名的效果器 |

### T3 · FM 音色（可选）

| 要素 | 设定 |
|---|---|
| 结构 | **4 OP FM**（经验值：4~6 OP 足够，⛔ 不堆几十个） |
| 包络 | 快 attack + 长 decay（钟声特性）；⭐ **调制器包络与载波包络分开**（这决定金属感衰减） |
| 定位 | ⛔ **不冲吞吐量** —— 只对应"FM 合成"评分项 |

## 三、⭐⭐ 波表怎么生成与存储（**这里有个实测过的地雷**）

### 3.1 ⛔ 地雷：`$readmemh` 加载外部 .mem → **上板 ROM 全 0**

经验库 **`U18`**，**实测器件就是 `GW5AT-60`（与我们同一颗）**：

> **现象**：ROM 用 `initial $readmemh("xxx.mem", rom)` 行为级写法，
> **Gowin 综合不把外部 .mem 数据打进 bitstream**（实测 GW5AT-60 不加载）。
> **后果**：ROM **全 0** → DDS 输出恒定 → **没声音**；
> 但 ⚠️ **仿真（iverilog）完全正常** —— **"仿真过 ≠ 上板过"**。
>
> **修法**：① ⭐ **数据内嵌**（把内容直接写进 `initial begin rom[i]=...; end`）
> ② 用高云 **pROM IP**（需 IDE 手动配置，新手易错）

> ### 🔴 对我们意味着什么
> 我们的波表正是"上板综合路径上的 ROM" → **必须处理**。
> ⚠️ 而且它**正好是"仿真导 WAV"看不出来的一类问题**（仿真一切正常）
> —— 与经验库 `C02`「开发环境通过 ≠ 真实环境行为一致」同族。

### 3.2 三种存储方案对比

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 内嵌 Verilog 常量** | `initial begin rom[0]=16'h...; ... end` | ⭐ **已验证可行**（经验库 P9/P14/P8 均改此） | ⚠️ **规模受限**：2048 点 × 4 音色 = 65536 个字 → 生成的 .v 约 **1 MB**，编译变慢 |
| **B. 高云 pROM IP** | Tools→IP Core→pROM 加载 .mem | 数据不占 RTL 体积 | ⚠️ **需 IDE 手动配置**；⚠️ 与 `gw_sh` 命令行流程的配合**要验证** |
| **C. 减少规模后内嵌** | 点数 2048 → **1024**；或音色 4 → 2 | 内嵌可行且轻 | 音色细节略降 |

> ### ⭐ 建议：**先用 C 的规模 + A 的方式**起步
> 即 **1024 点**、先做 **T1/T2 两张音色**（各 soft/hard 两表 = 4 表 × 1024 × 16 bit = **64 kbit**）
> → 内嵌后 RTL 约 **256 KB 量级，可接受**。
> 等跑通再考虑扩到 2048 点 / 更多音色，或改用 pROM IP。

### 3.3 ⚠️ 第二个待验证点：能否推断成 **BSRAM**

- 若点数多（1024 × 16 bit = 16 kbit/表），**必须推断成 BSRAM**（否则分布式 LUT RAM 吃光 LUT）
- ⚠️ **Gowin 能否从 `initial` 数组推断 BSRAM，需要验证**（写法或综合选项可能要对）
- 判据：综合报告里看这张表算进了 **BSRAM** 还是 **LUT**

### 3.4 ⭐⭐ 因此：**波表上板必须先做一个最小验证**（别等到最后）

| 项 | 内容 |
|---|---|
| **验证什么** | 波表能不能**真的上板出声**（不是仿真） |
| **怎么验** | 最小工程：**单音正弦波表 → DDS → I2S → DAC**，听/看波形 |
| **为什么现在验** | ⚠️ 若等到整机联调才发现"ROM 全 0"，**排查会淹没在其它问题里** |
| **顺带收益** | ⭐ 这一次验证**同时**完成了阶段 1 计划里的"假输入单音出声"里程碑 |
| **做什么** | 见 `files\00-总览\规划待办清单.md`（已列为阶段 1 第一件事） |

### 3.5 波表数据的生成流程

```text
① Python / MATLAB 生成单周期波形（float，归一化）
② 量化到 16 bit 有符号（⭐ 注意：不留直流偏置 → 见经验库 L21"带偏置的数据≠补码"）
③ 导出为 Verilog 常量文件（或 .mem 供 pROM IP 用）
④ 每张表配一个"表头注释"：点数 / 位宽 / 归一化峰值 / 生成参数
```

> ⚠️ **波表要"单周期 + 零直流"** —— 有直流偏置会吃掉动态范围，还会让后级发热。

## 四、⭐ 效果器规划（赛题原文点名"混响 / 延迟 / 合唱"）

> **赛题原文**（拓展要求 2）：「**在 FPGA 硬件内部实现混响、延迟、合唱等数字音频效果器**，丰富演奏听觉层次」
> ⚠️ 所以三个都要**在 FPGA 内部**（⛔ 不能用外部模块），且**可独立开关**（验收要 A/B 对比）。

### 4.1 三个效果器的实现与预算

| 效果器 | 实现结构 | BSRAM | 说明 |
|---|---|---|---|
| **混响** | **Schroeder / Freeverb 类**：4 条梳状 + 2 条全通 | **~600 kb**（等效 ~200 ms 总延迟） | 🔴 **BSRAM 大户** —— 条数与延迟长度都要克制 |
| **延迟** | 单条延迟线 + **反馈** | **154 kb**（200 ms） | ⚠️ **1 秒真延迟线 = 1,150 kb（吃掉一半预算）→ ⛔ 不做** |
| **合唱** | 2~3 条**短**延迟线 + LFO 调制延迟量 | 49 kb | ⭐ 与 T2 的**失谐双振荡器**叠加 → 合唱感更厚 |

**合计 ≈ 800 kb** → 加波表（64~128 kb）与可视化（~80 kb）后 ≈ **1,000 kb / 2,124 kb（48 %）** ✅
（与 `files/20-代码/FPGA平台与资源评估.md` §三之二 的 BSRAM 预算一致）

### 4.2 三条设计纪律

| # | 纪律 | 理由 |
|---|---|---|
| **1** | ⭐ **干湿混合不得引入通路延迟** | `files/历史/延迟预算逐段分解-过时-旧共享总线口径.md` 规定效果器段 **0 拍** —— 干声与湿声**并行**算完再相加，⛔ 不许"等效果器算完再输出" |
| **2** | **放在 W3c，可独立开关** | 效果器在**输出链**上；开关状态是运行时参数（验收要 A/B 对比） |
| **3** | ⛔ **不做长延迟线** | 用**短延迟 + 反馈**模拟长尾；赛题只要求"实现…等效果器"，**没要求延迟时长** |

> ⚠️ **若综合下来 BSRAM 不够，退让顺序**（照 `files/20-代码/FPGA平台与资源评估.md` §三之二）：
> ① 缩短延迟线时长 → ② 位宽 24→16 → ③ 减效果器数量 → ④ 波表点数 → ⑤ 最后才考虑 138K。
> ⛔ **"减复音"不在退让清单里**（它不吃 BSRAM，减了也没用）。

### 4.3 效果器与音色的搭配

| 音色 | 搭配 | 为什么 |
|---|---|---|
| **T1 弹拨类** | 混响（**短**，0.5~1 s 尾巴） | 弹拨乐器需要空间感，但⛔ 不要拖泥带水（会糊掉快速音符） |
| **T2 持续音类** | **合唱 + 混响** | ⭐ 合唱直接对应赛题点名的效果器，且与失谐振荡器叠加效果最好 |
| **T3 FM（可选）** | 延迟（短）+ 混响 | 钟声类适合有回声 |

## 五、音色切换机制

> **依据**：`A2-4 已定 = 多表切换`

```text
一个"音色" = 波表(soft/hard 两张) + ADSR 参数组 + 失谐量 + 力度映射曲线 + 效果器配置
切换音色   = 换表 + 换参数组
```

| 项 | 做法 |
|---|---|
| **参数存哪** | ⭐ 常量表（LUT RAM 或 BSRAM），`timbre` 索引 |
| **切换时机** | ⚠️ **在冻结点切换** —— 不能让正在响的音中途换表（会爆音/音色突变）<br>⭐ 这也是经验库 `L50`「多模式共用通道时参数必须在冻结点锁存」的同型场景 |
| **切换平滑** | 旧音色自然 release，新音色用新参数起音 |

## 六、力度 → 亮度：为什么值得多花一张表

| 方案 | 资源成本 | 效果 |
|---|---|---|
| **只调音量** | 0 | ⚠️ 力度只是"变响" —— **不像真乐器**，也浪费了"力度感应"这条基础要求 |
| ⭐ **两表插值（soft/hard）** | 波表 BSRAM **翻倍**（64 → 128 kbit@1024点）+ **1 次插值乘法**（TDM 共享） | ⭐ **力度真的改变音色** —— 这才是"力度感应"的完整体现 |
| 力度 → 失谐量 | 0（失谐系数已是每 voice 参数） | 🟡 有厚度变化，但"亮度"变化有限 |

> ### ⭐ 建议走"两表插值"
> **代价很小**（BSRAM 从 64 → 128 kbit，仍远低于我们 ~1,014 kb 的预算），
> **收益很直接**（评委一听就知道"力度真的起作用了"）。
>
> 📌 **而且它顺带帮了另一个忙**：验收时"力度维度"这一条要用**听感**证明，
> 而"变响"容易被当成"音量旋钮"，"**变亮**"才是**演奏力度**。
