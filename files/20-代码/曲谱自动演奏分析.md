## 一、⭐⭐ 你的三个新想法 —— 逐条分析

### 1.1 ⭐⭐ "用蓝牙发送，不存储，实时算着发声" —— **可行，而且更好**

| 维度 | 评估 |
|---|---|
| ⭐ **可行性** | ✅ **完全可行** —— 本质是**把"曲谱数据"从"ROM"换成"串口流"** |
| ⭐ **好处 1** | ⭐⭐ **不占 BSRAM**（省下 42 kbit/首 甚至更多） |
| ⭐ **好处 2** | ⭐⭐ **不用 SD 卡、不用烧录** —— 换歌**不用重新综合**（⚠️ ROM 方案换歌=重新综合+烧板，**极慢**） |
| ⭐ **好处 3** | ⭐ **曲库无限**（歌都在电脑/手机上） |
| ⚠️ **代价** | ⚠️ **多一个蓝牙模块**（⚠️ 但要**确认接口**，见 §1.3） |
| ⭐ **与我们架构的关系** | ⭐ **我们本来就有事件通路** ⇒ ⭐ **蓝牙来的数据 = 另一种"事件来源"** |

⭐⭐ **关键洞察**：⭐ **这不是"新的音频通路"，而是"多了一个自动演奏者"** ——
⭐ 与节拍器/鼓机/looper **同一类**（都往 `note_evt_t` 灌事件）。

### 1.2 ⭐ "是否需要外置 SD 卡" —— **蓝牙方案下：不需要**

| 方案 | 要 SD 卡吗 | 说明 |
|---|---|---|
| ⭐⭐ **蓝牙实时发**（你的想法） | ⛔ **不需要** | ⭐ 曲谱**不落在 FPGA 里** |
| ROM 内置曲谱 | ⛔ 不需要 SD | ⚠️ 但要**重新综合**换歌 |
| ⚠️ SD 卡自读 | 🟡 需要 | ⚠️ 要**实现 FAT32 文件系统** ⇒ ⚠️ **成本高、且属"用 MCU 的活"** |

> ⭐ **结论**：⭐ **蓝牙方案下，SD 卡完全不需要** ——
> ⚠️ 而**自己读写 SD 卡**（FAT32 + SPI）是**独立的复杂工程**，⛔ **不建议**。

### 1.3 ⭐⭐ 用户方案（2026-09-22 下午）：**一次性传完 → 再整体演算**

⭐ 用户原话：*"我想的是一次性传完，然后再整个读取开始演算"*

⭐⭐ **这是比"边传边放"更好的方案** —— ⭐ **彻底消除蓝牙抖动**：

| | 边传边放（⚠️ 之前讨论的） | ⭐⭐ **一次性传完再演算（用户方案）** |
|---|---|---|
| 蓝牙抖动影响 | ⚠️ **必须靠大缓冲吸收**，风险仍在 | ⭐⭐ **传输阶段和演奏阶段完全分开** ⇒ **零影响** |
| "确定性延迟" | ⚠️ 要论证缓冲够大 | ⭐⭐ **天然满足**（演奏时不依赖蓝牙） |
| 演奏期间断连 | 🔴 **会卡住** | ⭐ **无影响**（数据已在本地） |
| 需要的缓冲 | ⚠️ 几 KB~几十 KB（还要论证够用） | ⭐ **看曲子大小**（⚠️ 见下） |
| 换歌 | ⭐ 快 | ⭐ 快（重传一次） |

⭐⭐ **结论：采用用户的方案。** 传输阶段允许**任意慢/任意抖**，
⭐ 传完发一个"就绪"命令 ⇒ ⭐ **演奏阶段完全由 FPGA 本地时钟驱动**。

#### ⚠️ 代价：需要**放得下整首曲**的缓冲

| 曲目规模 | 事件数（估） | 需要空间 |
|---|---|---|
| **8 小节短循环** | ~256 | **16 kbit** |
| ⭐ **你那个文件**（190 小节，5 轨） | ~658（仅 on/off） | ⭐ **~42 kbit** |
| 3 分钟密集（8 音/秒） | ~2 880 | **~184 kbit** |

> ⭐ **好消息**：⭐ **即使是 190 小节的整曲，也只要 ~42 kbit**（⭐ 因为 329 个音符不算密）。
> ⚠️ 但 **5 轨全要**的话要**乘上轨数**（⚠️ 且鼓轨要单独处理）。
> ⇒ ⭐ **参照 looper 的每层 2048 事件（131 kbit）**，⭐ **整曲缓冲建议给 4 000~8 000 事件（256~512 kbit）**
> ⇒ ⚠️ **会与 looper 的 3 层（393 kbit）争 BSRAM** —— ⭐ **要一起核算**（见 §四）。

#### ⭐ 协议建议（极简）

```text
PC → FPGA：
  ① 曲目头（事件总数 N、BPM、拍号）      ← ⭐ FPGA 据此准备
  ② N 条事件（每条 64 bit）              ← ⭐ 允许慢/抖，无所谓
  ③ "传输完成"命令                        ← ⭐ 之后才允许开始演奏
FPGA → PC：
  ④ 状态回读（收到多少条 / 是否就绪）    ← ⭐ 可观测（`K-106` 纪律）
```

> ⚠️ **必须有"校验"** —— ⚠️ 蓝牙可能丢包 ⇒ ⭐ **收到后回读计数，与 PC 侧比对**，
> ⛔ **不一致就报错，不要"少几个音符照样播"**（⭐ 静默丢数据是 `K-106` 同族的坑）。

### 1.4 ⭐⭐ "串口是不是随便什么引脚都可以" —— ⚠️ **不能随便，两个硬约束**

⭐ 用户原话：*"串口是不是随便什么引脚都可以，没有强制的要求，因为驱动都是自己写的"*

⭐ **"驱动自己写"是对的** —— ⭐ **UART 的收发逻辑确实与引脚无关**（任意 IO 都能当 TX/RX）。
⚠️ **但引脚能不能用，取决于【硬件有没有把它引出来】** —— 这是**硬件约束，不是软件约束**：

| # | 硬约束 | 说明 |
|---|---|---|
| **1** | 🔴 **引脚必须物理存在/可接到** | ⚠️ **自己写的驱动不能凭空造出一个焊盘** —— 必须接到**连接器/排针/焊盘**上 |
| **2** | ⚠️ **电平与 Bank 电压** | ⚠️ **FPGA 的 IO Bank 有 VCCIO**（⭐ 我们板子**大部分 3.3 V**，⚠️ 但 `rst_n` 那个脚是 **1.5 V**，见 `constr/top.cst`）⇒ ⭐ **接错 Bank 可能电平不匹配** |
| **3** | ⚠️ **专用/复用脚要避开** | ⚠️ 某些脚是 **CPU 专用 / 配置脚 / JTAG / 时钟专用** ⇒ ⛔ **不能当普通 IO**（⭐ 本项目已踩过：`R19` 是 CPU 专用脚不可用） |
| **4** | ⚠️ **PCB 已投板** | 🔴 **我们的正式板已经画完/投板** ⇒ ⛔ **不能再"随便挑脚"**，⭐ **只能用已经引到连接器上的** |

#### ✅ 好消息：**我们板子上已经预留好了**

| 连接器 | 用途 | 说明 |
|---|---|---|
| ⭐ **`J2`**（4 pin：`5V`/`GND`/`UART_TX`/`UART_RX`） | ⭐ **UI 串口屏**（已定） | ⭐ **已引出 UART** —— ⭐ **可以接蓝牙** |
| ⭐⭐ **`J10`**（6 pin：`SPARE_IO0..3` / `3V3` / `GND`） | ⭐⭐ **备用通用 IO** | ⭐⭐ **文档已明确写"蓝牙等拓展走这里"** ⇒ ⭐ **这就是给蓝牙预留的** |

> ⭐⭐ **结论**：
> ① **软件上**：⭐ **UART 驱动确实与引脚无关**（你说得对）—— 改个 `.cst` 就能换脚；
> ② **硬件上**：⛔ **不能随便挑** —— ⚠️ **必须用已经引出来的**；
> ③ ⭐ **我们已经有现成的**：**`J2`（串口屏位）或 `J10`（专为蓝牙预留）** ——
> ⭐⭐⭐ **所以答案对你有利：虽然不能"随便"，但"已经留好了"，⛔ 不用改板子。**

⚠️ **待确认**：⭐ **`J10` 的 4 个 `SPARE_IO` 具体是哪些 FPGA 引脚**（⚠️ 需查正式板网表/原理图）。

### 1.5 用官方资料核实：ESP32 精度够吗？实现难度大吗？

> 用户问：*如果要让 esp32 跟着 fpga 的时序发，实现难度大吗，精度够吗*
> 另确认：手上是 **ESP32-S3**（32E）；**经费不是问题，可买最合适的**

#### 结论：**精度完全够，而且难度比想象小**

关键判据是**一个 tick 有多长**（`PPQN=960`）：

| BPM | 1 tick 时长 |
|---|---|
| 60 | **1041.7 us** |
| **120** | **520.8 us** |
| 200 | **312.5 us** |

听感阈值（经验）：**抖动 < 1~2 ms 基本听不出来**；
更严格地说，**相邻音符的相对抖动**比绝对抖动更敏感。

#### ESP32 精度（据 ESP-IDF 官方文档）

| 方式 | 抖动 | 说明 |
|---|---|---|
| `esp_timer` 任务回调 | **数十 us** | 官方：**回调最小 20 us**、周期定时器**最小周期 50 us** |
| **硬件定时器 + ISR** | **几 us** | 官方建议低延迟回调走 ISR |
| **UART 硬件 FIFO/DMA** | **字节间隔由波特率决定，极稳** | 一次写多字节，硬件匀速吐出 |

**ESP32 几 us 抖动 远小于 一个 tick 521 us** => **精度完全够**（富余约 100 倍）。

#### 杀手锏：**让 FPGA 侧对齐，ESP32 只需提前送到**

```
ESP32  提前 1~2 个 tick 把音符塞进 FPGA 的 FIFO（抖动无所谓）
          |
FPGA   由 beat_gen 拍点决定何时真正发声
```

=> **ESP32 抖动被彻底吸收**：只要**不太晚**即可。
**时间基准永远是 `beat_gen`** => **不违反确定性延迟**。

> 与已有 `note_manager` FIFO 同一思路（`K-106`）：**事件先排队，本地时钟决定何时消费**。

#### 实现难度

| 部分 | 难度 |
|---|---|
| ESP32 蓝牙收数据 / 串口发送 | **易** |
| **跟 FPGA 时钟对齐** | **中** |
| FPGA 侧 FIFO | **易**（与 `note_manager` 同构） |

**两种对齐做法**：

| 做法 | 说明 | 难度 |
|---|---|---|
| **A. FPGA 回传拍点** | 引一根线 -> ESP32 GPIO 中断 | 中（要写 ISR） |
| **B. 时间戳法**（不加线） | 每条事件带 `tick` -> FPGA 自己排队到点再发 | **最低（推荐）** |

> **推荐 B**：`note_evt_t` 本来就带时间语义，且 looper 的播放**就是按 tick 扫描**
> => **几乎不用新逻辑**。

#### ESP32-S3 选型

| 项 | 说明 |
|---|---|
| 手上 | **ESP32-S3**（请确认具体型号） |
| 够用吗 | **绰绰有余**：3 个 UART、支持 DMA、双核 |
| 经费 | 不是问题 => **S3 就很好**（P4 没必要） |

#### 一个必须注意的细节：**回传拍点的脉宽**

`beat_gen.tick` 是 **20 ns 宽的单周期脉冲** =>
**直接引到 ESP32 的 GPIO 中断是抓不住的**（ESP32 中断响应是 us 级）！

| # | 做法 |
|---|---|
| 1 | 在 FPGA 侧**展宽**（如 1 拍宽或 10 us）再引出 |
| 2 | 干脆**不用回传**（走做法 B）=> **推荐** |

> 不注意会出现 **ESP32 完全收不到拍点**，而**波形上 FPGA 侧明明在动**
> => 典型的脉宽不匹配坑。

### 1.6 ⭐⭐ 用户新想法（2026-09-22）：**用 ESP32 当"蓝牙模块"，串口连 FPGA**

⭐ 用户原话：*"其实可以用 esp32 充当蓝牙模块，然后和 fpga 之间通过串口连接
比较稳定的发送数据（？，这样就不用考虑 bsram 的问题了是吗"*

#### ✅ 这个想法**基本正确**，而且比裸蓝牙模块好很多

| 维度 | ⭐ ESP32 方案 | 裸蓝牙串口模块（`HC-05` 等） |
|---|---|---|
| **蓝牙栈** | ⭐ ESP32 内置（BLE/经典蓝牙） | 模块内置 |
| ⭐ **可编程** | ⭐⭐ **能自己写逻辑**（缓存、重传、流控、协议解析） | ⛔ 只能透传 |
| ⭐ **能本地缓存** | ⭐⭐ **有 SPI RAM/PSRAM**，可**先收完再匀速喂 FPGA** | ⛔ 没有 |
| ⭐ **时序可控性** | ⭐⭐ **高**（可以用"定时器 + 硬件 UART DMA"精确节拍） | ⚠️ 低（受蓝牙包间隔支配） |
| 开发成本 | ⚠️ 要写 ESP32 固件 | ⭐ 开箱即用 |
| ⚠️ **合规** | ⚠️ **见下方红线** | ✅ 无（纯透传，不算 MCU 参与功能） |

#### ⚠️⚠️ 但有一个**关键区分**必须说清（⛔ 否则会踩坑）

⭐ **"不用考虑 BSRAM" 和 "一次性传完" 是【互相冲突】的两个方案**：

| 方案 | FPGA 侧缓冲 | 省 BSRAM 吗 | 稳定性 |
|---|---|---|---|
| **A. ESP32 流式发送** | ⭐ **小 FIFO**（几 KB） | ✅ **省** | ⚠️ 取决于 ESP32 定时精度 |
| **B. ESP32 一次性发完**（⭐ 之前讨论的） | 🔴 **整车缓冲**（256~512 kbit） | ⛔ **不省** | ⭐⭐ 最稳（阶段隔离） |
| ⭐⭐ **C. ESP32 按【FPGA 反馈的时钟】精确定时发送** | ⭐ **小 FIFO** | ✅ **省** | ⭐⭐ **稳**（见下） |

⭐⭐ **方案 C 是"两全其美"的那个** —— ⭐ **让 ESP32 充当"按拍供数"的角色**：

```
① FPGA 把 beat_gen 的拍点脉冲【回传】给 ESP32（一根线 / 或用串口消息）
② ESP32 收到第 N 拍 => 才发第 N 拍该响的音符
③ FPGA 侧只需一个小 FIFO（⚠️ 最多缓冲几拍，几百字节）
```

⭐ **关键**：**FPGA 仍然是"时钟的主人"**，ESP32 只是"跟着拍子喂数据" ⇒
⭐ ① **省 BSRAM**（小 FIFO）② **稳**（有反馈闭环，不靠蓝牙的绝对时序）。

⚠️ **代价**：ESP32 侧要写"**跟着外部时钟走**"的固件（⚠️ 比纯透传复杂）。

#### ⭐ 更简单的替代（⚠️ 但要多花 FPGA 的 BSRAM）

⭐ 若不想写复杂固件：⭐ **让 ESP32 "提前一点、匀速发"** + FPGA 侧缓冲**几秒**（约 16~32 kbit）
⇒ ⭐ **对蓝牙的几十 ms 抖动已经绰绰有余**（⭐ 因为该曲平均只要 **13.9 字节/秒**，见下）

#### ⭐⭐ 吞吐量核算（已算 —— 结论：**绰绰有余**）

| 项 | 值 |
|---|---|
| 该曲事件数 | **658**（329 音符 × on/off） |
| 时长 | 190 小节 @120 BPM ≈ **6.3 分钟** |
| ⭐ **平均所需** | ⭐ **1.7 事件/秒 = 约 13.9 字节/秒** |

| 串口速率 | 能力 | 余量 |
|---|---|---|
| 9600 baud | 960 字节/秒 | ⭐ **69×** |
| 115200 baud | 11 520 字节/秒 | ⭐⭐ **829×** |
| 1 M baud | 100 000 字节/秒 | **7194×** |

> ⭐⭐ **结论**：⭐ **带宽完全不是问题**（⚠️ 即使 9600 baud 也有 69 倍余量）。
> ⚠️ **真正的风险是"抖动"不是"带宽"** ⇒ ⭐ 所以**方案 C（反馈同步）才是关键**。

#### 🔴 合规：ESP32 会不会踩"MCU 红线"？

⭐ `评分规则对齐.md` 第 177 行的**红线**：

> ⭐⭐ **选题二的「音频」与「视觉效果」部分绝对不要用软核/MCU**

| 问 | 答 |
|---|---|
| ESP32 参与"音频"了吗？ | ⚠️ **需要界定** —— 它**不生成音频**，只**传音符指令** |
| 音频是哪里生成的？ | ⭐ **完全在 FPGA 内逐样本合成** ⇒ ✅ **符合红线** |
| ⚠️ 风险 | ⚠️ **评委可能认为"曲谱来源"算功能的一部分** |

⭐ **建议话术**：
> **"ESP32 只是【外部存储/传输介质】—— 它把一个音符表传给 FPGA。
> 音频通路的每一级都在 FPGA 内，逐样本实时合成。
> ESP32 ⛔ 不参与任何音频计算、不产生任何音频。"**

⚠️ **且**：⭐ **主功能（实时演奏 32 复音）必须⛔ 不依赖 ESP32** ⇒
⭐ **拔掉 ESP32，手弹/节拍器/鼓机/looper 全部照常工作**（⭐ 同"拔掉串口屏"那条纪律）。

#### ⭐ 三条方案对比总结

| | 裸蓝牙模块 | ESP32 透传 | ⭐⭐ **ESP32 + 反馈同步（方案 C）** |
|---|---|---|---|
| BSRAM | ⭐ 小 FIFO | ⭐ 小 FIFO | ⭐ **小 FIFO** |
| 稳定性 | ⚠️ 差（抖动大） | ⚠️ 中 | ⭐⭐ **好（闭环）** |
| 开发量 | ⭐ 最小 | 🟡 中 | ⚠️ **最大**（要写同步固件） |
| ⚠️ 合规 | ✅ 最干净 | ⚠️ 要说明 | ⚠️ 要说明 |
| ⭐ **建议** | 🟡 先做原型 | ⭐ **先做这个** | ⭐ **稳定版目标** |

> ⭐ **务实建议**：⭐ **先用"ESP32 透传 + FPGA 几秒缓冲"跑通**（⚠️ 缓冲只要 16~32 kbit），
> ⭐ **若上板发现抖动影响听感，再升级到方案 C**（⚠️ 那时只改 ESP32 固件，FPGA 侧不动）。

### 1.7 ⚠️ 蓝牙模块选型（若不用 ESP32）

| 项 | 要求 |
|---|---|
| ⭐ **必须是"串口透传"型** | ⭐ `HC-05` / `JDY-31` / `AT-09`(BLE) 这类 —— ⭐ **对 FPGA 就是一根 UART** |
| 🔴 **⛔ 不能用蓝牙音箱模块** | ⚠️ A2DP 输出的是**音频**，⛔ 我们不要音频 |
| ⭐ **电平** | ⚠️ 确认模块是 **3.3 V TTL**（⭐ 与 `J10` 的 `3V3` 匹配） |
| ⚠️ **速率** | ⭐ 建议 **115200** 或更高（⚠️ 一次性传完的话，慢点也无所谓） |

### 1.8 ⭐ "曲谱播放时不需要 looper" —— **已明确，两者解耦**

| 项 | 结论 |
|---|---|
| ⭐ **关系** | ⭐ **独立** —— 曲谱播放**直接用事件流**，⛔ 不经 looper |
| ⭐ **好处** | ⭐ **可以独立做、独立验**；⚠️ **不必等 looper** |
| ⚠️ **但** | ⚠️ **两者抢 voice**（都从 `note_manager` 池里拿）⇒ ⭐ **同时用时注意配额** |
| ⚠️ **且** | ⚠️ **两者抢 BSRAM**（整曲缓冲 vs looper 3 层）⇒ ⭐ **见 §四** |

> ⭐ **修正上一条的说法**：我原说"做完 looper 这个几乎白送" ——
> ⭐ 更准确的是：**两者共用"按 tick 吐事件"的机制，但可独立实现** ⇒
> ⭐ **你可以先做曲谱播放，⛔ 不必等 looper**。

## 七、实现前的核心答案：ESP32-S3 能让 FPGA 稳定收到、且时间正常吗？

> 用户问：*确定 esp32-s3 能让 fpga 侧稳定收到这个并且时间正常是吧*

### 7.1 诚实答案：分两件事，一个能保证、一个不能“现在”保证

| 问题 | 答案 | 依据 |
|---|---|---|
| **数据能不能稳定收到？** | 能（工程上很容易） | 只需 **13.9 字节/秒**；115200 baud 有 **829 倍** 余量 |
| **时间能不能正常？** | **能，但不是因为 ESP32 准** | **是因为【FPGA 侧对齐】**（见 7.2） |
| **是不是“插上就行”？** | **不是** | **以下四件事必须做**，否则会出现“收到但时间不对” |

**必须做的四件事**（这就是“为什么不能直接说能”的原因）：

| # | 事项 | 不做的后果 |
|---|---|---|
| **1** | **每条事件带 `tick` 时间戳**（做法 B） | 只能“收到就发” => 抖动直接变成音准 |
| **2** | **FPGA 按 `beat_gen.tick` 到点才发声** | 时间基准变成“蓝牙到达时刻” => **违反确定性延迟** |
| **3** | **UART 接收器要自己写**（现在完全没有） | 根本收不到字节 |
| **4** | **提前量 + 缓冲**（见 7.3） | 密集和弦会丢音符 |

> **一句话**：**稳定收到 = ESP32 的功劳；时间正常 = FPGA 对齐的功劳。**
> 不能指望“ESP32 发得准，所以时间就对”—— 那条路很脆（蓝牙抖动 + 任务调度）。

### 7.2 为什么“FPGA 对齐”就能保证时间正常

```
ESP32  只需“提前一点”把事件（带 tick 时间戳）塞进 FPGA FIFO
          |            抖动多大都无所谓，只要不太晚
          v
FPGA   自己把它放到“该响的那个 tick”才发出去
          |            时间基准 = beat_gen（FPGA 内部）
          v
      evt_merge -> note_manager -> 逐样本合成
```

这与已有 `note_manager` FIFO **同一个机制**（`K-106`）：**事件先排队，本地时钟决定何时消费**。

> 这也是为什么我推荐【做法 B】而不推荐做法 A：
> A（回传拍点）把“时间”交给了 ESP32，而 B 始终把时间留在 FPGA。

### 7.3 缓冲到底要多大（已算）

前提：该曲平均只需 **13.9 字节/秒**。

| 场景 | 数据量 | @115200 传完耗时 |
|---|---|---|
| 一个满和弦（6 个音 = 12 事件） | **96 字节** | **8.3 ms** |

| 提前量 | 能传多少 | 够不够 |
|---|---|---|
| 2 拍（1.04 ms） | 120 字节 | 够 2 个满和弦 |
| **8 拍（4.2 ms）** | **480 字节** | **非常稳（推荐）** |

> **结论**：FPGA 侧只需 **2 KB 缓冲**（已是 **200 倍余量**），
> 不需要之前说的 256~512 kbit（那是“一次性传完整曲”的方案）。

### 7.4 一个真实的技术风险（必须知道）

| # | 风险 | 说明 | 对策 |
|---|---|---|---|
| **1** | **ESP32 发送会有间隙** | UART TX FIFO 只有 **128 字节**；FreeRTOS 任务调度会产生间隙 | 用**硬件流控 CTS/RTS** 或 **足够的提前量** |
| **2** | **FPGA 没有 UART 接收器** | **现在完全没有** | 要**新写** `uart_rx.v`（50 MHz 下 115200 每位 434 clk，余量充足） |
| **3** | **丢包 / 串错** | 蓝牙链路可能丢包 | **帧头 + 校验和 + 序号**；**丢了要能发现**（`K-106`） |

> **第 1 条是真风险**：所以我们靠的是“**提前量足够大**”，不是“ESP32 发得连续”。
> 8 拍提前量（4.2 ms）对 128 字节 FIFO 而言非常宽裕。

### 7.5 总结（回答用户）

| 问 | 答 |
|---|---|
| ESP32-S3 能稳定发吗？ | **能**（带宽 829 倍余量） |
| FPGA 能稳定收到吗？ | **能**，**但 UART 接收器要新写** |
| 时间会正常吗？ | **会**，**前提是【FPGA 按 tick 对齐】**，不是因为 ESP32 准 |
| 需要多大缓冲？ | **2 KB 足够**（提前量给 8 拍） |
| 现在可以直接上吗？ | **不可以** —— 先要：① Python 转换器 ② `uart_rx.v` ③ `play_seq.v` |

### 9.1 输入 / 输出

```
输入:  *.gp (GP7/8, ZIP+XML)  或 *.gp5 (GP3/4/5, 用 PyGuitarPro)

            v   tools/gp2evt.py
```

> **第 3 项是判据的关键** —— 不能只看“脚本跑通了”，

### 9.2 分步（每步可独立验证）

| 步 | 做什么 | 判据 |
|---|---|---|
| **1** | 读 `.gp`：解 ZIP -> 读 `Content/score.gpif` | 能打印出曲名/轨数/小节数 |
| **2** | 抽出每轨的音符（直接取 `Midi` 号） | 数量与实测一致（**329**） |
| **3** | **时值 -> tick**（跟 `<Rhythm ref>` 跳表） | 一小节总 tick 数 = **3840**（=PPQN960x4） |
| **4** | 合并连音线（tie） | 无重复触发 |
| **5** | 音高 -> `phase_inc` | 与手算表一致（A4=**37796**） |
| **6** | 力度 -> `velocity` | 映射单调 |
| **7** | 输出 `.hex` + `.csv` + `.mid` | **MIDI 用电脑听，与原谱一致** |

### 9.3 必须处理的四个难点

| # | 难点 | 不处理的后果 |
|---|---|---|
| **1** | **时值解析**（跳 `<Rhythm>` 表） | 节奏全错 |
| **2** | **连音线合并** | 听起来像重弹 |
| **3** | **5 轨 -> 我们的 voice** | **鼓轨要走鼓机**（不是 `phase_inc`） |
| **4** | **技法降级** | 滑音/推弦只能近似；**闷音/泛音先忽略**（要说明取舍） |

### 9.4 代码结构（预计 300~400 行）

```python
# tools/gp2evt.py   纯标准库（zipfile + xml），无第三方依赖
def read_gp(path)        -> str     # 解 ZIP，返回 xml 字符串
```

### 9.5 事件编码（与 `note_evt_t` 对齐）

```
每条 64 bit：
  [63:48] tick       16 bit   相对起点的 PPQN tick
  [47:16] phase_inc  32 bit   音高
  [15:12] axis       4 bit    轨/voice 映射
  [11:4]  velocity   8 bit    力度
  [3:2]   reserved   2 bit
  [1:0]   kind       2 bit    0=on 1=off
```

> 与 `Looper详细设计.md` 的 64 bit 记录格式一致 => **两者可共用播放引擎**。

## 十、用户 2026-09-22 下午的新确认（含一处重要修正）

### 10.1 修正：滑音【不是降级】，是【必做功能】

> 我原先把滑音和推弦/闷音混在一起当“可忽略的技法” —— **这个归类是错的**。

| 技法 | 新判断 | 依据 |
|---|---|---|
| **滑音（glissando）** | **本来就该做** —— 它是**已规划的功能** | 冻结表有 **`pitch_update_t`**；`note_manager` 已支持每 voice 独立 `phase_inc` 更新 |
| **推弦（bend）** | 先不管（但与滑音同族，将来可复用同一条通路） | 都是“音高连续变化” |
| **泛音（harmonic）** | 先不管 | 音色问题，不是音高问题 |
| **闷音（palm mute）** | **记档**，暂不急 | 在吉他谱里**出现频率很高**，较通用；但实现上要“按技法/音色分流” => 要动 `note_manager` 的链 |

**对转换工具的影响（重要）**：滑音要单独处理，而不是降级成两个音：

| 做法 | 说明 |
|---|---|
| 原计划（错误归类） | 滑音 -> 降级成“起点音 + 终点音”两个音 |
| **正确做法** | **`note_on`（起点）+ 若干 `pitch_update`（中间点）+ `note_off`** |

> 这正好用上已有的 `pitch_update_t` 通路，
> 且与 `Looper详细设计.md` 的“方案 C：按 tick 抽样 pitch_update”**完全一致**
> => **两者可共用同一套处理逻辑**。

### 10.2 `uart_rx` 已找到，并**实测通过**

用户提示：“我的 fpga 文件夹里面应该有 uart_rx” —— 确实有，而且能用。

| 项 | 内容 |
|---|---|
| 位置 | `Desktop/FPGA/ADDA/src/uart_rx.v`（4252 字节，8N1） |
| 配套 | `uart_baud_gen.v` / `uart_tx.v` / tb 在【本仓库之外】的（本仓库之外的另一个目录）FPGA招新题 phase4 下（uart_rx_tb.v） |
| 原 tb 实测 | **3/3 PASS**（0x69 / 0xA5 / 毛刺不误触发） |
| **我补测的真实速率** | **`BAUD_DIV=434`（115200 baud）** => **6/6 PASS**，含 `00`/`FF` 边界 |

**波特率误差核算**：`50MHz/115200 = 434.028` => 取 434 => 实际 115207.4（误差 **0.006%**），
累积到第 10 位仅 **0.001 个位宽** => 安全。

**但有两处要改（不能直接搬用）**：

| # | 问题 | 为什么必须改 |
|---|---|---|
| 1 | 复位是【异步】低有效 | 冻结表约定 2 要求“同步复位、全设计一致” => 混用是最常见的集成 bug |
| 2 | `clk_cnt <= 6'd0`（6 位常量） | 寄存器是 16 bit，值 0 无害，但语义误导 => 改 `16'd0` |

**搬用计划**：搬进 `rtl/w3c/`（⚠️ **尚未创建**）+ 改同步复位 + `6'd0 -> 16'd0` +
**补一个真实 BAUD_DIV 的 tb** + **加变异体**（纪律：没有变异体 = 没被验收）。

### 10.3 ESP32 与 FreeRTOS

**不必需，但 ESP-IDF 默认就是它。**

| 层面 | 事实 |
|---|---|
| ESP-IDF | 默认基于 FreeRTOS（`app_main` 本身就是一个任务） |
| 能不用吗 | 可以走单任务裸机：逻辑全塞进 `app_main` 循环，不创建额外任务 |
| Arduino | 能（底层仍是 FreeRTOS，但对你透明） |

> **但对我们这个项目，这个问题不重要**：
> 既然已决定“**让 FPGA 侧对齐**”，ESP32 的抖动根本不重要
> => 不需要为了降抖动去裸机化。

真正决定抖动的是（裸机也躲不掉）：

| 因素 | 影响 |
|---|---|
| UART TX FIFO 只有 128 字节 | 写满了就得等 => 产生间隙 |
| 蓝牙协议栈抢占 | 会产生几十 ms 级停顿（而蓝牙栈必须跑，自带调度） |

=> **FreeRTOS 不是问题；“提前量给够（8 拍约 4.2 ms）”才是解法**。
