## T1 🔴🔴 用"读文本+写文本"复制 `.sv`/`.v` ⇒ **静默改坏源码**（⭐ 最危险）

**实测现场（2026-10-03）**：WS2812 子代理为了验证 `LED_N=7`，把 tb 复制到 `%TEMP%` 再改：

```powershell
$t = Get-Content $src -Raw      # 🔴 PS 5.1 把【无 BOM 的 UTF-8】按 GBK 解码
$t = $t.Replace(...)
[IO.File]::WriteAllText($dst, $t)   # 🔴 写出时字节已变
```

⇒ ⭐ **框线字符 `─` 的字节序列吃掉了后面的换行** ⇒ **注释与下一行的 `for (li = 0; li < LED_N; ...)` 合并成一行** ⇒ **写口那 3 个 `for` 循环全被注释掉** ⇒ 颜色缓存从未写入 ⇒ `mem` 全 X ⇒ `dout_o = X` ⇒ 监视器收不到边沿 ⇒ **超时**。

🔴 **为什么比 `.md` 表格那次更危险**：
- `.md` 那次是**看得见的排版坏**（孤立残行）
- ⭐ 这次是 **`编译通过` + `仿真静默挂死`**（⭐ **报错为零**）⇒ ⚠️ 极易误判成"RTL 有 bug"

⭐ **机械判据**（改完**必须**跑）：
```powershell
Select-String -Path <改过的文件> -Pattern 'for \(li = 0; li < LED_N' | Measure-Object | % Count
#   坏副本 = 0 命中；好副本 = 3 命中
```
⇒ ⭐ **grep 那些"可能被吃掉换行"的行还在不在**，⛔ 别只看"编译通过"。

⭐ **安全做法（实测可用，三选一）**：
1. ⭐ `Copy-Item`（**字节级**复制）+ 用 **`edit` 工具**改
2. ⭐ `[Text.Encoding]::UTF8.GetString([IO.File]::ReadAllBytes($p))` → `Replace` → `[IO.File]::WriteAllText($p, $t, (New-Object Text.UTF8Encoding($false)))`
3. ⛔ **永不**用 `Get-Content -Raw` / `ReadAllText` + `WriteAllText` 去复制/重写**含非 ASCII 的源码**

## T2 🔴 `run syn` 是【增量】的 ⇒ 综合对照**不可比**

**实测现场**：`gowin_build.ps1` / `pnr_run.ps1` **只清 `impl/pnr`，⛔ 不清 `impl/gwsynthesis`**（`pnr_run.ps1:95-100`）。

| 口径 | HEAD 基线 | ROT32 探针版 |
|---|---|---|
| 增量（不删） | 37433 | 35311 |
| ⭐ **干净（先删 `impl/gwsynthesis`）** | **37559** | **35858** |

⇒ ⭐ **项目里旧的全部 P4/P5 探针数字互相之间也不严格可比** ⚠️（含我给用户的那几张表）
⭐ **机械判据**：任何综合对照，⭐ **先 `Remove-Item impl\gwsynthesis -Recurse -Force`** ✅
   ⚠️ **2026-10-03 23:30 更正（实测复现失败）**：修 T2 的子代理**没能复现**"增量导致数字不可比"——
   在 Gowin V1.9.12.03 上，用旧 rtl 先综合留残留、再换当前 rtl **不删**残留 ⇒ `T_Lut` 与干净口径**完全相同**，且两次日志**逐字节相同**；清与不清耗时差 ≈0（164.2 vs 164.9 s）。
   ⇒ ⭐ **结论**：`run syn` 在这个版本上**每次都全量重综合**，清 `impl/gwsynthesis` 目前是**零成本保险**，⛔ **不是"已证实的修法"**。
   ⚠️ 因此本文 T2 原文的 `37433` vs `37559` **来源未查明** —— 更可能是**不同 top/配置**（`impl/` 里当时留着 `_p31_base_process_config.json`/`_p32_fg_process_config.json`/`_p3_probe_process_config.json` 三个探针配置）或**读数时机**（读到上一版 rsc），⛔ 不是"增量残留"。
   ⭐ 保留动作：`gowin_build.ps1` / `pnr_run.ps1` 现在**默认清** `impl/gwsynthesis`（零成本），`-KeepSyn` 是逃生口。
⭐ 补充：⭐ **干净流程本身是确定性的**（同源连跑两次 xml **逐字节相同** ✅）

## T3 🔴 只跑综合的探针 **验证不了语义**

**实测现场**：ROT32 的探针版把三条写路径**共用一个** 3 选 1 mux 的移位器 ⇒
- 错法 1：**滑音段与 FSM 写可以同拍、写【不同】lane** ⇒ 一个 mux 表达不了
- 错法 2：**`cmt_en_r` 是锁存标志** ⇒ 进 `ST_RETRIG` 时可能还是 1 ⇒ 把陈旧值写进重触发 lane

⭐ **实测**：探针版 **50266 拍里 48932 拍不同（97%）**；正式版（两个移位器）**0 处不同** ✅
⇒ ⭐ **结论**：⭐ **"省了多少 LUT" 必须配"功能是否逐位等价"一起看**；⭐ 只跑综合的省额可能是**用错事买来的**。

## T4 🔴 僵尸 `gw_sh` ⇒ "等 gw_sh 为空"的脚本**永久卡住**

**实测现场**：`PID 37832`（`gw_sh.exe _probe.tcl`）**已经死了**（`taskkill /F` 报 *no running instance*），⭐ 但 `Get-Process gw_sh` / `Get-CimInstance Win32_Process` **仍然列着它，且杀不掉**。

⭐ **机械判据**：⛔ **别用 `Get-Process gw_sh` 是否为空**；⭐ 改成**按命令行过滤**（只把含 `gowin_build` / 根工程 `.gprj` 的当作占用），或只关心**自己启动的 PID**。

## T5 🔴 `gowin_build.ps1` 的收尾会**杀掉所有 gw_sh**

**实测现场**：`sim/gowin_build.ps1:117-128` 收尾是 `Get-Process gw_sh | Stop-Process -Force` ⇒ ⭐ **它会把别的子代理正在跑的综合一起杀掉** ⚠️（WS2812 的第一次综合就是这样被杀的）。
⭐ **修法**：只杀**自己 `Start-Process -PassThru` 得到的那个 PID**。

## T7 ⚠️ 顶层模块资源数字可能是**假象**（被常量折叠）

**实测现场**：`ws2812_driver` 在**探针**（写口接顶层输入）里 = **328 LUT / 474 FF**；⭐ 在整工程里 `u_ws2812` 只报 **138 LUT / 78 FF** —— ⚠️ 因为 top 的自检图案是常量推导的 ⇒ **384 FF 的颜色缓存被整块折掉**。
⭐ **机械判据**：⭐ 要量**模块自身**资源，必须用**探针顶层**（把输入接到端口、输出接出去）⇒ ⛔ 别读整工程里的子模块数字。
