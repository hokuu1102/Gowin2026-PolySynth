## 二、⭐⭐ 接口（⭐ 直接照 `metronome.v` 的模板）

### 2.1 ⭐⭐ 为什么能照抄 `metronome`

⭐ **两者在架构上完全同类**：

| 维度 | `metronome` | ⭐ `drum_gen` |
|---|---|---|
| 输入 | `beat_i` / `bar_start_i` / `transport_i` | ⭐ **同样三个** + ⚠️ **还要 16 分音符点**（见 §2.3） |
| 输出 | 单周期 `evt_valid_o` + 轴/相位/力度/类型 | ⭐ **完全一样** |
| 落点 | ⭐ 走 `evt_merge` → `note_manager` **专用池** | ⭐ **同一个池** |
| 包络 | ⭐ `perc_env_bank`（专用打击包络） | ⭐ **同一个** |

⇒ ⭐⭐ **结论**：⭐ `drum_gen` = **`metronome` 的"多乐器 + 节奏型"版本** ——
⚠️ **不是新架构，是同一个模式加料**。

### 2.2 ⭐ 端口定义（⭐ 建议）

```verilog
module drum_gen #(
    parameter integer AXIS_W    = 4,
    parameter integer PHASE_W   = 32,
    parameter integer VEL_W     = 8,
    // ⭐⭐ 本模块自己的 axis_id（⭐ 已拍板用 `0xF`，⭐ 见 §8.4 的"为将来留门"设计）
    //   ⚠️ 必须 >= `note_manager.RESERVED_AXIS_BASE`（= 14）⇒ ⭐ 才进专用池
    //   ⭐ 节拍器占 `0xE` ⇒ ⭐ 鼓机用 `0xF`（⭐ 分开 ⇒ 将来"同时用"不用返工）
    parameter integer AXIS_ID   = 15,      // ⭐ 4'hF（⭐ 实测 note_manager 注释就是这么建议的）
    parameter integer N_DRUM    = 4,       // ⭐ Kick/Snare/HiHat/Clap
    //   ⚠️ **⛔ 本模块不需要 `RESERVED_N`** —— ⭐ 那是 `note_manager`/`metronome` 的参数
    //      （⭐ 它由 `top.v` 例化时配对传入，⭐ 见 `K-106` 的"不配对会静默失效"）
    // ⭐ 节奏型形态
    parameter integer STEPS     = 16,      // ⭐ 16 分音符为一步
    parameter integer PATTERN_ID = 0       // ⭐ 选哪个内置型（0~7）
) (
    input  wire                 clk_i,
    input  wire                 rst_n_i,
    // ── 来自 `beat_gen`（⭐ 实测它有这些输出，⛔ 一个都不用新增）─────────
    input  wire                 tick_i,        // ⭐ PPQN tick 脉冲（960/四分音符）
    input  wire [15:0]          tick_cnt_i,    // ⭐ 小节内 tick 计数（⭐ 定位用）
    input  wire                 bar_start_i,   // ⭐ 小节起点
    input  wire                 transport_i,   // ⭐ run 状态（0 ⇒ ⛔ 不发事件）
    //   ⚠️ **不需要 `beat_i`** —— ⭐ 16 分音符由 `tick_cnt_i` 每 240 tick 推出（⭐ 见 §2.3）
    // ── 事件输出（⭐ 与 `metronome` 完全同构）────────────────────────────
    output reg                  evt_valid_o,   // ⭐ 单周期脉冲
    output wire [AXIS_W-1:0]    evt_axis_o,
    output wire [PHASE_W-1:0]   evt_phase_inc_o,
    output wire [VEL_W-1:0]     evt_velocity_o,
    output wire [1:0]           evt_kind_o,
    // ── 可观测性（`K-106`：⛔ 不许静默失效）──────────────────────────────
    output wire [15:0]          evt_cnt_o,     // ⭐ 已发事件总数（饱和）
    output wire [3:0]           step_cnt_o,    // ⭐ 当前第几步（⚠️ 上板调试用）
    output reg  [3:0]           hit_cnt_o,     // ⭐ 本轮已触发几个乐器（⭐ 防"一 tick 只发一个"）
    output wire                 cfg_warn_o     // ⭐ 参数不一致时报警
);
```

### 2.3 ✅ **16 分音符点从哪来 —— ⭐ 已查实：`beat_gen` 本来就有**

🔴 **我第一版写错了**（⚠️ 以为 `beat_gen` 只有 `beat_i`）——
⭐ **实测它的输出**（`rtl/w3c/beat_gen.v`）：
```verilog
output wire        tick_o,          // ⭐ PPQN 节拍脉冲，单周期
output wire [15:0] tick_cnt_o,      // ⭐ 小节内 tick 计数（⭐ 注释原文：
                                    //    "供鼓机/looper 定位"）
output wire        bar_start_o,     // ⭐ 小节起点
output wire        beat_o,          // ⭐ 四分音符拍点
output wire        transport_o,     // ⭐ run 状态
output wire [15:0] bar_cnt_o,       // ⭐ 已过小节数
output wire        tick_cnt_wrap_o  // ⭐ tick_cnt 回绕指示
```

⇒ ⭐⭐ **结论：⭐ 一个字段都不用加** —— ⭐ **`tick_cnt_o` 就是为鼓机准备的**。

⭐ **PPQN = 960** ⇒ ⭐ **一个 16 分音符 = 960 / 4 = 240 tick**：
```verilog
// ⭐ 做法：⭐ 用 tick_cnt_o 的低位判"16 分音符边界"（⭐ ⛔ 不做除法）
//   ⭐ 240 = 0xF0 ⇒ ⭐ 每 240 tick 一个 16 分音符
//   ⚠️ 判据：⭐ tick_cnt_o[7:0] == 8'h00  且  (tick_cnt_o % 240) == 0
//   ⭐ 更稳的做法：⭐ 内部维护一个 step 计数器，
//      在 bar_start_i 时清零，⭐ 然后每 240 tick 递增
localparam integer TICKS_PER_STEP = 240;   // ⭐ 960 PPQN / 4
reg [15:0] tick_at_step_q;                 // ⭐ 上一步的 tick 位置
wire step_edge = (tick_cnt_o - tick_at_step_q) >= TICKS_PER_STEP[15:0];
```

⚠️ **为什么用"差值 ≥ 240"而⛔ 不用"取模等于 0"**：
⭐ 因为 **`bar_start` 那一刻 `tick_cnt_o` 会归零**，
⚠️ 取模会被"跨小节跳变"搞乱 ⇒ 🔴 可能丢一步或**多发一步**。
⭐ **差值法天然容忍跳变**（⭐ 且不依赖 `tick_cnt_o` 的相位）。

> 📌 **修正记录（⭐ 保留痕迹）**：⭐ 我第一版提了三个选项（改 `beat_gen` / 内部数 / 用 tick）
> 并推荐"内部数" —— 🔴 **那个推荐是多余的**：⭐ `tick_cnt_o` 本来就在，
> ⭐ **直接用它即可**（⭐ 且比内部数拍**更准**：⭐ 内部数拍会跟着 `beat_i` 走，
> ⚠️ 若 `beat_gen` 中途变速，⭐ **tick 分辨率才是权威**）。
> ★ 这说明：⭐ **设计前必须把上游模块的输出列表【读一遍】**，⛔ 不能凭印象说"它没有"。

### 2.4 ✅ **`axis_id` 分配 —— ⭐ 已查实基址是 14**

⚠️ **我第一版写错了**（⚠️ 以为鼓机要用 12/13）——
⭐ **实测 `note_manager.v:75`**：`parameter integer RESERVED_AXIS_BASE = 14`
⇒ ⭐⭐ **`axis_id >= 14` 就进专用池** ⇒ ⭐ **和具体是 12 还是 15 无关**。

```
⭐ 已占用：
   · 节拍器 = 14 (4'hE)        ← ⭐ metronome.v 实测 AXIS_ID=14
   · ⚠️ 鼓机应从 15 (4'hF) 起？
```

🔴 **但这里有一个真约束（⭐ 必须解决）**：
⚠️ **`axis_id` 只有 4 位**（`AXIS_W = 4`）⇒ ⭐ **最多 16 个轴（0~15）**
⇒ 🔴 **`>= 14` 的只有 14、15 两个值** —— ⚠️ **装不下"节拍器 1 + 鼓机 4"**！

🔴🔴 **这是一个真正的设计冲突**，⭐ **必须解决才能落鼓机**：

| 方案 | ⭐ 做法 | ⚠️ 代价 |
|---|---|---|
| **(a)** ⭐ **扩大 `AXIS_W` 到 5** | ⭐ 16 轴 → 32 轴 ⇒ ⭐ 专用池能到 16~31 | ⚠️ **改 `note_manager`/`evt_merge`/事件格式**（⚠️ **动已落地模块 + 冻结接口**） |
| **(b)** ⭐⭐ **鼓机 4 个乐器【共用一个 axis_id】** | ⭐ 如鼓机全用 15，⭐ **靠 `PHASE_INC` 区分音色** | ✅ **⛔ 不改任何接口**<br>⚠️ 但缺"每乐器独立包络"（⭐ 4 种鼓包络不同） |
| **(c)** ⚠️ **鼓机不占专用池**，⭐ 走普通池 | ⭐ 用 0~13 的普通轴号 | 🔴 **会抢演奏的 voice**（⚠️ 用户弹琴时鼓会把音抢掉） |

⭐ **我的建议：(b)** —— ⚠️ 理由：
* ✅ **⛔ 不改 `AXIS_W`**（⭐ 那会动到**冻结的 64 bit 事件格式**，⚠️ 风险极高）
* ⚠️ **代价可接受**：⭐ 4 种鼓**共用包络形状**（⭐ 都是快速衰减）
  ⇒ ⭐ **靠 `PHASE_INC`（音高）+ `VELOCITY` 区分** ⇒ ⚠️ 听感够用
* ⭐ **若将来真需要**"每鼓独立包络" ⇒ ⭐ 那时再扩 `AXIS_W`（⭐ 属阶段 2）

🔴 **`RESERVED_N` 的账**（⭐ 用方案 (b) 后）：
```
⭐ 专用池需求 = 节拍器 1 + 鼓机 1 = 【2 个】
⭐ 当前 RESERVED_N = 5  ⇒ ✅ 余量充足（⛔ 不用改）
```
⭐ 而方案 (b) 之前的推算（"需要 5 个"）**是基于错误前提**（⭐ 以为 4 个鼓各占一个轴号）。

## 三、⭐⭐ 内部状态机（⭐ 建议）

```
⭐ 核心是"16 步 × 4 乐器"的 step sequencer
（⭐ 方案 §3.2 已定容量：16 步 × 4 乐器 × 5 bit ≈ 0.32 kbit ⇒ 可忽略）

   ┌─────────────────────────────────────────────────────┐
   │  S_IDLE   transport_i=0 ⇒ 停在此，⛔ 不发任何事件      │
   └──────────────┬──────────────────────────────────────┘
                  │ transport_i=1
                  ▼
   ┌─────────────────────────────────────────────────────┐
   │  S_BEAT   等 beat_i ⇒ 每拍推进 4 步（16 分音符）        │
   │           ⭐ 内部 4 分频计数器 sub_step_q                │
   └──────────────┬──────────────────────────────────────┘
                  │ 每 1/16 拍
                  ▼
   ┌─────────────────────────────────────────────────────┐
   │  S_FIRE   查 pattern[PATTERN_ID][step][drum]          │
   │           ⭐ **逐个乐器发事件**（⚠️ 见下方关键点 ①）     │
   │           ⭐ 发完 ⇒ step_q 递增（mod 16）               │
   └──────────────┬──────────────────────────────────────┘
                  │ step_q == 0 且 bar_start_i
                  ▼
   ┌─────────────────────────────────────────────────────┐
   │  S_BAR     小节对齐检查（⭐ 可选：更复杂的型需要）        │
   └─────────────────────────────────────────────────────┘
```

### 3.1 🔴🔴 **关键点 ①：一"步"可能同时触发多个乐器**

🔴 **这是最容易写错的地方** —— ⚠️ **必须"逐个发"，⛔ 不能"每步只发一个"**：

```
⭐ 正确：step=4 时 Kick+HiHat 都 on ⇒ ⭐ **在同一拍内连发 2 个事件**
🔴 错误：每步只发一个 ⇒ 🔴 **丢乐器**（⭐ 听感上"鼓点少了一半"）
```

⚠️ **为什么会写错**：⭐ 若用"单拍脉冲 `evt_valid_o`"的思维，
⚠️ 很容易写成"一步一个脉冲" ⇒ 🔴 **同一拍的第二个乐器被吞**。

⭐ **同族教训**：⭐ 库里的 **`U-18b`** 就是这个问题 ——
> ⭐ **`play_seq` 当年"16 项判据全过、变异体 4/4 全抓"，但 `tick` 字段从没被解码**
> ⇒ 🔴 **一 tick 上的 N 条被摊到 N 个 tick** ⇒ ⭐ **和弦被拉成琶音**（⭐ 实测一 tick 最多 **24 条**）。

⇒ ⭐⭐ **`drum_gen` 必须在**同一步**内把 N 个乐器**连发 N 拍**：
```verilog
// ⭐ 做法：⭐ 用一个"待发列表"逐拍清空
reg [N_DRUM-1:0] pending_q;      // ⭐ 本步要发的乐器（one-hot）
always @(posedge clk_i) begin
    if (!transport_i)      pending_q <= 4'd0;
    else if (fire_step_i)  pending_q <= pattern_hits;   // ⭐ 装载本步
    else if (evt_valid_o)  pending_q <= pending_q & ~next_hit;  // ⭐ 发一个、清一个
end
// ⭐ `evt_valid_o` 在 `pending_q != 0` 时**连续拉高** ⇒ ⭐ 逐个发完为止
```
⭐ **判据**：⭐ `hit_cnt_o` 必须等于本步 on 的乐器数（⭐ 见 §四 判据 ③）。

### 3.2 ⭐ 节奏型存储（⭐ `case` 常量表，⛔ 不用 `.mem`）

⚠️ **为什么不用 `.mem`**：⭐ `K-?` 记的 ——
> 🔴 **`$readmemh` 外部 `.mem` 在 GW5AT-60【不加载】** ⇒ ⭐ ROM 全 0
> ⇒ 🔴 **没声音，但仿真全对**（⭐ 这是 `T31` 波表验证要排在最前面的原因）

⇒ ⭐ **鼓机节奏型一律用 `case` 常量表**（⭐ ⛔ 不引入新的"加载不确定性"）。

```verilog
// ⭐ 一个内置型的样子（⭐ 4 个乐器 × 16 步）
//   ⭐ 位序：⭐ 每一步 5 bit = {vel[3:0], on}
function [STEPS*5*N_DRUM-1:0] pattern_of;
    input [2:0] pid;
    begin
        case (pid)
            3'd0: pattern_of = { /* 16 步 × 4 乐器 × 5 bit 常量 */ };
            // ... 4~8 个内置型
            default: pattern_of = { /* 全 0 = 静音 */ };
        endcase
    end
endfunction
```

⭐ **建议的 4 个内置型**（⭐ 方案 §3.2 说"4~8 个"）：

| id | 名字 | 形态 |
|---|---|---|
| **0** | ⭐ **四拍基本型（Rock）** | Kick 在 1、3；Snare 在 2、4；HiHat 每 8 分 |
| **1** | ⭐ **八分摇滚** | Kick 1、3 + 加花；HiHat 每 8 分；Snare 2、4 |
| **2** | ⚠️ **十六分放克** | HiHat 每 16 分；Kick 切分 |
| **3** | ⚠️ **圆舞曲（3/4）** | ⚠️ 只有 12 步有效（⭐ 其余留空） |

| # | 判据 | ⭐ 为什么 |

| **⑨** | ⭐ **`cfg_warn_o` 在参数不一致时拉起** | ⭐ `K-106`：⛔ 不许静默 |
| **⑩** | ⭐ **A8：⛔ 无 X/Z 传播** | ⭐ 项目惯例 |

## 五、⭐ 落地步骤（⭐ 建议顺序）

| # | 步 | 判据 | ⚠️ 依赖 |
|---|---|---|---|
| **1** | ⭐ **先写 `case` 常量表 + 参数** | ⭐ 4 个内置型，⭐ ⛔ 无 `.mem` | — |

## 八、✅ **已拍板：鼓机 `axis_id` 用方案 (b)**（⭐ 2026-09-24 用户确认）

### 8.1 ⭐ 约束（⭐ 三个硬事实，⭐ 全部实测）

| # | 事实 | 出处 |
|---|---|---|
| **1** | ⭐ `axis_id` **只有 4 位** ⇒ 一共 **16 个值（0~15）** | `note_manager` 的 `AXIS_W = 4` |
| **2** | ⭐ **`axis_id >= 14` 才进专用池** | `note_manager.v:263`：`pool_mask[pg] = (cur_axis >= RESERVED_AXIS) ? (pg >= NORMAL_N) : (pg < NORMAL_N)` |
| **3** | ⭐⭐ **设计意图本来就是"节拍器 `0xE` / 鼓机 `0xF`"** | `note_manager.v:74` **注释原文**：*"建议 `4'hE` 节拍器 / `4'hF` 鼓机"* |

⇒ 🔴 **所以"4 个鼓乐器各占一个 `axis_id`"【物理上做不到】** —— ⭐ `>= 14` **只剩 `14` 和 `15` 两个值**。

### 8.2 ⭐⭐ 三个方案的优劣与后果（⭐ 逐个说清）

#### 方案 (a) 🔴 **扩 `AXIS_W` 4 → 5 位** ⇒ ⛔ **不做**

```
⭐ 做法：axis_id 从 0..15 扩到 0..31 ⇒ 专用池能到 16~31 ⇒ 每鼓独立 id
```

| ⭐ 好处 | 🔴 后果 |
|---|---|
| ⭐ 每鼓**独立 `axis_id`** ⇒ ⭐ 可做**每鼓独立包络**（⭐ 听感最好） | 🔴 **要改【冻结的 64 bit 事件格式】** —— ⭐ `play_seq接口冻结契约.md` §1.1 明确写 `bit 22..19 axis (4 bit)`<br>⇒ ⚠️ **要动**：`mid2evt.py` + `evt2uart.py` + **ESP32 侧固件**（⭐ **另一条线**）+ `evt_uart_rx` + `play_seq` + `note_manager` + `event_extract` + `drum_gen`<br>⇒ 🔴 **≥ 7 个模块、跨 3 条线** |
| | 🔴 **`evt_merge` 的记录位宽**（⭐ `AXIS_W` 是它的参数）⇒ ⚠️ FIFO 深度/位宽**要重算** |
| | ⚠️ **ESP32 侧固件已按 4 位写好**（⭐ 在 `feat/s3-ble` 上）⇒ 🔴 **要它同步改 + 重测** |
| | ⚠️ **本轮所有 tb 判据与变异体**都要复核（⭐ 位域变了） |
| | 🔴 **时间成本**：⭐ **至少半天 + 跨线协调** |

⇒ ⭐ **结论：代价极高，⛔ 本周绝对不做。**

#### 方案 (b) ⭐⭐ **4 个鼓共用 `0xF`** ⇒ ✅ **【已拍板采用】**

```
⭐ 鼓机整体占 axis_id = 15 (4'hF)
⭐ 4 个乐器靠【别的字段】区分：
   · PHASE_INC ⇒ ⭐ 音高（Kick 低频／Snare 中频／HiHat 高频）
   · VELOCITY  ⇒ ⭐ 力度（重音/轻音）
   · KIND      ⇒ ⭐ 起音/收音
```

| ⭐ 好处 | ⚠️ 后果（⭐ 诚实说） |
|---|---|
| ✅ **⛔ 不改任何接口、不改事件格式、⛔ 不动其他模块** | ⚠️ **4 个鼓共用【同一条 `perc_env_bank` 包络路】** ⇒ 🔴 **包络形状只能一样** |
| ✅ ⭐ **与设计意图完全一致**（⭐ `note_manager.v:74` 注释就是这么建议的） | ⚠️ **听感后果**：⭐ Kick 该"低频快衰减"、HiHat 该"极快衰减"<br>⇒ 🔴 用同一包络时**只能靠 `PHASE_INC` 区分音高** ⇒ ⚠️ **HiHat 的尾巴可能偏长**（⭐ 上板听过再定） |
| ✅ ⭐ **改动最小**（⭐ `drum_gen` 内部一个映射常量） | ⚠️ ⭐ 4 鼓**同时响**时都占专用池 ⇒ ⭐ **要确认专用池够**（⭐ 见 8.3） |

#### 方案 (c) 🔴 **鼓机走普通池**（`axis_id` 0~13） ⇒ ⛔ **不考虑**

| 🔴 后果 |
|---|
| 🔴 **会抢演奏的 voice** —— ⭐ 用户弹琴时鼓把音抢掉（⭐ `note_manager` 按发音先后抢占） |
| 🔴 **违背设计意图** —— ⭐ 专用池存在的意义就是"**节拍器/鼓机不被抢**" |

### 8.3 ✅ **专用池的账 + `RESERVED_N` 的决定**

```
⭐ 现状 RESERVED_N = 5（⭐ top.v:559 实测）⇒ 专用池 = 5 个 voice
⭐ 节拍器占 1 ⇒ ⭐ 鼓机剩 4
⭐ 最坏情形：⭐ Kick + Snare + HiHat + Clap 在【同一步】全响 = 4 个
⇒ ⭐ 4 + 1(节拍器) = 5  ⇒ ⚠️ **正好够，但【零余量】**
```

🔴 **零余量的风险**：⭐ 将来只要**加一个乐器**（⭐ 或节拍器要加"重音/弱音两路"）
⇒ 🔴 **立刻不够** ⇒ ⚠️ 而**不够的表现是"静默丢音"**（⭐ `note_manager` 分配不到就丢）

✅ **最终决定（⭐ 用户 2026-09-24 拍板）：⭐ `RESERVED_N` 【保持 5，暂不改】**

> ⚠️ **更正记录（⭐ 保留痕迹）**：⭐ 本文档**曾写"从 5 提到 8"**（⭐ 那是"两者同时用"的旧结论）。
> ⭐ **后续用户明确了"鼓机与节拍器二选一"** ⇒ ⭐ **需求变成 `max(1, 4) = 4` ⇒ `5` 已经够**。
> ⇒ ⭐⭐ **最终：保持 5 不动**（⭐ 用户 2026-09-24 明确"暂时不改"）。
>
> 📌 **什么时候才需要提**：⭐ ① 将来**两者同时用** ② **鼓机加乐器** ③ 节拍器加弱拍
> ⇒ ⭐ 那时再提到 **6~8**（⚠️ `top.v` **两处**都要改：`:559` + `:1356`）


### 🔴🔴 **改的时候【两处都要改】**（⭐ 否则静默不一致）

⭐ **实测 `top.v` 里 `RESERVED_N` 出现 2 次**：

| 行 | 位置 | ⭐ 注释怎么说 |
|---|---|---|
| **`:559`** | ⭐ `u_metronome` 的例化 | *"AXIS_ID must stay >= RESERVED_AXIS (14 = 4'hE) ... **PAIRED with note_manager.RESERVED_N above**. cfg_warn_o asserts if the two [are inconsistent]"* |
| **`:1356`** | ⭐ `u_note_manager` 的例化 | *"MUST be >= 1 or the metronome lands in the normal pool and **gets stolen the moment 32 voices sound** ... deliberately **PAIRED with metronome.AXIS_ID**（`K-106` family: an unpaired setting **fails silently**）"* |

⇒ ⭐⭐ **两处必须【同时】从 5 改成 8** —— ⚠️ 只改一处的话
🔴 **`cfg_warn_o` 会拉起**（⭐ 好，⛔ 不是静默）——
📌 **但更危险的是"改错了别人不知道"**：⭐ 所以**改完必须复核 `cfg_warn_o` 没亮**。

⚠️ **⚠️ 而 `RESERVED_N` 与 `AXIS_ID` 是【两个不同的参数】**：
```
· `RESERVED_N`   = 专用池有【几个 voice】 ⇒ ⭐ 要改（5 → 8）
· `AXIS_ID`      = 节拍器用【哪个轴号】   ⇒ ⭐ ⛔ 不动（仍是 14）
· `RESERVED_AXIS_BASE` = 进专用池的【轴号门槛】 ⇒ ⭐ ⛔ 不动（仍是 14）
```
⚠️ **⚠️ 别把"改 `RESERVED_N`"误做成"改 `AXIS_ID`"** —— ⭐ 那是**两件不同的事**。

### 🔴 落地时的完整改动清单（⭐ 鼓机接入时）

| # | 改什么 | 位置 | ⚠️ 注意 |
|---|---|---|---|
| **1** | ⭐ `RESERVED_N` 5 → **8** | `top.v:559` **和** `:1356` | 🔴 **两处** |
| **2** | ⭐ 例化 `u_drum_gen` | `top.v`（⭐ 照 `u_metronome`） | ⚠️ `AXIS_ID = 15`（⭐ `4'hF`） |
| **3** | ⭐ `evt_merge` 源 B 的输入 | `top.v` | ⚠️ **源 B 现在接的是节拍器** ⇒ 🔴 **两个都要进源 B**<br>⇒ ⭐ **必须先 OR 合流**（⭐ 见下） |
| **4** | ⭐ 登记 `.gprj` | `Gowin2026.gprj` | 🔴 否则**静默丢弃**（`U-30`） |
| **5** | ⭐ 加变异体 | `mutation_test.ps1` | ⭐ 见 `新模块变异靶点设计` 的做法 |

🔴 **第 3 条是个真问题**（⭐ 本文件新发现）：
```
⚠️ `evt_merge` 的【源 B】现在只接了节拍器（⭐ 实测 top.v:1321-1323）
⚠️ 而鼓机也要走源 B（⭐ 因为它是专用池）
🔴 ⇒ 两个都要进源 B ⇒ ⭐ 必须【先合流】
```

### 🔴🔴 **已拍板：鼓机与节拍器【二选一】**（⭐ 用户 2026-09-24）

> ⭐ **用户原话**：*"鼓机和节拍器是**二选一**的 —— 使用节拍器时不会用鼓机，用鼓机不用节拍器"*
> ⭐ **且已拍板**：⭐ **运行时切换（可选）** + ⭐ **共用 `evt_merge` 源 B**

⭐⭐ **这条信息大幅简化了设计** —— ⭐ **原以为要改 `evt_merge`，现在⛔ 不用了**：

| 项 | ⭐ 原设计（假设两者同时用） | ⭐⭐ 二选一之后 |
|---|---|---|
| ⭐ `evt_merge` 入口 | 🔴 **要加第三入口** + `DEPTH` 4→6 | ✅ **⛔ 不用改** —— ⭐ **直接复用源 B** |
| ⭐ `axis_id` | ⭐ 节拍器 `0xE` + 鼓机 `0xF` | ✅ ⭐ **可以共用**（⭐ 甚至不用改） |
| ⭐ `RESERVED_N` | ⚠️ 需 **5 → 8**（节拍器 1 + 鼓机 4） | ✅ **`5` 已经够**（⭐ `max(1, 4) = 4`）<br>⚠️ 但⭐ **建议仍提到 6~8**（留余量，⭐ 见下） |
| ⭐ 重验成本 | ⚠️ `tb_evt_merge` 8 条判据要重跑 | ✅ **⛔ 不用** |

⭐ **依据（⭐ 实测）**：⭐ `note_manager.v` 的注释**早就写了**：
> *"⭐⭐ `T33b`: **metronome + drum machine** need a voice that user notes cannot steal.
> metronome emits `axis_id 4'hE`, and `note_manager` picks the reserved pool by that axis..."*

⇒ ⭐ **原设计就把"节拍器 + 鼓机"当成【一对】**（⭐ 共用专用池）
⇒ ⭐ 而**用户明确了它们二选一** ⇒ ⭐ **比原设计更省**。

#### ⭐ 运行时切换的具体做法（⭐ 用户选"可选"）

```
⭐ 两个都例化（⭐ 节拍器 + 鼓机），⭐ 用一个【运行时信号】选谁接到 `evt_merge` 源 B：
    wire sel_drum = <运行时输入>;          // ⭐ 0 = 节拍器 · 1 = 鼓机
    wire        b_valid = sel_drum ? drum_evt_valid : met_evt_valid;
    wire [3:0]  b_axis  = sel_drum ? drum_evt_axis  : met_evt_axis;
    // …其余三个字段同理
```

| ✅ 好处 | ⚠️ 代价 |
|---|---|
| ⭐ **现场能切**（⭐ 不用重新构建） | ⚠️ **两个模块都例化** ⇒ ⭐ **多占一点资源** |
| ⭐ **⛔ 不改 `evt_merge`**（⭐ 就地复用源 B） | ⚠️ **要一个"切换源"** ⇒ ⭐ **可用串口命令**（⭐ `calib_cmd` 已通！） |

⭐ **资源代价（⭐ 实测基线）**：
```
· `u_metronome`：⭐ **Register 3 / LUT 3** —— ⚠️ **极小**（⭐ 它只"发事件"，⛔ 不做合成）
· 总量：⭐ Register 8777 / 60780 · LUT 13325 / 59904
⇒ ⭐ 鼓机**同量级**（⭐ 也是"发事件"）⇒ ✅ **代价可忽略**
📌 **依据**：⭐ 鼓机的"声音"是**用 `note_manager` 的振荡器/包络合成**的（⭐ 事件域架构）
   ⇒ ⚠️ 它的**模块本身很小**，⭐ 大头在**共享的**振荡器/包络上。
```

#### 🔴 但仍有**一个真问题**：`axis_id` 的分配

```
⚠️ 节拍器占 `0xE`（`top.v:558` 实测 `AXIS_ID(14)`）
⚠️ 鼓机若也用 `0xE` ⇒ ⭐ 二选一 ⇒ ✅ **没问题**
🔴 但**若将来想"两者都用"** ⇒ ⚠️ 鼓机必须另占一个 id（⭐ 那时只剩 `0xF`）
```

⭐ **决定**：⭐ **鼓机用 `0xF`**（⭐ 与节拍器的 `0xE` **分开**）——
✅ **理由**：⭐ 这样**将来若要"同时用"，⛔ 不用改 id**（⭐ 只需改 `evt_merge`）
⇒ ⭐ **多占一个 id，换将来不用返工**。

#### ⚠️ `RESERVED_N` 的决定（⭐ 修正）

```
⭐ 原算（两者同时）：节拍器 1 + 鼓机 4 = 5  ⇒ 提到 8
⭐ 现算（二选一）：max(1, 4) = 4  ⇒ ⚠️ 5 已经够
```

✅ **最终（⭐ 用户 2026-09-24 拍板）：⭐ 保持 `RESERVED_N = 5`，暂不改。**
* ⭐ 理由：⭐ **二选一 ⇒ 峰值需求只有 4**（⭐ 鼓机 4 个乐器同时响）
* ⭐ 若**将来要改** ⇒ ⚠️ **两处都要改**（⭐ `top.v:559` + `:1356`，⭐ 必须配对）
* ⚠️ **不够时的现象**：🔴 **静默丢音**（⭐ `note_manager` 分配不到就丢）
  ⇒ ⭐ 所以**要看 `drop_cnt_o`**（⭐ `K-106`：丢了看得见）




### 8.4 ⭐⭐ **为将来升级留门（⭐ 关键设计）**

⭐ **做法**：⭐ **`drum_gen` 内部先按"逻辑乐器 id"（0~3）设计**，
⭐ 然后在**唯一的输出映射处**转成 `4'hF` ⇒ ⭐ **将来扩 `AXIS_W` 时只改那一行**。

```verilog
// ⭐ 内部：4 个逻辑乐器
localparam [1:0] DRUM_KICK  = 2'd0;
localparam [1:0] DRUM_SNARE = 2'd1;
localparam [1:0] DRUM_HIHAT = 2'd2;
localparam [1:0] DRUM_CLAP  = 2'd3;

// ⭐⭐ 输出映射 —— 🔴 **这是【唯一】需要改的地方**
//   ⭐ 现在（方案 b）：⭐ 全部映射到 4'hF
wire [AXIS_W-1:0] evt_axis = 4'hF;
//   ⭐ 将来若扩 AXIS_W 到 5：⭐ 改成 5'h10 + {3'd0, drum_sel}
//      ⇒ ⚠️ 只改这一行，⛔ 不用重写鼓机
```

📌 **依据**：⭐ `metronome.v` 也是这个模式（⭐ `AXIS_ID` 是个 `parameter`）
⇒ ⭐ **同一种做法，好理解、好维护**。
