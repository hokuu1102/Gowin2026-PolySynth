# 上位机「引导模式」实施计划（2026-10-15）

> **需求方**：用户 2026-10-15
> **一句话**：在**灌谱页面**里选一条**引导轨**（只亮灯不出声），其余轨当**背景**正常播，
> 并播放一个**跟着谱面变速**的 4/4 节拍器。
> **关联**：`ESP32侧需求-引导模式改成上位机逐事件控制-20261015.md`（给 FPGA 侧的需求单）

---

## 一、目标与非目标

| | 内容 |
|---|---|
| ✅ **要** | ① 选一条**引导轨**（该轨音符**只进 LED 指引链、不出声**）<br>② 其余轨**当背景正常出声**<br>③ **4/4 节拍器**（用鼓机事件生成，跟着谱面 tempo map 走）<br>④ 开关可关 —— 关掉后与现在**完全一致** |
| ⛔ **不要** | 不改 64 位字的**字段宽度**、不动 `axis`/`vel`/`kind`/`timbre` 的语义、不改灌谱协议其它部分 |
| ⚠️ **前置** | FPGA 侧接受**保留位 `bit6` = 仅指引**（需求单已发）。在那之前 `bit6` 被忽略 ⇒ 引导轨**照常出声**，⛔ **不损坏任何现有功能** |

---

## 二、协议：`bit6` = 仅指引

```text
bit 63..44 tick(20) · 43..23 inc(21) · 22..19 axis(4) · 18..11 vel(8)
    · 10..9 kind(2) · 8..7 timbre(2) · 6 = 仅指引(新) · [5:0] 保留(0)
```

| bit6 | 谁 | FPGA 行为（改完后） |
|---|---|---|
| **1** | 用户选的**引导轨** | 只送 `guide_lamp`（LED），⛔ 不进 `seq_arb` ⇒ **不出声** |
| **0** | 其余轨 + **节拍器** + tempo 事件 | 照旧出声 |

## 四、节拍器怎么生成（最简单 4/4）

**默认音型**（用户："用鼓机手动搓一个，最简单的 44 拍就行"）：

| 件 | 落点（每小节 3840 tick） |
|---|---|
| Kick | `0` · `1920`（第 1、3 拍） |
| Snare | `960` · `2880`（第 2、4 拍） |

**可选音型**（下拉第二项）：HiHat `0 960 1920 2880`（每拍一下，像电子节拍器）。

**要点**

1. **跟着谱面变速**：节拍器是 **tick 制**事件 ⇒ 谱面的 `kind=2` 一变，节拍器自动跟着变快变慢 ✅
   （比 FPGA 内置节拍器好：那个是**固定 BPM**，还要靠 `'Q'` 命令设，而上位机够不到命令口）
2. **范围**：`0 ~ tickMax`（与谱面同长），第 1 小节起
3. ⚠️ **避让谱面鼓**：节拍器与谱面已有的**同一件**鼓若间隔 < 480 tick ⇒ **跳过节拍器那一下**
   （保住判据 ⑩：同一件鼓相邻 ≥480，否则后一下会被前一下的 `note_off` 掐掉）
   ⇒ 日志里报"避让 N 下"
4. **力度**：用 `drum_map.py` 里那四个**生效值**（kick 230 / snare 235 / hihat 175 / tom 220）——
   ⛔ 不是 MIDI 原始力度（那个在鼓机上是无效的）
5. **轴**：按**方案 B** 走 12/13/14/15（一件一轴）—— 上位机已实现，节拍器复用同一套映射

## 五、验证方案（判据必须能失败）

新增 `check_guide.js`，用**真实调用**（不是复刻）逐条判：

| # | 判据 | 失败会长什么样 |
|---|---|---|
| ① | 引导轨的字 `bit6==1`，数量 == 该轨音符数 × 2 | 置位漏了 / 置错轨 |
| ② | **其余轨**的字 `bit6==0`（逐轨统计） | 误伤背景轨 |
| ③ | 节拍器字：每小节 kick@0/1920、snare@960/2880，数量 == 小节数 × 4 | 音型写错 / 少小节 |
| ④ | **节拍器 + 谱面鼓**：同一件相邻 ≥ 480（判据 ⑩ 同口径） | 避让逻辑没生效 |
| ⑤ | 全曲 `bit6==1` 的字数 **> 0**（非空洞） | 开关没生效却"通过" |
| ⑥ | ⭐ **反向证伪**：把引导轨设成"全部轨" ⇒ 判据 ① 必须**红** | 判据恒真（假绿） |
| ⑦ | `score_word.py` 的 `load_events_hex` **接受**这份 hex（`problems` 为空） | B1 没改 ⇒ 自相矛盾 |

### 10.2 实测数字（测试曲 St. James Infirmary，10 小节）

| 场景 | 字数 | 仅指引字 | 节拍器 | 避让 |
|---|---|---|---|---|
| 引导模式**关** | 576 | 0 | 0 | — |
| 引导模式**开**（引导轨=吉他） | 636 | **72** | 31 | 49 |

- 72 = 吉他轨的事件数（36 音符 × on/off 各一）——**一个不多一个不少**，其余 564 个字 bit6 全 0
- 关掉时 576 字与改动前**逐字节相同**（可回退）
- 同一件鼓相邻落点最小 **480 tick**（含节拍器，不变量成立）

### 10.3 节拍器为什么要"避让 49 下"（重要，别当 bug）

这首谱**自带鼓轨**（踩镲 76 下走满八分）。节拍器的踩镲/底鼓落点与它重合 ⇒
若硬发，同一件鼓相邻 < 480 tick，**后一下会被前一下的 `note_off` 掐掉**（方案 B 只隔离跨件）。
⇒ 所以按"同一件相邻 ≥ 480"跳过。**结果：谱面自带鼓的谱，节拍器主要让位给谱面鼓**
（谱面鼓本身就是拍点）；**没有鼓轨的谱，节拍器满额发声**。

### 10.5 浏览器验证的边界（诚实记录）

- 类型化 `browser_*` 工具在本机只回一行摘要、**拿不到 tab 句柄** ⇒ 用不了；
- 旧 `page` 通道的 JS 执行**被驱动禁用**（只读可用）；
- 前台点击被 Windows 前台锁挡（点完瞬间前台被别的窗口抢回，驱动按契约拒绝）。
⇒ **"打开 MIDI 之后"的 UI 链路（下拉填充 / 状态行刷新）没能在浏览器里点出来**，
改为在 node 里**直接调页面真函数** `buildTrackPicker(conv)` 验证（判据 ⑥⑦⑧）——
同一份代码、同一个函数，⛔ 不是另写实现。要在真浏览器里点这条链路，需先把
`gd_track` 的下拉用真鼠标点开（需要能前台激活浏览器窗口的环境）。
