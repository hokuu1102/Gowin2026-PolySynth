# ⚡ 仿真加速：把 `calib_span` 的三个参数提到 `top.v`（2026-09-24）

> **起因**：⭐ 用户提问 —— *"仿真不是可以通过修改 parameter 的值来加速吗"*
> ✅ **对，而且这正是当前回归/变异测试慢的一个主因。**

---

## 〇、⭐ 实测证据（⭐ 不是推测）

```
🔴 tb_top_sound 单独跑了 108 秒（⭐ 其余 tb 都是几秒）
```

**根因链**：
```
⭐ top.v:841-847   calib_span #( .NCH(8), .N_ADC(2), .AXIS_TOTAL(16), .POS_W(12) )
   🔴 ⚠️ 【没传】WAIT_TIMEOUT_CLK / STABLE_NEED / VOTE_N
   ⇒ 用模块默认：
       WAIT_TIMEOUT_CLK = 50_000_000  ⇒ ⚠️ **1 秒仿真时间** @50 MHz
       STABLE_NEED      = 24
       VOTE_N           = 32
   ⇒ 🔴 每次跑到"等按键"的超时兜底 ⇒ **烧掉整整 1 秒仿真时间**
```

⚠️ **而 `tb_calib_span` 自己就传了小值**（`STABLE_NEED=4` / `VOTE_N=4`）
⇒ ⭐ **说明"改小参数加速仿真"这个手法，项目里【早就有先例】**，⭐ 只是**顶层没覆盖到**。

## 一之二、🔴🔴 **更严重的发现：`tb_top_sound` 漏传了 3 个加速参数**（⭐ 2026-09-24 补充）

### ⭐ 各 tb 的传参现状（⭐ 实测）

| ⭐ tb | ⭐ `PA_ON_DELAY` | ⭐ `DEMO_NOTE_DELAY` | ⭐ `DEMO_HOLD_CYC` | ⭐ `AUTOTARE_DELAY_CLK` |
|---|---|---|---|---|
| `tb_e2e_key_to_sound` | — | ✅ `DEMO_DELAY` | ✅ `200_000` | ✅ `100_000` |
| 🔴 **`tb_top_sound`** | 🔴 **漏** | ✅ `2000` | 🔴 **漏** | 🔴 **漏** |
| `tb_top_m0` | ✅ `PA_DELAY_TB` | — | — | — |
| `tb_wavetable_tone_top` | ✅ `32` | — | — | — |

### 🔴 漏传的代价（⭐ 算得出来）

```
🔴 DEMO_HOLD_CYC      = 50_000_000  ⇒ ⚠️ **1 秒**仿真时间
🔴 AUTOTARE_DELAY_CLK = 10_000_000  ⇒ ⚠️ **200 ms**
🔴 PA_ON_DELAY        =  1_048_576  ⇒ ⚠️ **21 ms**
                              ─────────────
                              ≈ **1.22 秒**（⭐ 仿真时间）
⇒ ⭐ 而 `tb_top_sound` 实测跑 **108 秒** ⇒ 🔴 **就是这么来的**
```

⭐⭐ **注意**：⭐ `tb_e2e_key_to_sound` **传全了** ⇒ ⭐ **说明这些参数本来就是为加速准备的**，
⚠️ **只是 `tb_top_sound` 漏了** —— ⭐ **这是个"照抄漏项"，⛔ 不是设计缺陷**。

### ✅ 补法（⭐ 简短）

```verilog
    top #(
        .PA_ON_AFTER_RESET (0),
        .DEMO_CHORD_ON     (1),
        .SOURCE_A_SEL      (1),
        .DEMO_NOTE_DELAY   (2000),        // ⭐ 已有
        // ⭐⭐ 2026-09-24 补：漏传的 3 个加速参数（⭐ 照 tb_e2e 的口径）
        .DEMO_HOLD_CYC       (200_000),
        .AUTOTARE_DELAY_CLK  (100_000),
        .PA_ON_DELAY         (32),
        .POLY_TARGET       (POLY),
        ...
```

⚠️ **对 `tb_top_sound` 的安全性说明**（⭐ 为什么可以改小）：
* ⭐ 它测的是**出声链**（`T57`），⭐ **不测功放时序**（⭐ 注释明说 `PA_ON_AFTER_RESET(0)` 只为音频）
  ⇒ ⭐ `PA_ON_DELAY` **改小无影响** ✅
* ⭐ 它测的是**演示和弦出声**，⭐ **不测自检和弦的"持续时长"**
  ⇒ ⭐ `DEMO_HOLD_CYC` **改小无影响** ✅（⚠️ 但要确认**判据没依赖"和弦响了 1 秒"**）
* ⭐ 它**不测标定** ⇒ ⭐ `AUTOTARE_DELAY_CLK` **改小无影响** ✅

🔴 **但必须验**：⭐ **改完跑一次 `tb_top_sound`** ⇒ ⭐ **判据仍是全 ok**（⭐ ⛔ 不许"应该没事"）。

### 1.1 ⭐ 改动清单（⭐ 3 处）

#### ① `rtl/top.v` —— 新增 3 个参数（⭐ 放在 `AUTOTARE_DELAY_CLK` 旁边）

```verilog
    // ⭐ `calib_span` 的**超时兜底**（clk 数；默认 50M = 1 s @50 MHz）
    //   ⚠️ 它是"等不到按键就放弃"的上界 ⇒ 🔴 **仿真里每次触发都要烧 1 秒仿真时间**
    //   📌 **提成参数**同样是为了**让 tb 能改小**（⭐ 照 `AUTOTARE_DELAY_CLK` 的先例）
    parameter integer SPAN_WAIT_TIMEOUT_CLK = 50_000_000,
    // ⭐ `calib_span` 的**稳定判定帧数**（默认 24 帧 ≈ 4.7 ms @196 µs/帧）
    parameter integer SPAN_STABLE_NEED      = 24,
    // ⭐ `calib_span` 的**投票帧数**（默认 32）
    parameter integer SPAN_VOTE_N           = 32
) (
```

#### ② `rtl/top.v` —— 例化处传下去（⭐ 行 841-847）

```verilog
        calib_span #(
            .NCH              (8),
            .N_ADC            (2),
            .AXIS_TOTAL       (16),            // ⭐ = NCH × N_ADC（⚠️ 参数自检要求相等）
            .POS_W            (12),
            // ⭐⭐ 2026-09-24：新增 3 个可调参数（⭐ 让 tb 能把仿真时间改小）
            .WAIT_TIMEOUT_CLK (SPAN_WAIT_TIMEOUT_CLK),
            .STABLE_NEED      (SPAN_STABLE_NEED),
            .VOTE_N           (SPAN_VOTE_N)
        ) u_calib_span (
```

#### ③ ⭐ tb 侧传小值（⭐ 至少这两个重 tb）

| ⭐ tb | ⭐ 建议值 | ⚠️ 理由 |
|---|---|---|
| `tb/top/tb_top_sound.sv` | `.SPAN_WAIT_TIMEOUT_CLK(50_000)`<br>`.SPAN_STABLE_NEED(4)`<br>`.SPAN_VOTE_N(4)` | ⭐ 这个 tb **不测 `calib_span`** ⇒ ⭐ 只要"不卡住"即可 |
| `tb/e2e/tb_e2e_key_to_sound.sv` | 同上 | ⭐ 同上 |
| ⚠️ **`tb/w3a/tb_calib_span.sv`** | ⭐ **⛔ 不改** | ⚠️ **它就是要测 `calib_span`** ⇒ 🔴 **必须用真值**（⭐ 否则测的不是交付配置 —— ⭐ 这正是 `K-124` 的教训！） |
| ⚠️ `tb/w3a/tb_uart_calib_chain.sv` | ⭐ **⛔ 不改** | ⭐ 同上（⭐ 它测标定链） |

⚠️ **⚠️ 关键纪律**：⭐ **"不测该模块的 tb"** 才能改小；
🔴 **"专门测它的 tb" 必须用真值** —— ⚠️ **否则就是 `K-124` 那个坑的翻版**。


⇒ ⭐⭐ **它就是在烧那 `DEMO_HOLD_CYC = 50_000_000` 的 1 秒仿真时间**。

📌 **意义**：⭐ 本文档的结论**不是静态分析出来的**，
⭐ 而是**在缺陷发生的那一刻实测抓到的** —— ⭐ 这比推算更有说服力。

⚠️ **而且 `M102` 让它更慢**：⭐ 删掉 `abort_i` ⇒ 标定链上的 tb 只能**等超时兜底**
⇒ 🔴 **正好撞上 `WAIT_TIMEOUT_CLK = 50_000_000`** ⇒ ⭐ **两个问题叠加**。
## 二、⭐⭐ 判据（⭐ 防"改了但没生效"）

| # | ⭐ 判据 | ⚠️ 不符怎么办 |
|---|---|---|
| **1** | ⭐ `tb_top_sound` 耗时 **从 108 s 降到 < 30 s** | ⚠️ 没降 ⇒ 说明参数没传到（⭐ 查例化） |
| **2** | ⭐ **48/48 仍然全过** | 🔴 不降反升 ⇒ ⚠️ 参数改得太小 ⇒ 时序前提不成立 |
| **3** | ⭐ **`tb_calib_span` 的判据仍然全过**（⭐ 它用真值） | 🔴 说明改动波及了它 |
| **4** | ⭐ `WAIT_TIMEOUT_CLK` 的**自检**（⭐ 若模块有 `PARAM_OK`） | ⚠️ 要确保改小后仍满足关系 |

⚠️ **判据 2 的陷阱**：⭐ `STABLE_NEED`/`VOTE_N` **改太小** ⇒
🔴 **可能让某些 tb 的"稳定性"前提失效** ⇒ ⭐ **先改 `WAIT_TIMEOUT_CLK`（⭐ 收益最大、风险最小）**，
⭐ **再动 `STABLE_NEED`/`VOTE_N`**（⭐ 逐个改、逐个验）。
