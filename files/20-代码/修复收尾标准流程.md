# 🔁 修复收尾标准流程（⭐ 每次修复后必做，2026-09-28 用户确认）

> ⭐ **用户原话**：「不仅仅是这一次，后面的每一次修复都要重复这个过程」
> ⇒ 本文是**强制流程**，⛔ 不是一次性任务。

---

## 〇、触发条件

**每一次** RTL/逻辑修复完成后（⛔ 不论大小），**必须**依次执行下列 5 步。

---

## 〇之二、⭐⭐ **增量式工作流**（用户 2026-09-28 追加要求）

> ⭐ **用户原话**：「每次修复完一个模块之后，就更新清单，继续修复接下来的问题，
> 以及审查列表里面存在疑问的问题。**审查列表里面的疑问处也要仔细观察，
> 以防修改到不应该改的部分**」

### 循环（⭐ 一个模块一轮，⛔ 不要一次改多个）

```
┌─→ ① 选一个【模块】作为本轮目标（⛔ 不要一次改多个模块）
│   ② ⭐ 先【审视清单里的疑问项】—— 这一步⛔ 不许跳
│      · 该缺陷**真的可达**吗？（对照用户的【实际硬件接线】）
│      · 有没有**互相矛盾的审计结论**？（两个子代理说法不同时，必须自己判）
│      · 改了会不会**动到不该动的部分**？（接口 / 语义 / 别人负责的模块）
│      · ⭐ 若"不可达"或"证据不足" ⇒ **不改**，只在清单里标注"待验证"
│   ③ 写【可机械判定的判据】（红→绿）
│   ④ 改 RTL（⭐ 用最稳健的修法，⛔ 不是最小改动）
│   ⑤ 跑判据（⭐ 必须先在【未修复】代码上确认它会红）
│   ⑥ ⭐ **更新清单**（已修/证伪/未修 三张表同步更新）
│   ⑦ 进入下一轮 → 回到 ①
└──
```

### ⭐ 步骤 ② 的硬要求（**防误改**）

| 检查 | 判据 |
|---|---|
| **可达性** | ⭐ 对照用户的实际接线：`只接一块 8 轴左手板 + 外置 DAC`；⛔ 无 LED/第二块板/右手板/串口/ESP32<br>⇒ 与左手板霍尔**无关**的源**不会主动发信息** ⇒ 相关缺陷标为"潜在" |
| **证据充分性** | ⭐ 必须有**代码级**或**仿真级**证据；⛔ 不接受"看起来可疑" |
| **矛盾裁决** | ⭐ 两个审计结论冲突时 ⇒ **自己写最小 tb 裁决**（⛔ 不要挑一个信） |
| **影响面** | ⭐ 改动的**下游消费者**是否都被覆盖？有没有别人（队友）负责的文件？ |
| **语义变更** | ⭐ 若改了某个 mask/标志的**语义** ⇒ 必须**全仓库 grep** 它的所有消费者 |

## 一、⭐ 流程（5 步，顺序执行）

### 第 1 步 · 逐文件复审

```
✅ 对每一个被改动的文件：
   · 复核 diff 的【正确性】—— 新写法是否真的修好了原缺陷（代码级推理）
   · ⭐ 复核是否【引入新缺陷】：
       - 位宽 / 符号 / 截断
       - 时序（同块内多次非阻塞赋值 ⇒ 后写覆盖先写；改动后这个依赖还在吗）
       - 复位覆盖是否完整（新寄存器有没有被复位）
       - for 循环里的非阻塞赋值是否互相覆盖
       - 有没有"改了一半"（旧信号残留、注释与实现不符、死代码）
   · ⭐ 列出该文件【仍然存在】的缺陷与可疑点（⛔ 不因"已修过"就略过）
```

### 第 2 步 · 跨文件复审

```
✅ 逐对相邻模块重新核对【接口契约】：
   位宽 / valid 语义 / 数据与 valid 拍序 / 握手 /
   复位 / 时钟使能 / 语义映射
⭐ 重点：修复是否【改变了跨模块契约】（例如某个 mask 的语义变了）
⭐ 明确回答：哪一条最可能解释【当前仍未解决的症状】
```

### 第 3 步 · ⭐ 生成「修复后审计列表」

```
✅ 客观、真实，⭐ 不隐瞒任何缺陷和可疑点
✅ 必含四张表：
   ① 已修复（每项带【可机械判定的判据】+ commit）
   ② ⭐ 被证伪的假设（走过的弯路也要记）
   ③ ⭐ 已知但未修复的问题（位置 / 严重度 / 可达性）
   ④ ⭐ 工作方法教训
```

### 第 4 步 · 记录经验

> ⭐ 下面三行指向**经验库**（另一个仓库 `桌面\经验\`），⛔ 不在本仓库 ⇒ 已加 `refcheck:ignore-line`。

```
✅ 过程 → 经验库 `fpga/TROUBLESHOOTING.md`（`T##`，顶部索引补行） <!-- refcheck:ignore-line -->
        ⭐ 必写：现象 / 假设 / 验证 / ⭐【失败尝试】/ 根因 / 回归结果
        ⭐ 失败路径本身就是经验，⛔ 不许省略
✅ 结论 → 按类型分流：
        · 逻辑/时序 → `fpga/FPGA逻辑调试经验集.md`（`L##`） <!-- refcheck:ignore-line -->
        · 工具/操作 → `fpga/FPGA工具使用经验.md`（`U##`） <!-- refcheck:ignore-line -->
        · 跨领域共性 → `共性问题集.md`（`C##`）
✅ 编码：⭐ **UTF-8 无 BOM**，写完回读首 3 字节确认
✅ Git：只 commit，⭐ 满 10 条新经验才自动 push
```

### 第 5 步 · 生成修复记录总结

```
✅ 文件：`files/20-代码/修复记录总结-<日期>.md`
✅ 必含：
   · 已修清单（文件 / 缺陷 / 修法 / ⭐ 判据 / commit）
   · ⭐ 根因与证据链（本文最重要的一节）
   · ⭐ 被证伪的假设
   · ⭐ 已知未修清单
   · ⭐ 工作方法教训
   · 修复后复审结论（指向 `审计-修复后-*.md`）
   · 验收判据 + ⭐ 上板验证建议
```

## 二、⚠️ 执行本流程时的硬约束

| # | 约束 | 理由 |
|---|---|---|
| **1** | ⛔ **改 `rtl/`/`tb/` 前必须确认没有回归在跑** | 我在回归运行期间改 `rtl/` ⇒ **两次回归被污染**（污染的指纹：某 tb 单独跑 PASS、回归里 FAIL） |
| **2** | ⭐ **判"相位/边界相关缺陷"必须精扫边界** | 粗步长 64 跳过 1023 ⇒ **假绿**（我一度误判"重触发不是挂音路径"） |
| **3** | ⭐ **单轴测试测不到多轴交互** | `q_cnt` 缺陷只在**相邻轴**同帧越阈时触发；现有 tb 用间距 4 的轴**恰好避开 ⇒ 假守护** |
| **4** | ⭐ **诊断 tb 不能混进验收集** | `tb_nm_leak` 必然超时（从未产出结论）、`tb_osc_phase` 是假警报 |
| **5** | ⚠️ **PowerShell 里 `[IO.File]::*` 必须用【绝对路径】** | ⭐ `cd` 只改 PowerShell 的位置，⛔ **不改 .NET 进程的工作目录** ⇒ 相对路径会解析到**会话工作区**（我因此白写了一次经验条目） |
| **6** | ⚠️ **`git commit -m` 里塞多行 + 中文 + 特殊符号会破坏引号** | 改用 `git commit -F <消息文件>`（UTF-8 无 BOM） |
| **7** | ⚠️ **PowerShell 重定向保存补丁会按 GBK 编码** | `git diff > file` 后再 `git apply` 报 "No valid patches"（中文被破坏） |
