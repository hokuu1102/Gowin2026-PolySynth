## 二、🔴 缺陷 1：看门狗必然触发（⭐ 已修，`a310700`）

### 2.1 现象

🔴 **上电后 5 秒**，**两次独立实测均稳定复现**：

```
I (3601) blebridge: drain task started (mode=B/pool)
E (8561) task_wdt: Task watchdog got triggered.
E (8561) task_wdt:  - IDLE0 (CPU 0)
E (8561) task_wdt: CPU 0: drain
Backtrace: 0x4204E3A6:... 0x40383FF6:... 0x4200DFA2:...
```

### 2.2 栈回溯（`xtensa-esp32s3-elf-addr2line`）

| 地址 | ⭐ 符号 |
|---|---|
| `0x40383FF6` | **`vTaskDelay`** (tasks.c:1611) |
| **`0x4200DFA2`** | ⭐⭐ **`task_drain` at `ble_main.c:484`** |

### 2.3 🔴 根因

**关键常数**（⭐ 从 `sdkconfig` 实测，⛔ 不是假设）：

```
CONFIG_FREERTOS_HZ = 100        ← ⭐ 1 tick = 10 ms（⚠️ 不是 1000！）
CONFIG_ESP_TASK_WDT_TIMEOUT_S = 5
```

**`pdMS_TO_TICKS()` 是整数除法** ⇒ 100 Hz 下：

| 写法 | 计算 | ⭐ 结果 |
|---|---|---|
| `pdMS_TO_TICKS(1)` | `(1*100)/1000` | 🔴 **0** |
| `pdMS_TO_TICKS(2)` | `(2*100)/1000` | 🔴 **0** |
| `pdMS_TO_TICKS(9)` | `(9*100)/1000` | 🔴 **0** |
| `pdMS_TO_TICKS(10)` | `(10*100)/1000` | ✅ 1 |

⇒ 🔴 **任何 < 10 ms 的值全部塌成 0**：

```
pdMS_TO_TICKS(1) = 0
  ⇒ vTaskDelay(0) —— ⚠️ 几乎不延时，只触发一次任务切换
  ⇒ 🔴 任务优先级 9（BLE_TASK_PRIO_DRAIN），远高于 IDLE（0）
  ⇒ 🔴 立刻被重新调度回来 ⇒ 【忙循环】
  ⇒ 🔴 同核 IDLE0 永远得不到 CPU
  ⇒ 🔴 IDLE 任务【正是靠运行来喂看门狗】
  ⇒ 🔴 5 s 后 TWDT 必然触发
```

⭐ **为什么必然发生**：该循环不依赖任何外部输入 —— **只要缓冲是空的就 1000 次/秒空转**。

### 2.4 受害点（⭐ 两处，均为优先级 9）

| # | 位置 | 写法 | ⭐ 塌成 |
|---|---|---|---|
| 1 | `ble_main.c` `task_drain()` | `vTaskDelay(pdMS_TO_TICKS(1))` | 🔴 0 |
| 2 | `pool.c` `task_pool_pump()` | `pdMS_TO_TICKS(BLE_POOL_PUMP_PERIOD_MS)`（=2） | 🔴 0 |

⚠️ **#2 更阴险**：`s_running` 初始为 `false` ⇒ 走 `else` 分支的 `pdMS_TO_TICKS(10)` = 1（✅ 勉强能跑）
⇒ **平时"看起来没事"，一旦 `s_running` 置位就变 0** ⇒ **潜伏型缺陷**。

### 2.5 ✅ 修法

在 `ble_config.h` 新增：

```c
#define BLE_DELAY_TICKS_AT_LEAST_1(ms) \
    ((pdMS_TO_TICKS(ms) > 0) ? pdMS_TO_TICKS(ms) : 1)
```

⭐ **语义不变**（"想等就得让出 CPU"），只把 < 1 tick 的请求抬到 1 tick。

### 2.6 ⚠️ 失败路径（⭐ 值得记）

| # | 我的判断 | ⭐ 结果 |
|---|---|---|
| 1 | 猜 `CONFIG_FREERTOS_HZ = 1000` ⇒ `pdMS_TO_TICKS(1)` = 1 tick ⇒ 只是"唤醒太频繁" | 🔴 **错了** |
| 2 | 据此提出"改成信号量/事件通知"（架构级改动） | 🔴 **被推翻** —— 根因比那简单得多 |
| 3 | 实测 `sdkconfig` 后修正：`HZ = 100` ⇒ `pdMS_TO_TICKS(1) = 0` | ✅ **真根因** |

> ⭐ **教训**：⚠️ **"推测根因"和"实测常数"是两件事**。
> 差点按错误假设做大改动；⭐ **先读 `sdkconfig` 再动手，成本低得多。**

## 三、🔴 缺陷 2/3/4：BLE 广播从未启动（⭐ 已修，`c7d03ad`）

### 3.1 现象

🔴 **手机扫不到 `FPGA2026-Synth`** —— 日志里**只有** `ready. scan for "..."`（⭐ 那只是**提示语**），
**完全没有** `advertising as "..."`。

### 3.2 ⭐ 三个缺陷叠加（⚠️ 互相掩盖，必须全修才见效）

#### 缺陷 A：广播数据里服务 UUID 长度填错

```c
.service_uuid_len = 2,
.p_service_uuid   = (uint8_t *)&gatt_service_uuid16,   // 🔴 uint16_t，只有 2 字节
```

🔴 **IDF 要求 `p_service_uuid` 指向【16 字节完整 UUID】** ⇒ 报 **`0x102 ESP_ERR_INVALID_ARG`**。

#### 缺陷 B：GAP 回调事件常量不匹配（🔴 最隐蔽）

配置用的是 `esp_ble_gap_config_adv_data_raw()`，它回调的是
**`ESP_GAP_BLE_ADV_DATA_RAW_SET_COMPLETE_EVT`（枚举值 = 4）**，
⚠️ 而 `switch` 只 `case` 了 **`ESP_GAP_BLE_ADV_DATA_SET_COMPLETE_EVT`（= 0）**
⇒ 🔴 **事件落到 `default` 分支 ⇒ `ble_start_advertising()` 永不调用。**

> ⭐ **教训**：**换 API（`adv_data` → `adv_data_raw`）时必须同步改回调里的事件常量** —— 两者是配对的。

#### 缺陷 C：🔴 漏调 `esp_bt_controller_mem_release(ESP_BT_MODE_CLASSIC_BT)`（⭐ 最终根因）

修完 A/B 后，广播**被调用但仍失败**：

```
I blebridge: adv data set (evt=4) -> start advertising
E BT_BTM: btm_ble_write_adv_enable_complete failed
E blebridge: adv start failed: 0xD
```

⭐ **IDF 源码里该失败的唯一条件**（`btm_ble_gap.c`）：

```c
void btm_ble_write_adv_enable_complete(UINT8 *p)
{
    if (*p != HCI_SUCCESS) {              // 🔴 唯一失败条件
        BTM_TRACE_ERROR("%s failed", __func__);
```

⭐ **根因**：**S3 硬件只有 BLE**，但 **IDF 默认为经典蓝牙预留控制器内存** ⇒
⚠️ **不释放 ⇒ 控制器内存偏紧 ⇒ 广播这类 activity 申请资源失败。**

⚠️ **IDF 官方【每一个】BLE 例子都有这一行**（如 `ble_ibeacon` 在 `controller_init()` 之前）：

```c
ESP_ERROR_CHECK(esp_bt_controller_mem_release(ESP_BT_MODE_CLASSIC_BT));
esp_bt_controller_config_t bt_cfg = BT_CONTROLLER_INIT_CONFIG_DEFAULT();
esp_bt_controller_init(&bt_cfg);
```

🔴 **本工程漏了。**

### 3.3 ⭐⭐ 定位方法（⭐ 本轮最有价值的收获）

🔴 **我在这一个 `0xD` 上【先猜了 4 次】，全部落空**：

| 我的归因 | ⭐ 实测结果 |
|---|---|
| ① BLE 5.0 扩展广播冲突 | 🔴 关掉后仍失败（已回退） |
| ② 回调事件常量 | ✅ 确实是真 bug，但**没解决 `0xD`** |
| ③ `BLE_MAX_ACT=1` 太紧 | 🔴 改成 6 后仍失败（已回退） |
| ④ 广播参数非法 | 🔴 参数与官方例子一致 |

⭐ **真正有效的方法是【对照实验】**：

```
① 烧 IDF 官方例子 examples/bluetooth/bluedroid/ble/ble_ibeacon
   ⇒ I IBEACON_DEMO: Advertising start successfully     ✅ 成功
   ⇒ ⭐ 证明"板子 / IDF / 射频都没问题" ⇒ 🔴 是我们代码的问题

② 确认官方例子与我们【唯一实质差异】——
   ⭐ 逐项 diff sdkconfig + 逐行对照源码
   ⇒ 发现官方在 controller_init 前有一行 mem_release，我们没有
```

> ⭐⭐ **教训（⭐ 这条最值钱）**：
> **"代码看起来对但就是不工作"时，先做对照实验 + 完整 diff，⛔ 不要逐个猜参数。**
> ⚠️ **"改了没效果"也不等于"这个改动无关"** ——
> 缺陷 A/B/C 互相掩盖，**修了前一个才看得见后一个**。
> ⇒ ⭐ **必须先确认"改动所影响的代码路径【真的执行到了】"。**

### 3.4 ⚠️ 附带修复：返回值被丢弃

原来 `esp_ble_gap_config_adv_data(&adv);` **丢弃了返回值** ⇒ 失败时**什么都看不到**。
⭐ **加上日志后，缺陷 A（`0x102`）立刻现形** ⇒ 后面才可能查到 B 和 C。

## 五、⚠️ 环境与工具坑（⭐ 操作层面）

### 5.1 🔴 `monitor` 是交互式终端，脚本抓不到日志

`build.ps1 -Action monitor` 实际执行 `idf.py monitor`，**占住终端不退出**（要 `Ctrl+]`）。
⇒ ⭐ **自动化场景改用"限时读串口"**（打开 → 收 N 秒 → 关闭）。

### 5.2 🔴 端口号会漂移，⛔ 不能写死

⚠️ **本机 `COM7`/`COM8` 是【蓝牙串行口】**（`BTHENUM\...`），
⭐ **真实下载口是 `COM29`**（`USB\VID_303A&PID_1001`）——
🔴 **而且 USB-TTL 插拔后端口会从 `COM30` 变成 `COM31`。**

⇒ ⭐ **每次操作前先查**：

```powershell
Get-PnpDevice -Class Ports -PresentOnly |
  Where-Object InstanceId -like '*VID_303A*' |
  Select-Object -ExpandProperty FriendlyName
```

### 5.3 ⚠️ 串口句柄要及时释放

⚠️ **反复开串口抓日志会导致句柄残留** ⇒ 🔴 **后续烧录报 `PermissionError(13)`**。
⇒ ⭐ **每次 `serial.Serial()` 后必须 `close()`**。

### 5.4 🔴 扫引脚时⛔ 不要碰 `GPIO38/48`

⚠️ **这两个脚在开发板上接的是【板载 RGB LED】（WS2812）**。
⭐ **我曾在引脚扫描固件里驱动它们** ⇒ 🔴 **两颗 WS2812 亮白光**。
⚠️ **而且 WS2812 是锁存型** ⇒ ⚠️ **烧回正常固件后灯仍保持该颜色，需重新上电才灭。**

### 5.5 📌 BLE 桥工具的 `COM11` 用法（⚠️ 未完全打通）

| 路径 | ⭐ 结果 |
|---|---|
| 手机 App → BLE → ESP32 | ✅ **通**（`ble_rx=9`） |
| 桥工具**界面发送框** → BLE → ESP32 | ✅ **通**（`ble_rx=9`） |
| **脚本 → `COM11` → 桥 → BLE → ESP32** | 🔴 **不通**（`ble_rx=0`） |

⭐ **诊断结论**：
- ✅ **桥工具的 BLE 收发正常**（界面发送已验证）
- ⚠️ **桥工具是"懒连接"**：**打开 `COM11` 时才建立 BLE 连接**
- 🔴 **`COM11` 不在 `pyserial` 的端口枚举里**（但能 `open()`）⇒ ⚠️ **虚拟串口对可能没真正建好**

⇒ ⭐ **待办**：⭐ **建议改用 Python + `bleak` 库直接走 BLE**（⛔ 绕开虚拟串口），
或者配好虚拟串口对驱动。

## 六、⭐ 诊断方法论（⭐ 可复用，建议入经验库）

| # | 方法 | ⭐ 用途 |
|---|---|---|
| **1** | ⭐⭐ **烧 IDF 官方例子做对照** | **区分"我们的代码问题" vs "板子/IDF/环境问题"** —— 最高效的一步 |
| **2** | ⭐ **完整 diff `sdkconfig`**（官方 vs 我们） | ⛔ 不要只盯自己怀疑的那一项 |
| **3** | ⭐ **逐行对照官方例子的源码** | 找"官方有、我们没有"的调用 |
| **4** | **引脚自证**（输入+下拉/上拉，读电平） | 判断某脚**有无外部连接** |
| **5** | **本机自环**（TX 短接 RX） | 验证 UART/引脚**本身**是否可用 |
| **6** | **引脚定位器**（轮流在某脚发标识） | ⭐ **反推"哪个物理针 = 哪个 GPIO"**，绕开丝印 |
| **7** | **RX 定位器**（全脚扫描，看哪个脚被拉低） | ⭐ **反推"对端的数据进了哪个脚"** |
| **8** | **GAP 回调打 event 编号** | ⭐ **一眼看出事件常量对不对**（`evt=4` vs `case 0`） |

> ⚠️ **方法 4/5/6/7 的代码是一次性诊断工具，⛔ 不入库**（用完即删）。
> ⭐ **但方法本身值得记**：它们能在**不依赖外部设备**的前提下定位引脚级问题。
