## 〇、⭐ 一句话

> 🔴 **上机第一晚抓到一个【必然触发】的固件缺陷**（不是偶发）——
> ⭐ **`pdMS_TO_TICKS()` 的整数除法在 100 Hz 下把"小延时"全塌成 0** ⇒
> **忙循环饿死 IDLE 任务** ⇒ **Task watchdog 必然触发**。
> ✅ **已定位、已修、已重烧验证**（`a310700`，本地 commit，⛔ 未 push）。

## 二、🔴 缺陷：看门狗必然触发（⭐ 已修）

### 2.1 现象

🔴 **上电后 5 秒**，稳定复现（✅ **两次独立实测均触发**）：

```
I (3601) blebridge: drain task started (mode=B/pool)
E (8561) task_wdt: Task watchdog got triggered. The following tasks/users did not reset the watchdog in time:
E (8561) task_wdt:  - IDLE0 (CPU 0)
E (8561) task_wdt: Tasks currently running:
E (8561) task_wdt: CPU 0: drain
E (8561) task_wdt: CPU 1: IDLE1
Backtrace: 0x4204E3A6:0x3FC9C6B0 0x4204E7BC:0x3FC9C6D0 0x403778E9:0x3FC9C700
           0x40383FF6:0x3FCBB140 0x4200DFA2:0x3FCBB160 0x40382429:0x3FCBB180
```

⭐ **时序**：`drain task started` @ 3601 ms → 看门狗 @ 8561 ms ≈ **5 秒**（= `CONFIG_ESP_TASK_WDT_TIMEOUT_S`）。

### 2.2 栈回溯（⭐ `xtensa-esp32s3-elf-addr2line` 解出）

| 地址 | ⭐ 符号 |
|---|---|
| `0x4204E3A6` | `task_wdt_timeout_handling` (task_wdt.c:436) |
| `0x4204E7BC` | `task_wdt_isr` (task_wdt.c:509) |
| `0x403778E9` | `_xt_lowint1` (xtensa_vectors.S:1240) |
| **`0x40383FF6`** | **`vTaskDelay`** (tasks.c:1611) |
| **`0x4200DFA2`** | ⭐⭐ **`task_drain` at `ble_main.c:484`** |
| `0x40382429` | `vPortTaskWrapper` (port.c:139) |

⇒ ⭐ **卡点在 `task_drain` 的 `vTaskDelay` 上**（⚠️ 那正是"缓冲空时"的分支）。

### 2.3 🔴 根因（⚠️ 中途推翻过一次结论，见 §2.5）

**关键常数**（⭐ 从 `sdkconfig` 实测，⛔ 不是假设）：

```
CONFIG_FREERTOS_HZ = 100        ← ⭐ 1 tick = 10 ms（⚠️ 不是 1000！）
CONFIG_ESP_TASK_WDT_TIMEOUT_S = 5
CONFIG_ESP_TASK_WDT_CHECK_IDLE_TASK_CPU0 = y
```

**`pdMS_TO_TICKS()` 是整数除法** ⇒ 在 100 Hz 下：

| 写法 | 计算 | ⭐ 结果 |
|---|---|---|
| `pdMS_TO_TICKS(1)` | `(1 * 100) / 1000` | 🔴 **0** |
| `pdMS_TO_TICKS(2)` | `(2 * 100) / 1000` | 🔴 **0** |
| `pdMS_TO_TICKS(9)` | `(9 * 100) / 1000` | 🔴 **0** |
| `pdMS_TO_TICKS(10)` | `(10 * 100) / 1000` | ✅ 1 |

⇒ 🔴 **任何 < 10 ms 的值全部塌成 0**。

**因果链**：

```
pdMS_TO_TICKS(1) = 0
  ⇒ vTaskDelay(0) —— ⚠️ 几乎不延时，只触发一次任务切换
  ⇒ 🔴 该任务优先级 9（= BLE_TASK_PRIO_DRAIN），远高于 IDLE（0）
  ⇒ 🔴 立刻被重新调度回来 ⇒ 【忙循环】（每秒上千次）
  ⇒ 🔴 同核 IDLE0 永远得不到 CPU
  ⇒ 🔴 IDLE 任务【正是靠运行来喂看门狗】
  ⇒ 🔴 5 s 后 TWDT 必然触发
```

### 2.4 ⭐ 为什么它【必然发生】（⭐ 这条最关键）

⚠️ **该循环不依赖任何外部输入** —— 只要**缓冲是空的**（⭐ **没接 USB-TTL 时恒为空**），
`task_drain` 就 1000 次/秒空转 ⇒ **一上电、5 秒后必爆**。

⇒ ⭐ **这不是"运气不好撞上的偶发问题"，而是"不接数据源就 100% 复现"的确定性缺陷。**

### 2.5 ⚠️ 失败路径（⭐ 值得记：我第一次的判断是【错的】）

| # | 我的判断 | ⭐ 结果 |
|---|---|---|
| **1** | 猜 `CONFIG_FREERTOS_HZ = 1000` ⇒ `pdMS_TO_TICKS(1)` = **1 tick** ⇒ 只是"唤醒太频繁" | 🔴 **错了** —— 实测 `HZ = 100` |
| **2** | 据此提出"倾向改成信号量/事件通知"（架构级改动） | 🔴 **被推翻** —— 根因比那简单得多 |
| **3** | 实测 `sdkconfig` 后修正：`HZ = 100` ⇒ **`pdMS_TO_TICKS(1) = 0`** | ✅ **这才是真根因** |

> ⭐ **教训**：⚠️ **"推测根因"和"实测常数"是两件事**。
> 我差点按错误假设去做一个大改动；⚠️ **先读 `sdkconfig` 再动手，成本低得多。**
> （⭐ 与经验库 `C45`"防御性代码从不被触发 = 假安全"同源：**判据要能被证伪**。）

### 2.6 受害点（⭐ 两处，**都是无条件空转**）

| # | 位置 | 写法 | ⭐ 塌成 |
|---|---|---|---|
| **1** | `ble_main.c` `task_drain()` | `vTaskDelay(pdMS_TO_TICKS(1))` | 🔴 **0** |
| **2** | `pool.c` `task_pool_pump()` | `vTaskDelay(pdMS_TO_TICKS(BLE_POOL_PUMP_PERIOD_MS))`<br>（`= 2`） | 🔴 **0** |

⚠️ **两处优先级都是 9**（`BLE_TASK_PRIO_DRAIN = 9`）⇒ **两个任务一起饿死 IDLE0**。

⚠️ **注意 `task_pool_pump` 的隐蔽性**：`s_running` 初始为 `false` ⇒ 走 `else` 分支的
`pdMS_TO_TICKS(10)` = **1**（✅ 勉强能跑）⇒ ⚠️ **它平时"看起来没事"，一旦 `s_running` 置位就变 0**。
⇒ ⭐ **这是"潜伏型"缺陷，比 `task_drain` 更阴险。**

### 2.7 ✅ 修法（⭐ 已实现并验证）

⭐ **在 `ble_config.h` 新增一个"至少 1 tick"的宏**：

```c
#define BLE_DELAY_TICKS_AT_LEAST_1(ms) \
    ((pdMS_TO_TICKS(ms) > 0) ? pdMS_TO_TICKS(ms) : 1)
```

**为什么选它（⛔ 而不是改成信号量/事件）**：

| 维度 | ⭐ 本方案 | ⚠️ 信号量方案 |
|---|---|---|
| 改动面 | ✅ **3 处、42 行**（含注释） | 🔴 要动 BLE 回调 + 缓冲写入路径 |
| 语义 | ✅ **不变**（"想等就得让出 CPU"，只是把 <1 tick 抬到 1 tick） | ⚠️ 要重新设计唤醒条件 |
| 风险 | ✅ **低** | ⚠️ 中（动到中断/回调路径） |
| 是否除根 | ✅ **是**（0-tick 忙循环消失） | ✅ 是 |

⭐ **结论**：**根因是"延时为 0"，不是"架构不对"** ⇒ ⭐ **修延时即可，⛔ 不该为此动架构。**
（⚠️ 这也纠正了我 §2.5 里那个"倾向架构级改动"的错误倾向。）

### 2.8 ✅ 验证结果

| | 修复前 | ✅ 修复后 |
|---|---|---|
| Task watchdog | 🔴 `E (8561) task_wdt` **稳定复现** | ✅ **无告警** |
| `mode` | B / POOL | ✅ B / POOL（不变） |
| `baud` | 1000000 | ✅ 不变 |
| PSRAM | 8MB | ✅ 不变 |
| GATT | OK | ✅ 不变 |
| 体积 | `791120` B | ✅ `791136` B（**+16**，符合预期） |

⭐ **同一块板、同一端口、同样不接外设** ⇒ **唯一变量就是那 3 处改动** ⇒ 因果明确。

## 三、⚠️ 一处【已发现但刻意未改】的同类问题

🔴 **`ble_main.c:541`：`vTaskDelay(pdMS_TO_TICKS(BLE_TX_GAP_MS))`，`BLE_TX_GAP_MS = 2`** ⇒ 同样塌成 **0**。

⚠️ **但我没有改它**，理由（⭐ 有意为之，⛔ 不是遗漏）：

| # | 理由 |
|---|---|
| **1** | ⚠️ **它的触发条件不同** —— 位于 `task_uart_to_ble`（优先级 8），**只在真收到 UART 数据且已连接时**才进循环 ⇒ ⛔ **不是无条件空转**，**不是**本次看门狗的原因 |
| **2** | ⭐ **"一次只改一个变量"** —— 同时改会让"修复是否有效"的因果变糊 |
| **3** | ⚠️ **它有真实风险**：整曲 5200+ 包时该循环连续跑很久，⚠️ **同样可能饿死 IDLE** |

⇒ ⭐ **待办**：灌数据实测时**重点观察**这一处；⚠️ 若出现看门狗，**这就是第一嫌疑**。
（⭐ 修法与 §2.7 相同，改一个宏即可。）

## 五、🔴 一条重要的环境事实（⚠️ 会影响后续操作）

⭐ **下载口走的是【原生 USB】**（`USB mode: USB-Serial/JTAG`）⇒ 用的是 S3 的 `GPIO19/20`。

⇒ **推论**（✅ 对后续是**好消息**）：

| 用途 | 引脚 | ⭐ 是否受影响 |
|---|---|---|
| 下载/烧录/日志 | **原生 USB（GPIO19/20）** | — |
| 给 FPGA 的 UART1 | `GPIO17`(TX) / `GPIO18`(RX) | ✅ **不受影响，仍空着** |
| 给串口屏的 UART2 | `GPIO4`(TX) / `GPIO5`(RX) | ✅ **不受影响** |

⇒ ⭐ **USB-TTL 当"假 FPGA"接 `GPIO17/18` 的方案【仍然成立】**，⛔ 与下载口不冲突。

## 六、⚠️ 实测发现的另一处配置疑点（⚠️ 未验证，仅记录）

```
W (1117) spi_flash: Detected size(16384k) larger than the size in the binary image header(2048k).
         Using the size in the binary image header.
```

🔴 **实际 flash = 16 MB，但映像头写的是 2 MB** ⇒ 固件**只用了 2 MB**。

| 判断 | ⭐ 说明 |
|---|---|
| ⚠️ **当前是否阻塞** | ⭐ **不阻塞** —— 分区表 `factory` = 1 MB，app 只用 0.79 MB |
| ⚠️ **潜在风险** | 🔴 **若将来要往 flash 里放曲谱/字库**，⚠️ **2 MB 的头会白白浪费 14 MB** |
| ⭐ **怎么办** | ⚠️ **暂不改**（⛔ 与本次缺陷无关，改了混淆因果）⇒ ⭐ **记为待办** |
