# LED 指引「示范—重复」模式：最小改动方案（2026-10-16）

> 结论先行：**可行，且 FPGA 侧零改动、音频合成主链路零改动**。
> 理由：这个模式所需的三个机制**全都已存在**（下表 §一），
> 唯一的新增工作是把"示范段 / 跟奏段"分两次下发，**全在 `esp32/tools/score_studio.html` 一个文件里完成**。

---

## 一、现有数据流（逐条实测，非推测）

```
上位机 score_studio.html ──BLE──> ESP32 pool.c(缓冲+补发) ──UART 0xA5 帧(64 位字)──> FPGA
   每条事件字：
     [63:44] tick  [43:23] inc  [22:19] axis  [18:11] vel  [10:9] kind
     [8:7] timbre(旋律音色 / 鼓=drum_type)  [6] guide_only  [5] is_drum  [4:0] note_off5
                                                                          │
                            beat_gen(PPQN=960 相位累加器，run/pos_reset/tick_inc 外供)
                                        │ tick
                                        ▼
                            play_seq(按事件 tick 吐事件，支持逐事件提前 960 tick)
                                        │
                     ┌──────────────────┴───────────────────┐
                     ▼                                      ▼
        seq_arb(出声，唯一接触音频链路的地方)        guide_lamp(LED 指引)
        note_off5 + transpose_semi ──> NOTE2KEY 表 ──> guide_key_o[15:0]
```

### 三条决定性实测（都带出处）

| # | 事实 | 出处 |
|---|---|---|
| 1 | ⭐ **`guide=1`(bit6) 的事件 FPGA 现在就已经"只亮灯不出声"** | `top.v:5607` `.score_valid_i(SCORE_UART_ENABLE & ~guide_only_r & ~evt_guide_only …)`、`:5103` `ps_evt_timbre_valid = ps_note_valid & ~evt_guide_only`、`:1638` `evt_guide_only = ps_note_data[6]` |
| 2 | **LED 指引只吃 `play_seq` 的事件**（LED 亮/灭完全由"下发了什么事件"决定） | `top.v:1609` `ps_note_valid → seq_arb + guide_lamp`（同源）、`:643` |
| 3 | **LED 支持"灯比声音早一拍"**（逐事件提前 960 tick，现成） | `play_seq.lead_i` / `lead_sel_i`、`top.v:2637-2641` `ps_lead` / `ps_lead_evt` |

**另外三条支撑事实**

- `guide_lamp` 的键位来自 **`note_off5`**（`note_after = 45 + note_off5 + transpose_i`），**不是轴号**；
  且 `key_active_i`（按住的键）优先级最高、会消隐 ⇒ **跟奏阶段"提示该按哪个键"正是它本来的语义**。
- `guide_lamp` 的清灯只有两条路：**`note_off(key_valid)` 与 `rst_n`**（`guide_lamp.v:316-343`）
  ⇒ 想让 LED **按节奏顺序亮灭**，就必须下发 `note_off`（见 §三 设计点）。
- 节拍器由 **FPGA 本地**驱动（`met_on_r`，按键/命令），**不依赖灌谱旋律事件** ⇒ 跟奏段停旋律不影响节拍器。

## 二、为什么这需求 = 换"下发的事件序列"

| 你的需求 | 现状（实测） | 是否需要改动 |
|---|---|---|
| 示范阶段：自动播放片段，LED 与发声音符同步亮 | 正常灌谱即此行为 | ⛔ 不改 |
| 跟奏阶段：停止自动播放旋律 | 下发 `guide=1` 的事件 ⇒ 不出声（实测 1） | ⛔ 不改（改下发内容） |
| 跟奏阶段：保留节拍器 | 节拍器走 FPGA 本地通路 | ⛔ 不改 |
| 跟奏阶段：按相同节奏顺序提示 LED | `guide_lamp` 只吃事件（实测 2）⇒ 继续下发事件即继续亮灯 | ⛔ 不改 |
| BPM / 音符时值 | 照旧下发 tempo 事件 + `tick_inc`（上位机 `bpmToTickInc()` 与 mid2evt 同口径） | ⛔ 不改 |
| 不假设旋律固定长度 | 示范段长度 = 前 2 小节的**实际事件 tick 上界** | ✅ 新代码 |

## 三、改动清单（只动一个文件）

**文件**：`esp32/tools/score_studio.html`（灌谱通路的上游，卷帘/组包/上传的唯一入口是 `visibleWords`）

| # | 位置 | 改什么 | 量 |
|---|---|---|---|
| 1 | 引导面板（`gd_*` 控件区） | 新增模式开关 **「示范—重复」**（勾选即启用），可复用现有"引导轨/范围/鼓声/节拍器"控件 | 小 |
| 2 | `visibleWords()` | 分段：`tick < demoEnd` 的事件**原样**；`tick ≥ demoEnd` 的事件**置 `guide = 1`** | 小 |
| 3 | `visibleWords()` | `demoEnd = min(2 × conv.barTicks, tickMax)`（**实际事件 tick，⛔ 不假设固定长度**）；`conv.barTicks` 已导出（缩放后 = 3840） | 小 |
| 4 | 组包 `packWord(...)` | 无需改：`guide` 入参已存在（`:1311-1314` 现成用法） | 0 |
| 5 | `esp32/ble/main/pool.c` | ⛔ 不改（它只缓冲 + 补发，不解释事件语义） | 0 |
| 6 | FPGA RTL | ⛔ 不改 | 0 |

### 演示长度怎么算（⛔ 不假设固定长度）

```
demoEnd = min(demoBars × conv.barTicks, 最后一个事件的 tick)
其中 demoBars 默认 2；conv.barTicks = 3840（960 PPQN × 4 拍，division 缩放后恒定）
⇒ 本测试曲：2 × 3840 = 7680，第 2 小节末
```

⚠️ 若曲子**不足 2 小节**，`demoEnd` 自动退到"最后一个事件 tick" ⇒ 全部当示范、没有跟奏段
（并在 UI 上提示一句"曲子太短，没有跟奏段"）。

## 四、需要你拍板的设计点（⛔ 不自行决定）

### 设计点 A：跟奏段的音符**带不带 `note_off`**？

| 方案 | LED 行为 | 适合 |
|---|---|---|
| **A1 带（推荐）** | 每个音结束后该灯熄灭 ⇒ **按节奏顺序亮灭**，用户知道"该换下一个" | 顺序跟奏教学 |
| A2 不带 | 灯一旦亮了就**长亮**（`guide_lamp` 只能被 note_off/复位清） | 只要"提示用哪些键" |

⇒ 推荐 **A1**：你的需求原文是"按相同节奏**顺序**提示"，A1 才给出顺序感。
📌 A1 还顺带规避了一个已知坑：漏发 `note_off` 会让灯永不熄灭（正是 FPGA 线那封
「LED 挂灯上游缺口」在治的问题）。

### 设计点 B：示范段要不要**出声**？

- **B1 出声（推荐）**：示范段 = 普通事件（`guide=0`）⇒ 又出声又亮灯，用户先听一遍再跟。
- B2 静默：示范段也 `guide=1` ⇒ 只亮灯不出声（等于整曲都是跟奏，没有"示范"）。
⇒ 推荐 **B1**（否则不叫"示范"）。

### 设计点 C：`note_off5` 覆盖不到的音怎么办？

`note_off5` 可弹范围 **MIDI 45..75**（`NOTE5_BASE=45`、`NOTE5_MAX-1=30`），
越界写 **31 哨兵 = 不点灯**（已实现，实测本曲 68 条哨兵）。

⇒ 若旋律有 **< 45 或 > 75** 的音，那些音的 LED **不会亮**（键盘上也没这个键，本就无从提示）。
📌 这不是本功能的缺陷，但**要在 UI 上提示**"有 N 个音超出可弹音域、无 LED 提示"。
⚠️ 要扩范围就得改 FPGA 的 `NOTE2KEY` 表（两张 16 项表 = 键盘 16 键），**属 FPGA 侧改动，本轮不做**。

### 设计点 D：跟奏段要不要**提前一拍**亮灯？

`play_seq` 支持逐事件提前 960 tick（实测 3）。对"跟奏"而言提前亮灯能让用户**先看后按**，
但会让"顺序提示"与节拍错开一拍。

⇒ 建议 **默认不提前**（跟奏要的是同步提示）；做成可选开关，默认关。

## 五、验证方案（改完怎么证明它真的对）

| # | 判据 | 怎么测 |
|---|---|---|
| 1 | 示范段出声 + LED 亮 | 测试曲：示范段（前 7680 tick）解出的字里 `guide=0`、`note_off5` 正确 |
| 2 | 跟奏段只亮灯不出声 | 跟奏段所有旋律事件 `guide=1`，且 `packWord` 后 bit6=1 |
| 3 | 节拍器全程不受影响 | 节拍器事件（`srcTrack=-2`）在两段都照常下发、`guide=0` |
| 4 | 鼓/音色事件不被误标 | 鼓事件 `guide=0`（鼓本就不出声于旋律语义，且 `is_drum=1` 与 guide 独立） |
| 5 | tempo 事件保持 `guide=0` | tempo 是速度事件，`guide=1` 会让它不出声但会破坏 tick 基准 |
| 6 | 短曲子安全 | 造一个 < 2 小节的谱：`demoEnd` 退到末尾、UI 提示、不崩 |
| 7 | 不破坏现有判据 | 跑全套：`check_drum_split --hex/--mid` + `verify_piece` 37 + `check_roll` 39 + `check_guide` 20 |
| 8 | LED 与声音同步 | 上位机不能验（要上板）：`guide_lamp` 与 `seq_arb` 同源同拍（实测 2）⇒ 结构上同步；上板复核 |

📌 判据 7 是硬门槛：本功能是**上位机事件构造**的改动，⛔ 不许让任何既有判据变红。

## 六、风险与边界（如实列）

1. ⚠️ **`guide=1` 的语义现在有两处消费者**：`score_valid_i`（不出声）+ `evt_guide_seen_r`（引导模式的状态）。
   ⇒ 若引导模式也开着，`guide=1` 的事件会被引导模式的统计读到。
   **处置**：本功能与引导模式**互斥**（UI 上勾了"示范—重复"就禁用引导模式开关），⛔ 不叠加。
2. ⚠️ **跟奏段继续下发事件 = 占 BLE 带宽与 pool**：与正常灌谱同量级（同一份事件走一遍），
   不需要额外缓冲（`pool.c` 不改）。
3. ⚠️ **`note_off5` 越界不亮灯**（设计点 C）：要在 UI 报数，⛔ 不静默。
4. ⛔ **不动的东西**（明确划界）：FPGA RTL、音频合成主链路（`seq_arb` 之后的一切）、
   `pool.c` 的事件缓冲逻辑、`guide_lamp` 内部。
