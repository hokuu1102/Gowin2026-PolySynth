# 🔌 `uart_tx` FIFO 设计（⭐ 解决"事件挨太近会丢"）

> **日期**：2026-09-24 凌晨
> **起因**：🔴 **已知边界** —— `top.v` 的回传调度器**没有 FIFO**
> ```
> ⚠️ 波特率 1 Mbps ⇒ 一个字节 ≈ 10 µs
> 🔴 若两个回传事件挨得 < 10 µs ⇒ ⚠️ 后者被【静默丢弃】
> ```
> **状态**：⚠️ **本场景（人按键）够用** · 🔴 **但发连续数据（如波形）时必须加**
> **优先级**：⬜ **低**（⭐ 不是当前瓶颈，⚠️ 先记录方案）

---

## 〇、⭐⭐ 一句话

| 项 | 结论 |
|---|---|
| ⭐ **现在会丢吗** | ⚠️ **会，但概率极低** —— ⭐ 回传事件来自**人的操作**（⭐ 按键速度是**毫秒级**，≫ 10 µs） |
| 🔴 **什么时候必须加** | ⭐ **要回传连续数据时**（⭐ 波形 / 频谱 / 事件流的逐条确认） |
| ⭐ **建议** | ⬜ **现在不加**（⭐ 一次只改一个变量）；⚠️ 但**方案先写好**（⭐ 本文） |

---

## 一、⭐⭐ 现状（⭐ 实测）

### 1.1 ⭐ 回传调度器（`top.v`）

```verilog
// ⭐ 优先级编码（⭐ 高 → 低）
wire rep_req = ev_need | ev_reject | ev_axis_ok | ev_done
             | cmd_tare_req | cmd_span_req | cmd_abort_req
             | sp_start_rejected | (at_done & ~at_done_r);

assign tx_req  = rep_req;        // ⭐ 单拍请求
assign tx_byte = rep_byte;
```

### 1.2 🔴 丢失机制

```verilog
// uart_tx.v 的行为：⭐ 忙时【忽略】start
if (!active_q) begin
    if (tx_start_i) begin ... end     // ⭐ 只在空闲时接受
end
```

⇒ 🔴 **`tx_busy = 1` 期间来的 `tx_req` 直接消失**（⚠️ **没有任何计数**）。

📌 **这违反 `K-106`**（⭐ 纪律原文：*"任何会失效的路径都必须可观测 —— ⛔ 不静默"*）：
⚠️ 现在**丢了也不知道丢了**。

---

## 二、⭐⭐ 两个方案（⭐ 按代价排序）

### 方案 ① ⭐⭐ **加 FIFO**（⭐ 能真正解决）

```
⭐ 结构：
   rep_req/rep_byte ──> 【深度 N 的 FIFO】──> uart_tx.tx_start_i / tx_data_i
                        （⚠️ 满 ⇒ 丢 + drop_cnt++）
```

| 参数 | ⭐ 建议值 | ⚠️ 依据 |
|---|---|---|
| **深度** | ⭐ **8** | ⭐ 最坏情形："16 轴标定"时**每轴 2 个事件**（轴号 + 通过/被拒）<br>⇒ ⚠️ 但那是**人的速度**（⭐ 每轴至少几百 ms）⇒ ⭐ **8 足够** |
| **位宽** | ⭐ **8 bit**（⭐ 只存字节） | ⭐ 不需要存别的 |
| **资源** | ⭐ **8×8 = 64 bit** | ⭐ **可忽略** |

⚠️ **必须同时加"丢包可见"**：
```verilog
output reg [15:0] tx_drop_cnt_o;   // ⭐ 溢出丢包数（饱和）
output reg        tx_overflow_o;   // ⭐ sticky，复位清
```
📌 **依据**：⭐ `K-106` + ⭐ `evt_merge` 的**既有做法**（⭐ 它有 `drop_cnt_o` + `overflow_o`）
⇒ ⭐ **照抄那个模式**（⭐ 项目内一致性）。

### 方案 ② ⭐ **只加"丢包计数"，⛔ 不加 FIFO**（⭐ 最小改动）

| ✅ 好处 | ⚠️ 代价 |
|---|---|
| ⭐ 改动极小（⭐ 加 1 个计数器 + 1 个 sticky） | 🔴 **还是会丢**（⭐ 只是**丢得可见**） |
| ⭐ **满足 `K-106`**（⛔ 不静默） | ⚠️ 但本场景**根本丢不了** ⇒ ⭐ 加了也只是"以防万一" |

---

## 三、⭐ 我的建议：**先做方案 ②，⚠️ 真需要连续回传时再做 ①**

⚠️ **理由**：

| # | 理由 |
|---|---|
| **1** | ⭐ **当前场景丢不了** —— ⭐ 回传事件全是**人按键触发**（⭐ 毫秒级）⇒ ⚠️ 距 10 µs 差 100 倍 |
| **2** | ⭐ **方案 ② 满足纪律** —— ⭐ `K-106` 要求"**可观测**"，⛔ 不是"永不丢" |
| **3** | ⚠️ **FIFO 会引入新状态**（⭐ 读写指针、满/空判断）⇒ ⚠️ **新的变异靶点 + 新的卡死可能**（⭐ 本轮的教训：**每个"等待"都要有上界**） |
| **4** | ⭐ **一次只改一个变量** —— ⭐ 上板在即 |

📌 **触发条件**（⭐ 何时该做方案 ①）：
> 🔴 **当出现"需要连续回传"的需求时** —— ⭐ 例如：
> * ⚠️ 把 `pos` 的实时值回传（⭐ 做波形显示）
> * ⚠️ 把 `evt_uart_rx` 收到的每条曲谱事件**回显**给 PC（⭐ 调试用）
> * ⚠️ 标定进度**连续**回传（⭐ 现在只是"逐轴一个字符"，⭐ 够）
> 那时 ⭐ **必须做 ①**（⭐ 因为这时**真的会丢**）。

## 四、⭐ 方案 ② 的具体改法（⭐ 很小）

```verilog
// ⭐ 在回传调度器旁边加：
reg [15:0] tx_drop_cnt_q;
reg        tx_overflow_q;

always @(posedge clk) begin
    if (!rst_n_sync) begin
        tx_drop_cnt_q <= 16'd0;
        tx_overflow_q <= 1'b0;
    end else if (rep_req && tx_busy) begin
        //   ⭐ `uart_tx` 正忙 ⇒ 本次请求【会被丢掉】⇒ ⭐ 记下来（⛔ 不静默）
        //     ⚠️ 这就是 `K-106`：会失效的路径必须可观测
        tx_drop_cnt_q <= (tx_drop_cnt_q == 16'hFFFF) ? 16'hFFFF
                                                     : (tx_drop_cnt_q + 16'd1);
        tx_overflow_q <= 1'b1;
    end
end
```

⚠️ **注意两件事**：
1. ⭐ **饱和自增**（⛔ 不回绕）—— ⭐ 与 `evt_uart_rx` 的 `sat_inc16` 同一做法
2. ⚠️ **`tx_overflow_q` 是 sticky**（⭐ 复位才清）—— ⭐ 与 `evt_merge.overflow_o` 同

## 五、⚠️ 若将来做方案 ①（FIFO）的设计要点

⭐ **提前记下来**（⭐ 免得将来重新想）：

| # | 要点 | ⚠️ 为什么 |
|---|---|---|
| **1** | ⭐ **深度给 8**（⭐ 不是 4） | ⚠️ `evt_merge` 的 `DEPTH=4` 是**同拍相撞**场景；⭐ 回传是**异步**的 ⇒ ⭐ 给宽一点 |
| **2** | ⭐ **用"计数式"FIFO**（⭐ 不是满/空指针比较） | ⭐ 计数式**满/空判断简单** ⇒ ⚠️ 少一类 off-by-one 缺陷 |
| **3** | 🔴 **满时丢【新的】而不是覆盖【旧的】** | ⭐ 旧的更早 ⇒ ⭐ 顺序性更重要（⭐ 标定进度是有序的） |
| **4** | 🔴 **必须有 `drop_cnt` + sticky `overflow`** | ⭐ `K-106` |
| **5** | ⚠️ **读写指针都要有"上界"** | 🔴 ⭐ **本轮教训**：⭐ 任何等待/循环都要有上界（⭐ 见经验库 `98 号`） |
| **6** | ⭐ **tb 判据**：⭐ (a) 连续塞 N 个 ⇒ ⭐ **全部按序发出**；(b) 塞 N+1 个 ⇒ ⭐ **丢 1 个且 `drop_cnt=1`**；(c) ⭐ **无 X/Z** | ⭐ 三条就够 |
