# 🔧 `span` 标定后的阈值调整操作卡（⭐ 上板后立刻用）

> **日期**：2026-09-24 凌晨
> **场景**：⭐ **上板跑完 `span` 标定后**，`pos` 空间会变化 ⇒ 🔴 **`TRIG_TH`/`REL_TH` 必须跟着改**
> **状态**：🔴 **未改**（⭐ 现在 `top.v` 还是"只 `tare`"那套阈值）
> **用途**：⭐ **改的时候照这个填**（⭐ 数字已按源码公式推导）

---

## 〇、⭐⭐ 一句话

| 项 | 结论 |
|---|---|
| ⭐ **为什么必须改** | ⭐ `span` 会把行程**拉伸 5.5 倍**（⭐ 744 → 4094）<br>🔴 而阈值 `149`/`89` 是**按 744 算的** ⇒ ⚠️ **拉伸后"按 20%"变成了 3.6%** ⇒ 🔴 **过于灵敏**（⭐ 轻碰就触发） |
| ⭐ **改成多少** | ⭐ **`TRIG_TH = 0x333`（819）** · ⭐ **`REL_TH = 0x1EB`（491）** |
| ⭐ **为什么这样算** | ⭐ 保持"**触发 20% / 释放 12%**"的比例不变（⭐ 用户 2026-09-23 拍板的口径） |

---

## 一、⭐⭐ 推导过程（⭐ 全部基于源码，⛔ 不是估的）

### 1.1 ⭐ `calib` 的公式（⭐ `rtl/drivers/calib.sv` 实测）

```verilog
// ⭐ span 标定时算增益（calib.sv:106）
den_r <= raw - zero_r[cal_ch];           // 分母 = 满量程码 - 零点码
quo_r <= DIVIDEND;                       // 被除数 = FULL << 8 = 4095 << 8
                                         // ⇒ gain = (4095 << 8) / (raw_span - zero)

// ⭐ 正常通路（calib.sv:148）
prod_r <= (raw > zero_r[ch]) ? ((raw - zero_r[ch]) * gain_r[ch]) : 0;
wire [PW-1:0] shifted = prod_r >> 8;     // ⇒ pos = (raw - zero) * gain >> 8
```

### 1.2 ⭐ 场景 1：**只 `tare`**（⭐ 现状）

```
⭐ 未做 span ⇒ gain 保持初值 = 1<<8 = 256（即 1.0 倍）
⭐ 实测行程 = 744 码
⭐ pos@触底 = (744 × 256) >> 8 = 744
⇒ ⭐ pos 空间 = 0 .. 744
⭐ TRIG = 20% × 744 = 149  = 0x095     ← ✅ top.v:1122 实测就是这个
⭐ REL  = 12% × 744 =  89  = 0x059     ← ✅ top.v:1123 实测就是这个
```
✅ **与源码吻合** ⇒ ⭐ 说明推导方法正确。

### 1.3 ⭐ 场景 2：**做了 `span`**（⭐ 上板后）

```
⭐ gain = (4095 << 8) / 744 = 1409  （Q8.8 ⇒ ⭐ 5.50 倍）
⭐ pos@触底 = (744 × 1409) >> 8 = 4094
⇒ ⭐ pos 空间 = 0 .. 4094          （⚠️ 不是 4095 —— 定点截断少 1）
```

🔴 **此时若还用老阈值**：
```
⭐ 149 / 4094 = 3.6%   ← ⚠️ 意图是 20%！
⇒ 🔴 触发点从"20% 行程"变成"3.6% 行程" ⇒ ⚠️ 轻碰就响、松手也难释放
```

✅ **正确阈值**：
```
⭐ TRIG = 0.20 × 4094 = 819  = 0x333
⭐ REL  = 0.12 × 4094 = 491  = 0x1EB
```

## 二、⭐⭐ 怎么改（⭐ 两处，都在 `top.v`）

### 2.1 🔴 改 `event_extract` 的例化参数（`top.v:1122-1123`）

```verilog
// ⭐ 现状（⭐ 只 tare 那套）
.TRIG_TH   (12'h095),        // 149
.REL_TH    (12'h059),        //  89

// ⭐ 改为（⭐ span 之后）
.TRIG_TH   (12'h333),        // 819 = 20% × 4094
.REL_TH    (12'h1EB),        // 491 = 12% × 4094
```

⚠️ **⚠️ 顺带提醒**：⭐ `top.v` 里那段长注释（⭐ 行 803 附近）说
> *"⭐ 而**用户正在调定位板** ⇒ 行程一定变 ⇒ 🔴 这两个必须跟着重算"*

⇒ ⭐ **做完 `span` 之后这条警告就【失效了】**（⭐ 因为行程被归一到满量程）
⭐ **改阈值时顺手把那段注释更新**（⭐ 注明"⭐ 已启用 span ⇒ 阈值固定按 20%/12% 设"）。

### 2.2 ⚠️ 有没有别的模块也用这两个阈值？

| 模块 | 用阈值吗 | ⚠️ 结论 |
|---|---|---|
| `event_extract` | ✅ **是**（`TRIG_TH`/`REL_TH`） | ⭐ **就是它** |
| `param_extract` | ⚠️ 用 `VEL_T1`/`VEL_T2`（⭐ **速度的两级阈值**） | 🔴 **也要跟着改**（⭐ 见下） |

🔴 **⚠️ 一个容易漏的点**：`param_extract` 的 `VEL_T1=0x200`/`VEL_T2=0x600`（⭐ `top.v` 实测）
⚠️ 它们也是**按 `pos` 空间设的** ⇒ 🔴 **span 后同样要重算**。

⭐ **推导**：
```
⭐ 现状（行程 744）：T1 = 0x200 = 512 ⇒ 512/744 = 68.8% × 行程
                     T2 = 0x600 = 1536 ⇒ 1536/744 = 206% ⇒ 🔴 超过 744！
```
⚠️ **等一下** —— 🔴 **`T2 = 1536 > 744`** ⇒ ⚠️ **它现在【永远达不到**】！
⇒ ⭐ **这是一个【已有的真问题】**（⭐ 不是 span 引起的）

📌 **需要核实**（⭐ 见 §四 的待确认项）。

## 三、⭐⭐ 操作步骤（⭐ 上板后照做）

| # | 步 | ⭐ 判据 |
|---|---|---|
| **1** | ⭐ **上板，先验"只 tare"档**（⭐ 现状阈值） | ⭐ 按琴键出声（⭐ `TRIG=149`） |
| **2** | ⭐ **发 `'S'` 跑 `span`**（⭐ 16 轴逐个按到底） | ⭐ 串口回 `D`（⭐ 全完成） |
| **3** | 🔴 **此时【先别弹】** —— ⚠️ 阈值还不对 | ⚠️ 按 20% 算，现在等效 3.6% ⇒ ⭐ **会非常灵敏** |
| **4** | ⭐ **改 `top.v` 两行阈值** → `0x333` / `0x1EB` | ⭐ 改动见 §2.1 |
| **5** | ⭐ **重新构建 + 烧录** | ⭐ `gowin_build.ps1` exit 0 |
| **6** | ⭐ **⚠️ 注意：重新烧录会【丢失 span 结果】** | 🔴 **见下方"重要陷阱"** |

### 3.1 🔴🔴 **重要陷阱：烧录会清掉 `span` 结果**

```
🔴 `calib.gain_r[]` 是寄存器 ⇒ ⭐ 重新烧录/复位 ⇒ 🔴 **回到 1.0 倍**
⇒ ⚠️ 而 `tare` 也一起清掉 ⇒ ⭐ `calib_autotare` 会上电重跑（⭐ 好）
⇒ 🔴 **但 `span` 【没有自动重跑】**（⭐ 它需要人按 16 个轴）
```

⇒ ⭐⭐ **所以正确顺序是**：
```
① 先改好阈值（⭐ 按"span 后"的值） ⇒ 构建 + 烧录
② 再跑 tare（⭐ 自动）
③ 最后跑 span（⭐ 发 'S'，⭐ 16 轴）
④ ⭐ 此时阈值与 span 结果【同时有效】✅
```

⚠️ **若是"先 span 再改阈值再烧录"** ⇒ 🔴 **span 白做了**（⭐ 得重来）。

📌 **这正是 `span` 的一个结构性问题**：
> ⚠️ **`span` 结果不能持久化**（⭐ 掉电就没了）
> ⇒ ⭐ 每次上电都要重标（⭐ 或者接受"只 tare"的 744 行程）
> ⚠️ **要不要做"`span` 结果存到 flash"** ⇒ ⭐ **见 §四 待确认**

## 四、🔴🔴 **已确认的真缺陷：`param_extract` 的力度阈值超出量程**

> ⭐ **本项原来是"待确认"，我当场查证后【确认是真缺陷】**（⭐ 不是设计文档里该留的悬念）。

### 4.1 🔴 事实（⭐ 全部实测）

```verilog
// rtl/w3a/param_extract.v:47,49 —— ⭐ 参数默认值
parameter [POS_W-1:0] VEL_T1 = 12'h200,     // = 512
parameter [POS_W-1:0] VEL_T2 = 12'h600,     // = 1536

// rtl/w3a/param_extract.v:218 —— ⭐ 实际用法（⭐ 与 pos_i【直接比较】）
if (pos_i[scan_axis*POS_W +: POS_W] >= VEL_T2) begin
```

⇒ ⭐ **`VEL_T1`/`VEL_T2` 是【绝对码】，⛔ 不是比例**。

### 4.2 🔴 后果（⭐ 算一遍就知道）

```
⭐ 现状行程（只 tare）= 0 .. 744
   · VEL_T1 = 512  ⇒ 512/744  = 68.8%  ⇒ ✅ 能达到
   · 🔴 VEL_T2 = 1536 ⇒ 1536/744 = 206% ⇒ 🔴 **永远达不到**（⭐ 量程只有 744）

⇒ 🔴 所以：
   · `t1_seen` 会置起（⭐ 越过 512 时）
   · 🔴 但 `was_above_t2` **永远为假** ⇒ ⚠️ **`Δt` 永远算不出来**
   ⇒ 🔴 **力度功能静默失效**（⭐ 所有音都是同一个力度）
```

⚠️ **而它的自检【查不出来】**：
```verilog
// 行 304 —— ⭐ 只查"深阈 > 浅阈"
localparam PARAM_OK = (VEL_T2 > VEL_T1) && ...;
```
⭐ `1536 > 512` ⇒ ✅ **自检通过** ⇒ 🔴 **缺陷静默通过**（⭐ `K-87`/`K-106` 同族）。

### 4.3 ⭐ 这解释了 `tb_param_extract` 为什么"全过"

⭐ 实测 `tb_param_extract` 的输出（⭐ 本轮回归日志）：
```
NOTE [param_extract] PARAM_OK=1 (AXIS_N=16 VEL_T1=0x200 VEL_T2=0x600 ...)
  ok  : a fast press produces a vel_update
  ...
  ok  : FAST press gives a LARGER velocity than SLOW press (monotonic)
```
⚠️ **tb 用的是【自己的参数】**（⭐ `tb_param_extract.sv` 里另有 `VEL_T1`/`VEL_T2`）
⇒ 🔴 **而 `top.v` 例化时用的是默认值 512/1536** ⇒ ⚠️ **tb 从没测过交付配置**。

📌 **这正是库里的 `87 号`**：
> *"16 项判据全过 + 变异体 4/4 全抓，模块里却还藏着三个真缺陷"*
> ⭐ 根因：⭐ **判据围绕 tb 自己的配置设计，⛔ 从没覆盖 `top.v` 的实际配置**。

### 4.4 ✅ **修法（⭐ 两条路）**

| 选项 | ⭐ 做法 | ⚠️ 影响 |
|---|---|---|
| **⭐ (a) 改 `top.v` 的例化参数**（⭐ **推荐**） | ⭐ 显式传 `VEL_T1`/`VEL_T2`，⭐ 按**行程的 50%/80%** 算：<br>· 只 tare（744）：`T1 = 372 = 0x174` · `T2 = 595 = 0x253`<br>· span 后（4094）：`T1 = 2047 = 0x7FF` · `T2 = 3275 = 0xCCB` | ⚠️ **要在 `top.v` 加两行**<br>① 但 ✅ **不改模块本身** |
| (b) 改 `param_extract.v` 的**默认值** | ⭐ 把默认改成"按比例" | ⚠️ **改的是已落地模块** ⇒ ⚠️ 要重跑它的 tb + 变异体 |

⭐ **建议 (a)** —— ⭐ 理由：⭐ **与 `TRIG_TH`/`REL_TH` 的处理方式一致**
（⭐ 那两个也是**在 `top.v` 里显式传参**的）⇒ ⭐ **同一种模式，好理解**。

⚠️ **但要注意**：🔴 **`VEL_T1`/`VEL_T2` 与 `TRIG_TH`/`REL_TH` 必须【成套改】**
—— ⭐ 因为它们**共享同一个 `pos` 空间**：
```
⭐ 一组正确的配置（⭐ 只 tare，行程 744）：
   TRIG_TH = 0x095 (149, 20%)   REL_TH = 0x059 ( 89, 12%)
   VEL_T1  = 0x174 (372, 50%)   VEL_T2 = 0x253 (595, 80%)
   ⚠️ 约束：⭐ TRIG < VEL_T1 < VEL_T2 ≤ 行程   （⭐ 且 REL < TRIG）

⭐ 一组正确的配置（⭐ span 后，行程 4094）：
   TRIG_TH = 0x333 ( 819, 20%)  REL_TH = 0x1EB ( 491, 12%)
   VEL_T1  = 0x7FF (2047, 50%)  VEL_T2 = 0xCCB (3275, 80%)
```

### 4.5 🔴 **要不要现在修？**（⭐ 需你拍板）

| 选项 | ⭐ 说明 |
|---|---|
| ⭐ **(a) 上板前修** | ⭐ 改 `top.v` 两行 ⇒ ⚠️ **要重跑回归 + PnR**（⭐ ~25 分钟）<br>⚠️ **且要等变异测试跑完**（⭐ `K-119`） ⇒ 🔴 **与上板抢时间** |
| **(b) 上板后修** | ⭐ 先上板验"出声 + 标定"（⭐ 那是硬指标）<br>⭐ 力度功能**本来就不是本周硬指标**（⭐ `U-9`/`param_extract` 属加分项） |

⭐ **我建议 (b)** —— ⚠️ 理由：
* ⭐ 上板的硬指标是"**按琴键出声**"（⭐ 力度不影响）
* ⚠️ 而"上板前改 RTL"会**引入未验证的变量**（⭐ 违反"一次只改一个变量"）
* ⭐ 力度可以在上板验通后再修（⭐ 那时还能**实测**它在真板上的表现）
