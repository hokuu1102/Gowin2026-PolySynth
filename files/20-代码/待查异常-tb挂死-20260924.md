## 六、🔴🔴🔴 **根因：`cal_ch_mux` 与 `calib_span.busy_o` 形成组合环**（2026-09-24 定位）

### 6.1 ⭐ 环的路径（⭐ 全部实测行号）

```
⭐ top.v:881   wire [2:0] cal_ch_mux = sp_busy ? sp_ch : at_ch;
                                                    ↑
⭐ top.v:870   .busy_o  (sp_busy)          ← calib_span 的输出
⭐ top.v:190   assign busy_o = (state != S_IDLE) && (state != S_DONE);
                            ↑ ⭐ 【组合输出】—— 不是寄存器！
⭐ top.v:989   .cal_ch  (cal_ch_mux)       ← 喂给 calib 的通道
⭐ top.v:865   .cal_ch_o (sp_ch)           ← calib_span 也依赖 cal_ch
```

⇒ ⭐⭐ **闭环**：
```
cal_ch_mux ──> calib.cal_ch ──┐
    ↑                          │
    │                          ↓
sp_busy ←── calib_span.busy_o ←──（组合逻辑）←── calib_span 内部 state
    ↑                                                      │
    └──────────────────────────────────────────────────────┘
```

### 6.2 🔴 为什么在【时间 0】就死

⭐ `cal_ch_mux` 是**纯组合**（`? :`）⇒ ⭐ `sp_busy` 一变，⭐ `cal_ch` 立刻变
⇒ ⚠️ 若 `sp_busy` 又依赖 `cal_ch`（⭐ 通过 `sp_ch` 或 `calib`）⇒
🔴 **`iverilog` 在时间 0 反复求值 ⇒ 永不收敛 ⇒ 挂死**（⭐ **零时间循环**）。

⚠️ **而 `calib_span` 的独立 tb 不挂** —— ⭐ 因为那里 **`cal_ch` 是 tb 直接给的常量**，
🔴 **只有接进 `top.v` 形成回路才暴露**。

### 6.3 ⭐ 修复方案（⭐ 三选一）

| 选项 | ⭐ 做法 | ⚠️ 评价 |
|---|---|---|
| ⭐ **(甲) 把 `busy_o` 打一拍** | ⭐ `calib_span.v`：`always @(posedge clk) busy_r <= (state != S_IDLE) && ...`<br>⭐ `assign busy_o = busy_r;` | ⭐⭐ **推荐** —— ⭐ **打断环**，⭐ 且**符合"输出应寄存"的惯例**<br>⚠️ 代价：⭐ `busy` 晚一拍（⭐ 对仲裁无影响） |
| ⚠️ (乙) 把 `cal_ch_mux` 打一拍 | ⭐ 在 `top.v` 里寄存 `sp_busy` 再用 | ⚠️ 同样是打拍，⭐ 但**改动在集成层**（⭐ 不如改模块干净） |
| ⚠️ (丙) 让 `calib_span` 不看 `cal_ch` | ⭐ 用内部锁存值 | ⚠️ 语义变了（⭐ 它本来就要跟踪 `cal_ch`） |

⭐ **建议 (甲)** —— ⭐ 理由：
* ⭐ **`calib_span` 是我自己的模块**（⭐ ⛔ 不涉及队友）
* ⭐ **寄存器化输出**是更好的设计（⭐ 消除组合路径 ⇒ ⚠️ 也**改善时序**）
* ⚠️ **不影响功能** —— ⭐ `busy` 只用于"仲裁谁用 `cal_ch`"和"互锁 `retrig`"，⭐ 晚一拍完全可接受

### 6.4 🔴 这个缺陷**为什么能溜过去**（⭐ 重要教训）

| # | ⭐ 原因 |
|---|---|
| **1** | ⭐⭐ **`calib_span` 的独立 tb 【全过】**（⭐ 因为那里 `cal_ch` 是 tb 给的**常量** ⇒ ⭐ **不形成回路**） |
| **2** | ⭐ **`iverilog` 编译【零 error】**（⭐ 组合环**不是语法错误**） |
| **3** | ⭐ **PnR 也可能过**（⭐ 综合器只报 warning） |
| **4** | ⚠️ **提交时 `tb_top_sound.log` 写的是 PASS** —— ⚠️ 那是**更早的日志**（⭐ 提交时没重跑这个 tb） |

📌 **第 1 条最值得记**：⭐ **"模块的 tb 全过" ⛔ 不等于 "接进顶层没问题"** ——
⚠️ **组合环只在【跨模块回路】里才成立**，⭐ **单模块测不出来**。

📌 **这与库里的 `L66`/`L67` 同族**（⭐ "接线依赖"类），
⭐ **本条是它的新形态：⭐ 跨模块组合环**。

### 6.5 ✅ 修复验证（⭐ 实验 C 已证）

⭐ **实验 C 实证**：⭐ **只把 `cal_ch_mux` 改成不引用 `sp_busy`** ⇒ ✅ **`tb_top_sound` 立刻 PASS**
⇒ ⭐⭐ **环就是根因，⛔ 无需再找别的解释**。

⚠️ **`c6aa509` 提交时日志为什么是 PASS**：
⭐ **因为那次提交只跑了部分 tb**（⚠️ 不是全量回归）⇒ ⭐ **`tb_top_sound` 用的是旧日志**。
📌 **教训**：🔴 **"证据文件是 PASS" ⛔ 不等于 "最后一次改动的证据"** ——
⚠️ 必须**看日志时间戳 vs 代码修改时间**（⭐ 与 `L74` 同族：⭐ "退出码 0 不等于产物是新的"）。

## 五、⚠️ 一条**教训**（⭐ 已可记入经验）

> 🔴 **用 `Start-Process` + `.Kill()` 强杀仿真器，可能留下损坏的产物**
> ⇒ ⚠️ 之后的重跑会**误判成"代码挂了"**。

⭐ **正确做法**：⭐ **强杀之后，先清掉那个 tb 的 `build/` 目录再重跑** ——
⛔ 不要直接下"代码有问题"的结论。

📌 **与库里的 `L74` 同族**（⭐ *"'退出码 0' 不等于 '产物是新的'"*）——
⭐ 本条是它的**反面**：⚠️ **"跑不过"也不等于"代码坏了"**（⭐ 可能是**产物坏了**）。
