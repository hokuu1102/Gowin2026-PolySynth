# 🔴 代码缺陷：帧周期口径错 2.55 倍（196 µs vs 实测 500 µs）

> **状态**：⭐ **[已确认]**（⭐ 有仿真实测 + 逐拍算术两路证据，⭐ 两者吻合）
> **发现**：2026-09-25 · 接手 span 卡点排查时**顺带查出的口径错误**
> **关联**：`K-79`（帧周期新口径）· 本文**新增 `K-128`**
> **影响面**：⚠️ **所有"按帧数写死时间"的常量** —— ⛔ 不止 `span`

---

## 〇、⭐⭐ 一句话

```
🔴 代码里到处写着"一帧 ≈ 196 µs" ==> ⚠️ 这个数【作废了】。
⭐ 实测（tb_adc_farm 判据）：⭐ 帧周期 = 500000 ns = 【500 µs】。
⇒ 🔴 差 2.55 倍 ⇒ ⭐ 所有"用帧数换算毫秒"的常量都【小了 2.55 倍】。
```

---

## 一、⭐ 证据 A：仿真实测（⭐ 权威）

`sim/evidence/tb_adc_farm.log` 的**判据行**（⭐ 这是 tb 自己断言出来的数）：

```
PASS: 2 frames, 16 sample_valid, 24 samples total, frame period=500000 ns, fanout clean
```

⇒ ⭐ **`frame period = 500000 ns = 500 µs`** —— ⭐ 这是**测量值**，⛔ 不是估算。

---

## 二、⭐ 证据 B：逐拍算术（⭐ 独立复算，⭐ 与 A 吻合）

`rtl/drivers/` 三个模块的参数链：

| ⭐ 参数 | ⭐ 值 | ⭐ 出处 |
|---|---|---|
| `CLK_HZ` | 50 MHz | `top.v:719` |
| `SCLK_HZ` | 1 MHz | `top.v:720` |
| `CHANNEL_RATE_HZ` | **2000** | `top.v:721` |
| `N_ADC` | 2 | `top.v:718` |

**① `mcp3208_driver` 的单通道转换耗时**（`mcp3208_driver.sv`）：

```
HALF_DIV = CLK_HZ / (2*SCLK_HZ) = 50e6 / 2e6 = 25 拍
每位 = 2 × HALF_DIV            = 50 拍
24 位                          = 1200 拍
STATE_FINISH 再等 HALF_DIV      = 25 拍        （第 159 行）
⇒ 单通道 conv = 1225 拍 = 24.5 µs      ★ 这个 24.5 µs 是对的
```

**② `mcp3208_scanner` 的帧周期**（`mcp3208_scanner.sv:36-40`）：

```
FRAME_PERIOD = CLK_HZ / CHANNEL_RATE_HZ = 50e6 / 2000 = 25000 拍 = 500 µs
```

**③ 谁先到（⭐ 这一步是关键）**：

```
8 通道【顺序】扫 = 8 × 1225 = 9800 拍 = 196 µs   ← ⭐ 196 µs 是【转换本身】的耗时
FRAME_PERIOD    = 25000 拍          = 500 µs   ← ⭐ 但状态机【还必须等够这个数】
                          
9800 < 25000  ⇒ ⭐ 转换先完，然后 STATE_WAIT_PERIOD 空等到 25000 拍
⇒ 🔴 **实际帧周期 = 25000 拍 = 500 µs**（⛔ 不是 9800 拍 = 196 µs）
```

✅ **算术结果 500 µs ＝ 证据 A 的实测 500000 ns** ⇒ ⭐ **两路独立证据吻合，结论成立**。

## 三、🔴 为什么"196 µs"是【旧口径】的残留

`K-79` 记录过帧周期从旧口径改成新口径。⭐ 但**代码注释没跟着改**：

| ⭐ 位置 | ⭐ 写的是什么 | ⚠️ 对不对 |
|---|---|---|
| `adc_farm.sv:47` | ⭐ "并行帧时间与片数无关：8 笔 × 24.5 µs ≈ **196 µs**" | 🔴 **错**（⭐ 那是【转换耗时】，⛔ 不是帧周期） |
| `adc_farm.sv:8` | ⭐ "并行 8 笔 ≈ 196 µs ⇒ **5094 Hz**/通道" | 🔴 **错**（⭐ 实际 2000 Hz，⭐ `top.v:721` 明写 2000） |
| `adc_farm.sv:15` | ⭐ "帧时间恒为 196 µs" | 🔴 **错** |
| `adc_farm.sv:25` | ⭐ "帧周期 = `CLK_HZ/CHANNEL_RATE_HZ`（默认 2 kHz ⇒ 0.5 ms）" | ✅ **对** |

⇒ 🔴🔴 **同一个文件里，第 25 行和第 47 行【自相矛盾】**：
⭐ 第 25 行说 0.5 ms（✅ 对），⭐ 第 47 行说 196 µs（🔴 错）。
⚠️ **而下游模块抄的是第 47 行那条错的**。

## 四、🔴 被污染的常量清单（⭐ 逐个核过）

|---|---|---|---|---|

| `event_extract.v:188` | ⭐ 注释 | ⭐ "一帧 196 µs = **9800 拍**" | ⭐ **25000 拍** | ⚠️ 预算算错 2.55 倍 |
| `calib_span.v:54` 等 | ⭐ 多个 | ⭐ "@196 µs/帧" | ⭐ 500 µs | ⚠️ 误导 |

### ⚠️ `REFRACT_N` 是唯一有【实际功能后果】的

```
REFRACT_N = 150 帧
· ⭐ 以为是 150 × 196 µs = 29.4 ms
· 🔴 实际是 150 × 500 µs = 75 ms
⇒ ⚠️ 触键后的不应期是【期望的 2.55 倍】
⇒ 🔴 快速连续触键（⭐ < 75 ms 间隔）会被吞掉
```

⚠️ **这正是 `span` 排查要连带查的东西** —— ⭐ 它**不是** `span` 被拒的原因
（⭐ `span` 走的是 `calib_span`，⛔ 不经过 `event_extract`），
🔴 **但它是一个独立的真问题**，⭐ 且**只有在 `span` 通了之后才会显形**。

## 六、⭐ 教训（⭐ 值得进经验库）

```
🔴 **"实测"两个字会被抄进注释，然后被当成事实反复引用。**
   · `adc_farm.sv:47` 写"约 196 µs"⇒ ⭐ 下游 3 个模块抄了它
   · 🔴 而【真正的实测】在 `tb_adc_farm.log` 里 = 500 µs
   ⇒ ⚠️ **注释里的数字没有回归保护** —— ⭐ 代码改了它不会红

⭐ **防复发**：⭐ 把帧周期做成【被 tb 断言的常量】，⛔ 不写在注释里。
   📌 `tb_adc_farm` 已经在断言 `frame period=500000 ns` ✅
      ⇒ ⭐ 只要让它【从 RTL 参数算期望值】而不是写死，🔴 一旦口径再变就会红。
```

⚠️ **一个更普遍的教训**：⭐ **"转换耗时" ≠ "帧周期"**。
⭐ 前者是器件物理极限（⭐ 196 µs），⭐ 后者是设计选择的节拍（⭐ 500 µs）。
🔴 **把两者混为一谈，就会得出"每通道 5094 Hz"这种纸面达标、实际 2000 Hz 的结论。**
