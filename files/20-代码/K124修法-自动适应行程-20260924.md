# 🔧 `K-124` 修法设计：力度阈值【自动适应行程】

> **日期**：2026-09-24
> **起因**：🔴 `param_extract` 的 `VEL_T2 = 1536` **超出量程**（⭐ 行程只有 744）⇒ **力度功能静默失效**
> ⭐ **用户 2026-09-24 拍板**：⭐ **"改成自动适应行程"**
> **状态**：🔴 **待落地**

---

## 〇、⭐⭐ 一句话

| 项 | 结论 |
|---|---|
| 🔴 **问题** | ⭐ `VEL_T1=512` / `VEL_T2=**1536**` 是**绝对码**，⭐ 而行程只有 **744** ⇒ ⭐ **`T2` 永远达不到** ⇒ 🔴 **力度恒为常数** |
| ⭐ **用户要的** | ⭐ **自动适应行程**（⭐ 不管行程是 744 还是 4094，⭐ 阈值都合比例） |
| 🔴 **但有个硬约束** | ⚠️ **`param_extract` 【看不到】行程**（⭐ 它的输入只有 `pos_i`，⭐ 不知道满量程） |
| ✅ **最省的正解** | ⭐⭐ **用 `span` 把 `pos` 归一到满量程**（⭐ `calib` **已经这么做了**）⇒ ⭐ **阈值固定按 4095 的比例算** |

## 一、🔴 先说清楚：`param_extract` **为什么看不到行程**

```verilog
// rtl/w3a/param_extract.v —— ⭐ 实测它的全部输入
input  snap_valid_i;                       // ⭐ 快照有效
input  [AXIS_N*POS_W-1:0] pos_i;           // ⭐ 只有【归一化后的码值】
input  evt_valid_i; evt_axis_i; evt_kind_i;
```

⇒ ⚠️ **它只看到 `pos`，看不到"这段行程有多长"**。
⇒ 🔴 **所以"自适应"不可能靠"感知行程"实现**（⭐ 除非改模块接口）。

---

## 二、⭐⭐ 三个候选方案（⭐ 优劣对比）

### 方案 ① ⭐⭐ **靠 `span` 归一化**（⭐ **推荐**）

```
⭐ `calib` 的 `span` 已经把 pos 归一到【满量程 ≈ 4095】：
     gain = (4095 << 8) / (raw_span - zero)      ← ⭐ span 时算
     pos  = (raw - zero) * gain >> 8             ← ⭐ 之后恒为 0..4095
⭐ 而 `event_extract` 的 TRIG_TH/REL_TH 【就是按 4095 的比例设的】：
     TRIG_TH = 0x333 (819) = 20% × 4095          ← ⚠️ 那是 span 后的值
```

⇒ ⭐⭐ **结论：⭐ 只要【做过 span】，`pos` 空间就恒为 0..4095**
⇒ ⭐ **`VEL_T1`/`VEL_T2` 就按 4095 的比例【固定设死】**：

| 参数 | ⭐ span 后（行程 4095） | ⭐ 比例 |
|---|---|---|
| `VEL_T1` | ⭐ **`0x7FF`（2047）** | 50% |
| `VEL_T2` | ⭐ **`0xCCB`（3275）** | 80% |

| ✅ 好处 | ⚠️ 代价 |
|---|---|
| ⭐ **⛔ 不改 `param_extract`**（⭐ 只在 `top.v` 传参） | ⚠️ **必须先做 `span`** —— ⭐ 否则行程还是 744 ⇒ 🔴 **阈值又超量程** |
| ⭐ **与 `TRIG_TH`/`REL_TH` 同一模式**（⭐ 好理解） | ⚠️ **`span` 结果【掉电就丢】** ⇒ ⭐ **每次上电要重标 16 轴** |
| ⭐ **4 个阈值成套**（⭐ 语义一致） | |

### 方案 ② ⚠️ **`param_extract` 内部自适应**（⭐ 代价高）

```
⭐ 做法：⭐ 在模块内部【跟踪 pos 的观测最大值】⇒ 用它当"行程" ⇒ 按比例算阈值
```

| ✅ 好处 | 🔴 代价 |
|---|---|
| ⭐ **不需要 span** | 🔴 **要改 `param_extract.v`**（⭐ 加"最大值跟踪"状态） |
| | 🔴 **有"冷启动"问题**：⭐ 刚上电时观测最大值为 0 ⇒ ⚠️ **前几次按键的阈值不对** |
| | ⚠️ **新增状态 ⇒ 新增变异靶点** |
| | ⚠️ **且"最大值"会被噪声污染**（⭐ 一次尖峰就抬高行程） |

### 方案 ③ ⚠️ **加一个 `pos_full_i` 输入**（⭐ 接口改动）

```
⭐ 做法：⭐ `calib` 把 `den_r`（⭐ 满量程码）输出出来 ⇒ ⭐ 传给 `param_extract`
```

| ✅ 好处 | 🔴 代价 |
|---|---|
| ⭐ **显式、清晰** | 🔴 **改 `calib`（⭐ 队友文件）+ `param_extract` + `top.v`** |
| ⭐ **不依赖 span** | ⚠️ **3 个模块的接口都动** ⇒ ⚠️ 通知全员 |

## 三、⭐⭐⭐ 推荐方案：**加 `POS_FULL` 参数**（⭐ 真正的"自动适应"）

> ⭐⭐ **本节是 2026-09-24 上午的补充** —— ⭐ 在**核实 `param_extract` 的自检后**想出来的
> ⚠️ 它**同时解决两个问题**：⭐ **① `K-124` 的超量程** ② **"自动适应行程"**

### 3.1 🔴 为什么"只传阈值"不够

```verilog
// ⭐ 模块现有的自检（param_extract.v:304）
localparam PARAM_OK = (VEL_T2 > VEL_T1) && (DT_MAX > DT_MIN) &&
                      (VEL_MAX > VEL_MIN) && (PITCH_DELTA_TH > 0);
```

⚠️ **它只能查"参数【彼此】的关系"** —— 🔴 **因为它【看不到满量程】**
⇒ ⭐ 所以 `VEL_T2 = 1536 > 量程 744` 这种**超量程**，⭐ **自检永远抓不到**
⇒ 🔴 **这正是 `K-124` 能潜伏至今的原因**。

### 3.2 ✅ 解法：⭐ 加 `POS_FULL`（满量程）+ 阈值按比例算

```verilog
// ⭐⭐ 新增参数（⭐ 语义：⭐ pos 的满量程码值）
//   ⭐ 只 tare（行程 744）  ⇒ POS_FULL = 744
//   ⭐ span 后（归一化）    ⇒ POS_FULL = 4095
parameter [POS_W-1:0] POS_FULL = 12'd744,

// ⭐⭐ 阈值改成"按比例算"（⭐ 这才是真正的自动适应）
localparam [POS_W-1:0] VEL_T1_D = POS_FULL * 50 / 100;   // ⭐ 50%
localparam [POS_W-1:0] VEL_T2_D = POS_FULL * 80 / 100;   // ⭐ 80%

// ⭐⭐ 自检加上"不超量程"（🔴 这是 K-124 的直接守卫）
localparam PARAM_OK = (VEL_T2 > VEL_T1) && ... &&
                      (VEL_T2 <= POS_FULL);      // ⭐⭐ 新增！
```

| ✅ 好处 | ⚠️ 代价 |
|---|---|
| ⭐⭐ **真正"自动适应"** —— ⭐ **只改 `POS_FULL` 一个数**，⭐ 阈值按比例跟着变 | ⚠️ **要改 `param_extract.v`**（⭐ 1 参数 + 2 localparam + 1 断言） |
| 🔴 **自检能抓到超量程**（⭐ `K-124` 的根因被守住） | ⚠️ 新增参数 ⇒ ⚠️ `top.v` 要传 |
| ⭐ **语义清晰**（⭐ "满量程"是真实存在的物理量） | ⚠️ 要重跑它的 tb + 变异体 |

⭐ **`POS_FULL` 怎么定**（⭐ 两种做法）：

| 做法 | ⭐ 说明 | ⚠️ 风险 |
|---|---|---|
| ⭐ **(甲) 在 `top.v` 手工传**（⭐ `12'd744` 或 `12'd4095`） | ⭐ 简单直接 | ⚠️ 改档位时要人改（⭐ **但自检会拦住**超量程） |
| ⭐⭐ **(乙) 从 `calib` 引出来** | ⭐ `calib` 内部有 `den_r`（⭐ 满量程码）⇒ ⭐ 输出它 | ⚠️ **改 `calib`（⭐ 队友文件）** ⇒ ⚠️ 要通知 |

⭐ **建议 (甲) 起步** —— ⚠️ **因为 (乙) 要动队友模块**，⭐ 且 (甲) **已经解决了 `K-124`**。
📌 **将来若要真自动** ⇒ ⭐ 再做 (乙)（⭐ 那时 `POS_FULL` 已是现成接口）。

### 3.3 ⭐ 与"方案 ①"的对比（⭐ 我改主意了）

⭐ **我原本推荐"方案 ①（靠 span 归一化 + 传死阈值）"** —— ⚠️ **现在改为推荐本方案**：

| 维度 | 方案 ①（传死阈值） | ⭐ **本方案（`POS_FULL` + 比例）** |
|---|---|---|
| 改模块吗 | ✅ ⛔ 不改 | ⚠️ 改（⭐ 1 参数 + 2 localparam + 1 断言） |
| **真自动** | 🔴 **不是**（⭐ 换档要改代码） | ✅ **是**（⭐ 只改 `POS_FULL`） |
| 🔴 **能守住 `K-124`** | ⚠️ **不能**（⭐ 自检仍看不到量程） | ✅ **能**（⭐ `VEL_T2 <= POS_FULL`） |
| 风险 | ⭐ 低 | ⚠️ 中（⭐ 但改动**很小**，⭐ 且**有断言兜底**） |

⇒ ⭐⭐ **结论：多花一点点改动，换"真自动 + 真守卫" ⇒ 划算。**

### 3.4 ⚠️ 仍需注意：`POS_FULL` 要跟着档位改

| 档位 | ⭐ `POS_FULL` | ⚠️ 谁来设 |
|---|---|---|
| ⭐ **只 tare**（⭐ 上电默认） | **744** | ⭐ 默认值即可 ⇒ ✅ **开箱能用力度** |
| ⭐ **span 后** | **4095** | ⚠️ 改 `top.v` 的参数（⭐ 或在 `calib_span` 完成后**自动改**） |

⚠️ **"自动改"需要运行时信号**（⭐ 因为 `POS_FULL` 是 `parameter`）⇒ ⭐ 属**方案 (乙) 的范畴**。

## 三之二、⭐⭐⭐ **落地细节 + 一个必须先解决的冲突**（⭐ 2026-09-24 中午补充）

> ⭐ **本节是"能不能直接落代码"的关键** —— ⚠️ **我核实后发现一个设计冲突**。

### 3.2.1 🔴 冲突：**`tb_param_extract` 传的是【超量程的旧值】**

```
⭐ 实测 tb_param_extract.sv:32-33
   localparam T1 = 12'h200;   // 512
   localparam T2 = 12'h600;   // 1536  ← 🔴 这正是 K-124 的超量程值！
   ⇒ ⭐ tb 把它们传给 .VEL_T1 / .VEL_T2
```

⚠️ **若新逻辑"优先按 `POS_FULL` 比例算"** ⇒ 🔴 **tb 传的 `VEL_T1/T2` 会被忽略**
⇒ 🔴 **tb 的判据（⭐ 基于 512/1536）会失败**。

### 3.2.2 ✅ 解法：**三个参数并存 + 断言守量程**（⭐ 推荐）

```verilog
// ⭐⭐ ① 保留原有参数（⛔ 不删 —— tb 要用，⭐ 删了会破坏接口）
parameter [POS_W-1:0] VEL_T1 = 12'h200,
parameter [POS_W-1:0] VEL_T2 = 12'h600,

// ⭐⭐ ② 新增：满量程 + 比例
//   ⭐ `POS_FULL = 0` 是【哨兵】：⭐ "没告诉我满量程" ⇒ 回退到 VEL_T1/VEL_T2
parameter [POS_W-1:0] POS_FULL   = 12'd744,   // ⭐ 默认 = 只 tare 的行程
parameter integer     VEL_T1_PCT = 50,        // ⭐ 50%
parameter integer     VEL_T2_PCT = 80,        // ⭐ 80%

// ⭐⭐ ③ 有效阈值（⭐ 纯常量表达式 ⇒ 可综合）
localparam [POS_W-1:0] VEL_T1_EFF =
    (POS_FULL != 12'd0) ? (POS_FULL * VEL_T1_PCT / 100) : VEL_T1;
localparam [POS_W-1:0] VEL_T2_EFF =
    (POS_FULL != 12'd0) ? (POS_FULL * VEL_T2_PCT / 100) : VEL_T2;

// ⭐⭐ ④ 比较处改用【有效阈值】（⭐ 行 218）
if (pos_i[scan_axis*POS_W +: POS_W] >= VEL_T2_EFF) begin

// ⭐⭐ ⑤ 自检加"不超量程"（🔴 这是 K-124 的直接守卫）
localparam PARAM_OK = (VEL_T2_EFF > VEL_T1_EFF) && (DT_MAX > DT_MIN) &&
                      (VEL_MAX > VEL_MIN) && (PITCH_DELTA_TH > 0) &&
                      (VEL_T2_EFF <= POS_FULL);      // ⭐⭐ 新增
```

### 3.2.3 ⭐⭐ **`tb_param_extract` 必须改（⭐ 这才是 `K-124` 教训的正面回应）**

🔴 **`K-124` 的根因**：⭐ **tb 用【自己的一套参数】，⛔ 从没测过 `top.v` 的实际配置**。

⇒ ⭐⭐ **修法：让 tb 用【和 `top.v` 同一套】参数**：
```verilog
// 🔴 改前（⭐ tb 自己定值 ⇒ 测不到交付配置）
localparam T1 = 12'h200;
localparam T2 = 12'h600;

// ✅ 改后（⭐ 与 top.v 一致 ⇒ 真正测到交付配置）
localparam POS_FULL = 12'd744;      // ⭐ 与 top.v 的默认档一致
localparam T1 = POS_FULL * 50 / 100;   // 372
localparam T2 = POS_FULL * 80 / 100;   // 595
```
⚠️ **且 tb 喂的 `pos` 值要相应调整**（⭐ 让它跨越 372 / 595）。

📌 **并加一条判据**：⭐🔴 **`VEL_T2_EFF <= POS_FULL`** —— ⭐ **这就是 `K-124` 的守卫**
（⭐ 若将来有人把 `POS_FULL` 改小、⭐ 或比例改大 ⇒ ⭐ **立刻报错**）。

### 5.2 ⚠️ 同时要改 `event_extract` 的阈值（⭐ 成套）

```verilog
// ⭐ 现在是"只 tare"档（行程 744）：
```
