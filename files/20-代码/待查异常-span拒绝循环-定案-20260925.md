### ⭐ 先纠正我自己：这个格式我之前解错了

⭐ `span_probe.v` 的**真实**字节布局（⭐ `N_BYTES = 7`）：

| ⭐ `idx` | ⭐ 内容 | ⭐ 说明 |
|---|---|---|
| 0 | `'V'` | ⭐ 前缀 |
| 1 | `state` | ⭐ 1 位 hex |
| 2 | `axis` | ⭐ 1 位 hex |
| 3 | **`rej_lat` 的 hex** | ⭐ `hexch(rj_lat)` —— ⚠️ **发的是全部 4 位的 hex** |
| 4 | **常量 `'0'`** | 🔴 硬编码 `8'h30`（⭐ 设计时以为"低 4 位恒 0"） |
| 5 / 6 | CR / LF | ⭐ 行尾 |

⇒ ⭐ **所以 `V7090` 的正确解读是**：

```
⭐ state = 7  ==> **DONE**（⭐ 已放弃）
⭐ axis  = 0
⭐ rej   = 9   ==> ⚠️ 注意：idx4 那个 '0' 是【常量】，⛔ 不是 reject 的一部分
```

### 🔴 这里暴露了一个**诊断命令自身的缺陷**（⭐ 记为 `K-131`）

⚠️ 我（⭐ 上一轮）在设计 `span_probe` 时**以为** `reject_cnt` 需要 2 位 hex，
🔴 **但它其实是 `reg [3:0]`（0~15）** ⇒ ⭐ **1 位 hex 就够**。
⇒ 🔴 **`idx4` 那个常量 `'0'` 是【多余】的** ⇒ ⚠️ **它把输出变成"看起来像 4 位 reject"，
   实际只是个固定后缀** ⇒ 🔴 **极易误导**（⭐ 我自己就先解错了）。

📌 **修法**：⭐ 把 `idx4` 改成回**别的有用信息**（⭐ 见 §四的 `K-132` 建议）。

### ⚠️ `reject_cnt = 9` 与 `REJECT_MAX = 8` —— ⭐ **不构成矛盾**（⭐ 我一度过度解读）

```
⭐ 代码语义（calib_span.v:330/362/387/446/505/544 六处一致）：
     reject_cnt <= reject_cnt + 1;
     if (reject_cnt >= REJECT_MAX) state <= S_DONE;   // ⭐ 判【当前值】
⭐ 所以：⭐ 判 `>= 8` 为真时先 `+1` ⇒ ⚠️ 进 `S_DONE` 时可能是 **9**
   （⭐ 取决于"第 8 次拒绝"那一拍是否又走了一次 `+1`）
⇒ ✅ **9 是完全可能的，⛔ 不是缺陷** —— ⚠️ **我一度把它当成"同拍双赋值"，⭐ 那是过度解读。**
📌 **教训**：⭐ 看到"和预期差 1"先别急着定性，⭐ 先把**赋值与判定的先后**读清楚。
```
