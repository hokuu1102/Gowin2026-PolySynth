## 一、问题（实测，⛔ 不是推理）

```
Actual Fmax = 50.003 MHz   vs   Constraint = 50.000 MHz
⇒ slack = 【0.002 ns】= 2 皮秒  ·  Logic Level = 27
```

⚠️ **含义**：温度/电压稍偏最坏角、或**重新布局一次**，就可能不满足时序。
⭐ 而这类"偶发不满足时序"是**最难查**的一类故障（本项目已在 B2/B3 上吃过"偶发"的苦）。

📌 **为什么不能靠"多跑几次 PnR 碰运气"**：同量级网表两次 PnR 实测 Fmax 差 **20%**
（`59.600` / `50.003` / `49.181` 三个值，其中**旁路功能后反而更差**）
⇒ ⭐ **Fmax 被布局噪声主导** ⇒ 只有**降低逻辑深度**才是确定性改善。

## 二、根因（`impl/pnr/Gowin2026.timing_paths` 逐行解析）

```
SETUP  slack = 0.002 ns · 27 级逻辑
  clk_ibuf → 1.288  g_sound.u_tdm_render_mixer/mult_952_s2      ← 起点（已寄存的乘法输出）
         → 8.507 ~ 12.122   n2226_s → … → n2221_s               ← 🔴 进位链（每级 ~0.036 ns）
         → 14.237 ~ 18.390  mx_sample_23 → mx_sample_0 → mx_sample_5
         → 19.261  g_sound.u_master_mix/prod_0_s                ← ⚠️ 跨进第二个模块
         → 22.573  u_master_mix/g_sound.mm_sample_16_s
         → 23.530  g_sound.sample_r_16_s0                       ← 终点
```

| 段 | 区间 | 耗时 | 占比 |
|---|---|---|---|
| ⭐ `tdm_render_mixer` 内部 | 1.288 → 18.390 | **17.10 ns** | 77% |
| `master_mix`（乘法） | 18.390 → 22.573 | 4.18 ns | 19% |
| 到 `sample_r` | 22.573 → 23.530 | 0.96 ns | 4% |

🔴 **根因**：`tdm_render_mixer.v` 的 `samp_r` 写在 `always @(*)` 里
⇒ ⭐ **它是组合输出** ⇒ `dry_sample_o` **中间没有任何寄存器**就穿到顶层
⇒ 进 `master_mix` 的乘法 ⇒ ⭐ **一个 20 ns 周期里串了**：
```
归一化乘法 → 限幅（C1 软膝）→ 饱和 → 主音量乘法 → sample_r
```

### ⭐ 解析全部 50 条路径 ⇒ 证明这一刀切中要害

```
前 16 条最差路径（slack 0.002 ~ 0.244 ns）—— ⭐ 终点【全部】是 sample_r_XX_s0
   ⇒ 也就是【全部】走 master_mix → sample_r 那条链
   ⇒ ⭐ 这一刀把 16 条【全切掉】

第 17 条（slack 1.377 ns）—— u_note_manager/best_env_5_s0    ← ⭐ 下一个瓶颈
第 18~25 条（1.519 ~ 2.217 ns）—— note_manager 的 best_idx / best_valid / best_age
```

## 三、⭐ 修法：把 `samp_r` 从【组合】改成【真寄存器】

```verilog
// 改前（组合输出 —— 🔴 问题所在）
reg signed [SAMPLE_W-1:0] samp_r;
always @(*) begin
    if (over_pos)      samp_r = ...;
    else if (over_neg) samp_r = ...;
    else               samp_r = lim_w[SAMPLE_W-1:0];
end

// 改后（真寄存器 —— ✅ 切断"限幅/饱和 → 主音量乘法"这一段）
reg signed [SAMPLE_W-1:0] samp_r;
always @(posedge clk_i) begin
    if (!rst_n_i)      samp_r <= {SAMPLE_W{1'b0}};
    else if (over_pos) samp_r <= ...;
    else if (over_neg) samp_r <= ...;
    else               samp_r <= lim_w[SAMPLE_W-1:0];
end
```

⭐ **配套（⚠️ 流水线改造最容易漏的一步）**：`valid_d` 深度 **3 → 4**
```verilog
reg [3:0] valid_d;                                        // 原 [2:0]
always @(posedge clk_i) begin
    if (!rst_n_i) valid_d <= 4'b0000;                     // 原 3'b000
    else          valid_d <= {valid_d[2:0], valid_r};     // 原 {valid_d[1:0], valid_r}
end
assign dry_valid_o = valid_d[3];                          // 原 valid_d[2]
```
🔴 **漏了它的后果**：下游拿到"**上一拍的数据 + 本拍的 valid**" ⇒ 相位错位。
（📌 原 RTL 的注释 `:656-668` 自己就写着这条纪律。）

## 四、⭐⭐ 关键决策：为什么**改在这里**，⛔ 不在顶层加寄存器

### 4.1 两种方案的**时序收益完全相同**

```
方案 A（顶层 top.v 加寄存器）：切在 mx_sample       ⇒ 剩余最长段 17.10 ns
方案 B（本方案，mixer 内寄存 samp_r）：切在 dry_sample_o ⇒ 剩余最长段 17.10 ns
```
⇒ ⭐ **同一个切点**，差别只在**架构归属**：

| | 方案 A（顶层） | ⭐ 方案 B（本方案） |
|---|---|---|
| 寄存器放哪 | `top.v` 新加一个 | `samp_r` —— **它本来就声明成 `reg`** |
| 模块输出 | 仍是**组合输出**（不好的实践） | ⭐ **寄存输出**（正规做法） |
| 代价 | tb 不动 | 改一个**派生常量**标签 |

⭐⭐ **所以选 B**：`samp_r` 名字是 reg、类型是 reg、位置就在输出级
⇒ **把它变成真寄存器是它本来就该有的样子**；顶层那个反倒像"绕过 tb 的补丁"。

### 4.2 ⭐⭐ 「真契约 vs 派生常量」—— 用户的方法论指正（**已采纳**）

> **用户原话**：「tb 是为 rtl 服务的，没有必要为了遵循已验收的 tb
> 而强行在一个不是最好方案的位置修改代码。」

⭐ **采纳，并把项目纪律精确化为两类**：

| 判据类型 | 例子 | 能不能改 |
|---|---|---|
| ⭐ **真契约**（行为 / 接口语义） | "延迟必须**固定且确定**" · "反相幅度 ≥ 0.625×同相" · "无 X/Z" | ⛔ **不能改** —— 改了就是掩盖回归 |
| ⚠️ **派生常量**（随实现走的记账值） | `latency == POLY_TARGET+**6**` 里的 **6** | ✅ **应该改** —— 实现变了它必须跟着变 |

⭐ **判法**：「这个数字变了，用户/下游会受影响吗？」会 ⇒ 契约；不会 ⇒ 记账值。

### 4.3 ⭐ 而本次**连派生常量都没放松**（读断言原文才发现）

```verilog
tb_tdm_render_mixer.sv:239-240
   chk("latency is a fixed POLY_TARGET+6 (...)",
       k >= POLY + 3 && k <= (POLY + 8));        ← ⭐ 断言是【范围】，⛔ 不是等值
```

⇒ ⭐ 加一级流水（`POLY+7`）**本来就落在 `[POLY+3, POLY+8]` 内** ⇒ **断言照样通过**。
⭐ 只改了 **`chk()` 名字里的数字**（保持文档真实）—— 这正是 tb 自己的「配套纪律」
（`:237-238`）要求的：**改了流水级数就要同步改这个数**。

📌 **教训**：⭐ **先读断言原文，⛔ 别只看 `chk()` 的名字** ——
名字 `POLY_TARGET+6` 长得像等值，实际是范围。
