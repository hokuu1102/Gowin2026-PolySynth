## 三、⭐⭐ 三条可机械执行的纪律

### 纪律 1：⭐ **缩短仿真参数时，必须保持"比值"不变**

```
🔴 ⛔ 不能随便缩小 TIMEOUT 的绝对值
✅ 必须保持【超时 ÷ 帧周期】这个【比值】不变

⭐ 例：⭐ 上板 TIMEOUT=50e6 拍 / 帧 25000 拍 = **2000 帧**
      ⭐ tb 里帧压到 40 拍/通道 ⇒ 超时取 40×8×2000 = **640000 拍**
      ⇒ ⭐ 比值仍是 2000 ⇒ ✅ 结论才可迁移到上板
```

### 纪律 2：⭐ **复刻顶层时，逐个核对中间件**

```
🔴 漏一个中间件（⭐ 如 `uart_tx_fifo`） ⇒ ⚠️ 会造出"看起来像 bug"的假象
✅ 做法：⭐ 先 `grep` 顶层里这条路径上【所有】模块，⭐ 再照着接
```

### 纪律 3：⭐ **判据要落到"结果"，⛔ 不只到"状态"**

```
🔴 `tb_uart_calib_chain` 判的是"`need_press_o` 拉高了"（⭐ **状态**）⇒ ✅ 真
🔴 但它**没判"轴号字节真的发出去了"**（⭐ **结果**）
⇒ ⭐ **所以 `K-132` 在回归里【完全不可见】**

⭐ 修法：⭐ 端到端判据 —— ⭐ **把 UART 线上真实收到的字节数出来**
   ⇒ ⭐ 这正是 `tb_span_axis_over_uart` 做的事
```

> 📌 **`K-87` / `K-106` 同族**：⭐ "**看得见状态，看不见结果**"。
> ⭐ 本轮的 `K-132` 是它的**又一个实例** —— ⚠️ 说明这条教训**还在复现**。

## 五、📌 给下一个会话的建议（⭐ 优先级排序）

```
① ⭐⭐ **先要"可观测量"**（⭐ 上板能读什么就让它读什么）
   ⛔ 不要在没有任何实测数据时"推导根因"

② ⭐⭐ **写端到端 tb，⭐ 数"结果"**（⭐ 线上的字节、⭐ 屏幕上的数）
   ⛔ 不要只断言"某个中间信号拉高了"

③ ⭐ **仿真缩参数要同比例**（⭐ 纪律 1）

④ ⭐ **复刻顶层要核对中间件**（⭐ 纪律 2）

⑤ 🔴 **长任务在跑时，⛔ 不碰它读的文件**（⭐ 硬纪律）
```
