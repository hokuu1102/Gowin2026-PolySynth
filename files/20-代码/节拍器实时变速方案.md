## 〇、⭐ 30 秒结论

| 问题 | 答案 |
|---|---|
| **`beat_gen` 现在支持实时变速吗？** | ⭐ **支持** —— `tick_inc_i` 是**普通输入端口**，运行中随时可改 |
| **改 `tick_inc_i` 会跳拍/停表吗？** | ⭐ **不会** —— 相位累加器**相位连续**，只是**速率**变了 |
| **那还缺什么？** | ⚠️ **缺"谁来给这个端口喂数"** ⇒ 需要一个 **BPM 寄存器 + 选择逻辑（控制层）** |
| **工作量** | ⭐ **小** —— 一个查表 ROM + 一个寄存器 + 一个输入源（按键/旋钮/串口） |

> ⭐ **一句话**：**底座已经为变速设计好了**（`beat_gen` 就是个"每拍加一个数"的累加器），
> 缺的只是**把那个数变成"可写的"**。

## 一、⭐ 为什么 `beat_gen` 天然支持实时变速

`beat_gen` 的核心就是：

```verilog
wire phase_en = run_i;                      // 只要在走，每拍无条件推进
if (phase_en) phase_q <= phase_sum;         // phase_q += tick_inc_i
wire do_tick = run_i & phase_carry;         // 进位 ⇒ 出一个 tick
```

⭐ **`tick_inc_i` 只参与"每拍加多少"** ⇒
- ⛔ **不影响状态机的结构**（没有"数到 N 清零"那种会丢余数的分频）
- ⭐ **改它的那一拍起，速率立刻变**，而 `phase_q` **保持连续** ⇒ **不跳拍、不停表**

⚠️ **对比"错误做法"**（⛔ 不要走）：若当初写成"数够 N 个 clk 就出一拍"，
那改速度就得**清计数器** ⇒ 会产生**可听的跳拍/停顿**。⭐ 相位累加器没有这个问题。

## 二、⭐ 需要的三个新东西

### 2.1 BPM 查表（`TICK_INC` ROM）

| 项 | 设计 |
|---|---|
| **内容** | `TICK_INC = round(2^32 × BPM/60 × PPQN / 50 MHz)`，`PPQN=960` |
| **档数** | ⚠️ 文档建议 **32~64 项**（`TICK_INC` 32 bit × 64 = **2 kbit**，可放 LUT/ROM） |
| **⚠️ 实现方式** | ⭐ **必须用 `case` 常量表**，⛔ **不用 `$readmemh` 外部 `.mem`** —— ⚠️ GW5AT-60 **不加载外部 `.mem`**（`U18` 波表地雷的同一条教训） |
| **已算好的 5 档** | 60→**82 463** ｜ 90→**123 695** ｜ 120→**164 927** ｜ 140→**192 415** ｜ 200→**274 878** |

### 2.2 BPM 寄存器（运行期可写）

```verilog
reg [5:0] bpm_sel;          // 档位选择（0..63）
reg [31:0] tick_inc_r;      // 查表结果，直连 beat_gen.tick_inc_i
```

⚠️ **一个必须决定的细节：变速要不要"等到拍点/小节边界"才生效？**

| 方案 | 说明 | 评价 |
|---|---|---|
| **A. 立刻生效** | 写寄存器的下一拍就变速 | ⭐ **简单、直觉**；⚠️ 当前这一拍的时长会变（听感上没问题） |
| **B. 量化到拍点** | 等到下一个 `beat` 才切换 | 🟡 音乐上更"整齐"，但要一个 pending 标志（同 `Looper详细设计.md` §4.4 的 `rec_start` 对齐做法） |

> ⭐ **建议 A**（先做简单的）；⭐ 若上板听着别扭再加 B（**成本很低** —— 一个 pending 标志）。

### 2.3 输入源（谁来改 BPM）

| 选项 | 成本 | 说明 |
|---|---|---|
| **按键**（`debounce` 已有） | ⭐ 低 | 用现成的按键驱动 ⇒ ＋/－ 两档步进 |
| **编码器 EC11**（`debounce` 已支持） | ⭐ 低 | ⭐ **旋钮调速最自然**（转一下就变） |
| 串口屏 | ⚠️ 中 | ⚠️ 要另做协议 |
| 摇杆/推子（ADC） | ⚠️ 中 | ⚠️ 要接采集链（`adc_farm` 已有） |

> ⭐ **建议编码器**（`debounce.sv` 已提供 `enc_cw` / `enc_ccw` 端口，⭐ **零新增驱动**）。

## 三、⭐ 三条实现纪律

| # | 纪律 | 依据 |
|---|---|---|
| **1** | ⭐ **一次性改完 `tick_inc_r`，⛔ 不要让它中途是"半个值"** | ⚠️ 若分段写（如高低 16 bit 分两次），会在中间态产生**一个错拍的 tick** |
| **2** | ⭐ **BPM 变更要"可观测"** | ⭐ `K-106` 纪律：⛔ 不静默。给一个 `bpm_dbg_o` 输出当前档位 |
| **3** | ⚠️ **变速不要影响 `tick_cnt` 的语义** | ⭐ `tick_cnt` 是**音乐位置**（PPQN 计数），与速度**无关** ⇒ 变速时⛔ **不清零**（否则 looper 会错位） |

## 四、⚠️ 与 Looper 的交互（⭐ 必须提前想清楚）

> ⚠️ 这是"实时变速"**唯一有风险**的地方。

| 场景 | 后果 | 对策 |
|---|---|---|
| ⭐ **录 loop 时变速** | ⚠️ loop 里存的 `tick` 时间戳是**音乐位置** ⇒ 重放时会**跟着新速度走**（⭐ 这**通常是想要的**） | ✅ 无需特殊处理 |
| ⚠️ **录完 loop 后变速** | loop 会**跟着变速**（因为 `tick` = 音乐时间） | ⭐ **符合直觉**（像真 loop 机） |
| 🔴 **loop 播放中途变速** | ⚠️ 若 looper 自己按"clk 数"排程就会**错拍** | ⭐ **纪律**：looper **必须**用 `beat_gen.tick`（`Looper详细设计.md` §4.3 纪律 3），⛔ 不要自己分频 |

> ⭐ **结论**：⭐ **只要 looper 老老实实用 `beat_gen.tick`，实时变速就是免费的**。
> ⚠️ 反过来说：**这又是一条"⛔ 不许自己再分频"的理由**。
