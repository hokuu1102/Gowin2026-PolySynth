## 二、问题 2：起播等待能不能缩短 —— **FPGA 缓冲容量 = 1024 事件 / 8 KB**

⭐ **权威出处**：`rtl/w3c/evt_buf.v`（⭐ `U-19` 曲谱事件缓冲区 ✅）

| 参数 | 值 | 含义 |
|---|---|---|
| `DEPTH` | **1024 事件** | ⭐ 容量（⭐ `1024 × 64 bit = 64 kbit = 8 KB` ✅） |
| `EVT_W` | **64 bit** | ⭐ 每个事件 64 位 |
| `LOW_WM` | **256** | ⭐ 低水位（⭐ 低于它就喊 PC 补水 ✅） |
| `HIGH_WM` | **768** | ⭐ 高水位（⭐ `DEPTH − LOW_WM` 派生 ✅） |

📌 ⭐ 文件头原文的容量账：*"2 KB = 256 事件只够 **8 拍**；⭐ 8 KB 够**最密曲子的 8 小节**＋33% 余量"* ✅
📌 ⚠️ 而且**它必须滚动** —— ⭐ 你们那首 `夜洋风景` = **11 564 事件 = 90.3 KB** ⇒ 🔴 **远超 8 KB**（⭐ 只覆盖 8.6%）✅

⇒ ⭐ **你们可以据此算最短提前量**：
```
安全提前量(事件数) ≤ HIGH_WM = 768      ← ⭐ 保守（⛔ 别贴着 1024 算）
⇒ 提前 tick 数 ≤ 768 ÷ (每 tick 的平均事件数)
```
📌 ⭐ 你们现在的 `lead = 20000 tick`（⭐ @120 BPM/960 PPQN ⇒ **20.83 拍 ≈ 10.4 秒** ✅ 与你们写的 10.4 s 吻合）
⇒ ⭐ 若谱面平均每 tick < 0.038 事件，20000 tick 就是**安全但偏保守**的 ✅
⚠️ **UART 不是瓶颈**：⭐ 500 kbps / 9 B ≈ **18 000 事件/s**，远高于谱面速率 ✅

📌 ⭐ 另外提醒：⭐ **`evt_buf` 溢出是【可观测】的**（⭐ `eb_ovf` 在 `P0-29` 门里 ✅）
⇒ ⭐ 若你们看到 underrun/overflow 计数，说明提前量确实不够 ✅
