## 一、逐条实证结论

### ① `tools/mid2evt.py:502` —— **无需改，本来就是目标口径** ✅

你们的判断依据是"三个工具全都不写"。实测**不是这样**：

`mid2evt.py:764` 用**同一份 `base`** 造 ON 与 OFF（这是 2026-10-16 早先专门做的结构保证：
"鼓的 ON/OFF 由同一份 base 造出 ⇒ 结构上不可能漏 `is_drum`/`drum_type`"），
⇒ `note_off5` 也天然跟着 base 走，**OFF 与配对 ON 逐字节相同**。

实证（本测试曲 `events.hex` 576 条，我方逐条解码）：

```
配对 ON/OFF 对                 = 269
note5 不一致的对               = 0          ← ⭐ 你们要的那条
OFF 的 note5 分布 = {0:132, 2:18, 7:16, 9:3, 10:13, 12:4, 14:15, 15:1,
                    17:13, 18:3, 19:6, 21:1, 22:5, 24:4, 26:18, 27:1, 31:34}
ON  的 note5 分布 = 同一份（逐项相同）
```

⇒ 132 条 n5=0 **不是"恒 0"**，而是鼓/低音区音符的合法值（与其配对的 ON 相同）；
34 条 n5=31 是哨兵（越界旋律，ON/OFF 同为 31）。

⚠️ 唯一的注意点（与你们的兜底无关）：`guide_lamp` 侧对 **n5=31（哨兵）** 的处理是"不点灯"，
所以哨兵音的 ON/OFF 都不点灯 —— 这与"灯永不熄"无关，是设计意图。

### ② `esp32/tools/score_word.py:121` —— **位域与入参都已含 note_off5** ✅

- 位域表：`bit 4..0 note_off5(5) = MIDI − 45`（`OFF_NOTE5 = 0`，`MASK_NOTE5 = 0x1F`）
- `pack_word(...)` 的入参里有 `note_off5`（0..30 可弹 / 31 哨兵），
  且 `validate_fields()` 会把"越界却写 0"这类错误在**入参层**打出来
- ⚠️ 补充一个事实：**它不是灌谱主通路** —— `mid2evt.py` 自己打包，只用 `score_word`
  的 `validate_fields` 做入参层校验。所以即使改它，产物也不会变。

### ③ `esp32/ble/main/pool.c:724` —— **这条你们说对了，已修** ✅（提交 `553ef668`）

原状：`STOP flush` 补发的 off 帧确实**没写 `bit[4:0]`**（隐含 0）⇒ 补发的 OFF 灭错灯。

改法（⛔ 不从 `inc` 反算音高 —— 那要除法 + 音高表反查、有舍入误差，不可靠）：

```c
/* 扫已发帧时，把每个开音符【帧里已有的正确 note_off5】原样存下 */
static uint8_t open_n5[MAX_OPEN];
...
uint8_t n5 = (uint8_t)(w & 0x1F);        /* 扫帧处 */
open_n5[n_open] = n5;                    /* ON 入表时存 */
...
| ((uint64_t)(open_n5[j] & 0x1F))        /* flush 打包时写回 bit[4:0] */
```

位域核对：`tick<<44 · inc<<23 · axis<<19 · vel<<11 · kind<<9 · note_off5 在 bit 0..4`，
与 `score_word.py` 的 `OFF_NOTE5 = 0` 一致，不与 vel/kind 冲突。

⚠️ **本机无 IDF 工具链 ⇒ 只做了静态核对，⛔ 未编译验证**。上板前请我方编译一次（或你们若能跑我们的构建）。
