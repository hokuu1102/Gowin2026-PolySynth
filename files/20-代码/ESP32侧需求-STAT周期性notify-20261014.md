# ESP32 侧需求：让 `0xABF4`(STAT) 周期性 notify（2026-10-14）

> **收件人**：FPGA 线
> **提出人**：ESP32 线（用户实测暴露）
> **紧急度**：🟡 **不阻塞当前功能**，但它是**根治**「上位机蓝牙栈卡死」的唯一办法
> **前置**：池容量问题**已在我方解决**（见 §四），本文件只谈 **STAT 通知**

---

## 一、需求一句话

**请让 `0xABF4`(STAT) 周期性 notify 给客户端**，而不是只能靠客户端主动 `readValue`。

---

## 二、为什么必须（🔴 实测机制，不是推测）

### 2.1 事实：`0xABF4` **已经声明了 NOTIFY 位**

`gatt_svc.c`：

```c
L70  static const uint8_t s_prop_noti = ESP_GATT_CHAR_PROP_BIT_READ |
L71                                      ESP_GATT_CHAR_PROP_BIT_NOTIFY;
...
L186 /* ---- ④ 0xABF4 状态 ---- */
L191     (uint8_t *)&s_prop_noti }      // ← ⭐ 用的就是带 NOTIFY 的那个
```

⚠️ 而文件头的注释写的是：

```c
L18  0xABF4  状态  READ（⭐ 客户端【主动读】，⛔ 固件不 notify）
```

⇒ ⭐ **属性位允许 notify，但固件从不发** ⇒ 客户端**只能**用 `readValue()`。

### 2.2 🔴 而 `readValue()` 在你们忙的时候**必然读不到**

算一笔账（用户那份谱面，实测数据）：

| 项 | 值 |
|---|---|
| 谱面 | **23558 帧 × 9 B = 212 KB** |
| 串口 500 kbaud | ≈ 50 KB/s ⇒ **至少 4.2 秒**才能转完 |
| 但 FPGA 的 `evt_buf` | **只有 1024 深**，且**按音乐速度消耗**（≈131 事件/秒） |
| ⇒ 23558 帧全部转完需要 | **≈180 秒 = 整首曲子** |

⇒ 🔴 **ESP32 在【整个播放期间】都忙于往 FPGA 转发** ⇒
  这期间 BLE 的 read 得不到及时服务 ⇒ **客户端 `readValue()` 挂住**。

### 2.3 🔴 而 Web Bluetooth **无法取消**已发出的操作 ⇒ 浏览器永久卡死

实测日志（用户）：

```
14:41:43 上传完成
14:41:46 已发 起播
14:41:59 🔴 蓝牙栈卡住了（连续 3 次 GATT operation already in progress）
```

⭐ 机理：
1. 客户端发 `readValue()` ⇒ 挂住（ESP32 忙）
2. 客户端自己的超时到点 ⇒ **只丢弃 Promise，⛔ 取消不了浏览器里那个操作**
3. ⇒ 浏览器认为"还有一个操作在飞" ⇒ **之后每一个操作都报
   `GATT operation already in progress`**
4. ⇒ 起播/停止/清池**全部失效**，只能**断开重连**才恢复

⚠️ 我方已在自己这侧加了缓解（轮询不超时 + 不堆积 + 卡死检测），
   ⭐ 但**只要还依赖 `readValue`，就永远有这个风险** —— 因为读什么时候能回来，
   **取决于你们忙不忙**，而客户端**无法预知**。

---

## 三、请你们做的（建议做法）

### 方案 A（推荐）：周期性 notify 同一份 STAT 字符串

⭐ **负载可以就是现在 `readValue()` 返回的那份文本**（`V1 mode=...\npool=...\n...`），
   客户端解析代码**一行都不用改**（它已经在解析这个格式）。

| 项 | 建议 |
|---|---|
| 周期 | **200~500 ms**（⭐ 状态变化本来就慢，没必要更快） |
| 触发条件 | 建议**仅在已订阅时发**（⛔ 别对没订阅的连接发） |
| 内容 | 与 `0xABF4` 的 read 返回值**完全一致** |
| 停止 | 客户端断开 / 取消订阅时停 |

⚠️ 请评估对你们主循环的开销：`pool_stats()` 里有个 O(帧数) 求 `total_tick`
   的循环（为兼容多轴交织、tick 不单调）。⭐ 池加大后这个循环变长了
   （我方刚把池从 160 KB 提到 2 MB ⇒ 233016 帧 ⇒ 约 10 ms/次）。
   ⇒ ⭐ 若按 200 ms 周期发，就是 **5% CPU**；按 500 ms 则是 **2%**。
   📌 **若这个开销不可接受**，可以：只发**变化的部分**，或**只发几个关键字段**
   （`pool` / `sent` / `run` / `ovf`）—— 客户端能适配，请告知格式。

### 方案 B（备选）：至少让 `readValue()` 不被饿死

⭐ 若周期性 notify 不方便，退一步：**保证 BLE 的 read 回调能及时被服务**
（例如把 STAT 的文本**缓存在读之前就拼好**，⛔ 不在读的回调里现算
 —— 那样读回调就不会被 `pool_stats()` 的 O(n) 循环挡住）。

⚠️ 但这**只是缓解**：客户端仍然不知道"这次读要等多久"，
   ⛔ 无法从根上消除卡死。

## 四、池容量问题：**已在我方解决**（⛔ 不需要你们做）

⭐ 顺便同步：用户那份 212 KB 的谱面**装不下**我方的池 ——
`ble_config.h` 原来是 `BLE_POOL_BYTES = 160 KB`（= 18204 帧，
注释写明"按 104.3 KB 的谱设计"），而谱面是 **23563 帧** ⇒ 溢出不可避免。

✅ **已改成 2 MB**（= 233016 帧，**9.9 倍余量**）。
   模组是 **N16R8（8 MB PSRAM）**，`pool_alloc()` 本来就优先 PSRAM ⇒ 拿得到。

📌 这是**我方（ESP32 侧）**的问题，⛔ 与 FPGA 侧无关 ——
   **ESP32 存整曲、按时间放水，FPGA 只需小缓冲**，架构本来就是这样的。

---

## 五、做完之后我方会怎么用（供你们参照）

1. ⭐ **连接时订阅 `0xABF4`**，之后**完全不再调用 `readValue()`**
   ⇒ ⛔ **不可能再卡死**（没有读，就没有"读不回来"）
2. ⭐ **用 notify 里的 `pool=N/CAP` 做真流控**：
   灌谱时若发现 `pool` 涨到容量的 ~80%，就**暂停发送**，等它降下来再继续
   ⇒ ⭐ **`ovf` 可以真正做到 0**（现在只能靠"猜一个安全的节流速率"）
3. 状态面板与播放进度**实时刷新**（不用等轮询）
