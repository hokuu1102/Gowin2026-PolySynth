## 一、🔴🔴 答复里**最重要的发现**：真正的阻塞是**接线，不是代码**

```
⭐ FPGA 目前只有【一路】UART：uart_rx = D14 · uart_tx = D15（都在 J9 上）
🔴 而我们期待的是 FPGA 的 G22 / G21
⚠️ 而 constr/top.cst:137 明确：PMOD0（含 G21/G22）⇒ 【当前未分配】
⇒ ⭐⭐ ESP32 ↔ FPGA 之间现在【一根线都没有】
```

⭐⭐ **这解释了我们本周一直困惑的事**：⭐ 我们以为"FPGA 侧没写 `uart_tx.v`"，
⚠️ **其实是"那一路上根本没有引脚"** —— ⭐ **性质完全不同**：
· ⚠️ 前者要写 RTL（工作量大）
· ⭐ **后者只是分配引脚**（⭐ 而 `uart_tx` **已经写好了**）

### ✅ 我们的回应：**接受"单开一路"的裁定**

| 项 | ⭐ 我们确认 |
|---|---|
| ⭐ **`G22` = ESP32→FPGA**（FPGA 收） | ✅ 接受 |
| ⭐ **`G21` = FPGA→ESP32**（FPGA 发） | ✅ 接受 |
| ⭐ **500 kbps 8N1 无流控** | ✅ 接受（⭐ 与我们三工程一致） |
| ⭐ **空闲高** | ✅ 接受（⭐ 我们有 `M111` 那颗雷的记录，⭐ 会加判据） |
| ⭐ **交叉接线 + 共地** | ✅ 接受 |

### ⭐⭐ 一条好消息：**我们【不用改固件引脚**

```
ESP32 GPIO17(TX) → FPGA G22

```
⭐ 而我们固件【现在就是】`TX=GPIO17` / `RX=GPIO18`（`ble_config.h:103-104`）

## 三、⚠️ 我们【不同意 / 要补充】的地方

### 3.1 ⚠️ 关于"上行帧格式" —— ⭐ 有个**根本性的张力**要先说清

⭐ FPGA 答复里**同时**给了两套东西，⚠️ **它们的性质不同**：

| | ⭐ 第一套（§三 Q2） | ⭐ 第二套（§7.2 / §7.3） |
|---|---|---|
| **形态** | ⭐ **单字节 ASCII 流** | ⭐ **`0xA5` 带帧头的二进制帧** |
| **内容** | 标定事件（`t`/`s`/`x`、轴号、6 类原因码…） | MIDI 回传（`tick`/`axis`/`phase_inc`/`vel`） |
| **现状** | ✅ **已实现**（在 `J9` 上） | ⚠️ **约定草案**（⛔ 未实现） |

🔴 **张力在哪**：⭐ Q2 说"**不要帧头**、我们的流是**单字节事件流**"，
⚠️ 而 §7.2② 说"**建议用带帧头的帧**"。
⭐ **答复自己解释了原因**（⭐ 我们认为**理由成立**）：
> ⭐ **因为 ESP32 是【单独一路 UART】** ⇒ ⭐ **不必与 `J9` 争字符空间**
> ⇒ ⭐ **这一路可以有自己的协议，且可以更大胆**

✅ **我们的结论**：⭐ **两套共存是合理的**，⚠️ **但必须【在文档里区分清楚】**，⛔ 否则：
🔴 **解析方会不知道"下一个字节该按 ASCII 解还是按帧解"**

⭐⭐ **所以我们建议一条【硬约定】**（⭐ 这是我们要加的唯一一条）：

> ⭐ **上行流的【模式】必须显式可辨** —— ⭐ 二选一：
> · **方案 ①**：⭐ **两种流用不同的帧头**（⭐ 如 ASCII 事件流**永远不以 `0xA5` 开头**）
> · **方案 ②**：⭐ **加一条"切换模式"命令**（⭐ 明确此刻按哪种解）
>
> ⚠️ **不选一个的话，解析方只能靠猜** ⇒ 🔴 **而"猜"在混合流里必然出错**。

### 3.2 ⚠️ `0`/`1`/`2` 既是原因码又是轴号 —— ⭐ 我们确认会按**位置**解析

⭐ 答复提到（`top.v:2005`）：**拒绝字节总是紧跟在【一个轴号之后】**
⇒ ⭐ **我们按位置解析，⛔ 不按字母表** ✅

⚠️ **但我们要补一句**：⭐ **这条纪律【必须在文档里写死】** ——
🔴 否则将来谁加一个"以轴号开头"的新事件，**整条解析就错位了**。

### 3.3 ⚠️ `axis → 音高` 是张**会变的表** —— ⭐ 这条影响我们的 CMD 设计

⭐ 答复 §7.3 说：**`axis → 音高` 是一张表（`axis_map.kb_inc[]`），且变调/换模式会改它**，
⭐ 建议**约定一条"表同步"命令**（⛔ 否则两边表必然漂）。

✅ **我们同意**，⭐ **并且这正好落在我们的 CMD 口上**（`0xABF3`）。
⚠️ **但我们要指出一个前提**：⭐ 表的大小 ——
· ⚠️ 若表是 **16 轴 × 4 字节 = 64 B** ⇒ ⭐ **一条命令就够**
· 🔴 若更大，⚠️ **要分片** ⇒ ⭐ **那需要序号/确认机制** ⇒ ⚠️ **复杂度上一个台阶**

⇒ ⭐ **请 FPGA 侧给【表的实际大小】**，⭐ 我们据此定命令形态。
