> ⭐⭐ **2026-09-30 更正（乙 · 实际实现 H2 时发现）—— H2 的「免 PLL」写法做不到**：
>
> - **原说法**：`640×480@60` 免 PLL，`50 ÷ 2 = 25 MHz`，误差 0.70%。
> - **更正**：**必须用 PLL**。`50 MHz` 整数分频只能得到 25 MHz 的**像素**时钟；
>   而 TMDS 串行时钟必须是 **5 × 像素 = 125 MHz**，`50 MHz` 无法用整数分频得到 125 MHz。
> - **原因**：TMDS 用 `OSER10`（10:1 DDR）串行化，其时钟是像素时钟的 5 倍 ——
>   原措辞只算了像素时钟、漏了串行时钟。
> - 📌 **佐证**：H1 的 `bringup/hdmi_ref_720p/README.md` 早就写过
>   「H2 应重新生成自己的精确 **25.2/126 MHz PLL**」，即 H1 作者已知需要 PLL。
>   按 `K-114`，**PLL 用于外设 / TMDS 时钟属正常用法**，不违反「不用 PLL 输出做全设计系统时钟」的边界。
> - ✅ **实际实现**：`bringup/hdmi_640x480/`，默认方案用 PLL
>   （`MDIV=20 / ODIV0=8 / ODIV1=40` → 25 / 125 MHz），已构建、**0 setup / 0 hold**；
>   方案 B（25.2 / 126 MHz，`MDIV=63 / ODIV0=25 / ODIV1=125` + SDC 63/25、63/125）
>   也已于 2026-09-30 构建通过：三个时钟 TNS 全 0、`Actual Fmax 176.035 MHz`、
>   实测 pixel_clk **25.200 MHz**。⇒ ⚠️ 但"能综合、能收敛"⛔ 不等于"PLL 上板能锁 / 显示器能认"。
> - ⚠️ **H4 的措辞不受影响**（它本来就写明用 PLL 出 154.000 MHz）。

## 五、HDMI 技术要点

| 项 | 内容 |
|---|---|
| 目标分辨率 | 1920 × 1200 @ 60 Hz（16:10，VESA CVT，非 CEA 标准模式） |
| 像素时钟 | ≈ 154.0 MHz（实际按显示器 EDID/CVT 参数微调） |
| 时钟来源 | PLL：50 × 77 / 25 = 154.000 MHz（精确整数比） |
| 规则边界 | `K-114`：禁止的是"用 PLL 输出作为全设计系统时钟"；用于外设 / TMDS 时钟属正常用法。器件有 8 个 PLL；Gowin 官方 `TMDS_PLL_60HZ.v` 本身使用 PLL（50 × 297 / 200 = 74.25 MHz） |
| 必做验证 | 按 `K-41` 做 PLL 活体见证与 fVCO 核算 |
| 第 1 步 | 640×480@60（像素时钟 25.175 MHz；50 ÷ 2 = 25 MHz，误差 0.70%），先验证 TMDS 通路、引脚约束与时序 |
| 第 2 步 | 参数化后上 PLL，输出 1920×1200 |
| 参考实现 | Gowin 官方 DVI/TMDS 参考设计（引脚约束与时序参数可直接复用）；Project F（DVI/HDMI 系列教程，参数化时序）；fpga4fun DVI 教程；Digilent DVI 例程；`hdl-util/hdmi`（现成 TMDS 编码器） |
| 关键实现点 | TMDS 8b/10b 编码表；4 对差分（3 数据 + 1 时钟）；`OSER10` / `ODDR` 串行化；参数化时序 |
| 风险 | 154 MHz 差分输出可行性（先用 640×480 验证通路）；PLL 相位与抖动（按 `K-41`）；线缓冲 BSRAM 预算（现用 16/118） |
| 后续 | 实时频谱需 1024 点流水 FFT，单独立项，安排在第四周 |
