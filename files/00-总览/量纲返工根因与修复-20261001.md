## 三、⭐⭐ 两个根因的机制（⭐ 含算式）

### ① `BATCH 2` → 症状 ③（触发更不灵敏）

```
`AN` 的 `top.v:2276-2282` 自己写着：⭐ "跑 'S' 之前（pos ∈ 0..1023）⇒ 205/1023 = 20%
   ⇒ 默认档要按到 1/5 行程才出声 ⇒ 所以上板手册必须写【先跑 'S'】"
```
⇒ 🔴 **那个前提从未发生**（⭐ 用户上板一直是默认档）⇒ ⭐ 按实测行程 **752**：`205/752 = `**`27.3%`** ✅

### ② `BATCH 4` → 症状 ①②④

```
⭐ `POS_FULL` 决定力度阈值（`param_extract.v:110-113`，`VEL_T1_PCT=50` / `VEL_T2_PCT=80`）：
     4095 ⇒ `VEL_T1_EFF = 2047` · `VEL_T2_EFF = 3276`  ⇒ 🔴 **都越出实际行程 744**
     ⇒ ⭐ 深阈【永远越不过】⇒ `dt` 恒 0 ⇒ 🔴 **力度恒定** ⇒ ① ✅
     （⭐ 这正是 `param_extract.v:369` 点名过的 `K-124` 失败模式）
```

## 五、⭐⭐ 处置决定（⭐ 用户裁定：**放弃 span，写死行程档**）

⭐ **用户原话**：*"其实我感觉不太需要 span 标定了。甚至说按照当前进度写一个死的数据都可以，
span 改了太久了一直都没有改好"*

⭐ **为什么这是对的**：
1. ⭐ **物理行程固定** ⇒ ⭐ 一个数就够（⭐ 上板 `'N'` 扫描 811 次：松手全 = 0、max = **752**）
2. ⭐ **span 的唯一收益是把 744 映射成 4095**，而所有下游阈值**本来就是行程百分比**
   ⇒ ⭐ **基数用 744，百分比语义完全等价** ⇒ ⛔ **归一化不带来新能力**
3. ⭐ **span 是全项目唯一"需要人配合、失败后还静默"的环节** ⇒ ⭐ 去掉 = 去掉一个静默失效源
4. ⭐ **代码不删**：`calib`/`calib_span`/`calib_autotare` 原样保留，`'S'` 命令还在（⭐ 将来可再用）

⚠️ **代价（⭐ 写清）**：⭐ 换定位板高度 / 换板子 ⇒ 行程变 ⇒ ⭐ **四个数必须一起重算**：
```
量 `pos@松手`（应 0）与 `pos@触底` ⇒ 行程 T
  POS_FULL（= TRAVEL_TARE）  = T
  EVT_TRIG_TH                = round(0.086 × T)
  EVT_REL_TH                 = round(0.043 × T)
  vel 斜率                   = round(191 × 1024 / T)      （⭐ 使 T×斜率>>10 ≈ 191 ⇒ 64+191 = 255）
```
