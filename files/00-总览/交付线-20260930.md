## 一、为什么要新建一条交付线

旧线（主树 `main`，`e7c1395`）把**多个从未上板验证的改动**叠在一起：

```
9ccf742(基准) → looper三条 → 变调 → 池判据 → 新鼓点 → 时序修复 → pins3 → 变调回退 → ...
```

⇒ 🔴 **一旦上板出问题，无法定位是哪一个改动** —— 2026-09-30 一整天都在做这个二分。

⇒ ⭐ **本线从【唯一已上板验证干净的版本】重新开始，每加一个功能都单独验证。**

## 六、纪律（本线专用）

1. ⭐ **每加一个改动 ⇒ 一个独立提交 ＋ 一个 PnR ＋ 一次上板验证**（⛔ 不许把多个未验证的改动叠在一起）
2. ⭐ **PnR 判据**：**0 setup / 0 hold** 且 **`Actual Fmax ≥ 52.5 MHz`**（余量 ≥5%）—— ⭐ 本项目 PnR 是布局噪声主导（同源重跑差 2~3 MHz）⇒ **单次绿 ≠ 可上板**
3. ⭐ **回归判据**：**通过数 == 共数**（⛔ 不写死数字）
4. ⭐ **交付时必须在 `.meta.txt` 写清：基点 SHA · 含什么 · ⛔ 不含什么**
5. ⭐ **改 `note_manager` 的改动必须随一个余量 ≥5% 的 PnR 一起交付**
