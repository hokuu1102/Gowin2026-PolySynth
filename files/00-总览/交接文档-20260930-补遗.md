## 一、⭐ 用户对症状的【最新、最完整】描述（⭐ 这一条最重要）

> **"整个音色都是乱的，有时候按了没声音，有时候按了是之前的声音，有时候按了乱发声音。"**

| ⭐ 症状 | ⭐ 含义 |
|---|---|
| ⭐ 有时候按了**没声音** | ⭐ 事件到了但没写进 voice，或 voice 没被激活 |
| ⭐ 有时候按了是**之前的声音** | ⭐ **voice 的旧状态没被新事件覆盖**（音高/音色/力度之一陈旧） |
| ⭐ 有时候按了**乱发声音** | ⭐ 写到了错误的位置，或用了垃圾值 |
| ⭐ **整个音色都是乱的** | ⭐ 每次起音锁存的音高/音色不可信 |

⭐ **性质判定：⭐ 这是【非确定性】故障** ⇒ ⭐ 指向 **竞态 / 边缘时序 / 未初始化状态**，⛔ 不是稳定的逻辑错误。

### ⭐ 用户对"串键"的澄清（⭐ 二选一已答）

- ⭐ **"串键" = 按 A 键却发出【别的键的音高】**（⭐ 不是全局跑调、不是音量/包络）⇒ ⭐ 指向 **轴→音高** 那条链。
- ⭐ **当时只接了 USB-TTL**（⭐ **没接串口屏**）⇒ ⭐ 见 §二，那条 UART 机制的触发源**不成立**（⚠️ 除非调试口手动发过 `F`/`G`，或线上噪声）。

## 二、⭐ UART 机制：⭐ 真缺陷，⭐ 但**大概率不是本次元凶**

**机制（子代理 `e1f6c8ff` 查实，⭐ 有综合/代码级证据）**：

| ⭐ 环 | ⭐ 事实 |
|---|---|
| ⭐ 三消费者共线 | `top.v` 里 `uart_ui` / `calib_cmd` / `evt_uart_rx` **共用同一对** `ur_data/ur_done` |
| ⭐ `calib_cmd` 的帧边界 | `HEADER = 8'hA5`（⭐ 曲谱协议）；⭐ **只在帧外认命令** |
| ⭐ `'F'`/`'G'` 加在哪 | `953333e` 新增 `CMD_TRANS_DOWN=8'h46` / `CMD_TRANS_UP=8'h47`，⭐ **就加在帧外那一支** |
| ⭐ 串口屏协议 | `uart_ui.v` 用 `0x65/0x70/0x71/0x88` ＋ `FF FF FF` ⇒ ⭐ **永不含 `0xA5`** |
| ⭐ 后果 | ⭐ 屏帧的**每个载荷字节**都被当"帧外命令"⇒ ⭐ 出现 `0x46/0x47` 就静默 ±1 半音（⭐ 增量）⇒ ⭐ 再叠 `base_semi` 那条可抬多个八度 |

**⭐ 最硬的机械判据**：`calib_cmd.v` 的 `N_CMD` —— ⭐ **主树 = 13（无 F/G）** vs ⭐ **`AJ`(b2156d6) = 15（有 F/G）**。

⚠️ **但它解释不了用户的症状**：
1. ⭐ 用户**没接屏** ⇒ ⭐ 触发源不成立；
2. ⭐ 它改的是**全局变调**（所有音一起 ±半音）⇒ ⭐ **不会**"按 A 键发出 B 键的音高"。

⇒ ⭐ **仍然必须修**（⭐ 真缺陷 ✅），⭐ 但**优先级低于** §四。

**安全重做方案**（⭐ 供后续）：① 比例表改**显式 `case` 常量**（`default ⇒ 32768`）；② **加显式旁路 mux**（`trans_semi==0 && base_oct==0` ⇒ 乘法器不在通路上，逐位恒等**由构造保证**）；③ 起始音**先校验再提交**（`base_oct_r` 收窄 0..2）；④ ⭐ **变调改走"带帧的绝对量命令"**，⛔ 不再用共享线上的裸字母做增量。

**唯一能抓到它的判据（⭐ C3）**：⭐ 往**同一条 `uart_rx`** 灌真实屏帧（如 `0x71 00 46 FF FF FF`）⇒ ⭐ 断言 `trans_down_req_o==0 && trans_up_req_o==0` 且 `trans_semi_r`/`base_oct_r` 一个字不变 ⇒ ⭐ **必须在未改的 `953333e` 上先跑成红**。⚠️ 只写 C1/C2（比例表/复位值）**抓不到**。

## 三、⭐ 新判据 + 新发现：`vel_r` ±8 斜坡 **8 位回绕**（⭐ 真缺陷，⭐ 但基准也有）

**新加的跨键隔离判据**（`stepB` 分支 `043b453`，⭐ XKEY-1~5，⭐ 双向设计）在**时序修复版上跑出唯一一条红**：

```
ok  : XKEY-3: vel_upd on key B does NOT move key A's velocity
FAIL: XKEY-3: vel_upd on key B really moves key B (non-vacuous)
```

**真因**（`rtl/w3b/note_manager.v:892-894`）：

```verilog
if      (vtgt_val[axis_r[i]] > vel_r[i] + 8'd8) vel_r[i] <= vel_r[i] + 8'd8;
else if (vtgt_val[axis_r[i]] + 8'd8 < vel_r[i]) vel_r[i] <= vel_r[i] - 8'd8;
else                                            vel_r[i] <= vtgt_val[axis_r[i]];
```

⭐ `vel_r` 是 8 位、`8'd8` 是 8 位 ⇒ ⭐ **比较在 8 位里做** ⇒ ⭐ 目标 = 250 时：
`vel_r=248` ⇒ `248+8` **回绕成 0** ⇒ `250 > 0` 为真 ⇒ ⭐ 又加 8 ⇒ ⭐ 在 `0→8→…→248→0` **打转**，`else` 永远进不去 ⇒ ⭐ **永远到不了目标**。

- ⭐ **可达性**：`top.v` 的 `pos_to_vel` 饱和到 `8'd255`，`pos ≥ 717` 就进 248..255 ⇒ ⭐ **用力按就会踩到**。
- ⭐ **为什么一直全绿**：既有 tb 的 `vel_upd` 目标**全 ≤240**（240/230/220/200/123/100）⇒ ⭐ 只有新判据用了 250。
- 🔴 **但它⛔ 不是 AH/AJ 症状的原因**：⭐ 这段斜坡在 **`9ccf742 → 19bcef2` 之间一字未改** ⇒ ⭐ **基准也有** ⇒ ⭐ 顶多是"未被听见的潜在缺陷"。

**裁定（⭐ 已定）**：⭐ 当**独立缺陷**修（⭐ 比较提到 **9 位** ✅）＋ ⭐ **保留 250 这个目标** ✅；⛔ **不把判据改软**（那是把刚抓到的 bug 藏回去）；⚠️ 按 §26.3-f，⭐ 动 `note_manager` 必须**随一个余量 ≥3% 的 PnR** 交付。
> ⚠️ **2026-10-01 更正**：⭐ 门槛已由 **5% 降到 3%**（⭐ 用户裁定）⇒ 判据改为 **`Fmax ≥ 51.5 MHz`**。
> ⭐ 理由：⭐ 5% 的原始依据已被用户撤回（⭐ 那次 0.18% 上板异常是**代码 bug**，⛔ 非时序问题）；
> ⭐ 当前实测 `52.372 MHz`（+4.744%）⭐ 在 3% 下通过。⚠️ **新增 UART 后必须重测并对比**。
