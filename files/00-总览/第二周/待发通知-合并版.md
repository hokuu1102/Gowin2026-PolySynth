## 〇、⭐⭐ 最要紧的一条（**请务必看**）：开工前先拉远端

> **【纪律】每次开始写代码之前，先把远端拉下来。**

```powershell
git fetch origin
git status -sb                    # 看本地是 ahead / behind
git log --oneline HEAD..origin/main    # ⭐ 远端有没有别人的新提交
git pull --rebase origin main     # ⭐ 有就先 rebase 到最新，再动手
```

**为什么定这条规矩**

- ⚠️ 三个人推同一个仓库，**唯一真正会毁掉进度的事就是"两人各写一份"**。
  而"两人各写一份"的**根因**，几乎总是**动手时用的是旧版本**。
- ⭐ 我们已经吃过一次同类亏（见 `K-28`）：**"队友不会动这块"这种判断，
  本地一切自洽、只有 `fetch` 才暴露**。
- ⭐ 本周期我这边就是靠它避免了一次返工：`rtl/w3c/` 下的文件当时**真的不存在**，
  但**先 `fetch` 确认**之后才动手 —— 如果我凭印象认为"乙在做 w3c"，
  就会整块白写。

**同步去做（30 秒，别省）**

| 步骤 | 命令 | 看什么 |
|---|---|---|
| **1** | `git fetch origin` | ⭐ 拿到远端最新状态 |
| **2** | `git log --oneline HEAD..origin/main` | ⭐ **远端有没有你还没见过的提交** |
| **3** | 有 ⇒ `git pull --rebase origin main` | ⭐ **先 rebase 再动手**，⛔ 不要在有落后状态下开始写 |
| **4** | `git status -sb` | 确认不再显示 `behind` |

> ⚠️ **写代码前、提交前**各做一次。⛔ 不要只在"准备 push 的时候"才 fetch ——
> 那时冲突已经产生了，代价高得多。

## 二、⭐ 接口契约变更（**两处，请留意**）

### 变更 A · `note_manager` 的延迟：`≤ 4 拍` → `≤ 34 拍`

> **改了什么**
> - `files/20-代码/W3接口冻结表.md` §四：`note_manager` 的延迟由 `≤ 4 拍`
>   改为 **`≤ POLY_TARGET + 2` 拍**（`POLY_TARGET=32` ⇒ **34 拍 = 0.68 µs**）。
> - ⛔ **端口列表（名字 / 位宽 / 语义）一个字都没改**。
>
> **为什么要改**
> - `T57` 把出声链接进 `top.v` 之后，**交付顶层时序崩了**：
>   `Actual Fmax` 从 55.96 MHz **掉到 8.424 MHz**、**1408 个 setup 违规**。
> - 25 条最差路径**全部**在 `note_manager` 里：`age_r → phase_r` 的时钟使能，
>   `slack = −98.7 ns`（可用只有 20 ns）。
> - 根因：三级抢占选择（空闲 → Release 最低 → 年龄最老）写成了
>   **一整条组合优先级链**（约 96 级逻辑），而它的结果直接驱动
>   **32×32 位 `phase_r` 的 CE**。
> - 修法：改成**每拍只考察一个 voice**，扫完 32 拍再提交（≈2~3 级逻辑）。

**⚠️ 对你们的影响（很小）**

| 影响面 | 说明 |
|---|---|
| **接口** | ⛔ **不用改** —— 端口名 / 位宽 / 语义全部不变 |
| **tb** | ⚠️ 若你的 tb **假设"发事件后 1~4 拍就生效"**，请改成**等 ≤34 拍**（或直接等 `alloc_valid`） |
| **听感延迟** | ✅ **不变** —— `adsr` 的 `gate` 只在 `sample_tick_i`（每 1024 拍）采样，34 拍仍在一帧内 |
| **复音数** | ✅ **不变** —— 仍是 32 voice / 64 振荡器（⛔ 没有降 `POLY_TARGET`） |
| **端到端延迟** | ✅ **不变** —— 仍 ≤1.233 帧（`K-44` 实测） |

**实测结果**：✅ 0 setup / 0 hold 违规、`Actual Fmax` = **58.610 MHz**（比崩之前还高）；
LUT **14097 → 12019**；回归 **29/29**（当时）。

### 变更 B · ⭐⭐ `note_manager` **新增 3 个端口**（事件队列溢出可观测性，`K-106`）

> ⚠️ **这一处【真的改了端口】**（与变更 A 不同）⇒ ⭐ **请留意**。

| 端口 | 方向 | 说明 |
|---|---|---|
| `event_lost_o` | **output** | ⭐ **sticky**：曾发生队列溢出（⭐ 置位后保持，⛔ 不被后续正常帧掩盖） |
| `event_lost_cnt_o[7:0]` | **output** | ⭐ **累计丢弃事件数**（⚠️ **饱和**到 255，⛔ **不回绕**） |
| `event_lost_clr_i` | **input** | ⭐ 读走后清零 |

**为什么要加**

- 🔴 **原来溢出是【静默丢弃】** —— `fifo_push = note_valid_i && !fifo_full`，**没有任何指示**。
- ⚠️ 最坏突发 = **16 键 + 节拍器 1 + 鼓机 1 = 18** > 原深度 **16** ⇒ **丢 2 个**。
- 🔴 **真正的危害不是"丢一个音"，而是【挂音】**：⚠️ 若丢的是 **`note_off`** ⇒
  ⭐ **那个音永远关不掉** —— 正是 `T38`（Looper 防挂音）要防的失效模式。
- ⚠️ 而**上板时你只会听到"有个音一直响"** ⇒ 若不能确认是不是溢出造成的，
  会**去查错方向**（怀疑包络 / DDS / 按键）。

**⭐ 一条必须说清的概念（⛔ 别误解）**

> ⭐ **加深度 ≠ 不丢音；加指示 ≠ 不丢音。两者【正交】。**
>
> | | 加深度（16→32） | 加指示 |
> |---|---|---|
> | 作用 | ⭐ **降低**丢音**概率** | ⭐ 让丢音**可被发现** |
> | 能否"不丢" | ⚠️ **不能** —— 超过 32 照样丢 | ⛔ **完全不能** |
>
> ⛔ **"永不丢音"不存在**（队列有限 + 上游无限 ⇒ 数学上必然溢出）。
> ⭐ **可接受的工程语义 = "要么不丢，要么丢了立刻知道"。**

**⚠️ 对你们的影响**

| 影响面 | 说明 |
|---|---|
| **接口** | ⚠️ **新增 3 个端口** ⇒ 若你的例化**按名字连接**，**不接也合法**（`clr` 恒 0 ⇒ 只置位不清） |
| **⛔ 端口名/位宽** | ⭐ **既有端口一行未改** |
| **行为** | ✅ 队列深度 16→32 ⇒ ⚠️ 排空时间 560 → **1120 拍 = 22.4 µs**；⭐ **听感延迟不变**（`gate` 每 1024 拍采样一次） |

**⭐ 新增纪律（建议全员遵守）**

> ⭐ **任何"容量有限"的队列/计数器，都必须有【可观测的溢出/回绕指示】；
> 且计数必须【饱和】，⛔ 不能回绕。**
>
> ⚠️ 回绕会把"丢了 256 个"显示成"**丢了 0 个**" —— **那是另一种静默**。
>
> 📌 出处：`K-106` 的原话 —— ⭐ **"静默丢弃比报错危险得多"**。

**验证**：`tb_note_manager.sv` 新增 `section 10`（**15 条判据**，含**反证基线**与**饱和**验证）；
⭐ 变异体 `M45`–`M48` 守卫上报路径（静默化 / 不计数 / sticky 不置位 / 取消耗和）。

### 2. ⭐ `rtl/w3c/metronome.v` + `rtl/w3c/perc_env_bank.v` —— 节拍器（`T33`，⭐ **2026-09-22 新落地**）

| 项 | 说明 |
|---|---|
| **`metronome.v`** | ⭐ **合成 click**（⛔ 无采样）—— 强拍 **1760 Hz / 力度 220**、弱拍 **880 Hz / 力度 140** |
| **`perc_env_bank.v`** | ⭐ **打击包络**（一击到底、无 sustain、~20 ms）—— **新增文件**，⛔ **不改你们的 `envelope_bank`/`adsr`** |
| **走哪条路** | ⭐ **走已有的【事件通路】**（发的是标准 `note_evt_t`）⇒ ⛔ **零新增音频通路** |
| **判据** | ⭐ 每 960 tick 恰好 1 个事件（**与 `beat_gen` 严格同拍**）；**每 4 拍一个强拍**；事件**真的分配出 voice** |

**⭐ 为什么必须新建 `perc_env_bank`（⛔ 不是"参数没调对"）**

⚠️ 我读了 `adsr.v` 并**算出确切数字**：它是 **ADSR**，衰减到 sustain 就**停住**：

```
峰值 51200 → sustain 12800，每采样拍降 4
⇒ (51200−12800)/4 = 9600 采样拍 = 197 ms
```

⭐ 而打击音（click）只要 **10~20 ms**。
🔴 **关键**：即使把 `DECAY_STEP` 调大，`adsr` 也只是**更快到达 sustain 然后停住** ——
那个音会**一直响到 `note_off`**，⛔ **不会自己消失**。
⇒ ⭐ **这是"模型不对"（ADSR vs 一次性打击），不是"参数不对"**。

**⚠️ 一处必须成对改的地方（⭐ 只改一边会静默失效）**

`note_manager` 的**专用池是按 `axis_id` 选的**（我读了源码核实）：

```verilog
pool_mask[pg] = (cur_axis >= RESERVED_AXIS) ? (pg >= NORMAL_N) : (pg < NORMAL_N);
```

⇒ ⭐ 节拍器发 **`axis_id = 4'hE`** 就**自动进专用池**。
⚠️ **但前提是 `note_manager.RESERVED_N ≥ 1`** —— ⚠️ `top.v` 现在是 **`RESERVED_N(0)`**。
🔴 **`RESERVED_N = 0` 时专用池不存在** ⇒ 节拍器事件会落进普通池 ⇒
⭐⭐ **32 音全响时，"节拍器被抢占、听不到拍子"** —— 而这**正是 `T33` 的核心判据**。

> 📌 **`metronome.v` 给了 `cfg_warn_o` 把这件事变成【可观测的】**（⛔ 不静默）——
> `RESERVED_N = 0` 时它置位，⚠️ 上板时可据此直接判定"是不是没给专用 voice"。

**⭐ 一处真 bug：`valid` 与它的数据不同拍**（`K-109`，已修）

🔴 第一版 `evt_valid_o` 是**寄存器**、而载荷（`phase_inc`/`velocity`）是**组合**的
⇒ ⭐ **`valid` 比数据晚一拍** ⇒ 消费者读到的永远是**下一拍（弱拍）**的音：

| 时刻 | `inc`（载荷） | `evt_valid` |
|---|---|---|
| clk 63（**强拍**） | **151183** ✅ | **0** ❌ |
| clk 64 | **75591**（弱拍） | **1** ✅ |

⇒ 🔴 **强拍永远发不出去**。⚠️ 最阴的是**计数是对的**（`accent_cnt` 数到了 2）
⇒ 现象是"**计数器说发了强拍，耳朵听到弱拍**"。
⭐ 修法：**载荷也在同一拍锁存**。📌 这条纪律与你们的接口都相关：
⭐ **"脉冲"与"脉冲携带的数据"必须同拍锁存**。

**验证**：`tb_metronome.sv`（**26 条判据**）+ `tb_perc_env_bank.sv`（**31 条判据**）；
回归 **32/32**；变异体 `M49`–`M55` **全 caught**；
⭐ 综合实测 `Compiling module 'metronome'` / `'perc_env_bank'`（`K-46`/`K-91`）。

- ⭐ **判据 = 真的跑过一次 Gowin 综合**，⛔ **"iverilog 过了"不算**。
- ⛔ **别用**：`N'()` / `longint` / `logic` / `always_ff` / `typedef` / `interface`。
- ⚠️ 另：**Verilog-2001 不能对 `integer` 参数做位选**（`FULL[DW-1:0]` 非法）⇒ 先落成向量。

### 2. ⚠️ `synth_check` **只跑综合、⛔ 不查时序**（`K-104`）

- ⭐ **建议**：**新模块落地时接进 `Gowin2026.gprj` 跑一次 `sim\gowin_build.ps1`（含 PnR）**。

### 3. ⭐ 新增：两个踩过的写法坑（`K-107`，我已记档）
