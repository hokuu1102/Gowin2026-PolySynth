# 第一部分 · 需求逐条扣出（⭐ 原样照抄）

## A. 基础要求（⭐ 必须满足）

> **A1 多维交互控制检测**
> 原文：*"自主设计演奏交互形态，基于传感器精准采集，支持**选音、触发、拨弦、力度感应**等操作，具备**至少 2 个**独立可控维度，交互逻辑灵敏稳定"*

> **A2 FPGA 纯硬件实时音频合成**
> 原文：*"完整音频通路**全部基于 HDL**，逐样本实时运算；可用波表采样/加法合成/FM/物理建模任意方案；**控制→音频输出总延迟 ≤10ms**；杜绝软件串行"*

> **A3 合规实时发声与多复音**
> 原文：*"基础复音 **≥4**；**所有输出音频均由 FPGA 根据实时演奏指令逐音、逐样本实时生成**；支持单音实时变调、ADSR 调控、多声部实时混音；**严禁直接播放预录 PCM、预置推流及整段录音触发**"*

## B. 拓展要求（⭐ 冲分项）

> **B1 超高规模并行合成引擎**
> 原文：*"复音数 **≥32**，**或**单音加法合成分量 ≥32 路，**或**多条并行物理建模运算单元，最大化并行优势"*

> **B2 多维表情控制与音频效果处理**
> 原文：*"**≥3 维**表情（力度动态、滑音、颤音）；**≥2 种乐器音色**自由切换；**在 FPGA 硬件内部实现混响、延迟、合唱等数字音频效果器**"*

> **B3 极致低延迟与实时视听反馈**
> 原文：*"延迟压到 **≤5ms 且确定性无抖动**；基于 FPGA 逻辑实时生成可视化：**LED 演奏指引、李萨如图形、实时频谱、波形显示**"*

> **B4 智能联动与脱机拓展**
> 原文：*"脱机演奏 **LED 曲目指引**；**可**搭载蓝牙与手机 App（在线曲谱下载、键位自定义、演奏录音回传）"*

## C. ⭐⭐ 核心评分规则与现场验证标准

> **C1 振荡器统计规则**（原文）
> *"独立发声单元为包含**独立相位累加器、频率调控、包络控制**的完整振荡器；
> **单波表采样查表不计多谐波数量，仅计单个振荡器**；
> 加法合成按**运算分量**统计、FM 按**调制运算器**统计、物理建模按**并行弦/模态单元**统计。"*

> **C2 系统吞吐量指标**（原文）
> *"以「**同时活跃可闻独立振荡器总数 × 实际音频输出采样率**」为核心评分依据，**过采样不叠加加分**。"*

> **C3 现场验证要求**（原文）
> *"支持**测试模式下输出多路不同频率音频，频谱可观测对应数量独立谱峰**，
> 同时可通过 **RTL 代码佐证**纯硬件实时合成通路，验证无预录音频播放行为。"*

## D. ⭐⭐ 官方合规口径（主办方答复，已确认）

| # | 答复要点（原样） |
|---|---|
| D1 | 使用 **MCU** 的部分**可能不计入工作量**（成品或自制一样） |
| D2 | 只要**不是绝大部分功能**都用软核/MCU，**不会导致弃赛** |
| D3 | ⭐⭐ **选题二的「音频」与「视觉效果」部分绝对不要用软核/MCU** |
| D4 | ⭐⭐⭐ **"软核"= 通用 CPU/MCU 软核**（跑 C 语言那种）；⭐ **专用状态机 / 串行架构的算法加速器【不是】软核** |
| D5 | "不计入工作量" ⛔ **不是扣分**，而是**影响该部分功能的设计与实现得分**；**1% 用了不会让整个模块清零** |
| D6 | ⚠️ **要考虑实时性影响** —— 今年三道题对实时性要求都高 |

# 第四部分 · 🔴 刚报的 looper bug（复现 + 排查计划）

## 复现（⭐ 用户原话）

```
按 R 开始录制 → 再按一次 R 停止录制 → 之后按 L ⇒ 听不到回放
另外：发 'Y' 返回 '!'（= 操作被拒）
```

## 代码级线索（⭐ 已读出的）

**① `'Y'` 回 `'!'` 的判据**（`top.v:4731`）：
```verilog
wire rd_reject_event = (cmd_recdump_req && (rd_lock || looper_layer_state || (looper_evt_cnt == 0))) ||
                       (rd_lock && (cmd_loop_rec_req || cmd_loop_play_req || cmd_loop_clear_req)) || ...
```
⇒ 🔴 **第二条同时解释两个症状**：⭐ 若 **`rd_lock` 卡住** ⇒ `'Y'` 被拒 **＋** `R`/`L`/`C` **全被拒** ⇒ **录制回放都出问题** ✅

**② 录制/回放的门控**（`top.v:4698`）：
```verilog
if (cmd_loop_rec_req  && !rd_lock)  loop_rec_on_r  <= ~loop_rec_on_r;
if (cmd_loop_play_req && !rd_lock)  loop_play_on_r <= ~loop_play_on_r;
```

**③ `rd_lock = rd_pending | rd_busy`**（`top.v:900`）
⇒ ⭐ `rd_pending_r` 由 `'Y'` 置位、由 `rd_start_w` 清零；
`rd_start_w = rd_pending_r && txf_idle && !pp_busy && !vp_busy && !np_busy && !dp_busy`
⇒ 🔴 **若 `txf_idle` 一直不为真 ⇒ `rd_pending_r` 卡住 ⇒ `rd_lock` 永久为真** ✅

## ⚠️ 为什么之前没抓到

| 事实 | 后果 |
|---|---|
| `tb_looper` **5/5 全绿** | ⭐ 它验的是 **looper 模块本身** |
| 🔴 **没有任何 tb 覆盖 `R`→`R`→`L` 的【顶层】端到端** | ⭐ 也没有 tb 覆盖 `rd_lock` 与 `'Y'` 的交互 ⇒ **这个缺口一直存在** |
| 🔴 **合并后的全量回归从未跑过** | ⚠️ 无法排除 **AT 那次 `note_manager` 合并**引入 |

## 排查计划（⭐ 按序，每步有判据）

| 步 | 做什么 | 判据 |
|---|---|---|
| **1** | 写 **顶层 tb**：真 UART 发 `R` → `R` → `L`，看 `looper_evt_cnt` / `loop_rec_on_r` / `loop_play_on_r` / `rd_lock` | ⭐ 复现 ⇒ 定位到哪个信号卡住 |
| **2** | 若 `rd_lock` 卡 ⇒ 查 `txf_idle` / `rd_pending_r` / `rd_start_w` | ⭐ 找出"为什么没开始" |
| **3** | 若 `looper_evt_cnt == 0` ⇒ 查录制数据源（`rec_valid_i` 从哪来） | ⭐ 找出"为什么没录进去" |
| **4** | **跑全量回归**（⭐ 从未跑过） | ⭐ 排除/坐实 **AT 合并**的责任 |
| **5** | 修复 + 顶层判据（⭐ **必须能失败**）+ PnR | ⭐ 0 setup/0 hold |
