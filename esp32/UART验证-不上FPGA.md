# 🔌 UART 发送通路验证（⭐ 不依赖 FPGA）

> **目的**：⭐ **在不上 FPGA 的前提下，证明「ESP32 从 `GPIO17` 发出的字节是正确的」**
> **建立**：2026-09-30
> **关联**：`esp32/上机指南.md` · `esp32/tools/uart_rx_check.py`

---

## 〇、🔴 先说清楚：为什么不能直接用正式固件验

### 0.1 ⚠️ 事实：模式 B 下 `GPIO17` 不发数据（⭐ 但这**不是缺陷**）

| 事实 | 证据 |
|---|---|
| ⚠️ **`pool_start()` 零调用** | 全仓库只有 `pool.c:408`（定义）、`pool.h:51`（声明）、`pool.c:616`（注释）—— ⛔ **没有任何调用点** |
| ⚠️ **`s_running` 恒为 `false`** | 写入点仅 3 处：`pool.c:125`（初值）、`:299`（reset→false）、`:414`（`pool_start`→true） |
| ⭐ **`pool_mark_done()` 也是零调用** | `s_pool_done` **只被写、从不参与任何 `if` 判断**（`pool.c:114/298/389/444`）⇒ ⚠️ 纯观测标志 |

⇒ ⚠️ 后果：`task_pool_pump` 每轮走 `else` 分支空转（`pool.c:643-645`）
⇒ **`GPIO17` 不发任何数据** ⇒ 日志里 `sent=0` 会一直保持。

### 0.2 ⭐⭐ 但这是【设计如此】—— ⛔ 不是 bug

🔴 **`pool_start()` 零调用与已拍板方案一致**（`files/20-代码/FPGA侧答复-ESP32对接清单-20260923.md`）：

| 行 | 原文 |
|---|---|
| **L24** | 「答复：**方案③ —— 上板手动按键起播。协议保持冻结，⛔ 不新增命令帧，⛔ 你那边不用改固件。**」 |
| **L58** | 「固件要不要改 \| ⭐ **一行都不用改**」 |
| **L16** | 「起播动作**不由发送端触发**，⭐ 所以**"灌完自动开演"这个流程不存在**」 |
| **L159** | 起播键 = **`Y12`**（`BANK9` 1.5 V，⭐ 空闲） |

⇒ ⭐ **起播是 FPGA 板上的物理按键，ESP32 完全不参与。**

🔴🔴 **所以 ⛔ 不要"给 `pool_start()` 加调用"** ——
那会与方案③ 冲突，且造成**双重起播**（ESP32 放水 + 人按键 FPGA 才开始消费）
⇒ ⚠️ 水位与 underrun 判据**全部失真**。

> ⚠️ **本条是本文档初稿的一个错误结论的更正** ——
> 初稿写"`pool_start()` 零调用是缺陷、要修固件"。**已核实为错**，故更正于此。

### 0.3 ⭐ 顺带更正另一条

⚠️ **`pool_set_expected()` 确实被调用**（`ble_main.c:464`，模式 B 内）。
⇒ ⭐ 日志里的 `exp=200` / `mismatch=0` 是**真判据**，✅ 不是"校验没跑"。

### 0.4 🔴 文档未点破的真问题（⭐ 不替它编答案）

⭐⭐ **模式 B 与方案③ 在架构上互斥**：

| 侧 | 它说 |
|---|---|
| ESP32 侧 | 模式 B：**ESP32 自己按谱子时间放水**（`pool.c:9`、`ble_config.h:146`） |
| FPGA 侧 | 方案③：**FPGA 自己缓冲 + 人按按键起播** |

🔴 **两者都要"自己决定什么时候放"** ⇒ 没有交集。
⭐ **文档没有任何一处描述"ESP32 何时该调用 `pool_start()`"** ——
⚠️ 这是**真实的文档空白**，⛔ 不替它编一个。⇒ ⭐ **需用户 / FPGA 侧裁定**。

### 0.5 ⭐ 对本次验证的影响：⛔ 没有影响

⭐ 本次目标「**证明 ESP32 从 `GPIO17` 发出的字节正确**」**恰好不依赖起播**。
⇒ ⭐ **对策**：用 `esp32/uart_test/` 那个**一次性诊断固件** ——
它把 UART 通路**单独隔离**出来，⛔ 不经过水池、⛔ 不依赖起播、⛔ 不改正式固件。

## 一、⭐ 接线（⚠️ 两条铁律：交叉 + 共地）

```
ESP32-S3                    USB-TTL
────────                    ───────
GPIO17  (UART1 TX)  ────→   RX      ⭐ 收数据（本测试的主线）
GPIO18  (UART1 RX)  ←────   TX      ⚠️ 本测试不用，可不接
GND     ────────────────    GND     🔴 必须共地，⛔ 不共地必失败
                            VCC/5V  ⛔ 不要接（ESP32 自己从 USB 取电）
```

⭐⭐ **最容易错的两点**：

| # | 坑 | 说明 |
|---|---|---|
| **1** | 🔴 **TX 要接对方的 RX** | ⛔ 不是 TX→TX。接错就是"两边都在说、没人听" |
| **2** | 🔴 **GND 必须连** | ⚠️ 只接信号线不接地 ⇒ 电平没有共同参考 ⇒ ⭐ **收到乱码或 0 字节** |

⚠️ **ESP32 自己用板载 USB 线供电 + 看日志**（那是 `COM29`），
⛔ 与本测试的 USB-TTL **是两回事**。

## 二、⭐⭐ 操作步骤

### 步骤 1：查口（⛔ 不要写死）

```powershell
Get-PnpDevice -Class Ports -PresentOnly | Select-Object FriendlyName,InstanceId |
  Format-Table -AutoSize
```

⭐ **认准**：

| 设备 | 看什么 |
|---|---|
| **ESP32** | `VID_303A` ⇒ ⭐ 当前是 `COM29` |
| ⭐ **USB-TTL** | `FTDIBUS\VID_0403+PID_6010` ⇒ ⭐ 当前是 **`COM27` / `COM28`** |

🔴 **⛔ 不要弄混**：`COM29` 是 ESP32 自己的口，`COM27/28` 才是 USB-TTL。

### 步骤 2：烧诊断固件到 ESP32

```powershell
cd C:\Users\hokuu\Desktop\FPGA\FPGA2026-esp32\esp32\uart_test
. "C:\Espressif\tools\Microsoft.v5.5.PowerShell_profile.ps1"
idf.py -p COM29 flash
```

⚠️ **把 `COM29` 换成你实际查到的 ESP32 口**。

### 步骤 3：⭐ 开两个窗口（⚠️ 一个看日志、一个抓数据）

**窗口 A —— 看 ESP32 日志**（`COM29`，115200）：

```powershell
cd C:\Users\hokuu\Desktop\FPGA\FPGA2026-esp32\esp32\tools
python read_log.py --port COM29 --seconds 20 --reset
```

⭐ **期望看到**：

```
I uarttest: === ESP32-S3 UART1 TX self-test ===
I uarttest: uart=1 baud=500000 tx=GPIO17 rx=GPIO18     ← 🔴🔴 2026-09-30 更正：原为 1000000
I uarttest: burst = 36 frames = 324 bytes, every 1000 ms, 3 bursts
I uarttest: UART ready. sending in 2 s ...
I uarttest: burst 1/3: wrote 324 bytes (36 frames), seq up to 35
I uarttest: burst 2/3: wrote 324 bytes (36 frames), seq up to 71
I uarttest: burst 3/3: wrote 324 bytes (36 frames), seq up to 107
I uarttest: === test done: 108 frames (972 bytes) sent ===
```

🔴 **`wrote` 必须 = 324**。少于 324 ⇒ ⚠️ UART FIFO 问题（`SHORT WRITE` 会报错）。

**窗口 B —— 抓 USB-TTL 上的数据**：

```powershell
cd C:\Users\hokuu\Desktop\FPGA\FPGA2026-esp32\esp32\tools
python uart_rx_check.py --port COM27 --baud 500000 --seconds 15 --dump 8
```

⚠️ **`COM27` 换成你 USB-TTL 的口**。

### 步骤 4：⭐ 看判据

| 判据 | ⭐ 期望 | 🔴 不对说明 |
|---|---|---|
| 收到字节数 | ⭐ **972**（= 108 帧 × 9） | 0 ⇒ 见 §三 |
| **9N 对齐** | ⭐ **是 9 的整数倍** | 有余数 ⇒ 🔴 **截帧**，9N 铁律被破坏 |
| **帧头** | ⭐ **全 `0xA5`** | 有别的 ⇒ 🔴 帧错位 |
| 首帧内容 | ⭐ `A5 00 00 00 00 00 00 00 00` | — |
| 第 2 帧 | ⭐ `A5 00 00 00 00 00 00 00 01` | ⚠️ 序号不连续 ⇒ 丢字节 |

> ⭐ **序号递增是故意的**：⭐ **丢一个字节就会立刻看出来**（所有后续帧都错位），
> ⭐ 比"只比对长度"强得多。

## 三、⚠️ 收到 0 字节怎么排查（⭐ 按概率）

| # | 查什么 | ⭐ 怎么做 |
|---|---|---|
| **1** | 🔴 **ESP32 到底发了没** | ⭐ 看窗口 A 的 `burst N/3: wrote 324`。⚠️ 没这行 ⇒ 固件没跑起来/没烧进去 |
| **2** | 🔴 **TX/RX 接反了没** | ⭐ ESP32 `GPIO17` → USB-TTL **RX**（⚠️ 交叉） |
| **3** | 🔴 **共地了没** | ⭐ GND 对 GND，⚠️ 万用表量一下通断 |
| **4** | ⚠️ **USB-TTL 撑不到目标档位** | ⭐ 把 `uart_test_main.c` 的 `TEST_BAUD` 改 **115200**（⚠️ 现值 `500000`），⚠️ **两端都改**，重烧重测 |
| **5** | ⚠️ **口选错了** | ⭐ `COM29` 是 ESP32，⛔ 不是 USB-TTL |
| **6** | ⚠️ **口被别的程序占着** | 🔴 关掉串口助手 / 别同时开 monitor |

> ⭐ **判据 4 的依据**：⭐ 见上机指南 §5.2 ——
> 🔴 **"有些 USB-TTL 撑不到高档位"**（经验 `FPGA问题排查手册 27`）——
> ⚠️ **2026-09-30 更正**：⭐ 现在只要 **500 k**（`TEST_BAUD 500000`），⭐ 比 1 Mbps 宽松一倍。

## 四、⭐⭐ 这一步能证明什么、⛔ 不能证明什么

| ✅ 能证明 | ⛔ 不能证明 |
|---|---|
| ESP32 的 **UART1 外设**配置正确 | 🔴 **水池（pool）逻辑正确** |
| **`GPIO17` 引脚**能真的输出 | 🔴 **放水节奏（tick 限流）正确** |
| **500 kbps** 下字节能正确收发 | 🔴 **FPGA 会正确解析**（⚠️ 时钟/采样要 FPGA 侧验） |
| **9N 对齐**在物理层没被破坏 | 🔴 **`play_seq` 会出声**（⚠️ `top.v` 里仍未例化） |

⚠️ **特别注意**：本固件**绕过了** `pool_feed` → `frame_filter` → `pool_pump`
整条链路 ⇒ ⭐ **它绿了不代表正式固件的数据通路就是对的**。
