## 一、⭐ 被验证的链路

```
⭐ 上位机 / 跳线  ──写──▶  ESP32 GPIO18 (UART1 RX)
                              │
                              ▼
                    task_uart_to_ble()           ← esp32/ble/main/ble_main.c:607-685
                              │  ① 原样读字节（⛔ 不解析、⛔ 不重组）
                              │  ② 按 MTU-3 分块
                              ▼
                    esp_ble_gatts_send_indicate(  s_gatts_if, s_conn_id,
                                                  s_handle_noti, ... )   ← :663
                              │
                              ▼
                    BLE 特征 0xABF2 (NOTIFY)     ← esp32/ble/main/gatt_svc.c:16/115
                              │
                              ▼
                    PC 侧订阅 0xABF2 收通知       ← esp32/tools/send_frames_ble.py:240-244
```

## 三、🔴 修复的真 bug（⭐ 本轮的关键改动）

| 项 | ⭐ 内容 |
|---|---|
| **现象** | 蓝牙**已连接**、`s_handle_noti` 非 0、字节**确实到了** `GPIO18`（`u_rx` 在涨）—— 🔴 **但上位机一个 notify 都收不到** |
| **铁证** | `E BT_APPL: Unknown connection ID: 255 fail sending notification`（⭐ ESP-IDF 蓝牙栈自己打的） |
| **根因** | 🔴 `esp_ble_gatts_send_indicate()` 的第 1 个参数传了 **`ESP_GATT_IF_NONE`（= 0xFF）** ⇒ 被当成 `conn_id=255` ⇒ **必然失败** |
| **修法** | ⭐ 改传 **`s_gatts_if`**（⭐ 在 `ESP_GATTS_REG_EVT` 里由 `param->reg.gatts_if` 给出，`ble_main.c:261`） |
| **⚠️ 易混点** | ⭐ `s_gatts_if`（**接口** id）≠ `s_conn_id`（**连接** id）—— 🔴 **两个都要对** |
| **代码** | `esp32/ble/main/ble_main.c:650-663` |

### 3.1 ⚠️ 同族的第二处：延时陷阱（⭐ 一并修了）

| 项 | ⭐ 内容 |
|---|---|
| **位置** | `ble_main.c:682`（段间让出 CPU） |
| **问题** | ⚠️ `BLE_TX_GAP_MS = 2`，⭐ 而 `CONFIG_FREERTOS_HZ = 100` ⇒ `pdMS_TO_TICKS(2)` = 🔴 **0** ⇒ `vTaskDelay(0)` 几乎不让出 CPU |
| **为何潜伏至今** | 🔴 **这条反向通路一直没跑通**（⭐ 刚修掉 `gatts_if`）⇒ **这个延时从未真正执行过** |
| **修法** | ⭐ 走 `BLE_DELAY_TICKS_AT_LEAST_1()`（`ble_config.h:330-331`）⇒ 至少 **1 tick = 10 ms** |
| **⚠️ 副作用（⭐ 必须知道）** | ⭐ 这同时给反向通路**定了名义速率上限**：⚠️ **每包 ≥ 10 ms** ⇒ ⭐ 上限 ≈ **514 B / 10 ms ≈ 51 KB/s**（⚠️ 实际更低） |

## 六、🔴🔴 重要限制：**大流量会丢字节**（⭐ 2026-09-30 压力测试发现）

### 6.1 ⭐ 实测

⭐ **从 `GPIO18` 一次性灌 2000 字节**（⭐ 0..255 循环斜坡，⭐ 内容可校验）：

| 量 | ⭐ 值 |
|---|---|
| PC 写入 | **2000 字节** |
| ⭐ **固件实际收到**（`u_rx=`） | ⭐ **1611 字节** |
| BLE notify 出来 | **1611 字节** |
| 🔴 **丢失** | 🔴 **389 字节** |

⭐⭐ **关键判读**：🔴 **丢的是在【UART 接收侧】，⛔ 不是 BLE 侧** ——
⭐ 因为 `u_rx=1611` 说明**固件压根没收到那 389 字节**。

### 6.2 🔴 根因：**上行没有流控**（⭐ 正是对接单提醒的那条风险）

| 环节 | ⭐ 数值 |
|---|---|
| UART **RX 环形缓冲** | ⚠️ **仅 1026 字节**（`ble_config.h:117` = `9 × 114`） |
| 2000 字节到达耗时 | ⭐ **约 40 ms**（⭐ 500 k，20 µs/字节） |
| 通知分段 | ⚠️ **4 段**（⭐ `MTU-3 = 514`） |
| 每段间隔 | 🔴 **≥ 1 tick = 10 ms**（⭐ `BLE_TX_GAP_MS` 经 `AT_LEAST_1` 后） |
| ⇒ 搬运耗时 | 🔴 **≥ 40 ms** |

⇒ 🔴 **搬得和进得一样快（甚至更慢）** ⇒ ⚠️ 缓冲瞬间满 ⇒
🔴 **溢出丢字节，且【没有任何报错】**。

⭐ 与实测吻合：`1026（缓冲）+ 部分已搬走 ≈ 1611`。

### 6.3 ⚠️ 这条限制意味着什么

| # | 说明 |
|---|---|
| **1** | ⭐ **21 字节的小包【完全正常】**（⭐ 本轮验收就是 21 字节，逐字节一致） |
| **2** | 🔴 **大流量会静默丢** —— ⚠️ **FPGA 若回传整曲事件流，必然丢** |
| **3** | 🔴 **而 ESP32 目前【没有】向 FPGA 反压的手段**（⭐ 同一份"不做反向通道"的假设） |
| **4** | ⭐ **⇒ 这正需要 FPGA 侧在接线前先裁定**（⭐ 见对接单 §四「上行带宽风险」） |

### 6.4 ⭐ 改进方向（⭐ 未实施，⛔ 待裁定）

| # | 手段 | ⚠️ 代价 / 前提 |
|---|---|---|
| **1** | ⭐ **加大 UART RX 缓冲** | ⚠️ 吃内部 DRAM（⭐ 但 PSRAM 有余量）—— ⚠️ **只能缓解，不能根治** |
| **2** | ⭐ **提高搬运优先级 / 缩小段间隔** | ⚠️ 段间隔已到 1 tick 下限（⭐ 再小会塌成 0 ⇒ 看门狗） |
| **3** | ⭐⭐ **让 FPGA 侧限速（推荐）** | ⭐ **从源头控制** —— ⚠️ 需 FPGA 侧配合（⭐ 他们要限速发，⛔ 不能一口气发） |
| **4** | ⭐ **加流控/握手** | ⚠️ **要新增信号** —— ⚠️ 与「不做反向通道」的旧决策冲突 |

⚠️ **⇒ 本报告只【记录现象 + 定位根因】，⛔ 不擅自选方案** ——
⭐ **方案选择依赖 FPGA 侧裁定**（⭐ 见对接单 Q1~Q5）。
