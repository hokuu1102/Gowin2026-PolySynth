## 二、🔴 根因（⭐ 两个，都在**上游**）

### 根因 1：`DONE` 不可达 —— ⭐ **池自然放完后 `s_running` 没清**

🔴 **代码已经知道"放完了"** —— `pool.c` 的 `pool_pump()` 末尾：

```c
if (!s_feed_done_logged && s_frames > 0 && (s_play_idx >= s_frames)) {
    s_feed_done_logged = true;
    ... 打遥测日志 ...        /* ⚠️ 只打日志！ */
}
```

⚠️ **这个判据点（游标追上了池内帧数）就是"放完"的确定判据**，
🔴 **但它只打日志** ⇒ 既不清 `s_running`，也不通知任何人。

**两个连带后果**：

| # | 🔴 后果 |
|---|---|
| 1 | ⭐ `HMI_ST_DONE` 没有任何 set 点 ⇒ **屏上 `播完` 不可达** |
| 2 | ⭐ `pool_is_running()` **说谎** —— 放完后仍返回 `true` ⇒ ⚠️ 再按 START 被 `"already running"` **拒掉** |

### 根因 2：`READY` 语义不符 —— ⭐ **"灌完"的判据没被用起来**

⭐ `hmi.h` 的注释写的是：

```c
HMI_ST_READY,   /* 就绪 —— 灌完，等上板按键起播 */
```

⚠️ 而代码里 `READY` **只有"按 STOP"一个入口** ⇒ 🔴 **注释 ↔ 代码不一致**
（⭐ 这正是 0.11 第 4 类检查要抓的东西）。

⭐ 而"灌完"的判据**其实就在手边**（`frame_filter()` 里）：

| ⭐ 量 | ⭐ 来源 |
|---|---|
| `s_song_total` | ⭐ **总数帧**（`0x00`）给的**应到**事件数 |
| `s_song_events_rx` | ⭐ **实到**事件数 |

⇒ ⭐ **实到 == 应到（且应到 > 0）就是灌完**，⛔ 不用另设标志。

---

### 根因 3：`IDLE` 不可达 —— 🔴 **`case 0x01` 绕过了 wrapper，而"绕过"的原因是【调不到】**

⭐ 修完前两个根因后再测，⭐ **`待机` 仍读不到**（⭐ 屏上一直是 `断链`）。

⭐ **定位过程**（⭐ 每步都有独立判据）：

| ⭐ 步 | ⭐ 判据 | ⭐ 结果 |
|---|---|---|
| 1 | ⭐ 日志里有没有 `CMD 0x01: pool reset`？ | ✅ **有** ⇒ ⭐ 命令**到了**处理函数 |
| 2 | ⭐ 连读 6 次 `t1`（⭐ 跨 ~8 s） | 🔴 **全是 `断链`** ⇒ ⭐ 排除"重绘延迟" |
| 3 | ⭐ 读 `case 0x01` 的源码 | 🔴 **直接调 `pool_reset()`** ⇒ ⭐ 绕过 wrapper |

⇒ 🔴 **`start_action_reset()` 全工程**只有**一个**调用点（⭐ 串口 `X` 那条），
⭐ **BLE 的 `0x01` 走的是另一条路** ⇒ ⭐ `hmi_set_state(HMI_ST_IDLE)` 永不执行。

⭐⭐ **但真正的原因是第 4 步查出来的**：

```
275: static void start_action_play(void);
276: static void start_action_stop(void);
     ← 🔴 没有 start_action_reset 的前向声明！
```

🔴 **`start_action_reset()` 定义在 1037 行，⛔ 而 `case 0x01` 在 644 行**
⇒ ⭐ **没有前向声明就【调不到】** ⇒ ⚠️ 于是只能退而直接调 `pool_reset()`。

📌 **教训（⭐ 这条最值钱）**：
⭐ **"为什么这里没走公共封装"往往不是疏忽，而是【调不到】。**
⭐ 追根因时要问「⭐ **他为什么没这么写？**」—— ⛔ 不是"他忘了"。
⚠️ 而且 662 行的注释写的恰恰是「**复用 `start_action_play/stop/reset`**」
⇒ 🔴 **注释与代码相反**（⭐ 0.11 第 4 类检查的现场）。

✅ **修法**：⭐ **补上缺失的前向声明** ⇒ ⭐ 绕过的**理由**自然消失 ⇒
`case 0x01` 就能与 `0x03`/`0x04` 走同一条路。⛔ 不是在 `case 0x01` 里补一句
`hmi_set_state()`（⭐ 那是打补丁 —— 下一条新命令还会再绕过一次）。

## 二·补、⭐⭐ 把"不绕过"变成**代码里的不变量**（⛔ 不是"记得以后别忘"）

⭐ 按 0.12 第③步的判据：⭐ **若"补完之后你还得记住以后别忘" ⇒ 那还是补丁。**

⇒ ⭐ 新增 `esp32/tools/wrappers_check.py`：

| ⭐ 检查什么 | ⭐ 判据 |
|---|---|
| ⭐ `pool_reset()` / `pool_start()` / `pool_stop()` 的**每个**调用点 | ⭐ 必须落在某个 `start_action_*()` 的**函数体内** |
| ⭐ 例外 | ⭐ 必须带 `ALLOW-DIRECT-POOL-CALL` **显式标记**（⭐ 例外要看得见） |
| ⭐ **非空洞性** | ⭐ 合成一个"绕过"样本 ⇒ ⭐ **检查必须报红**（⛔ 否则全绿证明不了任何事） |
| ⭐ **真源码非空洞** | ⭐ 真源码里必须确实存在 ≥3 处封装内调用 ⭐ 和 1 处显式豁免 |

⭐ **实测结果**：⭐ 封装区间 `(1036,1054)` / `(1056,1061)` / `(1063,1068)`，
封装内调用 **3** 处 · 豁免 **1** 处（⭐ 开机初始化）· 🔴 绕过 **0** 处 ✅

⚠️ **踩过的坑（⭐ 值得记）**：⭐ 第一版检查**误报了 6 处** ——
🔴 **全是注释散文里的提及**（⭐ 例如 "🔴 原来这里直接调 `pool_reset()`"）
⇒ ⭐ 修法：**先剥块注释/字符串，并要求调用出现在【语句位置】**。
📌 ⭐ **误报比没有检查更坏** —— ⚠️ 它会让人**直接关掉检查**。

### ⭐ 为什么用 **take 语义**（⛔ 不是"读一个 bool"）

⚠️ `task_drain` 是**轮询**的 ⇒ ⭐ 若只读不清，它会**每一轮都上报一次**
⇒ ⭐ 状态被反复重设（⚠️ 且遥测刷屏）。

⭐ **take 语义让"事件"只被消费一次** —— ⭐ 与"电平"区分开。

### ⭐ 为什么 D 必须**有条件**（只在 `LOADING` 时迁移）

⚠️ 若无条件：⭐ **重播途中**若收到重发的帧 ⇒ 🔴 会把 `PLAYING` / `播完`
**打回 `就绪`**。⭐ 所以判据是「⭐ 当前状态 == `LOADING`」。

## 四、⚠️ 清理点（⭐ 枚举"同类路径"的另一半）

⭐ 新标志 `s_finished` 是**一次性事件** ⇒ ⭐ 必须在**每个"新一曲"的入口**清掉：

| ⭐ 入口 | ⭐ 清了没 | ⭐ 不清会怎样 |
|---|---|---|
| `pool_reset()` | ✅ | ⚠️ 新曲一开就**误报 `播完`** |
| `pool_start()` | ✅ | ⚠️ 重播同一首时，上一轮的完成事件**残留** |

📌 ⭐ **判据：凡是"一次性标志"，都要问一句"谁清它"** ——
⭐ 只置不清 = 泄漏（⭐ 见 0.11 第 2 类检查）。

### 🔴 附：⭐ 又发现一个**同类**死功能 —— `g0`（曲谱名）

⭐ 排查时顺手查的（⭐ **同一类问题：函数写了但没人调**）：

```c
hmi.h:79   void hmi_set_song(const char *name);        /* ⭐ 声明 */
hmi.c:302  void hmi_set_song(const char *name) { ... } /* ⭐ 定义 */
hmi.c:415  snprintf(cmd, ..., "g0.txt=\"%s\"", s_c.song);  /* ⭐ 发给屏 */
```

🔴 **全工程没有任何地方调用 `hmi_set_song()`** ⇒ ⭐ `s_c.song` 永远是初值 `"----"`
（`hmi.c:282`）⇒ ⭐ **屏上曲谱名永远显示 `----`**。

⭐ **实测印证**：⭐ `get g0.txt` 回 `p----` ✅（⭐ 与推断一致）。

📌 **同类模式的教训**：⭐ **"定义了但没人调"的函数，编译器⛔ 不会报警**
（⭐ 它是非 static 的，链接器也不报）⇒
⭐ **必须靠"枚举所有 set 点/调用点"来发现** —— ⭐ 这正是 0.12 第 ① 步。

### ✅ 已修（⭐ 用户裁定 2026-10-01）：新增 CMD `0x22` 设曲名

| ⭐ 项 | ⭐ 内容 |
|---|---|
| ⭐ 格式 | `0x22` + UTF-8 曲名（⛔ 不需要结束符） |
| ⭐ 空 payload | ⭐ 回落 `----` |
| ⭐ 净化 | ⭐ 去 `"` · `\` · `0x7F` · 控制字符（⭐ **在 `hmi_set_song()` 源头做**） |
| ⭐ 验证 | ⭐ `hmi_song_check.py`：**24 项自检 + 7 个真机用例全过** ✅ |

⚠️ **净化为什么必须在源头**：⭐ 曲名会拼成 `g0.txt="<名字>"` ——
🔴 含 `"` 会**截断命令**（⭐ 多出来的部分被当成下一条命令 ⇒ 后面全乱）；
🔴 含 `0xFF` 会**提前结束**（⭐ TJC 用 `FF FF FF` 当结束符）。

⚠️ **顺带发现的一个"测量陷阱"**（⭐ 不是固件 bug）：
⭐ 固件 RX 缓冲是 `uint8_t buf[32]`（`hmi.c` 的 `hmi_poll_rx`）
⇒ ⭐ **长回复会被拆成多行日志** ⇒ 🔴 只取最后一段 ⇒ **测量结果被截断**
（⭐ 实测：60 字符曲名只读到 31 个 ⇒ ⚠️ 差点误判"固件截断了"）。
⭐ 判据：⭐ **回复以 `FF FF FF` 结束** ⇒ ⭐ 要**拼到看见结束符**为止。
📌 同族 `C139` —— ⭐ 都是**测量层**的误判。
