### 补充 3：tempo 双 0 + 旋律 `is_drum` 任何路径都是 0

工具内自查（`check_drum_split` 的 ⑦/④/⑥）跑在**读回来的 hex** 上：

```

[A4] 每个 axis 内 is_drum 取值唯一 : 是  每轨取值 {0:[0],1:[0],2:[0],3:[0],12:[1],13:[1],14:[1],15:[1]}
     旋律记录里 is_drum!=0 的 : 0 条
变异7: tempo 置 is_drum=1   报错 符合预期 | ERROR: 记录 0 是鼓 (is_drum=1) 但 inc=131941 != 0 …
```

"任何路径都是 0"的机械保证：旋律的 `is_drum` 由 `base` 里的常量给出（`1 if drum else 0`），

`route_pool()` 是唯一的路由函数，它只看 `is_drum`。

## 七、坑（都是实测踩到的）

1. **`--drum-track` 的轨序号含第一条约等于空的 Tempo/指挥轨**。真曲里 `--drum-track 4` 命中的是 **Pad**（第 5 条轨），不是鼓轨（鼓轨是序号 5）。这不是 bug（用户说哪条就是哪条），但极易误用 ⇒ 已改成：① 报告里写明规则 ② 指定项一个都没匹配上时出 **WARNING**（实测 `--drum-track 99,Nope` 会报"轨序号 99（本文件共 6 条轨）, 轨名子串 'nope'"）。
2. **判据③逼出一条隐含约束**：`is_drum=0` 的事件轴号不许落 12..15 ⇒ 旋律不能用 12..15。原来的顺序编号（0,1,2,…）在 ≥13 条旋律轨时会撞上，所以旋律改成 `nxt % 12`，并在报告里出警告（实测 14 条旋律轨：警告正确出现，轴号仍全 ≤11，不崩）。**≥13 条旋律轨时会有旋律轨共用轴号** ⇒ 同轴同源 (SRC_SCORE) 的 note_off 会互相清 voice，这是要 FPGA 侧扩轴号位宽才能根治的（4 位字段只剩 12 个值）。
3. **轴号从"整条鼓轨一个号"改成"一件一轴"之后**，旋律轴号又回到与改前完全一致的 0..3（鼓不占顺序号）—— 这让 [B] 的逐条对比能成立（314 条旋律 bit63..5 一字不差）。
4. **`score_word.py` 在本轮被改了两次**（14:38、14:40）。所以交叉校验做成"尽力而为"：导入失败或签名不匹配就降级成跳过并打印原因，⛔ 不让 mid2evt 因为另一个文件的接口变动而罢工。
5. **报告里漏了一个 `%d`**（轴号预算警告那行）⇒ 已在边界测试里发现并修掉（第 2 次实测输出已是正常文字）。
6. `tools/evt2wav.py` 的试听产物**不受影响**：新旧 CSV 各渲染一遍，两个 wav **逐采样完全相同**（1204426 帧、0 个不同采样）—— 因为它对 `f<=0` 的音符直接跳过，而鼓事件 inc=0。⚠️ 但它**不渲染鼓**（U-16b 已知缺口），本次未动它。

## 八、边界与未做

- 鼓事件的 `vel` 仍是 130（与旋律同口径，本次未改；手册未要求）。
- 鼓事件**不受 `--transpose` 影响**（GM 打击乐音符号=鼓件身份，移调会变成另一件鼓）；已在注释与报告里写明。
- `evt2uart.py` / `send_frames*.py` / `score_uploader.py` 等下游只读 `events.hex`（一行一字），本次新增位不影响它们；CSV 的两列加在**末尾**，按下标 0..7 读的老工装不受影响。
- 本报告与全部产物在 `build/drumsplit-verify/`（该目录被 `.gitignore` 忽略）。若要把本报告归档进仓库，建议移到 `files/20-代码/` 或 `esp32/evidence/` —— 我**没有**替你们放，因为那两个目录里此刻有别的线在写。
