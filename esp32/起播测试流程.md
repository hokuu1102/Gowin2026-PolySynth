## 一、⭐ 三条硬前提（⛔ 漏一条就测不出来）

| # | 前提 | ⚠️ 说明 |
|---|---|---|
| **1** | 🔴 **波特率两侧必须同档** | ⭐ **FPGA 侧 = 500 k**（`FPGA2026/rtl/top.v:682`）<br>⭐ ESP32 侧已改 500 k ✅<br>⚠️ 不同档 ⇒ **静默乱码**（⛔ 不报错） |

| **3** | ⚠️ **起播后要等 ~10 秒才出数据** | 🔴 `BLE_POOL_LEAD_TICKS = 20000` ⇒ ⭐ 提前量<br>⚠️ **不是"按了没反应"** |

### 1.1 🔴 第 3 条特别容易误判

⭐ `pool.c:500-507`：提前量没走完 ⇒ **本轮一帧都不发**。

| 速度 | 20000 tick 实际时间 |
|---|---|
| 120 BPM | ⭐ **约 10.4 秒** |
| 168 BPM | ⚠️ 约 7.4 秒 |

⇒ ⭐ **按了起播后要等约 10 秒才会看到 `sent=` 开始涨。**
⚠️ 这是**设计的提前量**（给 FPGA 缓冲打底），⛔ 不是 bug。

### 1.2 ⭐⭐ 精确时间轴（⭐ 用 200 帧假曲谱算出来的，⚠️ 决定抓取窗口）

⭐ 依据：`pool.c:526-533` 的 `lead_end = s_t0_tick + BLE_POOL_LEAD_TICKS`，
且 `send_frames_ble.py` 的假曲谱 `tick = 1000 + i*37`（⭐ 首帧 tick=1000）。

| 项 | 值 |
|---|---|
| `s_t0_tick`（首帧 tick） | **1000** |
| `BLE_POOL_LEAD_TICKS` | **20000** |
| ⇒ `lead_end` | **21000** |
| 1 tick @120BPM | **520.83 µs** |
| ⭐ **第 1 帧发出** | ⭐ **起播后 10.42 s** |
| 末帧 tick | **8363** |
| ⭐ **第 200 帧发出** | ⭐ **起播后 14.25 s** |
| ⭐ **发完窗口** | ⭐ **3.83 s** |

⭐⭐ **⇒ 抓取窗口必须 ≥ 15 秒**，⚠️ 且**前 10.4 秒必然是空的** ——
🔴 **这不是故障，⛔ 不要据此判失败。**

⚠️ **`pace` 仍应 ≈ 1.0** —— 因为 pace 只统计**已发出的帧**
（tick 跨度 7363，⭐ 而它们确实用了 3.83 s 发出 ✅）。

### 步骤 2：⭐ 起播（两种方式,选一）

#### 方式 A：串口字符触发（⭐ 当前默认,⛔ 不用接线）

⭐ **把 USB-TTL 的 TX 接到 ESP32 的 `GPIO18`（UART1 RX）**：

```
USB-TTL TX  ──→  ESP32 GPIO18   ⭐ 触发字符从这里进
USB-TTL GND ───  ESP32 GND      🔴 必须共地
```

⭐ 然后发一个 `S`：

```powershell

time.sleep(0.2)
s.write(b'S')          # ⭐ 起播
s.flush(); time.sleep(0.2)
s.close()              # ⭐ 必须释放
print('sent S')
"
```

⭐ 日志应立刻出现：

```

W pool: pool marked DONE: 200 frames (1.76 KB)
W pool: pool START from tick=... at t0_us=...
```

#### 方式 B：按键触发（⭐ 需接线）

```
按键一端 ──→ ESP32 GPIO6     ⭐ 低有效
按键另一端 ─→ ESP32 GND
```

⭐ 用 `-DBLE_START_TRIGGER=1` 编译烧录。

## 三、⭐⭐ 验收判据

### 3.1 ESP32 日志（窗口 A）

| 字段 | ⭐ 期望 | 🔴 不对说明 |
|---|---|---|
| ⭐ **`sent=`** | ⭐ **开始往上涨**（⚠️ 起播后约 10 s 起） | 🔴 一直 0 ⇒ 起播没生效 |
| `pool=` | 200 | 应保持 |
| 🔴 `unk=` / `ovf=` / `mismatch=` | ⭐ **恒为 0** | 非 0 ⇒ 真故障 |
| ⚠️ **`late=`** | ⚠️ **可以有值** | ⭐ 含义:放水落后谱子的最大 tick 数 |
| ⭐ **`clamp=`** | ⚠️ **可以有值** | ⭐ tick 限流截断次数（大 = 老落后,但不致命） |
| 🔴 **看门狗** | ⭐ **不触发** | ⭐ 触发 ⇒ 查 `pdMS_TO_TICKS` 类陷阱 |

### 3.2 时序脚本（窗口 C）⭐ **核心判据**

| 判据 | ⭐ 期望 | 🔴 说明 |
|---|---|---|
| ⭐⭐ **节奏比**（实测墙钟 / 谱子应耗时） | ⭐ **≈ 1.0**（±10%） | 🔴 **远小于 1（如 0.01）⇒ 没限速,一次性倾泻** |
| 9N 对齐 | ⭐ 是 9 的整数倍 | 有余数 ⇒ 截帧 |
| 帧头 | ⭐ 全 `0xA5` | 有别的 ⇒ 错位 |
| ⭐ **帧间间隔分布** | ⭐ 随谱子密度变化 | ⚠️ 全为 0 ⇒ 倾泻 |
| 换速事件（`kind=2`） | ⚠️ **假曲谱里应为 0** | 🔴 **非 0 ⇒ 见 §3.4** |

### 3.3 ⭐⭐ 一句话判据

> ⭐ **如果"节奏比 ≈ 1.0" ⇒ 放水是按谱子时间限速的 ✅**
> 🔴 **如果远小于 1 ⇒ 它在【一次性倾泻】,⚠️ 会把 FPGA 的 8 KB 缓冲瞬间灌满** ⇒
> ⚠️ **静默丢事件**（⭐ 这正是 `pool.c:24` 说的「宁可饿着,不可撑着」要防的事）

### 3.4 🔴🔴 假曲谱必须【不含换速事件】—— 实测踩过的坑

⚠️ **2026-09-30 实测**：⭐ 起播后 `sent=` **涨到 3 就停住**。
🔴 **根因不是固件**，⭐ **是测试数据本身不合协议语义**：

| 项 | ⚠️ 原来的假曲谱 | 🔴 后果 |
|---|---|---|
| `kind = i % 4` | ⭐ 产生 **50 个 `kind=2`** | 🔴 固件把它当**换速**处理 |

⭐ 固件里 `kind==2` 的语义（`pool.c:634-642`）：
```c
if (kind == KIND_TEMPO && inc > 0) {
    s_tick_inc = inc;                   // ⚠️ inc 被当成新的 tick_inc
    s_t0_tick  = tick;  s_t0_us = now;  // 🔴 重锚时间基准！
}
```

🔴 **⇒ 每个伪造的换速事件都会【重锚时间基准】⇒ 提前量从头累积 ⇒ 又要等 ~10 秒。**
⭐ 50 个换速事件 ⇒ 🔴 **永远在重锚，根本放不完 200 帧。**

⭐ 固件日志的**铁证**：
```
I pool: tempo @tick=1222 -> tick_inc=53900 (time base re-anchored)
```

⭐⭐ **⇒ 判据：假曲谱的 `kind` 只能取 `0`（note_on）/ `1`（note_off），
`inc` 必须是【恒定】的音高增量。** ⛔ **⛔ 绝不能出现 `kind=2`。**

⚠️ **为什么这个坑隐蔽**：
- ✅ **帧完整性验收【会通过】**（9N 对齐、帧头全 `0xA5`）
- 🔴 **只有【放水时序】验收才暴露** ⇒ ⚠️ 两套判据必须**都跑**

## 三点五、⭐⭐⭐⭐ 已修的历史缺陷：`delta_us_to_ticks` 的【夹紧】

> ⭐ **2026-09-30 实测发现并修复** —— ⚠️ **这是"`sent=` 恒为 0"的真正根因之一。**

### 3.5.1 🔴 现象与根因

| 项 | 说明 |
|---|---|
| **现象** | ⭐ 起播成功（`pool START` 有日志）、`s_running=true`，🔴 **但 `sent=` 恒为 0** |
| ⚠️ **迷惑点** | 🔴 再次按 `S` 会得到 `START ignored: already running (sent=0)` ⇒ ⚠️ **看起来像"已经在跑了"** |

🔴 **根因**（`pool.c` 的 `delta_us_to_ticks`）：

```c
if (dus > BLE_POOL_MAX_DELTA_US) {
    dus = BLE_POOL_MAX_DELTA_US;      // 🔴 夹紧到 500 ms
}
return ((uint64_t)dus * tick_inc * F_CLK_HZ) / US_NUM_DEN;
```

⭐⭐ **两个量纲矛盾**：

| 量 | 值 | 量纲 |
|---|---|---|
| `BLE_POOL_MAX_DELTA_US` | **500 ms** | ⚠️ 墙钟（⭐ 为防中间量溢出而设的上限） |
| `BLE_POOL_LEAD_TICKS` | **20000 ticks ≈ 10.4 s** | ⭐ 音乐时间 |

⇒ 🔴 **`elapsed_ticks` 最大只能到 `960`，而放水要求 `> 21000`** ⇒
🔴 **数学上永远达不到** ⇒ `allow_emit` 恒 `false`。

> ⚠️ **注意**：`pool_pump()` 传进去的是**绝对经过时间**（`now_us - s_t0_us`），
> ⚠️ 而那个夹紧是**为【增量】设计的**（原注释写"pump 本身就是周期性的"）
> ⇒ 🔴 **调用约定与实际用法不一致。**

### 3.5.2 ✅ 修法（结构性，⛔ 不是调大数字）

⭐ **把"夹紧"改成"分段累加"**：

```c
uint64_t ticks = 0;
while (dus > 0) {
    uint64_t seg = (dus > BLE_POOL_MAX_DELTA_US) ? BLE_POOL_MAX_DELTA_US : dus;
    ticks += (seg * tick_inc * F_CLK_HZ) / US_NUM_DEN;   // ⭐ 单段 ≤ 500ms ⇒ 中间量恒定安全
    dus -= seg;
}
```

⭐ **两条判据**：

| # | 判据 | ⭐ 结果 |
|---|---|---|
| **1** | ⭐ **单调性**：输入变大 ⇒ 输出必须变大 | ✅ `0.5s→960` · `11s→21120` · `60s→115200` |
| **2** | ⭐ **中间量不溢出** | ✅ **仍是 62 bit**（< 64） |

⚠️ **⛔ 不要只把 `BLE_POOL_MAX_DELTA_US` 调大** ——
⚠️ 那只是把门槛往后推，🔴 **同样的缺陷会在更长的时长上复现**，而且会**真的溢出**。

⚠️ **对照经验**：`C102`（⭐ "防溢出"的夹紧把长时长静默截短）。
