# 🎵 evt2midi —— FPGA 回传事件 → 可播放 MIDI

> ⭐ **用户 2026-10-01**：「这个是实现 **FPGA 乐曲回传**的，
> 也就是**回到电脑上能逆向回 MIDI**」
> ⇒ ⭐ **本目录就是那条链路的【最后一环】**。

---

## 一、⭐ 一句话

```
FPGA ──事件──> ESP32 ──BLE──> PC ──[rec_upstream.py]──> rec.bin
                                                        │
                                          [evt2midi.py] │
                                                        ▼
                                                     song.mid  ⭐ 任意播放器可放
                                                        │
                                          [midi_verify.py]  ⭐ 读回来核对
```

---

## 二、⭐ 四个工具 + 一个"格式定义处"

| 文件 | ⭐ 作用 | ⚠️ 关键设计 |
|---|---|---|
| **`rec_upstream.py`** | ⭐ **录制**上行字节流（BLE 订阅 `0xABF2`） | 🔴 **只落盘原始字节，⛔ 不解析** —— ⚠️ 格式还没冻结，⭐ 存原始字节 ⇒ 格式定了能**重新解析** |
| **`evt2midi.py`** | ⭐ **转换**成标准 `.mid` | ⭐ 校验驱动 + 坏帧记账 + 取模 Δt（⭐ 见下） |
| **`midi_verify.py`** | ⭐ **按 MIDI 规范读回** `.mid` | 🔴 **独立实现**（⛔ 不复用写侧代码）—— ⚠️ 读写共用一套 ⇒ "自己写的 bug"会被"自己写的检查"放过 |
| **`frame_format.py`** | ⭐⭐ **上行帧结构的【唯一】定义处** | 🔴 格式未冻结 ⇒ ⭐ **会变的东西集中在这一处**，⭐ 改版只动它 |
| `_e2e_check.py`<br>`_find_real_risk.py`<br>`_mutation_check.py`<br>`_live_test.py` | ⭐ 证据 / 验证脚本（⭐ `_` 开头 ⇒ `selftest_all.py` 会跳过） | ⚠️ 它们**直接跑**，⛔ 没有 `--selftest` |

### 用法

```powershell
# ① 录（⭐ --start 会发 CMD 0x03 让 ESP32 起播）
python rec_upstream.py --out rec.bin --seconds 30 --start --hex rec.hex

# ② 转（⭐ --verify 会写完立刻读回核对）
python evt2midi.py --in rec.bin --out song.mid --verify

# ③ 只想看看解析出了什么
python evt2midi.py --in rec.bin --dump

# ④ 按规范读回一个 .mid（⭐ 也可以拿 --expect 逐项核对）
python midi_verify.py --in song.mid

# 离线自检（⛔ 不需要硬件）
python evt2midi.py --selftest
python frame_format.py                 # ⭐ 直接跑就是自检
python midi_verify.py --selftest
```

⚠️ `evt2midi.py` 的 `--table-fallback`：⭐ **默认关**。
🔴 默认时 `phase_inc = 0` 的事件**跳过并计数**（⛔ 不猜音高）；
⭐ 只有显式打开，才会用**表同步帧里的标称增量**兜底（⭐ 且**单独计数**，两种来源分得清）。

## 三、⭐⭐ 三个"想当然会错"的地方（⭐ 都实测校准过）

### ① `phase_inc` 反算必须用 **50 MHz**，⛔ 不是音频帧率

```
⭐ 正解： f = inc × 50e6 / 2³²          （⭐ inc 就是这么造出来的）
🔴 错解： f = inc × 48.828e3 / 2³²      （⚠️ 错 1024 倍！）
```
⚠️ 先例：`tools/evt2wav.py:59-70` **明确警告过**这个坑（⭐ `FS = 48828.0` 与 `CLK = 50_000_000.0`）
⇒ ⭐ 本工具沿用同一口径。

⭐ **自检怎么抓它（⭐ 加固后）**：⚠️ 光验"`inc_to_hz(inc440) ≈ 440`"是**抓不住的** ——
🔴 因为 `inc440` 是从 `CLK_HZ` **反推**的 ⇒ ⚠️ `CLK_HZ` 整体改错时两边一起错 ⇒
**往返自洽** ⇒ 🔴 假绿。⇒ ⭐ 现在**额外用写死的规范值 `inc = 37796`** 把 50 MHz 这个前提钉死，
⭐ 并把那个错解**显式算出来**，断言"两解必须能区分"。

### ② `tick` 是**自由运行**的 32 位计数器 ⇒ **Δt 必须取模，而且要【逐事件累加】**

```
⭐ 正解： Δ = (t_n − t_{n−1}) mod 2³²       （⭐ 逐事件累加 ⇒ 支持任意次回绕）
🔴 错解 A： Δ = t2 − t1                     （⚠️ 回绕时得到巨大负数）
🔴 错解 B： Δ = (t_n − base) mod 2³²        （⚠️ 固定基准 —— 只在"一圈内"才对）
```
📌 32 位 @50 MHz ⇒ ⭐ **85.9 秒就回绕一次** ⇒ ⚠️ **真实曲子必然跨第二圈**。
🔴 错解 B 的后果：⭐ **第 90 秒会被算成第 4.1 秒**（⭐ 差 86 秒），🔴 **而文件依然"看起来正常"**。
⇒ ⭐ 2026-10-01 加固时已改为**逐事件累加**（⭐ 见 §八）。

⭐ 自检 ⑤ **不是自己算一遍取模**（🔴 那是空洞的 —— 它根本不碰生产代码），
⭐ 而是**走 `build_midi` 产出 MIDI 字节 → 用 `midi_verify.py` 读回来**核对真实时间差。

### ③ 🔴 **只检查 `MThd` 文件头是假绿**

⚠️ 文件可以**头对、内容全错**（音高错 / 力度错 / 时间轴整体偏移 —— 头都还是对的）。
⇒ ⭐ 判据必须是 **按 MIDI 规范把事件读回来，逐项比对音高 / 力度 / 时序**。

## 四、⚠️ 一条**我自己更正过的**判断（⭐ 留档，⛔ 免得后人重踩）

> ⭐ 我原先以为：「载荷里出现 `0xA5` 会让"扫描式"解析失步」
> 🔴 **实测推翻了它**（⭐ 见 `_find_real_risk.py`）。

| ⭐ 场景 | ⭐ 定长状态机 | 🔴 扫描式 |
|---|---|---|
| 正常连续流 | ✅ | ✅ |
| `tick = 0xA5000000`（⭐ 载荷含 `0xA5`） | ✅ | ✅ **也对** |
| `tick = 0xA5A5A5A5`（⭐ 连续 4 个） | ✅ | ✅ **也对** |

⭐⭐ **为什么**：⭐ 「见 `0xA5` 就吃 14 字节」**不会去检查帧内载荷**
⇒ ⭐ 载荷里的 `0xA5` 被**整帧跳过去**了。

### ⭐⭐ 真正的差别：**坏帧会不会伪装成好数据**

| ⭐ 场景 | 🔴 扫描式（无校验） | ✅ 状态机（本工具） |
|---|---|---|
| 帧内混入 `0xA5`（⭐ `_find_real_risk.py` 用例 D1） | ⭐ 输出 **933**（⚠️ **错的，但看起来正常**） | ⭐ **拒收 + 计数** |
| 帧内丢 1 字节（⭐ 用例 C1） | ⭐ 输出 **256003**（⚠️ 同上） | ⭐ **拒收 + 计数** |

🔴 **⇒ 风险不是"失步"（那你看得出来），而是"错值伪装成合理值"（你看不出来）。**
⇒ ⭐ 所以本工具的核心是 **校验 + 坏帧记账**，⭐ 而不是"怎么找帧头"。
📌 ⚠️ 顺带更正：⭐ 状态机**救不回**被破坏的那一帧（数据真的丢了）——
⭐ 它的价值是**把"丢了"这件事报出来**（⭐ `_find_real_risk.py` 的期望值已按此修正）。

## 五、⚠️ 格式状态：⭐ 仍是**草案**

| ⭐ 部分 | ⭐ 状态 |
|---|---|
| **ASCII 事件流**（`t`/`s`/`x`/轴号/6 类原因码…） | ✅ **已是事实标准**（⭐ FPGA 侧已在跑） |
| **二进制帧**（`0xA5` + 14 B 音符类 / 68 B 表同步） | ⚠️ **草案，⛔ 未冻结**<br>⭐ 见 `files/20-代码/ESP32侧再回函-20261001.md` §三 |

⇒ ⭐ **帧布局集中在 `frame_format.py`**（⭐ 帧头 / 类型 / 长度 / 偏移 / 校验 全在那一个文件）
⇒ ⚠️ **格式冻结后只改那一处**，⛔ 不用动解析逻辑，⛔ 也不会出现"两处漂"。

⚠️ **已知的格式待定项**（⭐ 我在回函里提了，⛔ 还没答复）：
1. ⭐ **`tick` 与"谱面第几拍"的对齐** —— ⚠️ 现在只能算**相对间隔**，算不出"弹在第几拍"
2. ⚠️ **`seq` 只有 8 位** ⇒ ⭐ 750 事件/s 时 **0.34 秒就回绕** ⇒ 只能当短窗口丢帧检测

## 八、⭐⭐ 2026-10-01 加固记录（⭐ 为什么这么改）

> 🔴 起因：⭐ 本轮复核发现**判据本身有多处假绿**（⭐ 全绿⛔ 不代表有保护）。

| # | 🔴 加固前的问题 | ⭐ 加固后 |
|---|---|---|
| **1** | `parse_frame` 对**未知类型**按 14 B 回退着解；解析器还把未知类型**计入 `frames_ok`** 并产出一个事件 | ⭐ 类型**白名单** + `frame_len_known()`（⭐ 未知 ⇒ `None`）⇒ ⭐ **拒收 + 计数 + 记原因**，⛔ 不进 `frames_ok` |
| **2** | 长度不足 / 半帧与"校验错"**混在同一个计数器**里 | ⭐ 拆开：`frames_bad_csum` / `bad_type` / `truncated`，⭐ 并有 `rejected` 合计与 `rejects` 明细 |
| **3** | 重同步**只认 14 B 帧**，且窗口只有 `14×4 = 56 B` ⇒ ⚠️ **跨不过 68 B 的表帧** ⇒ 🔴 坏表帧后面那一帧被静默丢掉 | ⭐ 逐候选点试**每一种已知帧长** + 类型必须在白名单 + 窗口放宽到 `68+14`；⭐ **优先试帧对齐的下一个位置** |
| **4** | `build_midi` 用**固定基准**取模 ⇒ 🔴 跨第二圈（>85.9 s）时间轴整体错 | ⭐ 改为**逐事件累加**取模 ⇒ ⭐ 支持任意次回绕；⚠️ 单步 Δ>43 秒另计 `big_tick_steps` |
| **5** | ⛔ **不写 Tempo 元事件** ⇒ ⚠️ `--bpm != 120` 时文件里**没有任何东西**告诉播放器速度 ⇒ 🔴 播放速度错 | ⭐ 写 `FF 51 03 <µs/四分音符>` ⇒ ⭐ 文件**自描述** |
| **6** | `inc = 0` 时会**静默**回退到表（⚠️ 且没有单独计数） | ⭐ 默认**跳过 + 计数**（⛔ 不猜音高）；⭐ 表兜底改为**显式开启**且**单独计数** |
| **7** | 自检 ⑤ **自己算取模**（⭐ 不碰生产代码）⇒ 🔴 空洞 | ⭐ 改走 `build_midi` → **读回 MIDI** 核对 |
| **8** | `frame_format` §5 只断言"表帧按 14 B 解结果不同" ⇒ 🔴 弱断言 | ⭐ 改成"**必须抛错拒收**"，⭐ 并加 §6 一整段"不合法输入必须拒收" |
| **9** | 自检 ① 的 440 Hz 往返**自洽**（⭐ `inc440` 由 `CLK_HZ` 反推）⇒ 🔴 抓不到 `CLK_HZ` 整体改错 | ⭐ 加**写死的规范值 37796** + 把错解显式算出来对比 |
| **10** | `stats.orphan_off` 声明了但**从没被赋值**（⭐ 死字段） | ⭐ 真的实现（⭐ 没 on 就 off ⇒ 通常意味着前面有帧被拒收） |
| **11** | 没有"读回来核对"的能力 ⇒ ⚠️ 只能看 `MThd` | ⭐ 新增 `midi_verify.py`（⭐ 独立实现，含 running status / meta / sysex / 坏文件拒收） |

⚠️ **未改**：⭐ 帧格式本身（⛔ 草案未冻结，⭐ 我只做"能识别不合规"的加固，⛔ 不改语义）。
