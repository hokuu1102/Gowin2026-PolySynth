# HDMI 参考实现调研与移植（H1）

> 日期：2026-09-29
> 板卡：Tang Console + Tang Mega 60K SOM（GW5AT-LV60PG484A）
> 范围：第三周 H1——参考实现调研、管脚与时钟确认、最小移植方案
> 当前状态：**调研、独立最小 RTL 移植、Gowin 全流程构建和引脚核验已完成；官方 720p 参考工程已于 2026-09-30 上板出图（对照码流 F，见 bringup/hdmi_640x480/上板调试记录-20260930.md）。**

## 1. 结论摘要

1. Tang Console 板载一个 DVI（HDMI 兼容）TX 接口；官方页面标称能力为 `1080P30 / 720P60`，因此本项目不需要另做 HDMI 扩展板。[Sipeed Tang Console 官方 Wiki](https://wiki.sipeed.com/hardware/zh/tang/tang-console/mega-console.html)
2. Tang Mega 60K 官方 `cam_dvi` 工程已经给出可作为 Console 60K 软件基线的 TMDS 管脚、HPD 控制、Gowin PLL 与 DVI TX IP；该工程演示的是 `720P@60/30`，并带有摄像头和 DDR3 帧缓冲，不能整工程直接并入合成器。[官方 cam_dvi 说明](https://github.com/sipeed/TangMega-60K-example/tree/main/cam_dvi)
3. 官方设计意图是 `50 MHz -> 74.25 MHz pixel + 371.25 MHz pixel×5`，DVI TX 用 5 倍像素时钟完成 DDR 10:1 串化；但本次真实构建发现，官方提交的 `TMDS_PLL_60HZ.v` 实际参数为 `MDIV=22 / ODIV0=3 / ODIV1=15`，Gowin 1.9.12.03 推导为 `73.333/366.667 MHz`。因此本项目最小参考工程按实际 RTL 约束，不把官方元数据中的名义频率冒充为真实输出。[官方 TMDS_60HZ.sdc](https://github.com/sipeed/TangMega-60K-example/blob/main/cam_dvi/src/TMDS_60HZ.sdc)、[官方 PLL RTL](https://github.com/sipeed/TangMega-60K-example/blob/main/cam_dvi/src/gowin_pll/TMDS_PLL_60HZ.v)
4. H2 的 `640×480@60` 不能表述为“50 MHz 除二，所以完全免 PLL”：像素时钟即使取 25 MHz，三个数据通道仍需每像素发送 10 bit。若采用 DDR 5:1 串化，就仍需约 `125/126 MHz` 的高速时钟以及 PLL 或等效的专用时钟资源。[fpga4fun TMDS 说明](https://www.fpga4fun.com/HDMI.html)、[hdl-util 5× DDR 接口](https://github.com/hdl-util/hdmi/blob/master/src/hdmi.sv)
5. H4 的 `1920×1200@60` 超出 Console 官方标称档位，且仅按有效像素计算就已经需要大于 `138.24 MHz` 的像素吞吐、每条数据 lane 大于 `1.3824 Gbit/s`；加上消隐后还会更高。Sipeed 的 60K SOM 页面给出的普通 LVDS 指标是 `1.25 Gbit/s`，所以 H4 必须作为高风险探索项，不能在 H1 阶段承诺可用。[Tang Console 官方能力](https://wiki.sipeed.com/hardware/zh/tang/tang-console/mega-console.html)、[Tang Mega 60K 官方参数](https://wiki.sipeed.com/hardware/zh/tang/tang-mega-60k/mega-60k.html)

## 2. Console 60K HDMI/TMDS 管脚

Tang Console 官方 Wiki 确认底板支持 Mega 60K SOM，具有 DVI（HDMI 兼容）TX；软件侧的准确成对约束来自 Sipeed 官方 TangMega-60K `cam_dvi/src/NEO_DOCK.cst`。[Console 硬件资料入口](https://wiki.sipeed.com/hardware/zh/tang/tang-console/mega-console.html)、[官方 NEO_DOCK.cst](https://github.com/sipeed/TangMega-60K-example/blob/main/cam_dvi/src/NEO_DOCK.cst)

| 信号 | 官方端口名 | FPGA 差分管脚（P, N） | 官方端口属性 |
| --- | --- | --- | --- |
| TMDS Data 0 | `tmds_d_p_0[0]` | `J14, H14` | `PULL_MODE=NONE DRIVE=3.5 BANK_VCCIO=3.3` |
| TMDS Data 1 | `tmds_d_p_0[1]` | `J15, H15` | `PULL_MODE=NONE DRIVE=3.5 BANK_VCCIO=3.3` |
| TMDS Data 2 | `tmds_d_p_0[2]` | `K17, J17` | `PULL_MODE=NONE DRIVE=3.5 BANK_VCCIO=3.3` |
| TMDS Clock | `tmds_clk_p_0` | `G15, G16` | `PULL_MODE=NONE DRIVE=3.5 BANK_VCCIO=3.3` |
| HPD 板级使能/控制 | `hpd_en` | `K13` | `PULL_MODE=UP DRIVE=12 BANK_VCCIO=3.3` |

注意事项：

- 上表的差分对必须继续按官方 Gowin 成对约束使用，不能拆成八个互不相关的 LVCMOS 输出。
- 官方 `.cst` 没有为这些 TMDS 端口显式写 `IO_TYPE`；移植时不要自行补造一个未经验证的 IO 标准，应由官方 DVI TX IP/差分输出原语和 Gowin 工具共同生成并检查最终 I/O 报告。[官方 NEO_DOCK.cst](https://github.com/sipeed/TangMega-60K-example/blob/main/cam_dvi/src/NEO_DOCK.cst)
- `K13` 在官方 README 中被描述为 HDMI HPD 信号的板级控制脚：显示器无信号时可能需要将它拉高。它不是可以随意改作普通按键的空闲 GPIO。[官方 cam_dvi README](https://github.com/sipeed/TangMega-60K-example/tree/main/cam_dvi)
- 合入主工程前仍需用当前 `constr/top.cst` 做一次管脚冲突检查，并在 Gowin 的 Pin Report 中确认 P/N 配对和 Bank 电压；不能仅靠端口名判断。

## 3. 官方实现的时钟与串化结构

官方 720p60 工程的输入时钟为 `50 MHz`（`clk -> V22`）。TMDS 专用 PLL 从该时钟产生两路相关时钟：[官方 NEO_DOCK.cst](https://github.com/sipeed/TangMega-60K-example/blob/main/cam_dvi/src/NEO_DOCK.cst)、[官方 TMDS_60HZ.sdc](https://github.com/sipeed/TangMega-60K-example/blob/main/cam_dvi/src/TMDS_60HZ.sdc)

```text
50 MHz board clock
    │
    └─ TMDS PLL
         ├─ 74.25 MHz  : pixel clock
         └─ 371.25 MHz : pixel×5 serializer clock

RGB888 + DE + HSYNC + VSYNC
    └─ DVI_TX_Top
         ├─ 3 × TMDS encoder: 8-bit colour/control -> 10-bit symbol
         ├─ DDR serializer: 10 serial bits/pixel, driven by pixel×5
         └─ 3 data pairs + 1 forwarded clock pair
```

官方 SDC 声明的频率关系是：

- `clk_tmds_5x = 50 × 297 / 40 = 371.25 MHz`
- `clk_74_25 = 50 × 297 / 200 = 74.25 MHz`

但是，2026-09-29 使用 Gowin 1.9.12.03 对本仓库独立 H1 工程实际构建后，工具对官方 PLL RTL 的推导结果是：

- `CLKOUT0 = 50 × 22 / 3 = 366.667 MHz`
- `CLKOUT1 = 50 × 22 / 15 = 73.333 MHz`

首次仍照抄官方 SDC 时出现 `TA1123`（约束频率与 PLL 输出不一致）；把 SDC 改为约束官方 RTL 的实际频率后消除该警告。标准 1650×750 总时序下实际帧率约为 `59.26 Hz`。这说明 `.ipc/.sdc` 的“期望频率”和已提交 `.v` 不能只看其一，必须以当前工具的 PLL 推导报告为最终证据。

官方工程的 `dvi_tx` 目录包含 Gowin 生成的 `DVI_TX_Top` IP，`gowin_pll` 目录同时包含 30 Hz、60 Hz 和 800×600@60 的 PLL 版本。[官方 dvi_tx 目录](https://github.com/sipeed/TangMega-60K-example/tree/main/cam_dvi/src/dvi_tx)、[官方 gowin_pll 目录](https://github.com/sipeed/TangMega-60K-example/tree/main/cam_dvi/src/gowin_pll)

约束风险：官方 `TMDS_60HZ.sdc` 同时包含摄像头、DDR3 和多个异步时钟组；本项目不能整文件复制。应只迁移 50 MHz 输入时钟、TMDS PLL 的 generated clock 关系和本项目确有需要的例外，并重新检查像素时钟与 5× 时钟之间的时序关系，避免宽泛 false-path 掩盖 serializer/CDC 问题。[官方 TMDS_60HZ.sdc](https://github.com/sipeed/TangMega-60K-example/blob/main/cam_dvi/src/TMDS_60HZ.sdc)

## 5. 本项目建议的最小移植边界

H2 首版只实现“静态彩条通过 Console HDMI 口稳定显示”，不把摄像头、DDR3、帧缓冲、EDID/DDC、CEC 或 HDMI 音频带入主工程。

### 5.1 必须移植/实现

1. **板级输出层**
   - 四对 TMDS 管脚和 `K13 hpd_en`，参数严格以官方 `.cst` 为基线。
   - 保留 Gowin 官方 DVI TX 所需的差分输出/serializer 原语。
2. **时钟层**
   - 从板载 `50 MHz` 产生一对相关时钟：`clk_pix` 与 `clk_pix_5x`。
   - 640×480 推荐 `25.2 MHz + 126 MHz`；如果先以 `25.0 + 125 MHz` 做兼容性试验，必须记录它不满足 Project F 引用的 VESA 0.5% 容差结论，不能当成最终精确配置。[Project F 640×480 时序](https://projectf.io/posts/video-timings-vga-720p-1080p/)
   - reset 必须等待 PLL lock，并在像素域同步释放。
3. **显示时序层**
   - H2 固定参数：水平 `640 / 16 / 96 / 48`，总计 800；垂直 `480 / 10 / 2 / 33`，总计 525；HSYNC/VSYNC 均负极性。[Project F 640×480 时序](https://projectf.io/posts/video-timings-vga-720p-1080p/)
   - H3 再把 active/front/sync/back/polarity 参数化，不要在 H2 首版引入多模式动态切换。
4. **像素源**
   - 纯组合或单拍寄存的八色/多色彩条，输入只依赖当前 `(x, y, de)`；无需 BRAM 和帧缓冲。
5. **编码与输出层**
   - 输入边界保持 `RGB888 + DE + HSYNC + VSYNC + clk_pix + clk_pix_5x`。
   - 优先复用/重新生成与 GW5AT-60K 匹配的 Gowin DVI TX IP，避免把 Xilinx `OSERDESE2/OBUFDS` 直接翻译成普通逻辑。

### 5.2 明确不在首版范围

- 摄像头输入与 I2C 初始化；
- DDR3 帧缓冲与跨帧缓存；
- HDMI 音频、InfoFrame、数据岛；
- EDID/DDC 自动模式选择；
- 1920×1200@60；
- 与合成器音频 RTL 的深度耦合。首个彩条版本应能单独综合和烧录，以隔离视频问题。

### 5.3 验收顺序

1. 仿真验证 800×525 周期、同步宽度/极性、`de` 区间和帧率。
2. 对 TMDS encoder 验证消隐期四个控制码、有效期 8b→10b 结果及 running disparity；可用 Project F 的 Python 模型交叉比对。[Project F TMDS 模型说明](https://github.com/projf/display_controller)
3. Gowin 全量构建，检查 PLL lock、所有 clock 报告、Fmax、跨时钟告警、Pin Report 和差分配对。
4. 先烧录独立彩条 bitstream；显示器稳定锁定、无闪屏且多次重新插拔可恢复后，H2 才算上板完成。
5. 最后再将经过验证的视频模块接入合成器主工程，并重新检查音频时序余量。

## 6. H2 关键纠错：25 MHz 像素时钟不等于免 PLL

TMDS 对每个 8-bit 颜色/控制输入产生 10-bit 符号。三条数据 lane 每个像素周期各自发送 10 bit；转发时钟 lane 仍输出像素时钟。[fpga4fun 原始教程](https://www.fpga4fun.com/HDMI.html)

对 640×480：

```text
推荐像素时钟       = 25.2 MHz
每 lane 串行码率   = 25.2 × 10 = 252 Mbit/s
DDR serializer 时钟 = 25.2 × 5 = 126 MHz
```

所以：

- `50 MHz ÷ 2 = 25 MHz` 只能近似生成像素节拍；
- 它没有生成 TMDS serializer 所需的 5× 高速时钟；
- 若不用 PLL，也必须存在另一个相位/频率受控的等效高速时钟与可验证的串化资源；当前主工程没有证据证明存在这种替代路径；
- 最稳方案是用 Gowin PLL 同时生成 `clk_pix` 和 `clk_pix_5x`，沿用官方 720p 的双时钟结构。[官方 TMDS_60HZ.sdc](https://github.com/sipeed/TangMega-60K-example/blob/main/cam_dvi/src/TMDS_60HZ.sdc)、[hdl-util 5× DDR 结构](https://github.com/hdl-util/hdmi/releases)

## 7. H4：1920×1200@60 的带宽与时钟风险

不计任何消隐，H4 的最低像素吞吐已经是：

```text
1920 × 1200 × 60 = 138.24 Mpixel/s
TMDS 每 lane 最低码率 = 138.24 × 10 = 1.3824 Gbit/s
DDR 5× 时钟最低值 = 138.24 × 5 = 691.2 MHz
```

真实显示时序必须加入水平和垂直消隐，因此实际像素时钟、5× 时钟和 lane 码率都会高于上述下限。风险包括：

- Console 官方只承诺 `1080P30/720P60`，没有承诺 1920×1200@60。[Tang Console 官方 Wiki](https://wiki.sipeed.com/hardware/zh/tang/tang-console/mega-console.html)
- Tang Mega 60K 官方参数列出的 LVDS 速率为 `1.25 Gbit/s`，而 H4 的理论最低 lane 码率已经超过它。[Tang Mega 60K 官方 Wiki](https://wiki.sipeed.com/hardware/zh/tang/tang-mega-60k/mega-60k.html)
- 即使使用 reduced blanking，Project F 也提醒其时钟容差更严格、电视兼容性更差，只适合锁定特定显示器型号；不能用它掩盖器件 I/O 上限。[Project F Reduced Blanking 说明](https://projectf.io/posts/video-timings-vga-720p-1080p/)
- 官方 720p60 已使用 `371.25 MHz` 的 5× 时钟；H4 所需 5× 时钟至少 691.2 MHz，P&R、输出抖动、serializer 和 PCB 信号完整性风险显著增加。[官方 TMDS_60HZ.sdc](https://github.com/sipeed/TangMega-60K-example/blob/main/cam_dvi/src/TMDS_60HZ.sdc)

因此 H4 的正确决策门槛是：先完成 H2/H3；再依据目标显示器 EDID 选定明确时序；在 Gowin 器件手册、PLL/IP 可生成范围、静态时序和板上长时间实测全部通过后，才能升级目标。若任一项不通过，应降为官方支持档位（优先 1280×720@60 或 1920×1080@30），而不是以“显示器偶尔能锁定”判定完成。

## 8. H1 完成边界与后续任务

### H1 本次已经完成

- 确认 Console 60K 板载 DVI（HDMI 兼容）TX 接口；
- 确认四对 TMDS 管脚、HPD 控制脚和官方端口属性；
- 确认官方 720p60 的 1×/5× 时钟与 Gowin DVI TX 结构；
- 对五个参考实现完成可复用性、许可证与风险比较；
- 定义 H2 的最小移植边界与验收顺序；
- 纠正“640×480 可完全免 PLL”的错误假设；
- 给出 H4 的最低带宽计算和不承诺结论。
- 新增独立最小工程 `bringup/hdmi_ref_720p/`，只包含官方 PLL、加密 DVI TX IP、测试图案和板级约束；没有修改主合成器 RTL。
- Gowin 1.9.12.03 已完成综合、布局布线和 bitstream 生成：器件为 `GW5AT-LV60PG484AC1/I0`，setup/hold 违例均为 0。
- Pin Report 已确认四对输出被实现为 `LVDS25`，位置分别为 `J14/H14`、`J15/H15`、`K17/J17`、`G15/G16`，`hpd_en=K13`。

### 尚未完成，不能计作上板通过

- 尚未把 HDMI/TMDS RTL 或 Gowin IP 接入**主合成器工程**；
- 尚未向当前 `top.cst/.sdc` 合入管脚和时钟约束；
- 尚未用显示器验证彩条、热插拔、长期稳定性；
- 因此当前 H1 已达到“调研 + 可构建最小参考移植”，但不是“已经上板出图”的 H2 硬件结果。

## 9. 剩余风险

最终构建仅剩 `PR1014`：官方加密 `DVI_TX_Top` 内部时钟 `clk_d` 使用通用布线资源。时序报告中 setup/hold 违例均为 0，因此它不阻塞 H1 的“调研记录 + 可构建最小例程”交付；但加密 IP 无法在本仓库内修正，必须在 H2 的显示器上板测试中继续观察，不能把“构建成功”写成“已经稳定出图”。
