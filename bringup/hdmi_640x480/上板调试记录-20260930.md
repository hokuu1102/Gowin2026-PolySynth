# H2 上板调试记录（2026-09-30）

> **结论**：H2 上板验收通过 —— `J_TOKENFIX_led.fs` 烧入 Tang Console 60K 后出八色彩条。
> **根因**：TMDS 控制码表 `2'b01` / `2'b10` 两行写反（详见 `SPEC.md` §四 的更正块）。
> **用途**：把「从全黑到出彩条」的完整排查链与可复现配方固化下来，避免重走。

---

## 一、症状

- 烧入后屏幕**全黑**，显示器**没有任何 OSD 提示**（不是"不支持的模式"）。
- `V13` 心跳 LED **0.5 s 亮 / 0.5 s 灭（~1 Hz）** ⇒ 码流在跑 + 50 MHz 时钟正常 + PLL 已锁。

---

## 二、排查链（每一步都有对照实验，只改一个变量）

| # | 假设 | 实验 / 证据 | 结果 | 判定 |
|---|---|---|---|---|
| 1 | 没烧进去 / 时钟没跑 / PLL 没锁 | 加 `V13` 心跳 LED：1 Hz=已锁、5 Hz=未锁、不亮=未配置 | ~1 Hz | **三者全正常** |
| 2 | 串行化位序错 | 用 Gowin 自带 `OSER10` 行为模型（`IDE/**/prim_sim.v`）核对输出抽头 | 抽头 `Dd3[0]`/`Dd3[1]` ⇒ **D0 先出**，与 TMDS LSB-first 一致 | 排除 |
| 3 | 时钟通道做法错 | 对照 `nand2mario/tangcore` 的 「src/hdmi2/serializer.sv」（外部参考路径） | 同样是**第 4 个 OSER10 + `10'b0000011111`** | 排除 |
| 4 | 复位脚定义错 | 对照官方 `TangMega-60K-example/cam_dvi/src/NEO_DOCK.cst` | `rst_n AA13 LVCMOS15 BANK_VCCIO=1.5` **逐字一致** | 排除 |
| 5 | TMDS 引脚不对 | 对照 `nand2mario/tangcore` 的 `src/boards/console.cst`（Console 实测跑通） | 8 个 P/N 引脚**完全一致** | 排除 |
| 6 | IO 标准（LVDS25）错 | 试 `ELVDS_OBUF + IO_TYPE=LVCMOS33D`（G 版） | **仍全黑**；第三方记录：ELVDS + **配对语法**写在 TRUELVDS 引脚上 ⇒ PnR 配成**真差分** ⇒ 3.3 V 下**哑掉**（"core alive, TV no signal"） | 该路不通 |
| 7 | 显示器不认 640×480 / 25 MHz | **对照 I**：官方加密 IP + 640×480@25.000 MHz + LVDS25 | **出彩条** | 显示器 / 模式 / 25 MHz / LVDS25 **全部无罪** ⇒ **责任在我们自己的 RTL** |
| 8 | 编码器控制码 | 对照 hdl-util/HDMI（`tangcore src/hdmi2/tmds_channel.sv`，本板实测跑通） | **`(c1,c0)=2'b01` 与 `2'b10` 两行写反** | ⭐ **根因** |

> 另有 **F** 对照：官方加密 IP 的 720p（+ 同一颗心跳灯）**出彩条** ⇒ 引脚 / 连接器 / 线材 / 显示器 / HPD 全部正常。

---

## 三、根因（一句话）

编码器 `case ({c1,c0})` 里 **`(1,0)` 与 `(0,1)` 两个控制码写反**，于是**只要 HSYNC 或 VSYNC 有一个有效**
（即整个行同步脉冲期间 + 场同步期间）蓝通道就发出**错误的控制码** ⇒ 接收端解不出同步 ⇒
**有 TMDS 活动但出不了图（全黑）**，而心跳 LED 与 PLL 一切正常 —— 与实测症状完全一致。

**为什么之前没抓到**：tb 的 `token()` 参照表与解码模型 `tb/tmds_decoder.sv` **抄了同一张错表** ⇒
编码/解码往返**自洽** ⇒ 判据"证明"了错误实现；对抗式复核也只对照了 `SPEC.md` 里那张表。

## 四、可复现配方（对照码流）

| 码流 | 内容 | 用途 | 配方 |
|---|---|---|---|
| **F** | 官方加密 IP，720p **+ 心跳灯** | 证明物理层 | 给 `bringup/hdmi_ref_720p/hdmi_ref_top.v` 加 `led_hb`（V13）+ cst 加脚，跑 `build_hdmi_ref.ps1`（见 `tools/build-h1-led.ps1`） |
| **I** | 官方加密 IP **+ 640×480@25.000 MHz** | 隔离"显示器/模式" vs "我们的 RTL" | 把 H1 工程复制到**纯 ASCII 路径**（H1 的构建脚本不支持中文路径），改 `testpattern` 的 `I_h_*`/`I_v_*`（800/96/48/640、525/2/33/480、**极性改负**）+ `TMDS_PLL_60HZ.v` 的 `MDIV=20/ODIV0=8/ODIV1=40` + SDC 生成时钟，跑 `build_hdmi_ref.ps1`（见 `tools/build-i-official-640x480.ps1`） |

## 五、教训（建议作为纪律）

1. **协议常量必须对照外部权威实现核对，不能只靠往返自证。** 本次 tb 的参照表与解码模型
   抄了同一张错表，往返自洽 ⇒ 判据"证明"了错误实现。这是 `K-84`「黑盒说不清」之外的另一类风险：
   **自证式判据**。
2. **对照实验只改一个变量。** F（同设计、不同分辨率）与 I（同分辨率、不同实现）把问题空间一刀切开，
   比任何"再想想"都有效。
3. **心跳 LED 是最高性价比的诊断手段。** 不依赖显示器、不依赖示波器，就能区分
   「没配置 / 没时钟 / PLL 未锁 / PLL 已锁」四种状态。
4. **构建告警必须逐条读。** B 版的 `PA1019`（VCO 3150 MHz 越界）藏在构建日志里，
   只看 TNS 与 Fmax 会得出「B 可用」的错误结论。
5. **第三方同板资料是高价值一手材料。** `nand2mario/tangcore`（Console 官方文档背书的实现）
   与 `Papipapito/MSXimus`（同为 Console 60K）的约束文件与踩坑注释，直接定位了引脚与 IO 标准问题。
6. **`OSER10` 的 `Q` 不能经 LUT**（综合报 `CK0021`），必须直连 I/O 缓冲 ⇒
   差分对必须由 I/O 原语生成，⛔ 不要试图在 fabric 里取反生成 N。
