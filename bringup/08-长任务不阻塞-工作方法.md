# ⏳ 长任务不阻塞 —— 工作方法（**独立交接文档**）

> **为什么单独写这份**：⭐ 这是**方法**，⛔ 不是项目知识。
> ⚠️ 之前只在交接文档里写了一句规则（"长任务挂后台"），
> 🔴 **但没写"怎么做到"** ⇒ ⭐ 新会话会**重复踩同一个坑**。
>
> **适用**：⭐ 本项目的**任何**会话（FPGA / ESP32 / 以后的新会话）

---

## 〇、⭐⭐ 一句话

```
⭐ 问题不是"别等" —— ⚠️ 等待是必须的（结果决定下一步）
⭐ 问题是"**在等的时候干什么**"
```

## 一、⭐⭐ 本项目的长任务清单（⭐ 实测耗时）

| 任务 | ⭐ 耗时 | ⚠️ 能不能省 |
|---|---|---|
| ⭐ **全量回归**（`sim/tb_all.ps1`） | ⭐ **~15 分钟** | ⛔ 不能 —— ⭐ 唯一的整体验证 |
| ⭐ **PnR**（`sim/gowin_build.ps1`） | ⭐ **~10 分钟** | ⛔ 不能 —— ⭐ 唯一的时序/引脚验证 |
| 🔴 **变异测试**（`bringup/mutation_test.ps1`） | 🔴 **~5 小时**（91 个） | ⚠️ 可用 `-Filter` 缩短 |

> ⭐ **单日规模参考**：2026-09-23 一天跑了 **21 次全量回归 + 4 次 PnR**
> ⇒ ⭐ **约 6 小时的等待** —— ⚠️ **不并行就是纯浪费**。

## 二、⭐⭐⭐ 核心机制（⭐ 四步）

### ① ⭐ 启动时就要挂后台

```powershell
# ⭐ 关键：run_in_background: true
powershell -NoProfile -ExecutionPolicy Bypass -File sim\tb_all.ps1
```

⭐ **判据**：预计 **> 3 分钟** ⇒ ⭐ **一律挂后台**，⚠️ **不估时间**。

> 🔴 **最容易犯的错不是 `wait: true`，而是【压根没挂后台】。**
> ⚠️ 前台跑长命令 = **直接卡死本轮**。

### ② ⭐ 立刻简短报告（⛔ 不要等结果）

⭐ **报告四要素**：
```
1. ⭐ job id
2. ⭐ 在跑什么（命令 + 说明）
3. ⭐ 预计多久
4. ⭐ 跑完检查什么（判据）
```

⭐ **例**：
> ⏱️ **`pwsh-1`（全量回归,~15 分钟）**
> 判据：44/44 通过。

### ③ ⭐⭐ **然后继续干【不被阻塞】的活**（⭐ 这才是重点）

> 📌 **判断标准**：⭐ **后续任务是否依赖长任务的【产物/输出/退出码】**。
> · ⭐ **依赖** ⇒ ⛔ **不能做**（⭐ 那才是真阻塞）
> · ⭐ **不依赖** ⇒ ⭐ **可以并行做** ✅

### ④ ⭐ 系统通知完成 ⇒ 取结果

⭐ 长任务完成时**系统会通知** ⇒ ⭐ 收到后再 `job_output` 查看。

## 三、⭐⭐ 怎么判断"能不能并行"（⭐ 实用的分类）

### ✅ 可以并行的（⭐ 我实测并行过的）

| 长任务在跑 | ⭐ 可以同时做 | ⚠️ 为什么安全 |
|---|---|---|
| ⭐ **PnR** | ⭐ 写**文档**（上机指南/交接文档） | ⛔ 不读 RTL 产物 |
| ⭐ **回归** | ⭐ 改**别的文件**（如引脚表） | ⚠️ 见下方"⚠️ 注意" |
| 🔴 **变异测试** | ⚠️ **只能写文档** | 🔴 **它会就地改 `rtl/`**（⭐ 见 §5） |

### ⛔ 不能并行的

| 长任务在跑 | ⛔ 不能做 | ⚠️ 为什么 |
|---|---|---|
| ⭐ 回归 | ⛔ **改 `rtl/` 或 `tb/`** | 🔴 **会污染正在跑的回归**（⭐ 它读工作区文件） |
| 🔴 **变异测试** | ⛔ **改 `rtl/`** + ⛔ **`git add`** | 🔴 见 §5（`K-119`） |
| ⭐ PnR | ⛔ **改 `constr/` 或 `rtl/`** | 🔴 同上 |
| 任何 | ⛔ **`git commit`**（⭐ 除非确认干净） | ⚠️ 可能把中间态提交进去 |

---

## 四、⚠️ 空闲时怎么办（⭐ 也要说清楚）

⭐ **如果确实【没有可并行的活】**：

```
⭐ 在答复里写清：下一步是什么、为什么必须等这个结果
⭐ 标注「长任务挂起中（job id, ⏱️ 预计多久）」
⭐ 然后【结束本轮】
```

⛔ **不要**：
- 🔴 **反复轮询**（busy-poll）—— ⭐ 系统会通知，⛔ 不用空转
- 🔴 为了"在同一轮给出完整结论"而**卡在前台等**

## 五、🔴 禁令（⭐ 机械判定，无例外）

| # | 🔴 禁令 |
|---|---|
| **1** | 🔴 **长任务（>3 min）绝对禁止 `wait: true`** —— ⭐ **没有任何例外** |
| **2** | 🔴 **禁止用"我现在就是真阻塞"当理由** —— ⚠️ **这个理由永远成立**，⭐ 一旦这样自我论证，就说明正在违规 |
| **3** | ⛔ 禁止反复轮询后台任务 |
| **4** | ⛔ 禁止因为"想给完整结论"而把长任务卡前台 |
| **5** | 🔴 **变异测试跑的时候⛔ 不碰 `rtl/`、⛔ 不 `git add`**（`K-119`） |

### ⭐ 短任务可以等

⭐ **< 3 分钟**的任务**可以** `wait: true`；⚠️ **判不准时按长任务处理**。

## 六、⭐⭐ 收到通知后要做什么

```
① git 状态检查（⭐ 确认没有中间态）
     git status --short
② 读长任务结果
     job_output <job_id>
③ ⭐ **核对判据**（⛔ 不只看"完成了"）
     回归 ⇒ 必须 44/44
     PnR  ⇒ 必须 0 setup / 0 hold
④ ⭐ 若失败 ⇒ 先查【是不是环境问题】（⭐ 见 §7）
```

## 七、⚠️ 本项目的三个真实陷阱（⭐ 都踩过）

### ① 🔴 **DSH 重启会杀掉后台任务**

```
⚠️ 2026-09-23 实测：跑了 15 个 tb 的回归，DSH 一重启 ⇒ 🔴 进程没了
⭐ 现象：日志停在半路、`job_list` 变空、无进程
⇒ ⭐ **对策**：重启后【先查日志时间戳】，⭐ 确认在跑再等
```

⚠️ **判据**：⭐ `job_output` 报 `unknown job` + 日志几分钟没写 ⇒ ⭐ **已经死了**，⭐ **重跑**。

### ② ⚠️ **"CPU 在降"不代表卡住**

```
⚠️ 每个 tb 会起【第一个】vvp 进程 ⇒ PID 和 CPU 都会变
⇒ ⭐ **别用"CPU 在降"判断卡死**
⭐ 正确判据：⭐ **日志文件的时间戳在推进**
```

### ③ 🔴 **日志缓冲会让"零输出"骗人**

```
🔴 `Tee-Object` / 重定向**带缓冲** ⇒ ⚠️ 中途看日志可能【大小一直不变】
⚠️ 我因此误判成"仿真挂死"，白花两轮
⇒ ⭐ **对策**：⭐ 看【日志文件的 LastWriteTime】，⛔ 不是看内容长没长
```

## 八、⭐⭐ 可复制的模板

### 启动一个长任务时

```text
⏱️ <job_id>（<在跑什么>,预计 <多久>）
判据：<跑完检查什么>
```

### 长任务挂起、本轮结束时

```text
⏱️ <job_id> 正在跑（预计 <多久>）
判据：<...>
⭐ 本轮已并行完成：<做了什么>
⏳ 下一步（⭐ 等结果才能做）：<什么>
```

### 收到完成通知后

```text
✅ <job_id> 完成
结果：<判据是否满足>
⇒ 下一步：<...>
```

## 九、⭐ 一句话总结

```
⭐ 挂后台 → ⭐ 报四要素 → ⭐ 干不依赖它的活 → ⭐ 等通知 → ⭐ 核判据
⚠️ 没活干就标"挂起中"结束本轮 —— ⛔ 不要空转、⛔ 不要 wait
```
