## 二、⭐ 这条路上有什么（⭐ 逐行读 `calib.sv`）

```verilog
:337  wire [DW:0] dcode  = (raw_f > zero_rd) ? (raw_f - zero_rd) : 0;   // ⭐ 表读 ＋ 减
:341  wire [DW:0] dlim   = ((span_rd != 0) && (span_rd < MAXT)) ? span_rd : MAXT;  // ⭐ 表读 ＋ 比较
:343  wire [DW:0] dclamp = (dcode > dlim) ? dlim : dcode;               // ⭐ 比较 ＋ 二选一
:373  prod_r <= dclamp * gain_rd;                                       // ⭐ 表读 ＋ 乘
```

⭐ 而三个表读（`zero_rd` / `span_rd` / `gain_rd`）**都由 `ch` 组合索引** ✅：

```verilog
:129  wire [GW-1:0] gain_rd = gain_vld[ch] ? gain_r[ch] : (1 << 8);
```

⇒ ⭐ **一条路上串了**：⭐ **三个 N 选 1 表读**（⭐ 每个 ≈ 4~5 级 LUT）
＋ ⭐ **减** ＋ ⭐ **两级比较** ＋ ⭐ **钳位二选一** ＋ ⭐ **乘法器输入** ✅
⇒ 🔴 **13.9 ns 完全说得通** ✅

## 四、✅ 真正能缩短它的做法（⭐ 下一轮的候选，⭐ 判据已定）

⭐ **在 `calib` 内部插流水**（⭐ 这是唯一的办法，⭐ 因为逻辑层数太多 ✅）：

```
阶段 1（现在）：raw → zero_rd → dcode → dlim → dclamp → 乘法器
阶段 2（提议）：raw/ch 先打一拍  ⇒  再从【本地寄存器】做三个表读 ＋ 算术 ＋ 乘
```

⭐ **为什么这样能省**：⭐ 现在 `raw` 来自 `adc_farm`（⭐ **物理上远**）
⭐ 且 `ch` 的组合扇出**横跨全芯片** ⇒ ⚠️ 走线 3.9 ns 只是表象，
🔴 **真正的代价是"表读的 LUT 被迫放在离 `adc_farm` 很远的地方"** ✅
⇒ ⭐ 打一拍后，⭐ 表读/算术/乘**全部挤在 `calib` 本地** ⇒ ⭐ 走线大减 ✅

### ⚠️ 代价与风险（⭐ 必须说清）

| ⭐ 项 | ⭐ 说明 |
|---|---|
| ⭐ **延迟 +1 拍**（⭐ 20 ns） | ⚠️ ⭐ `calib` 的输出晚一拍 ⇒ ⭐ **`tb_calib` 等判据会动** ✅ |
| ⭐ 为什么"大概率可接受" | ⭐ `calib` 的消费方是**位置快照/映射**（⭐ 它们按 `sample_valid` 走 ✅），⭐ 20 ns 相对采样帧（⭐ 1024 clk = 20.48 µs ✅）**可忽略** ✅ |
| ⭐ **判据（⭐ 先定）** | ⭐ ① `tb_calib` 等 7 个 tb **全绿**（⭐ 或按"延迟 +1 拍"显式更新 ✅）<br>⭐ ② **PnR 的最差 slack 必须改善 ≥ 0.3 ns**（⭐ 否则"白付"⇒ 回退 ✅，⭐ 同 `P2-37` 的判据形式 ✅） |

📌 ⭐ **注意**：⭐ 若 ① 需要改 tb 的期望值 ⇒ ⚠️ **那是契约变更**，
⭐ 必须先问"⭐ 这个延迟对**用户可见行为**有没有影响" ✅
（⭐ 本项目的纪律：⭐ **改契约要能说清为什么** ✅）

## 五、✅ 本轮实际落地的一项：`P2-24` ①（⭐ 省功耗，⭐ 非时序）

⭐ 改动（⭐ 一行）：

+ if (valid) prod_r <= dclamp * gain_rd;

### ⭐ 为什么行为安全（⭐ 逐条查过）

| # | ⭐ 事实 | ⭐ 出处 |

### ⭐⭐ 判据（⭐ 新增 3 条，⭐ 而且是**能红**的）

| # | ⭐ 判据 |
