## 一、⭐ 为什么 `play_seq` 一直没能例化（⭐ 先把根因说清）

⭐ `play_seq.v` 是 **2026-09-22 写完并验收过的**（⭐ `tb_play_seq` 16 项判据全过、
⭐ 变异体 4/4 全抓 ✅），⭐ **但它从来没有被 `top.v` 例化过** ✅

🔴 **原因不是"忘了"，而是它的读侧契约对不上上游**：

| 侧 | 契约 |
|---|---|
| ⭐ `play_seq` 要的 | ⭐ **标准同步 FIFO**：`evt_valid_i`（有事件）＋ `evt_data_i`（队头）＋ `evt_rd_o`（取走） |
| ⭐ `evt_uart_rx` 给的 | 🔴 **单拍脉冲**（⭐ 它**不是** FIFO） |

⇒ 🔴 直接对接 ⇒ ⭐ **凡是"`tick` 还没到"的事件，当拍就被丢掉** ✅
⇒ ⭐ 中间**必须**有一级缓冲 —— ⭐ 而那一级就是**一直没建的 `U-19`** ✅

📌 ⭐ 这一点**权威文档里早就写明了**：
`files/20-代码/play_seq接口冻结契约.md` §五 的接口边界表 ——
*"缓冲区 | ⚠️ 依赖 U-19 | ⭐ 2 KB 滚动预灌"* ✅
📌 ⭐ 而容量**后来已拍板改成 8 KB**：`上位机与ESP32通路实施计划.md` §六 第 4 条 ——
*"✅ 已拍板：**8 KB / 1024 事件**（🔴 不是原建议的 2 KB）"* ✅

## 二、⭐ 落地了什么

### 2.1 ⭐ `U-19`：`rtl/w3c/evt_buf.v`

| 项 | 设计 |
|---|---|
| ⭐ 深度 | ⭐ **1024 事件**（⭐ 已拍板；⭐ 64 kbit = **4 个 BSRAM**，⭐ 118 个里 ✅） |
| ⭐ 读侧 | ⭐ **FWFT**（first-word-fall-through）—— ⭐ `rd_valid_o` 恒等于"非空"、⭐ `rd_data_o` **无空隙** |
| ⭐ 握手 | ⭐ **标准同步 FIFO** ⇒ ⭐ 直连 `play_seq` ✅ |
| ⭐ 溢出 | ⭐ **sticky `ovf_o`** ＋ ⭐ **饱和计数 `drop_cnt_o`**（⭐ `K-106`：⛔ 不许静默丢 ✅） |
| ⭐ 低水位 | ⭐ `low_o`（⭐ 供**将来反向流控**；⚠️ 按拍板"反向通道先不做"⇒ ⭐ 今天只做可观测 ✅） |
| ⭐ 写穿 | ⭐ **同址写穿旁路** —— ⭐ 见 §三（⭐ 那是**一个真 bug 的修法** ✅） |

📌 ⭐ **为什么必须滚动预灌**（⭐ 实测密度，⛔ 不是估算）：
`09_Conjurer` 全曲 **11,858 事件 = 92.6 KB**、⭐ `夜洋风景` **11,564 事件 = 90.3 KB**
⇒ ⭐ **8 KB 只覆盖 8.6%** ⇒ ⭐ **无论 2 KB 还是 8 KB 都必须滚动** ✅

### 2.2 ⭐ `top.v` 的接线（⭐ 三级依赖链的最后一环）

```text
uart_rx ──► evt_uart_rx ──► u_evt_buf（U-19）──► u_play_seq ──┬─► seq_arb.score（出声）
   │                              ▲                    │        └─► u_guide_lamp ──► led_data.guide_key_i（指引）
   │                              └── ps_evt_rd ───────┘
   └─► calib_cmd / uart_ui            u_play_seq.tick_inc_o ──► beat_gen.tick_inc_i（换速）
```

| 接线 | 说明 |
|---|---|
| ⭐ `beat_gen.tick_inc_i` | ⭐ 从**常量 `TICK_INC_120BPM`** 换成 ⭐ **`play_seq.tick_inc_o`** |
| ⭐ `play_seq.run_i` | ⭐ **`1'b1`** —— ⭐ **必须与 `beat_gen.run_i` 相同**（⭐ 否则位置静默错位 ✅） |
| ⭐ `play_seq.pos_reset_i` | ⭐ **`met_start`** —— ⭐ **与 `beat_gen.pos_reset_i` 同一个信号**（⭐ 契约硬要求 ✅） |
| ⭐ `seq_arb.score_*` | ⭐ 从**裸 `eu_evt_*`** 换成 ⭐ **`ps_note_*`**（⭐ 这才是"按 tick 播放"生效的地方 ✅） |
| ⭐ `led_data.guide_key_i` | ⭐ 从**常量 `16'd0`** 换成 ⭐ **`guide_lamp.guide_vis_o`**（⭐ 消隐后的 ✅） |

⭐ **安全性论据（⭐ 最重要的一条）**：⭐ `play_seq` 复位默认 `TICK_INC_DEFAULT = 164927`
⭐ **与原来的常量 `TICK_INC_120BPM` 逐位相同** ⇒ ⭐ **没有曲谱时行为一字不变** ✅

⭐ **可用的工作流（⭐ 这是 `pos_reset` 语义的自然结果）**：
**"先按 S2（音乐位置归零）⇒ PC 再灌谱子 ⇒ 谱子从头按拍播放 ＋ LED 指引"** ✅
⚠️ **已知局限（⭐ 诚实标注）**：⭐ **播放中按 S2** ⇒ `cur_tick_r` 归零
⇒ ⚠️ 缓冲里"未来"的事件**全部立刻到期** ⇒ 🔴 一次性地吐出来 ✅
📌 ⭐ 正确用法：⭐ **起拍之后不要中途按 S2**（⭐ 要重放就让 PC 重灌 ✅）

## 三、🔴🔴 抓出的真缺陷 ①：`evt_buf` 的**同址读写**（⭐ 由新判据抓出）

### 现象（⭐ 首次由 `tb_score_chain` 抓出）

⭐ 在 `top.v` 里接好线后，⭐ `tb_top_score_path` **整片红**，⭐ 而根因在**模块内部**：

```text
[dbg] cnt=X ovf=1 eb_rd_v=x ps_rd=x cur_tick=0
```

### 根因（⭐ 两层）

🔴 **"空 ⇒ 非空"的那一拍**：⭐ `wr_ptr == rd_ptr`（⭐ 都指向 0）
⇒ ⭐ **同一沿上既写 `mem[0]`、又预取读 `mem[0]`**
⇒ 🔴 读拿到的是**写之前**的值（⭐ Verilog 非阻塞语义）
⇒ 🔴 `rd_data_r` = **未初始化值**（⭐ 仿真里是 `X`）

⭐ **后果**：
1. ⭐ **仿真**：⭐ `X` 顺 `play_seq.evt_data_i` ⇒ `evt_tick = X`
   ⇒ `evt_due = 1 & (X <= cur_tick_r) = X` ⇒ ⭐ `evt_rd_o = X`
   ⇒ 🔴 **回灌进本模块的 `take_ok`** ⇒ **`cnt` 整条变 `X`** ✅
2. 🔴🔴 **硬件（⭐ 更严重）**：⭐ 没有 `X`，⭐ `rd_data_r` 会拿着**上一次的残留位型**
   ⇒ ⚠️ 若残留 `tick` **恰好 `<= cur_tick_r`** ⇒ 🔴 **`play_seq` 发一次"伪读"**
   ⇒ ⭐ **那条真事件被取走却没被吐出来** ⇒ 🔴 **静默丢事件** ✅

### ✅ 修法

```verilog
wire rd_wr_same = push_ok & (wr_ptr == rd_addr);
...
rd_data_r <= rd_wr_same ? wr_data_i : mem[rd_addr];   // ⭐ 同址【写穿】
```

⭐ 语义上就是 **BSRAM 的 bypass / write-through 模式** ✅
📌 ⭐ 而"读走最后一条"那一拍：⭐ `cnt` 归零 ⇒ ⭐ `rd_valid_o = 0`
⇒ ⭐ 之后的垃圾值**被 `rd_valid_o` 掩掉** ⇒ ⭐ 不需要额外处理 ✅

### ⭐ 判据（⭐ 已进 `tb_evt_buf`，⭐ 且**能红**）

⭐ `tb_evt_buf` 判据 **`0b`**：⭐ **写那一沿的紧后一拍**，`rd_data_o` 必须**已经是新写的那条** ✅
🔴 **变异体实测**（⭐ 把 `rd_wr_same` 旁路去掉）⇒ ⭐ **`0b` 立刻红**（⭐ `63 pass / 1 fail`）✅
⚠️ **检查时机是关键**：⭐ 多等一拍 ⇒ 预取已经读到正确值 ⇒ 🔴 **判据就抓不到了** ✅

## 四、🔴🔴 抓出的真缺陷 ②：`P0-02` 的门控**把曲谱接收器关死了**（⭐ 由调试抓出）

### 现象

⭐ 串口发一帧完整曲谱（`0xA5` ＋ 8 字节）⇒ ⭐ **9 个字节只有 1 个通过门控**：

```text
   [byte 1] data=a5 ui_in_frame=0 cmd_idx=0 evt_rx_done=1     ← 只有它过
   [byte 2] data=00 ui_in_frame=0 cmd_idx=1 evt_rx_done=0     ← 之后 8 个全被挡
   ...
   ur_done 脉冲数=9  其中通过门控的=1
   eu_frame=0 eu_idx=1 eu_synced=0
```

### 根因（⭐ 读源码双重确认，⛔ 不是推测）

⭐ `top.v` 的门控原文：`evt_rx_done = ur_done & ~ui_in_frame & (cmd_idx == 4'd0);`

🔴 而 `calib_cmd` 的 `idx_q`（= `cmd_idx`）**只在一种情况下**离开 0 —— ⭐ **看到 `0xA5`** ✅
（⭐ `calib_cmd.v:408-412` 原文：*"⭐ 帧外：这里只可能是帧头或命令 … `if (byte_is_header)
idx_q <= 4'd1;` ⭐ 事件帧开始 ⇒ ⭐ 进入帧内，⛔ 之后 8 个字节一律不认命令"* ✅）
⭐ 而**命令只在 `idx_q == 0` 时被识别、⭐ 且不推进 `idx_q`** ✅
（⭐ `calib_cmd.v:447` 原文：*"`idx_q <= 4'd0;` ⭐ 命令不推进帧位置"* ✅）

⇒ ⭐⭐ **所以 `cmd_idx != 0` ⟺ "有一个 `0xA5` 事件帧正在收"** ✅
—— ⚠️ 它**⛔ 完全不能**表示"别人（屏/命令）在帧内" ✅
⇒ 🔴 **门控把曲谱接收器【正好在它最需要的时候】关掉了** ✅

### 🔴 为什么它一直没被发现（⭐ 最值得记的一条）

⭐ **判据 tb 与 `top.v`【漂移】了**：

| 位置 | 门控表达式 |
|---|---|
| ⭐ `tb/w3c/tb_evt_uart_rx_gate.sv`（**真正的代码**，`:88` 附近） | ⭐ `rx_done & ~ui_in_frame` ✅ |
| 🔴 `top.v` | 🔴 `ur_done & ~ui_in_frame & (cmd_idx == 4'd0)` ❌ |
| ⚠️ 该 tb 的**注释** | ⚠️ 写着含 `cmd_idx` 的那一版（⭐ 与 `top.v` 一致）❌ |

⇒ ⭐ 该 tb **修前修后都是全绿**（⭐ 3/3）⇒ 🔴 **它结构上不可能抓住这个缺陷** ✅
📌 ⭐⭐ **教训（⭐ 可复用）**：⭐ **"与 `top.v` 同式接线"必须【逐字符】核对【表达式本身】，
⛔ 不能只核对"例化了哪几个模块"** —— ⚠️ **注释里写着 A、⭐ 代码里写着 B**
⇒ 🔴 **缺陷就藏在 A 与 B 之间** ✅

### ✅ 修法

```verilog
wire evt_rx_done = ur_done & ~ui_in_frame;      // ⭐ 只留这一条
```

⭐ **`P0-02` 的保护【完整保留】**：⭐ 实测的伪事件源是 **8 个【串口屏】帧**，
⭐ 而屏帧由 `uart_ui` 认领 ⇒ ⭐ `ui_in_frame == 1` ⇒ ⭐ 曲谱接收器**照样不看字节** ✅
📌 ⭐ **判据证据**：⭐ `tb_evt_uart_rx_gate` 的 3 条判据（⭐ 含 `G1`：8 个含 `0xA5` 的屏帧
⇒ 曲谱侧 **0 条事件**）⭐ **一字未改、修后仍全绿** ✅
📌 ⭐ **顺带**：⭐ 该 tb 的表达式**本来就是对的** ⇒ ⭐ 本次修法是**让 `top.v` 追上判据** ✅
⚠️ ⭐ `cmd_idx` 在 `top.v` 里**从此没有消费者**（⭐ 会被综合剪掉）——
⭐ 它与 `eu_idx` **恒等**（⭐ 两者数的是同一个 9 字节帧）⇒ ⭐ 信息没丢 ✅

### ⭐ 修复后实测（⭐ 同一条激励）

```text
   ur_done 脉冲数=9  其中通过门控的=9        ← ⭐ 9/9 全过
   eu_frame=1 eu_idx=0 eu_synced=1           ← ⭐ 帧收满了
   eb_cnt=1 eb_rd_valid=1 eb_ovf=0           ← ⭐ 事件【躺在 U-19 缓冲里】
   play_seq evt_cnt=0                        ← ⭐ 而 play_seq 还没吐（tick 未到）✅
```
